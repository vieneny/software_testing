# 性能、可靠性与可观测性开源项目

性能测试的目标不是“把并发调到 100”，而是用业务模型验证容量、延迟、吞吐、错误、资源和降级是否满足目标。可靠性测试继续验证超时、限流、重试、熔断、故障恢复和数据一致性；可观测性负责提供解释这些结果的证据。

## 一、通用性能测试工具

| 项目 | 里面有什么 | 可以做什么、学什么 | 定位 |
|---|---|---|---|
| [Grafana k6](https://github.com/grafana/k6) | Go 引擎、JavaScript/TypeScript 脚本、scenario、arrival rate、metric、threshold 和扩展 | 建立代码化 smoke/load/stress/spike/soak 场景；用阈值形成 CI 退出码 | **本仓库主线，L2→L3** |
| [Apache JMeter](https://github.com/apache/jmeter) | 多协议 Sampler、线程组、断言、提取、参数化、分布式和 HTML 报告 | 学存量企业压测、关联和非 GUI 执行；理解线程模型与资源消耗 | **市场兼容，L1→L3** |
| [Locust](https://github.com/locustio/locust) | Python 用户行为、事件扩展、负载曲线、Web UI、headless 和分布式 worker | 用 Python 表达复杂用户旅程、动态数据和自定义指标 | **Python 选修，L2→L3** |
| [Gatling](https://github.com/gatling/gatling) | Java/Kotlin/Scala DSL、session、feeder、check、注入模型和报告 | 在 JVM 团队构建类型化、可版本控制的性能测试 | **Java 选修，L2→L3** |
| [Artillery](https://github.com/artilleryio/artillery) | YAML/JavaScript 场景、HTTP/WebSocket、处理器和报告生态 | 在 Node.js 团队快速建立 API/WebSocket 负载；比较开放/封闭模型 | **JS 选修，L2** |
| [Vegeta](https://github.com/tsenart/vegeta) | Go 编写的轻量 HTTP load generator、固定速率和结果绘图 | 做简单基准、固定请求率实验和工具链嵌入；不适合复杂业务状态 | **轻量工具，L1→L2** |

### 三条主线怎么选

- 已有本仓库 Python/前端自动化，希望代码化并接 CI：先学 **k6**；
- 目标职位明确要求 JMeter 或需要多协议/存量 JMX：学习 **JMeter**；
- 用户流程需要大量 Python 数据处理：选择 **Locust**；
- Java 项目强调 DSL、Maven/Gradle：按需选择 **Gatling**。

同一作品只需一套主工具，再用另一套重写一个小场景做对照。

## 二、大模型与生成式 AI 服务性能

普通 HTTP 压测可以测端到端延迟和错误率，但无法自动理解生成式服务的 Token、流式和 Goodput 指标。

| 项目 | 里面有什么 | 可以做什么、学什么 | 定位 |
|---|---|---|---|
| [AIPerf](https://github.com/ai-dynamo/aiperf) | OpenAI-compatible/推理服务负载、并发/速率/Trace 回放、多轮与多模态数据；TTFT、ITL、Token 吞吐、Goodput、SLO 和 OTel/MLflow 输出 | 对本地 Ollama、vLLM 或自有接口做容量实验；学习首 Token、逐 Token、输出吞吐和 SLO 约束 | **AI 性能主线，L3** |
| [GuideLLM](https://github.com/vllm-project/guidellm) | 同步、并发、恒定速率、Poisson、Sweep，多种数据源和 JSON/CSV/HTML 报告 | 找安全并发区间，对比模型、量化和服务配置；理解 TTFT/ITL 分布 | **AI 性能选修，L3** |
| [MLPerf Inference](https://github.com/mlcommons/inference) | 标准化 LoadGen、场景、准确率、性能和合规规则及多类参考实现 | 阅读行业 Benchmark 如何保证可比性；小规模复现，不把个人电脑结果冒充官方成绩 | **高级参考，L4** |
| [vLLM](https://github.com/vllm-project/vllm) | OpenAI-compatible Server、连续批处理、KV Cache、并行和内置 benchmark | 学服务端批处理、显存、吞吐、延迟、排队与取消；需要合适 GPU 后再深入 | **服务端进阶，L4** |

2026 年新教程不再把已弃用的 GenAI-Perf 当首选；使用 AIPerf 或 GuideLLM，并记录工具版本、模型、硬件、量化、输入/输出 Token 分布和并发模型。

AI 服务至少报告：

- TTFT（Time to First Token）；
- ITL/TPOT（Token 间延迟）；
- 端到端请求延迟；
- 输入/输出 Token 数；
- 请求吞吐与输出 Token 吞吐；
- 错误、超时、限流和取消；
- 满足 SLO 的 Goodput；
- 模型、量化、硬件、显存和服务配置；
- 质量没有因截断、降级或换模型而不可接受地下降。

## 三、可观测性基础

| 项目 | 里面有什么 | 可以做什么、学什么 | 定位 |
|---|---|---|---|
| [OpenTelemetry](https://github.com/open-telemetry) | traces、metrics、logs 的规范、API/SDK、语义约定和各语言实现 | 给测试请求注入 trace id，串联浏览器/API/服务/数据库/模型/工具调用 | **质量工程核心，L2→L3** |
| [OpenTelemetry Collector](https://github.com/open-telemetry/opentelemetry-collector) | receiver、processor、exporter 和可组合数据管道 | 学采集、批处理、采样、脱敏、路由和多后端导出 | **平台选修，L3** |
| [Prometheus](https://github.com/prometheus/prometheus) | 时序指标、抓取、PromQL、规则和告警 | 采集吞吐、错误、延迟、CPU、内存、线程池、队列和依赖指标 | **性能证据核心，L2→L3** |
| [Grafana](https://github.com/grafana/grafana) | Dashboard、数据源、告警和可视化平台 | 把负载工具与被测端指标放到同一时间轴，解释瓶颈而非只截图 | **可视化选修，L2** |
| [Jaeger](https://github.com/jaegertracing/jaeger) | 分布式 Trace 存储、查询和服务依赖分析 | 定位慢请求在哪个服务、数据库或外部依赖；学习 trace/span 关系 | **Trace 后端选修，L2→L3** |
| [OpenTelemetry GenAI 语义约定](https://github.com/open-telemetry/semantic-conventions-genai) | 模型、Agent、事件和工具调用的快速演进语义约定 | 设计 AI Trace 字段并固定版本；避免记录完整 Prompt、密钥和隐私 | **AI 平台参考，L3** |

可观测性不是“装一个 Grafana”。一份合格实验要能从负载阶段跳到：

```text
外部请求指标
→ 服务端资源
→ 线程池/连接池/队列
→ 数据库和缓存
→ 下游 API
→ 对应 Trace
→ 日志中的同一关联 ID
```

## 四、网络与依赖故障注入

| 项目 | 里面有什么 | 可以做什么、学什么 | 定位 |
|---|---|---|---|
| [Toxiproxy](https://github.com/Shopify/toxiproxy) | TCP Proxy、延迟、抖动、断连、限带宽、超时等 toxic | 对数据库、缓存和 HTTP 下游验证 timeout、retry、circuit breaker 和恢复 | **本地韧性主线，L2→L3** |
| [Pumba](https://github.com/alexei-led/pumba) | Docker 容器 kill/pause、网络延迟、丢包和带宽故障 | 在本地 Compose 环境练习容器和网络故障；设置明确持续时间 | **Docker 选修，L3** |
| [Chaos Mesh](https://github.com/chaos-mesh/chaos-mesh) | Kubernetes Pod、网络、I/O、时间、压力等故障与工作流 | 在隔离 K8s 集群验证稳态、降级、告警、恢复和自动终止 | **云原生进阶，L3→L4** |
| [LitmusChaos](https://github.com/litmuschaos/litmus) | Chaos Center、工作流、探针和 ChaosHub 实验 | 学稳态假设、实验编排和结果可视化；适合 SRE/平台岗位 | **云原生进阶，L3→L4** |

故障注入前必须写：

- 目标和稳态指标；
- 资产所有者和授权；
- 环境、命名空间和影响范围；
- 最大持续时间、流量和成本；
- 立即停止条件；
- 自动恢复与人工兜底；
- 证据、复盘和剩余风险。

## 五、公开练习与参考实现

### [Grafana QuickPizza](https://github.com/grafana/quickpizza)

里面有 Web/API 服务、OpenTelemetry、Grafana 生态和 k6 练习路径。适合：

- Docker 本地启动；
- 先做低负载基线；
- 用场景和 threshold 验证；
- 将 k6 指标与服务 Trace/Metric 对齐；
- 主动注入慢依赖并解释变化。

### 本仓库 `demo-shop`

优先在本地虚构服务完成：

- 商品浏览、下单和 AI 接口场景；
- k6/Locust 脚本；
- 429、500、延迟和异常数据；
- 可重置的内存状态；
- 不涉及任何第三方或公司系统。

## 六、建议形成的作品

### 作品一：容量与稳定性报告

- 业务量假设与峰值换算；
- 开放/封闭负载模型；
- smoke、load、stress、spike、soak 五类中选择必要场景；
- p50/p95/p99、错误率、吞吐和资源；
- 拐点、瓶颈证据、容量结论和环境限制；
- 不伪造生产容量。

### 作品二：韧性测试

- WireMock/Toxiproxy 注入超时、429、断连和抖动；
- 验证重试上限、退避、熔断、隔离和恢复；
- 检查重试风暴和重复写入；
- 用 Trace 证明请求经历了什么；
- 输出恢复时间和数据一致性结论。

### 作品三：LLM 服务性能

- AIPerf 对本地 Ollama 或自建 OpenAI-compatible Mock；
- 短/长输入、短/长输出、流式、多轮和并发；
- TTFT、ITL、Goodput、错误和 Token 吞吐；
- 同时用小型黄金集检查质量；
- 明确硬件和成本限制，不把低端本机结果外推到生产。
