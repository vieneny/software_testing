# 测试管理、报告与持续集成开源项目

这一类项目解决“测试怎样被组织、执行、汇总、分诊和用于发布决策”，不负责替你设计有效测试。小白先让测试在命令行稳定运行，再逐步增加报告、CI 和管理平台。

## 一、测试报告与结果分析

| 项目 | 里面有什么 | 可以做什么、学什么 | 定位 |
|---|---|---|---|
| [Allure 3](https://github.com/allure-framework/allure3) | TypeScript 重写的 CLI、插件系统、Awesome Report、实时 watch、附件、分类和多框架结果生态 | 把步骤、截图、日志、请求响应、设备和环境组织成可读证据；学习结果模型与报告生成分离 | **报告主线，L1→L2** |
| [Allure 2](https://github.com/allure-framework/allure2) | 成熟的多语言报告生成器、历史趋势和广泛适配器 | 接手存量项目与理解现有插件生态；新项目先核对 Allure 3 与所用适配器的兼容状态 | **存量兼容，L1→L2** |
| [ReportPortal](https://github.com/reportportal/reportportal) | 多服务测试结果平台、实时日志、失败分类/聚类、自动分析、Dashboard 和质量门禁 | 汇总多流水线结果，区分产品/脚本/环境问题，研究失败分诊和质量平台架构 | **平台进阶，L3** |

### 选择建议

- 个人作品、静态报告和附件：先用 Allure；
- 多团队、多流水线、历史失败聚类和中心化分析：再研究 ReportPortal；
- 报告必须链接原始日志/Trace，不能只显示绿色百分比；
- flaky、环境失败、跳过和真正产品失败要分开统计；
- 报告中的请求、Header、Token、Prompt 和 Trace 默认脱敏。

## 三、持续集成与流水线

| 项目 | 里面有什么 | 可以做什么、学什么 | 定位 |
|---|---|---|---|
| [Jenkins](https://github.com/jenkinsci/jenkins) | Pipeline、Agent、插件、凭据、定时任务、制品和测试报告 | 建立平台无关的 lint→unit→API→UI→report→gate 流水线；学习节点和 Secret 治理 | **企业 CI 主线，L2→L3** |
| [GitHub Actions Starter Workflows](https://github.com/actions/starter-workflows) | 官方 workflow 示例、语言矩阵、CI 和安全配置参考 | 阅读 matrix、cache、权限、制品和最小 token；命令可迁移到其他 CI | **公开求职参考，L1→L2** |
| [act](https://github.com/nektos/act) | 用 Docker 在本地近似运行 GitHub Actions | 本地调试事件、matrix、环境变量和测试命令，减少远程试错 | **选修，L2** |
| [Tekton Pipelines](https://github.com/tektoncd/pipeline) | Kubernetes 原生 Task、Pipeline、Workspace 和 Results 生态 | 学云原生可复用任务、供应链和平台工程；完成普通 CI 后再学 | **平台岗进阶，L3→L4** |

本仓库托管在 Gitee。GitHub Actions 文件作为公开作品和通用 CI 示例保留；实际执行可适配 Jenkins、Gitee Go 或其他平台。测试入口、退出码和 JUnit 报告不应绑定某一家 CI。

## 五、安全与供应链门禁

这些项目只提供一种证据，不能替代威胁建模、人工审查和授权测试。

| 项目 | 里面有什么 | 可以做什么、学什么 | 定位 |
|---|---|---|---|
| [OWASP ZAP](https://github.com/zaproxy/zaproxy) | Web Proxy、被动/主动扫描、Automation Framework 和 API | 在本地 Juice Shop 等授权靶场做基线扫描；人工确认并回归修复 | **安全选修，L2→L3** |
| [Trivy](https://github.com/aquasecurity/trivy) | 容器、文件系统、依赖、IaC、Secret 和许可证扫描 | 给 Docker/依赖建立基础供应链门禁；处理误报和例外到期 | **CI 安全推荐，L2** |
| [OWASP Dependency-Check](https://github.com/dependency-check/DependencyCheck) | 依赖与已知漏洞匹配、Maven/Gradle/CLI 和报告 | 学 CVE、CPE、抑制文件和依赖升级验证 | **Java/多语言选修，L2** |
| [Semgrep](https://github.com/semgrep/semgrep) | 语义代码搜索、规则、SAST 和 CI 集成 | 写简单安全/质量规则并验证误报；区分开源引擎与商业平台能力 | **静态分析选修，L2→L3** |

只能扫描自己的仓库和本地/授权实例。不要对公共演示站、招聘网站或第三方开源项目在线环境执行主动扫描。

## 六、最小质量流水线

```text
代码提交
→ 格式与静态检查
→ 单元测试
→ API/契约测试
→ 关键 Web/移动 smoke
→ 安全与依赖基线
→ JUnit/Allure 证据
→ 按明确阈值给出通过、阻断或人工审批
```

阈值至少说明：

- 哪些用例是发布阻断；
- flaky 如何隔离、谁负责、何时到期；
- 环境失败是否允许重跑以及重跑上限；
- 报告与制品保留多久；
- 哪些安全发现可以临时接受，批准人和复查日期是什么；
- AI 评测的随机性如何通过多次运行、置信度和人工抽检控制。

## 七、建议形成的作品

### 作品一：个人 CI 质量门禁

- Ruff/pre-commit；
- pytest unit/API；
- Playwright smoke；
- JUnit + Allure；
- Docker Compose 本地靶场；
- Trivy 依赖/镜像基线；
- 明确快速层、慢速层和阻断阈值。

### 作品二：测试管理闭环

- 用 Kiwi TCMS 建一个完全虚构的版本；
- 维护风险、计划、套件、用例、执行和缺陷；
- 通过 API 关联一批自动化结果；
- 输出手工/自动化覆盖差异；

### 作品三：失败分诊平台

- 将 API、Web、App 的合成失败发送到 ReportPortal；
- 人工标记产品、自动化、环境和数据问题；
- 比较自动聚类和人工真值；
- 计算准确率、误分类和节省时间；
- 证明 AI/ML 分诊效果，而不是只展示 Dashboard。
