# 人工智能提效与测试智能体开源项目

这一类项目用于研究“怎样让 AI 辅助测试”以及“怎样测试 AI 生成的测试”。它们可以生成候选用例、辅助写代码、操作 UI、分析 PR 和归类失败，但不能自动承担质量责任。

合格的 AI 提效实验必须同时衡量：

- 采纳率；
- 正确率和有效缺陷；
- 误报、漏报和返工；
- 人工审核时间；
- 总耗时、延迟和模型成本；
- 多次运行稳定性；
- 数据和权限风险。

### 为什么 AI UI 不能直接替代 Playwright/Appium

- 同一句自然语言可能产生不同动作；
- 页面上“看起来相似”的元素可能业务语义不同；
- Agent 可能绕过预期步骤后仍给出成功；
- 模型、Prompt、截图和页面变化都会影响结果；
- AI 判断通过不等于业务状态正确；
- Token、模型 API、网络和隐私成为新依赖。

建议实验矩阵：

| 维度 | 对照 |
|---|---|
| 方法 | Playwright/Appium 确定性脚本 vs AI 工具 |
| 页面变化 | 文案、DOM、布局、颜色、图标、遮挡 |
| 运行次数 | 每任务至少多次，报告 success@1 与 success@3 |
| 指标 | 成功、误动作、p95、成本、重试、人工接管、证据完整度 |
| Oracle | API/数据库/环境终态，而非 Agent 自述“完成” |

### 值得让 AI 辅助的工作

- 从公开需求生成候选测试点；
- 给现有手工用例做边界/异常补充；
- 生成 Mock 数据和 JSON Schema 草稿；
- 把一次性脚本重构为 Page/API Client；
- 解释 Trace、日志和失败差异；
- 生成代码后自动运行 lint/unit/API；
- 对 PR 提示缺少测试、输入验证和 Secret；
- 归类失败候选，再由人确认。

### 不应直接交给 AI 的决定

- 是否可以发布；
- 是否接受安全风险；
- 删除或修改真实数据；
- 操作公司账号和系统；
- 把生产日志、公司代码或需求发送给模型；
- 自动接受自愈定位器；
- 只因为测试通过就合并 AI 生成补丁。

## 三、AI 测试 Agent 的评价方法

### 用例生成

准备 20 条公开需求，由人工先建立基准测试点。比较：

- 覆盖到的有效风险；
- 新增但有效的风险；
- 重复、不可执行和错误假设；
- P0/P1 风险漏检；
- 人工修改量；
- 生成+复核总耗时；
- 不同模型/Prompt 的稳定性。

不要用“生成了 100 条用例”作为效果指标。

### 自动化代码生成

固定 10 个小任务：

- 新增 API 用例；
- 新增 Playwright 定位；
- 修复 flaky 等待；
- 写 WireMock 失败；
- 补 JSON Schema；
- 重构 fixture；
- 添加日志脱敏；
- 增加 CI 标签；
- 修复一个故意缺陷；
- 解释一次失败。

每个任务记录：

- 首次可运行率；
- 最终通过率；
- 人工编辑行数；
- 引入回归数；
- 测试是否真的能在故意缺陷下失败；
- 时间和成本。

### 失败分诊

准备有真值的合成失败：

- 产品缺陷；
- 自动化脚本；
- 环境/网络；
- 测试数据；
- flaky；
- 已知问题。

比较 AI 与人工标签，输出混淆矩阵、精确率、召回率和人工复核时间。若 AI 把产品缺陷错分为脚本问题，风险远高于普通误报。

## 四、推荐提效工作流

```text
公开需求/合成输入
→ AI 生成候选
→ 人工检查事实、边界和数据
→ 在隔离分支运行 lint/test
→ 主动注入缺陷验证测试有效
→ 审查 diff、依赖、Secret 和权限
→ 只合并可解释且可复现的结果
→ 记录采纳、返工、有效缺陷、时间和成本
```

## 五、权限与隐私控制

使用任何代码或浏览器 Agent 前：

- 在专用练习项目和分支运行；
- 工作目录只包含当前项目；
- 默认禁止读取父目录和用户主目录；
- 默认禁止任意 shell、删除、外部发送和真实写操作；
- API Key 放环境变量，不进 Prompt、日志和 Git；
- 检查遥测、云端 Trace、缓存和数据保留；
- 对浏览器工具设置域名 allowlist；
- 对 MCP 工具设置只读能力和 Schema；
- 每个写操作需要人工审批；
- 运行后审查 `git diff` 和新依赖。

## 六、建议形成的作品

### 作品一：AI 用例生成评测

- 公开需求集和人工基准；
- 两个 Prompt 或模型；
- 风险覆盖、错误、重复、采纳、返工和耗时；
- 按功能、异常、安全和非功能切片；
- 最后沉淀“哪些任务适合 AI，哪些不适合”。

### 作品二：AI UI 稳定性实验

- 本地 `demo-shop`；
- Playwright 为基线；
- Midscene 或 Stagehand 为实验；
- 正常、文案、布局、网络和遮挡变化；
- 多次运行；
- 终态 Oracle、成功率、误动作、延迟、成本和 Trace。

### 作品三：AI 失败分诊

- 100 条合成失败样本；
- 规则基线、LLM 方法和人工真值；
- 混淆矩阵和严重误分类；
- 敏感字段替换为合成 canary；
- 只在准确性和风险可接受时给人工排序建议，不自动关闭缺陷。

### 作品四：受控编码 Agent

- Aider、OpenHands 或 mini-SWE-agent 中选择一个；
- 只操作虚构仓库；
- 每个任务必须运行测试和静态检查；
- Agent 不能改测试来掩盖实现缺陷；
- 输出补丁成功率、测试有效性、人工修改和安全事件；
- 展示权限、沙箱和回滚设计。
