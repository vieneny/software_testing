# 自动化测试故障排查手册

> 核对日期：2026-07-27
> 适用范围：Python、pytest、Requests、Playwright、Appium、Android、iOS
相关教程：

- [接口自动化项目全流程](../02-接口测试/04-接口自动化项目全流程.md)
- [Web 自动化项目全流程](../03-UI自动化/04-Web自动化项目全流程.md)
- [App 自动化学习阶段](../03-UI自动化/02-App自动化学习阶段/README.md)
- [自动化框架设计与进阶项目](./03-自动化框架设计与进阶项目.md)

排障目标不是“想办法让这次变绿”，而是用最少变量找出失败位于哪一层，并留下
别人可以复核的证据。

## 1. 六条基本原则

1. **保留第一次失败。** 不要先重跑到成功再删除红色证据。
2. **一次只改变一个变量。** 不要同时升级 Python、重装驱动、改 Locator 和加超时。
3. **从外到内分层。** 环境 → 连接 → 会话 → 页面/Screen → 状态 → 断言。
4. **先最小化。** 单用例、单浏览器、单设备、单进程复现。
5. **验证事实。** 记录版本、命令、目标、状态和时间，不凭感觉归因。
6. **不盲目重试。** Retry 只能帮助调查，不能证明第一次失败不存在。

## 2. 第一次失败先保存什么

### 通用信息

```bash
date
python --version
python -m pip --version
python -m pytest --version
git status --short
```

再记录：

- 完整执行命令；
- pytest node id；
- 首次失败时间；
- 当前分支和提交；
- OS 与架构；
- 目标是 Offline、Local、Public 还是 Device；
- 是否单独运行、是否并行；
- 最近一次代码、依赖、浏览器、驱动、App 或系统变更。

只记录代理、Secret 是否存在，不打印值：

```bash
python - <<'PY'
import os

for name in ("HTTP_PROXY", "HTTPS_PROXY", "NO_PROXY"):
    print(f"{name}: {'set' if os.getenv(name) else 'not set'}")
PY
```

### 分技术线证据

| 技术线 | 最小证据 |
|---|---|
| API | 脱敏 URL、方法、超时类型、状态码、脱敏 Body、Schema 路径 |
| Web | pytest 堆栈、Trace、失败截图、URL、浏览器版本 |
| Android | Appium 日志、设备序列号、截图、Page Source、必要的 logcat |
| iOS | Appium/WDA 日志、Simulator UDID、截图、Page Source、Xcode/Runtime |

上传前检查证据只含公开 Demo 和合成数据。来源不确定就不要上传。

## 3. 快速分层决策

```text
pytest 是否能收集用例？
├─ 否 → Python / 依赖 / 导入 / pytest 配置
└─ 是
   └─ 目标服务能否独立连接？
      ├─ 否 → 网络 / 本地服务 / 公共环境
      └─ 是
         └─ 能否创建 Browser/Appium Session？
            ├─ 否 → Browser / Driver / Capability / 设备
            └─ 是
               └─ 能否到达目标页面或 Screen？
                  ├─ 否 → 导航 / App 状态 / 权限 / 登录
                  └─ 是
                     └─ 元素能否稳定定位并满足条件？
                        ├─ 否 → Locator / Context / Frame / 等待
                        └─ 是 → 测试数据 / 业务断言 / 产品缺陷
```

不要跳过前一层。例如 Appium 连不上服务器时，修改 XPath 没有意义。

## 4. Python 与虚拟环境

### 4.1 `python` 和 `pip` 不是同一个环境

检查：

```bash
which python
python -c "import sys; print(sys.executable); print(sys.version)"
python -m pip --version
```

`python -m pip` 能确保 pip 属于当前解释器。不要混用：

```text
pip install ...
另一个 python -m pytest ...
```

修复：

```bash
cd labs/automation-practice
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[all,dev]'
```

zsh 会把方括号当 glob，extras 必须加引号。

### 4.2 `ModuleNotFoundError`

先查模块和工程安装位置：

```bash
python -m pip show qa-automation-practice
python -m pip show pytest python-dotenv requests jsonschema
python -c "import qa_learning; print(qa_learning.__file__)"
```

判断：

| 现象 | 原因方向 | 修复 |
|---|---|---|
| `No module named qa_learning` | 没有 editable install 或环境错误 | 在实验目录执行 `pip install -e ...` |
| `No module named dotenv` | 只装了部分/错误依赖 | 重新安装项目依赖，不手工复制模块 |
| IDE 能导入、终端不能 | IDE 与终端解释器不同 | 统一到 `.venv/bin/python` |
| 终端能导入、pytest 不能 | 调用了全局 `pytest` | 使用 `python -m pytest` |

不要在仓库里新建一个同名 `requests.py`、`pytest.py`、`appium.py` 或
`playwright.py`，它会遮蔽真正的第三方包。

### 4.3 Python 版本不满足

本工程要求 Python 3.11+：

```bash
python -c "import sys; print(sys.version_info)"
```

升级解释器后应重新创建虚拟环境。不要把旧环境目录复制到新 Python。

### 4.4 安装失败

保存 pip 错误中最早出现的根因，而不是只看最后一行。优先检查：

- Python 版本；
- 网络和证书；
- 磁盘空间；
- 当前平台是否支持依赖；
- pip 是否属于当前 venv；
- 是否误把 extras 的引号去掉；
- 是否使用了失效镜像。

TLS 失败不要用关闭证书校验来“解决”。应修复系统时间、CA、代理或镜像配置。

## 5. pytest 收集与开关

### 5.1 先只收集

```bash
python -m pytest --collect-only -q
python -m pytest tests/api --collect-only -q
python -m pytest tests/web --collect-only -q
python -m pytest tests/mobile --collect-only -q
```

收集失败通常属于：

- 语法错误；
- import 错误；
- marker 未注册且启用了 strict markers；
- `conftest.py` fixture 名称错误；
- 在模块导入阶段访问网络、浏览器或设备。

测试模块导入时不应建立外部连接。

### 5.2 “为什么全是 skipped”

这是安全设计：

```bash
pytest tests/api -q --run-public-api
pytest tests/web -q --run-public-web
pytest tests/mobile -q --run-mobile
```

只有确认目标后才加对应开关。不要删除：

```text
public_api_guard
public_web_guard
mobile_guard
```

本地 Demo Shop 集成还需要先启动服务，并设置 `DEMO_SHOP_URL`。

### 5.3 Fixture not found

检查 fixture 可见范围：

- 根 `tests/conftest.py` 对所有测试可见；
- 子目录 `conftest.py` 只对该目录及子目录可见；
- fixture 不需要显式 import；
- 名称必须完全一致；
- 不要从另一个测试文件导入 fixture。

用：

```bash
python -m pytest --fixtures -q
```

确认 pytest 实际发现的 fixture。

### 5.4 单独通过、批量失败

高概率原因：

- 共享 Session/Page/Driver；
- 数据名不唯一；
- 上一条用例未清理；
- 测试依赖顺序；
- 多 Worker 共用同一账号、端口或设备；
- BrowserContext/localStorage 污染；
- App 没有恢复初始状态。

验证方法：

```bash
python -m pytest path/to/test_file.py::test_name -q
python -m pytest path/to/test_file.py -q
python -m pytest tests -q
```

然后随机化顺序或重复运行用于调查。不要通过固定顺序让依赖隐藏起来。

## 6. API 与网络

### 6.1 先绕过测试框架检查目标

本地服务：

```bash
curl -i --max-time 10 http://127.0.0.1:8000/health
```

公开 API：

```bash
curl -I --max-time 10 https://jsonplaceholder.typicode.com/
```

判断：

| 错误 | 优先方向 |
|---|---|
| Connection refused | 服务未启动、地址/端口错误 |
| DNS resolution failed | DNS、网络、域名 |
| Connect timeout | 路由、防火墙、代理、目标不可达 |
| Read timeout | 已连接但目标响应慢 |
| TLS/Certificate | 系统时间、CA、代理中间证书 |
| 401/403 | 鉴权、Cookie、WAF、权限 |
| 404 | 路径、版本、资源状态 |
| 409/422 | 业务状态或输入校验 |
| 429 | 访问过快，应停止并降低频率 |
| 5xx | 目标服务、依赖或输入触发的服务错误 |

不要把 connect timeout 和 read timeout 合并成“网络超时”。两者指向不同阶段。

### 6.2 本地 Demo Shop 404/Connection refused

确认服务终端仍在运行：

```bash
curl -sS http://127.0.0.1:8000/health
```

确认自动化工程使用的变量名：

```bash
DEMO_SHOP_URL=http://127.0.0.1:8000 \
  python -m pytest tests/api/测试_本地演示商城接口.py -q
```

相邻 `labs/demo-shop` 自己的测试使用 `DEMO_BASE_URL`，两个工程的变量名不同，
不要混淆。

### 6.3 JSONPlaceholder 创建后查不到

这是官方设计：POST/PUT/PATCH/DELETE 只模拟响应，不会真正保存。正确用例应：

- 验证 POST 返回结构；
- 再次 GET 时预期资源不存在；
- 不把模拟 201 当作数据库落库。

需要真实 CRUD 时使用 Restful Booker 或本地 Demo Shop。

### 6.4 Restful Booker 数据消失或冲突

公共实例：

- 与其他学习者共享；
- 会周期重置；
- 包含故意保留的缺陷；
- 不保证你看到固定总数。

使用唯一 `run_id`，只断言自己创建的资源，在 `finally` 中清理。不要断言全局
Booking 总数，也不要并行创建大量记录。

### 6.5 Schema 失败

按顺序看：

1. HTTP 状态是否正确；
2. Content-Type 是否为 JSON；
3. 实际 Body 是否是网关 HTML；
4. 错误路径是根、数组索引还是字段；
5. Schema 是否过度严格；
6. 上游契约是否真的变化。

不要为了通过就把所有字段改成可选或允许任意类型。先确认业务契约。

### 6.6 证书错误

禁止：

```text
requests.get(..., verify=False)
curl -k
```

这些只会关闭安全校验并掩盖环境问题。正确方向：

- 核对系统时间；
- 核对官方 HTTPS 域名；
- 更新受信 CA；
- 检查代理是否做 TLS 中间处理；
- 对本地自签名环境配置明确的测试 CA。

## 7. Playwright

### 7.1 浏览器可执行文件不存在

典型信息包含“Executable doesn't exist”。修复：

```bash
python -m playwright install chromium
```

Linux CI 缺系统依赖时：

```bash
python -m playwright install --with-deps chromium
```

确保安装浏览器与运行 pytest 使用同一个 Python 环境中的 Playwright。

### 7.2 浏览器能开，但页面访问失败

先用同一台机器的普通浏览器或 curl 验证 URL。再检查：

- `TODO_MVC_URL` / `SAUCE_DEMO_URL`；
- 代理；
- DNS；
- 证书；
- 站点是否 403/429/5xx；
- CI 是否限制外网；
- 页面是否跳到登录、验证码或地区限制。

公共站点失败不要立即改测试。先区分站点可用性与产品断言。

### 7.3 Locator strict mode violation

表示 Locator 匹配多个元素。正确修复：

- 使用 role + accessible name；
- 先定位目标卡片/行，再定位内部按钮；
- 与产品约定稳定 test id；
- 使用明确的 exact 文案或结构关系。

不要立即改成 `.first`、`.last` 或 `.nth(2)`。这些方法可能让错误元素被静默选中。

### 7.4 Locator 找不到

检查：

1. 当前 URL 是否正确；
2. 是否在 iframe；
3. 是否打开了新 Page；
4. 元素是否在 Shadow DOM；
5. 可访问名称是否与肉眼文案不同；
6. 页面是否还处于登录/错误状态；
7. Locator 是否在页面更新后仍引用正确元素；
8. 当前语言、视口和实验账号是否不同。

调试：

```bash
PWDEBUG=1 python -m pytest \
  tests/web/测试_公开待办事项网站.py \
  --run-public-web \
  -k crud \
  -s
```

使用 Inspector 的 Pick Locator 观察，但最终源码仍应表达业务语义。

### 7.5 点击超时

Playwright 会检查元素是否可见、稳定、能接收事件、已启用。失败常见原因：

- 遮罩或弹窗挡住；
- 按钮禁用；
- 动画未结束；
- Locator 指向隐藏副本；
- 页面还没达到业务就绪状态；
- 点击触发目标在 iframe；
- 站点脚本报错。

不要先使用 `force=True`。强制点击会绕过用户真实可操作条件。先查看 Trace 的
Actionability 日志和 DOM 快照。

### 7.6 页面加载或断言超时

正确等待业务条件：

```python
expect(page).to_have_url(...)
expect(page.get_by_role("heading", name="...")).to_be_visible()
```

不要：

- 固定 `sleep(5)`；
- 所有导航都等 `networkidle`；
- 把全局 timeout 调成数分钟；
- 失败就刷新直到页面出现。

带广告、分析和长连接的公共页面可能永远不“网络空闲”，关键元素才是业务就绪
信号。

### 7.7 查看 Trace

运行：

```bash
python -m pytest tests/web \
  --run-public-web \
  --tracing retain-on-failure \
  --screenshot only-on-failure \
  --output test-results
```

打开：

```bash
python -m playwright show-trace test-results/<case>/trace.zip
```

检查：

- 操作前后的 DOM；
- 实际 Locator；
- URL；
- Console；
- Network；
- 元素遮挡和可操作性；
- 第一次与重跑的差异。

## 8. Appium 通用问题

### 8.1 服务是否真的启动

检查：

```bash
appium --version
appium driver list --installed
curl -sS http://127.0.0.1:4723/status
```

若 connection refused：

- Appium 未启动；
- 端口不同；
- `APPIUM_SERVER_URL` 错误；
- 服务启动后立即崩溃；
- 端口被其他进程占用。

Appium 2/3 默认 Base Path 是 `/`。旧教程常使用 `/wd/hub`，不要不加判断地照抄。

### 8.2 驱动未安装或不兼容

```bash
appium driver list --installed
appium driver doctor uiautomator2
appium driver doctor xcuitest
```

只安装需要的驱动。升级顺序：

1. 记录当前 Appium、Driver、Node、OS 版本；
2. 阅读驱动 Release Notes；
3. 单独升级一个驱动；
4. 运行一个最小 Session；
5. 再跑 smoke；
6. 最后扩大回归。

### 8.3 SessionNotCreated

从 Appium 服务端日志找到最早的具体原因。检查：

- `platformName`；
- automationName 是 UiAutomator2 或 XCUITest；
- 设备名与 UDID；
- 平台版本；
- App 绝对路径；
- Android package/activity；
- iOS Bundle ID；
- App 是否与设备架构/Simulator 匹配；
- 同一设备是否已被另一个 Session 占用。

Capability 名称应符合 W3C/Appium 规范。不要不断添加网上复制的 capability；
每增加一个都要知道它改变什么行为。

### 8.4 App 路径存在但无法安装

检查：

```bash
python -c "from pathlib import Path; p=Path('/绝对路径/练习应用'); print(p.exists(), p.resolve())"
```

再确认：

- Android 使用 APK，iOS Simulator 使用 Simulator `.app`；
- iOS 真机包和 Simulator 包不能互换；
- zip 已正确解压；
- 下载来自官方 Release；
- 文件没有损坏；
- 设备架构和最低系统版本兼容；
- App 没有被 Git LFS 指针文件替代。

不要从第三方网盘寻找“同名可用包”绕过问题。

### 8.5 元素定位失败

先保存截图和 Page Source，再确认：

- 当前 Screen；
- 原生还是 WebView Context；
- 系统权限弹窗是否覆盖；
- 键盘是否遮挡；
- App 是否首次启动；
- accessibility id/resource-id/name 是否实际存在；
- 列表元素是否需要滚动；
- 动画是否完成；
- 定位是否绑定了错误语言文案。

优先：

- Android：accessibility id、稳定 resource-id；
- iOS：accessibility id、predicate/class chain；
- XPath：最后选择，且限制范围。

不要通过“找不到就循环滑动 100 次”解决。要定义滚动终止条件。

## 9. Android 与 adb

### 9.1 设备列表

```bash
adb devices -l
```

| 状态 | 含义 | 排查 |
|---|---|---|
| `device` | 已授权、可连接 | 继续检查目标 UDID |
| `unauthorized` | 未接受这台电脑的调试授权 | 解锁手机、接受指纹弹窗、重插 |
| `offline` | adb 看见但无法通信 | 换数据线/端口、重启 adb、重连 |
| 没有设备 | USB/驱动/调试未生效 | 检查开发者选项、连接模式和线缆 |

重启 adb 服务：

```bash
adb kill-server
adb start-server
adb devices -l
```

不要删除 adb 密钥作为第一步；这会影响已授权设备。先走设备 UI 的正常授权流程。

### 9.2 多台设备

错误信息通常包含 `more than one device/emulator`。每条命令明确目标：

```bash
adb -s DEVICE_SERIAL get-state
adb -s DEVICE_SERIAL shell getprop ro.build.version.release
```

在 `.env` 设置：

```dotenv
MOBILE_UDID=DEVICE_SERIAL
```

不要让框架自动选择 `adb devices` 的第一行。真机、模拟器和其他连接设备的顺序
可能变化。

### 9.3 包名、Activity 与当前页面

查看公开练习 App：

```bash
adb -s DEVICE_SERIAL shell pm list packages
adb -s DEVICE_SERIAL shell dumpsys window
```

缩小输出时可按已知公开包名过滤。核对：

- `ANDROID_APP_PACKAGE`；
- `ANDROID_APP_ACTIVITY`；
- App 是否安装在该 UDID；
- Activity 是否可启动；
- Splash 是否跳转到另一个 Activity。

安装官方练习 APK：

```bash
adb -s DEVICE_SERIAL install -r /绝对路径/公开练习.apk
```

这会修改指定设备，执行前再次核对序列号和来源。

### 9.4 安装错误

常见方向：

| 错误片段 | 排查 |
|---|---|
| `INSTALL_FAILED_VERSION_DOWNGRADE` | 设备已有更高版本；不要直接覆盖未知 App |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 签名不同；核对是否为同一公开练习 App |
| `INSTALL_FAILED_INSUFFICIENT_STORAGE` | 设备空间不足 |
| `INSTALL_FAILED_OLDER_SDK` | App 最低 Android 版本更高 |
| `INSTALL_PARSE_FAILED...` | 文件损坏、架构/格式或下载错误 |

卸载会删除 App 数据，属于有影响操作。只有确认包名、设备和数据可丢弃后才执行，
不要对未知包名批量清理。

### 9.5 Appium 连上但操作不稳定

检查：

- 系统动画；
- 键盘；
- 权限弹窗；
- 电池优化/后台限制；
- 屏幕方向；
- 分辨率和字体缩放；
- App 数据是否来自上一条测试；
- 网络是否让 App 卡在 Loading；
- Appium Settings/UiAutomator2 Server 是否正常。

先用一台设备串行复现。稳定后再做设备矩阵，不要一开始并行。

### 9.6 logcat

只采集复现窗口，避免巨大且含其他 App 信息的日志：

```bash
adb -s DEVICE_SERIAL logcat -c
adb -s DEVICE_SERIAL logcat
```

复现后立即停止。提交前只截取与公开练习 App 相关且不含敏感信息的必要片段。

## 10. iOS、Xcode 与 WebDriverAgent

### 10.1 基础环境

iOS 自动化只能在 macOS + Xcode 环境进行：

```bash
xcode-select -p
xcodebuild -version
xcrun simctl list runtimes
xcrun simctl list devices available
appium driver doctor xcuitest
```

如果 `xcode-select` 指向 Command Line Tools 而不是完整 Xcode，打开 Xcode 完成
首次启动组件、许可和平台 Runtime 安装。不要通过复制其他机器的 Xcode 目录
绕过正常安装。

### 10.2 Simulator 不存在或不可用

检查：

- Xcode Settings 中是否安装对应 iOS Runtime；
- `.env` 的 `IOS_DEVICE_NAME` 是否与 `simctl` 一致；
- 指定的平台版本是否真的存在；
- Simulator 是否处于 unavailable；
- Apple Silicon/Intel 与 App 架构是否匹配。

可按 UDID 启动已存在的 Simulator：

```bash
xcrun simctl boot SIMULATOR_UDID
open -a Simulator
```

若已启动，`simctl boot` 可能提示状态错误；先看 `simctl list`，不要不断重复。

### 10.3 `.app` 无法安装

Simulator 只能安装为 Simulator 构建的 `.app`：

```bash
xcrun simctl install SIMULATOR_UDID /绝对路径/公开练习.app
xcrun simctl launch SIMULATOR_UDID com.saucelabs.mydemo.app.ios
```

失败时检查：

- zip 是否完整解压；
- App 是否来自官方 iOS Simulator Release；
- Bundle ID；
- 支持的 Runtime 和架构；
- App 是否被 Gatekeeper/下载损坏影响；
- 磁盘空间。

iPhone 真机 `.ipa`/签名包与 Simulator `.app` 不是同一种资产。

### 10.4 WDA 启动失败

WebDriverAgent 是 Appium XCUITest Driver 控制 iOS 的桥梁。按顺序查：

1. `appium driver doctor xcuitest`；
2. Appium 服务端最早的 WDA/xcodebuild 错误；
3. Xcode、iOS Runtime、XCUITest Driver 兼容性；
4. Simulator UDID；
5. 端口 8100 是否冲突；
6. 真机签名、Team、Provisioning 与设备信任；
7. WDA 是否在启动后崩溃。

端口检查：

```bash
lsof -nP -iTCP:8100 -sTCP:LISTEN
```

不要把“清空全部 DerivedData、重装 Xcode、重装所有驱动”作为第一步。先保存
xcodebuild 的第一条根因。缓存清理是后续有证据的动作，不是通用修复。

### 10.5 真机签名

iOS 真机比 Simulator 多出：

- Apple Developer Team；
- Signing Certificate；
- Provisioning Profile；
- 设备注册与信任；
- WDA Runner 签名；
- 可能的组织策略。

先在 Xcode 中让一个最小 WDA Runner 对目标真机成功构建运行，再回到 Appium。
如果 Xcode 自己不能签名，修改 Appium capability 无法解决。

不要把证书、Profile、Team Secret 或开发者账号提交到仓库。

### 10.6 WDA 可达但测试卡住

检查：

- 当前前台 App 与 Bundle ID；
- 系统 Alert；
- SpringBoard 与 App Context；
- Simulator 键盘；
- Screen 是否加载；
- 元素是否存在但不可点击；
- Appium/WDA 命令耗时；
- App 是否访问了不稳定公共网络；
- 上一条测试是否留下状态。

截图 + Page Source + Appium/WDA 时间线通常比增加超时更有价值。

## 11. 公共网络与第三方靶场不稳定

公共服务可能：

- DNS 故障；
- TLS/证书更新；
- 页面或接口变更；
- 403/WAF；
- 429 限流；
- 5xx；
- 数据被其他学习者修改；
- 周期重置；
- 暂时下线。

### 11.1 处理流程

```text
保留首次失败
  → 用 curl/普通浏览器做一次独立检查
  → 查官方页面/仓库状态
  → 单用例、串行、低频复现
  → 对比本地可控靶场
  → 分类为环境变化或真实断言失败
  → 记录并停止制造额外流量
```

如果是 429：

- 立即停止循环；
- 关闭并行；
- 不切换账号/IP绕过限制；
- 等待服务允许的恢复窗口；
- 将场景迁到本地 Mock/自建环境；
- 公共 smoke 不作为 PR 硬门禁。

如果是 5xx：

- 保存请求关联信息和脱敏响应；
- 确认请求是否合法；
- 单次低频复现；
- 不自动轰炸服务；
- 对公开靶场记录为环境阻塞；
- 用本地服务继续验证框架本身。

### 11.2 什么时候切换本地靶场

出现任一情况应切本地：

- 需要稳定 CI；
- 需要故意制造 429/5xx/延迟/断连；
- 需要大量测试数据；
- 需要性能测试；
- 需要可重复状态机；
- 需要固定版本契约；
- 公共目标没有明确授权相关测试。

选择：

- `demo-shop`：业务全链路；
- WireMock：匹配、故障、延迟、Scenario；
- Mockoon：可视化 CRUD；
- Prism：OpenAPI Mock/验证；
- 本地 httpbin：HTTP 行为。

## 12. 为什么不能用盲目重试掩盖缺陷

| 现象 | 错误处理 | 正确处理 |
|---|---|---|
| Locator 偶尔找不到 | 失败就重跑 3 次 | 查状态、Locator、Context、Trace |
| Appium Session 失败 | 无限重启服务 | 查设备、端口、Driver、Capability |
| 公共站 429 | 并发重试 | 停止、降频、迁本地 |
| API ReadTimeout | 把超时改 5 分钟 | 区分环境慢、服务慢和错误等待 |
| 用例顺序相关 | 固定执行顺序 | 数据隔离、fixture 清理 |
| WDA 启动失败 | 循环重装驱动 | 查第一条 xcodebuild/签名根因 |

有限重试必须同时满足：

- 操作幂等；
- 有最大次数和总等待；
- 有退避；
- 保留每次尝试证据；
- 最终报告显示曾失败；
- 不绕过第三方限流；
- 已说明为什么 retry 属于产品/协议策略。

测试框架的“自动 rerun 直到通过”不满足这些条件。

### Flaky 临时隔离

如果不稳定用例暂时无法修复，应记录：

- Issue；
- owner；
- 首次发现时间；
- 失败证据；
- 失败率；
- 影响范围；
- 临时处理；
- 到期日期；
- 恢复门槛。

隔离不是永久 `skip`。到期必须修复、重写或删除没有价值的测试。

## 13. 常见反模式速查

| 反模式 | 后果 | 替代 |
|---|---|---|
| `sleep(5)` | 快慢环境都不可靠 | 等可观察条件 |
| `verify=False` | 隐藏 TLS 风险 | 修复 CA/代理 |
| `.nth(2)` | DOM 顺序变就点错 | 语义 Locator + 容器 |
| 全局 Page/Driver | 状态污染 | fixture 生命周期 |
| 自动选第一台设备 | 控制错误设备 | 显式 UDID |
| 每失败就刷新 | 隐藏产品错误 | 保留证据、定位层 |
| 无限增大超时 | 失败更慢 | 区分阶段与条件 |
| 公共站并行 | 限流与数据冲突 | 低频串行 |
| 全量上传日志 | 数据泄露、噪声 | 截断、脱敏、按失败收集 |
| 清空整台设备 | 破坏其他数据 | 只清理目标公开 App |

## 14. 缺陷还是环境问题

提交缺陷前至少回答：

1. 目标版本和环境是什么；
2. 是否可在最小路径复现；
3. 单独、串行是否仍失败；
4. 请求/页面/Screen 的前置状态是什么；
5. 预期依据来自哪里；
6. 实际结果和第一次失败证据是什么；
7. 本地可控环境是否出现同类问题；
8. 是否排除设备掉线、公共站点中断和测试数据冲突；
9. 重现概率和影响范围；
10. 是否只使用公开/合成数据。

### 建议缺陷模板

```text
标题：
环境与版本：
目标来源：
前置条件：
合成测试数据：
最小复现步骤：
预期结果及依据：
实际结果：
复现次数：
影响：
证据：
排除过的环境因素：
临时规避：
```

不要用“自动化失败”作为缺陷标题；那只是现象。

## 15. 排障完成标准

- [ ] 已保留第一次失败；
- [ ] 已记录版本、命令、目标和 node id；
- [ ] 已确认未泄露 Secret 或非公开资料；
- [ ] 已在单用例、单进程、单设备下复现；
- [ ] 已确认目标服务与设备连接；
- [ ] 已区分 Session、Locator、状态、数据和断言；
- [ ] 已找到最早根因，而不是最后一条级联错误；
- [ ] 没有用盲目 retry、固定 sleep、`force=True` 或关闭 TLS 校验掩盖问题；
- [ ] 修复后已单独、批量、乱序验证；
- [ ] Flaky 隔离有 owner 和到期日；
- [ ] 结论能被另一个人根据证据复核。
