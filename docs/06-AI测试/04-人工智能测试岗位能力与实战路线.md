# 人工智能测试岗位能力与实战路线

> 岗位依据：2026-07-27 BOSS 直聘公开岗位快照，详见[软件测试与人工智能测试招聘需求调研](../00-学习指南/04-软件测试与人工智能测试招聘需求调研.md)。
>
## 一、不要用“AI 测试”四个字选择课程

当前岗位至少分成五条路线：

| 路线 | 你主要交付什么 | 适合谁 |
|---|---|---|
| 普通测试 + AI 提效 | 更快但仍可信的测试分析、脚本和分诊流程 | 所有测试学习者 |
| AI 应用测试 | LLM/RAG/多模态产品的功能、效果、性能与安全证据 | 有功能/API/自动化基础者 |
| 大模型/多模态评测 | 数据集、指标、比较实验和误差分析 | 喜欢数据、统计和模型效果者 |
| Agent 测试 | 工具、状态、权限、终态、副作用和恢复证据 | 有 API、状态机和安全基础者 |
| 测试开发/评测平台 | 可复用的评测任务、执行、结果、版本和门禁平台 | 编程与后端能力较强者 |

这五条路线共享底座，但学习深度和作品完全不同。求职前必须回答：

1. 我是在**用 AI 测普通软件**，还是在**测试 AI 系统**？
2. 我负责的是产品交付、模型效果、Agent 行为，还是评测平台？
3. 我的作品能运行并制造失败吗，还是只有截图和概念？

## 二、所有路线共用的基础

### 2.1 测试与软件工程

- 需求分析、风险排序和测试预言；
- HTTP/JSON、鉴权、幂等、流式响应和错误处理；
- SQL、Linux、Git、日志和基本网络诊断；
- Python + pytest，或目标岗位要求的 Java + JUnit/TestNG；
- 接口自动化、少量 UI 关键旅程、数据清理和失败证据；
- CI/CD、Docker、配置、密钥和制品管理；
- 性能模型、p95/p99、错误率、资源和依赖观测。

### 2.2 AI 系统

- Token、上下文窗口、采样参数、结构化输出；
- Embedding、向量检索、Rerank 和 RAG；
- Tool/Function Calling、MCP、Agent 状态与记忆；
- 模型、Prompt、知识库、工具和数据集的独立版本；
- 限流、超时、重试、降级、成本和供应商切换。

### 2.3 评测

- 任务定义、样本分布、黄金集和 holdout；
- 确定性检查、人工 rubric、模型裁判及其校准；
- 切片、基线、配对比较、置信区间和失败分类；
- 事实性、鲁棒性、公平性、无害性、拒答和安全；
- 数据泄漏、污染、重复、过时事实和标注分歧。

没有这些基础时，先不要堆叠多个 Agent 框架或评测工具。

## 三、路线一：普通测试加人工智能提效

### 目标

让 AI 生成候选内容，人和可执行测试对结论负责。

### 必做流程

```text
公开/合成需求
  → 人工建立风险基线
  → AI 生成候选风险、用例或脚本
  → 人工逐项采纳、修改、拒绝
  → 在本地目标运行
  → 记录有效率、误报、返工和节省时间
  → 把确认有效的结果进入回归
```

### 作品要求

至少提供：

- 一份人工基线与 AI 草稿的差异表；
- 采纳、修改、拒绝及原因；
- 生成脚本的代码审查和真实运行结果；
- AI 造成的一次错误及其拦截机制；
- 提效前后反馈时间、有效缺陷或返工的对比。

### 不合格表现

- 只展示聊天记录；
- 用“生成了 100 条用例”代替质量；
- 不运行生成代码；
- 把公司需求发给个人模型；
- 让 AI 自动提交、发布或发消息而没有人工确认。

建议先完成[人工智能提效工作流](03-人工智能提效工作流.md)。

## 四、路线二：人工智能应用测试

### 目标

验证一个包含模型、RAG、业务 API 和前端的完整产品，而不是只评价一句回答。

### 分层测试

| 层 | 测试对象 | 关键检查 |
|---|---|---|
| API 契约 | 请求、响应、流式事件、错误模型 | Schema、顺序、终止事件、超时、取消、幂等 |
| 模型适配 | provider、参数、重试、切换 | 429/5xx、坏 JSON、慢响应、截断、拒绝 |
| RAG | 解析、Chunk、检索、重排、引用 | Recall@k、权限过滤、忠实性、过时/冲突资料 |
| 产品逻辑 | 会话、权限、业务规则 | 多轮上下文、角色隔离、状态一致性、回退 |
| 非功能 | 延迟、吞吐、成本、稳定性 | 首 Token、完整响应、并发、预算、降级 |
| 安全 | Prompt、检索内容、输出和工具 | 注入、泄露、越权、不安全输出、供应链 |

### 最小实战

以虚构客服为例：

1. 建立 30～50 条合成数据，包含可答、不可答、冲突、过时、权限和攻击样本；
2. 实现一个无密钥假模型，可注入超时、429、坏 JSON、无引用和敏感词；
3. 分开报告检索和生成结果；
4. 比较两个 Prompt 或知识库版本；
5. 在 CI 中设置确定性门禁；
6. 输出质量、延迟、成本和残余风险。

### 验收

- 同一失败可重放；
- 每个结果能追溯模型、Prompt、知识库和数据集版本；
- 模型裁判有人工校准样本；
- 严重安全失败不会被平均分掩盖；
- 不调用真实生产数据。

配套学习：[大语言模型、检索增强生成与智能体评测](01-大语言模型检索增强生成与智能体评测.md)。

## 五、路线三：大模型与多模态评测

### 目标

把“模型好不好”转成有定义、有样本、有不确定性和有边界的测量。

### 学习重点

1. **任务定义**：用户、场景、失败成本和能力维度；
2. **数据构造**：来源许可、覆盖、困难样本、对抗样本和 holdout；
3. **标注治理**：指南、培训、盲标、分歧处理和一致性；
4. **指标选择**：指标与业务风险对应，避免只追一个总分；
5. **评审校准**：人工、规则、模型裁判各自的误差；
6. **统计比较**：配对样本、置信区间、切片和多次运行；
7. **误差分析**：不是只出榜单，要能解释失败簇和改进方向。

### 多模态补充

图像、视频、音频还要考虑：

- 主观质量与客观缺陷分开；
- 审美、清晰度、时序一致性、文字、人体结构和物理合理性；
- ASR、NLU、TTS 等链路分层；
- 专业评审者与普通用户的分歧；
- 版权、肖像、偏见和不安全内容。

### 最小实战

- 为一个公开小模型或固定候选输出建立 50 条数据集；
- 写一份可由另一位同学复现的标注规范；
- 让两名评审者独立标 20 条并分析分歧；
- 用确定性评分和模型裁判分别预测人工结果；
- 输出混淆矩阵、失败切片、置信区间和限制；
- 保留 10 条未参与调优的封存集。

### 验收

- 能解释数据为什么代表目标任务；
- 指标变化能追到具体样本；
- 不把 Benchmark 分数直接等同于产品质量；
- 不把模型裁判当成真值；
- 数据来源、许可证和版本清楚。

## 六、路线四：Agent 测试

### 目标

同时验证最终答案、工具轨迹和环境终态。

### 必测风险

| 风险 | 示例断言 |
|---|---|
| 选错工具 | 查询任务不能调用写入工具 |
| 参数错误 | Tool Schema、类型、范围和资源 ID 正确 |
| 越权 | 普通用户不能读取或修改其他主体数据 |
| 重复副作用 | 重试不会重复下单、扣款或发消息 |
| 无限循环 | 最大步数、时间和 Token 预算生效 |
| 记忆污染 | 新会话不继承不允许的旧状态 |
| Prompt Injection | 工具返回中的恶意文本不能改变系统权限 |
| 中断恢复 | 检查点后重启不会丢失或重复关键动作 |
| 人工审批 | 高风险写操作在审批前不能执行 |
| 多 Agent 失控 | 委派范围、共享上下文和停止条件明确 |

### 推荐 Mock 环境

构造完全虚构的“测试任务助手”：

- 只读工具：查询公开缺陷样例、读取合成测试计划；
- 写入工具：在内存中创建虚构任务；
- 高风险工具：模拟发送消息，但默认只返回“等待人工批准”；
- 重置接口：每条用例恢复初始状态；
- Trace：记录计划、工具、参数、返回、状态和预算；
- 故障注入：超时、重复返回、坏 Schema、权限拒绝和部分成功。

### 验收

- 不只断言最后一句文本；
- 每条用例验证允许/禁止工具和最终状态；
- 相同任务多次运行，报告成功率与最差失败；
- 每个写操作有幂等和补偿说明；
- 高风险工具默认最小权限并要求人工确认。

## 七、路线五：测试开发与评测平台

### 目标

把单次评测脚本发展成多人可用、可审计、可扩展的质量基础设施。

### 最小架构

```text
数据集/实验版本
      ↓
任务编排与队列
      ↓
模型、RAG、Agent 或 Mock 执行器
      ↓
确定性评分 / 人工任务 / 模型裁判
      ↓
逐例结果、Trace、成本和失败证据
      ↓
版本比较、质量门禁和报告
```

### 必须设计

- 数据集、样本、Prompt、模型、知识库和工具版本；
- provider/scorer 插件边界；
- 并发、限流、超时、重试、取消和恢复；
- 结果幂等写入和重复任务去重；
- 访问控制、密钥隔离、正文脱敏和审计；
- 指标聚合仍能下钻到逐例证据；
- CI 快速集与离线完整集分层；
- 成本预算与供应商故障降级。

### 最小作品

用 FastAPI 或 Spring Boot 实现：

- 创建数据集和实验；
- 提交异步评测；
- 查询状态和逐例结果；
- 对比基线与候选；
- 产生非零退出码的 CI 门禁；
- 注入 provider 超时并恢复；
- 导出不含敏感正文的报告。

### 验收

- 不是只有一个 Notebook；
- 任务失败后可定位、重试或取消；
- 结果可重复且版本可追溯；
- 权限与数据流画清楚；
- 有负载测试、故障注入和运维说明。

## 八、建议学习周期

以下是课程规划，不是招聘年限承诺。

| 当前基础 | 目标 | 建议增量周期 | 必须交付 |
|---|---|---:|---|
| 软件测试小白 | 普通测试 + AI 提效 | 在测试主线后 2～4 周 | 人工基线、AI 差异、可运行回归 |
| 会 API/pytest | AI 应用测试 | 6～8 周 | 模型 Mock、RAG 分层、性能与安全报告 |
| 会自动化与数据分析 | 模型评测 | 8～12 周 | 黄金集、标注规范、校准和配对实验 |
| 会 API/状态机 | Agent 测试 | 6～10 周 | 工具/权限/终态/恢复测试 |
| 会后端和 CI/CD | 评测平台 | 12～20 周 | 异步评测服务、结果库、门禁与观测 |

可并行学习，但作品只选一条主线做深。五个只能演示的项目，不如一个有失败、有诊断、有修复和有边界的项目。

## 九、简历与面试证据

### 不要这样写

> 熟悉 ChatGPT、Prompt、RAG、LangChain、Agent、DeepEval、Ragas。

### 改为可验证表达

> 基于 50 条公开/合成样本建立 RAG 分层回归，分别测检索召回、引用支持和正确拒答；为模型超时、429、流式中断和 Prompt Injection 建立 Mock 与 CI 门禁，并记录基线/候选的逐例差异及残余风险。

面试时按下面顺序讲：

```text
用户与风险
→ 为什么这样采样
→ 评分和人工标准
→ 自动化与环境
→ 发现的失败
→ 修复与复测
→ 仍然不知道什么
```

## 十、自我验收

- [ ] 我能区分五类 AI 测试岗位，不按标题猜职责；
- [ ] 我已完成普通测试、API、编程和 CI 基础；
- [ ] 作品的数据来源与授权范围可说明；
- [ ] 模型、Prompt、知识库、工具和数据集版本可追溯；
- [ ] 评测同时保存总览和逐例失败证据；
- [ ] 模型裁判经过人工校准；
- [ ] Agent 同时验证轨迹、权限、终态、副作用和恢复；
- [ ] 性能报告包含首 Token、完整延迟、错误、并发和成本；
- [ ] 严重安全失败有独立门禁；
- [ ] 我能说明样本限制，不把小实验包装成市场事实或生产经验。
