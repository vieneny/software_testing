# 功能测试：从需求到风险覆盖

> 本章只使用仓库内的虚构应用 `labs/demo-shop`。商品、价格、库存、规则和接口均为合成内容，不对应任何真实公司或业务。

功能测试不是“照着页面点一遍”。它的核心任务是：理解用户与系统要完成什么，识别最值得优先发现的失败，选择合适的测试方法，并提供足以支持发布决策的证据。

## 学习目标

完成本章后，你应该能够：

- 把模糊需求拆成角色、对象、规则、状态、数据、依赖、异常和非功能目标；
- 识别业务、数据、接口、环境和用户体验风险，并解释优先级；
- 为不同风险选择等价类、边界值、判定表、状态迁移、场景法或探索式测试；
- 决定哪些检查放在单元、API、UI、性能或人工探索层；
- 写出可复现、可行动的缺陷报告；
- 用覆盖、证据、未测范围和残余风险形成测试结论，而不是只汇报“执行了多少条”。

## 方法与示例

本章以 `demo-shop` 的“查商品 → 创建订单 → 查询订单”为贯穿示例，按范围、模型、风险、分层、执行取证和发布结论六步完成一次功能测试。等价类、边界值、判定表和状态迁移的详细推导见配套设计章节。

## 一、先运行虚构系统

在仓库根目录执行：

```bash
cd labs/demo-shop
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[test]'
uvicorn app.商城服务:app --host 127.0.0.1 --port 8000
```

Windows PowerShell 激活虚拟环境时通常使用：

```powershell
.venv\Scripts\Activate.ps1
```

另开终端，执行最小观察：

```bash
curl -i http://127.0.0.1:8000/health
curl -i http://127.0.0.1:8000/api/products
curl -i 'http://127.0.0.1:8000/api/products?keyword=马克杯&limit=10'
```

预期至少观察到：

- `/health` 返回 `200` 和 `{"status":"ok"}`；
- 商品列表返回 JSON；
- 响应包含 `Cache-Control: no-store`；
- 关键词可以过滤商品；
- `limit` 控制最多返回多少条。

浏览器访问 `http://127.0.0.1:8000` 可以观察最小购买流程。服务只监听本机回环地址，所有订单保存在内存中，重启服务即可重置。

## 二、认识测试对象

`demo-shop` 当前提供以下公开、虚构能力：

| 能力 | 主要规则 |
|---|---|
| 健康检查 | `/health` 返回服务状态 |
| 商品列表 | 可按 `keyword` 过滤；`limit` 范围为 1～100 |
| 商品详情 | 已知 ID 返回商品；未知 ID 返回 `404 product_not_found` |
| 创建订单 | 至少 1 个、最多 20 个条目；每项数量 1～10；商品必须存在且数量不能超过库存 |
| 幂等控制 | 请求头 `Idempotency-Key` 长度 8～128；同键同请求返回同一订单；同键不同请求返回 `409` |
| 查询订单 | 已存在订单可查询；未知订单返回 `404 order_not_found` |

这只是当前实现可观察到的行为，不代表完整电商需求。例如系统没有支付、取消、发货、库存扣减、用户鉴权和持久化。测试人员必须把“不在范围”写清，不能擅自把想象当成需求。

## 三、功能测试的完整方法

```text
确认目标与范围
    ↓
建立对象、规则、状态和依赖模型
    ↓
识别失败方式并按风险排序
    ↓
选择测试方法、层级、数据和环境
    ↓
执行、观察、记录最小证据
    ↓
汇总覆盖、缺口、残余风险和建议
```

### 第 1 步：确认目标与范围

先回答：

- 谁在使用？本章把用户简化为匿名购买者和调用 API 的客户端。
- 用户目标是什么？浏览商品、创建订单、查询订单。
- 成功的业务结果是什么？合法请求创建金额正确且可查询的订单。
- 失败会造成什么影响？重复订单、金额错误、超卖、错误信息不稳定或服务不可用。
- 这次不测什么？支付、物流、真实库存扣减、生产容量和真实用户数据。
- 环境有什么限制？单进程、内存数据、重启清空，不代表生产架构。

推荐范围声明：

```markdown
本轮验证商品查询、订单创建、幂等和订单查询的功能正确性。
不验证支付、发货、持久化和生产容量。
测试数据均为 demo-shop 内置商品与本地生成的订单。
```

### 第 2 步：建立测试模型

至少建立四类模型：

1. **对象模型**：商品、订单项、订单、幂等键。
2. **规则模型**：数量、库存、总价、必填字段、长度限制。
3. **状态模型**：幂等键从“未使用”到“已绑定请求和订单”。
4. **场景模型**：查商品 → 创建订单 → 查询订单。

模型的价值是暴露冲突和缺口。例如：

- 每项数量允许 1～10，但某商品库存只有 8；数量 9 应命中库存规则，而不是字段上限。
- 同一个幂等键绑定请求后，再发不同请求应该冲突；如果只验证第二次得到 `201`，可能漏掉是否创建了新订单。
- 商品详情和商品列表是否使用一致的字段与价格？
- 服务重启后幂等记录丢失是否属于当前环境限制，还是产品缺陷？必须先确认范围。

详细设计方法见 [测试分析与用例设计](01-测试分析与用例设计.md)。

### 第 3 步：建立风险清单

可以用“影响 × 发生可能性”做初排，每项 1～5 分。分数不是科学测量，只用于让团队讨论更具体。

| 风险 | 影响 | 可能性 | 分数 | 优先级 | 首选证据 |
|---|---:|---:|---:|---|---|
| 重试导致重复订单 | 5 | 4 | 20 | P0 | 同键重放和订单 ID 对比 |
| 总价计算错误 | 5 | 3 | 15 | P0 | 商品单价 × 数量的独立计算 |
| 超库存仍创建订单 | 5 | 3 | 15 | P0 | 库存边界和冲突响应 |
| 无效数量被接受 | 4 | 3 | 12 | P1 | 0、1、10、11 的边界测试 |
| 未知商品错误不稳定 | 3 | 3 | 9 | P1 | 状态码和稳定错误码 |
| 关键词前后空格导致错误结果 | 2 | 3 | 6 | P2 | 等价类与探索测试 |
| 页面按钮文本变化导致自动化失败 | 2 | 2 | 4 | P2 | UI 可访问角色与稳定契约 |

优先级建议：

- **P0**：发布前必须有可信证据；失败通常阻止发布。
- **P1**：重要功能和异常；失败需要明确负责人和决策。
- **P2**：低影响、低概率或可接受限制；可以在时间盒内探索。

不要把所有风险都标为 P0。无法排序通常说明没有理解业务影响。

### 第 4 步：选择方法和层级

| 风险 | 设计方法 | 推荐层级 | 原因 |
|---|---|---|---|
| 数量范围 | 等价类 + 边界值 | API / 单元 | 数据组合多，UI 验证成本高 |
| 幂等键重用 | 状态迁移 + 场景法 | API | 需要精确控制请求头和请求体 |
| 库存与字段上限交叉 | 判定表 | API | 多条件组合需要明确预期 |
| 用户购买主路径 | 场景法 | 少量 UI + API | UI 只证明跨层可见旅程 |
| 未知错误与文案 | 等价类 + 探索式测试 | API / UI | 同时关注协议和用户可理解性 |
| 高并发超卖 | 并发与性能测试 | API / 性能 | 常规单次功能测试不能证明 |

分层原则：

```text
大量规则组合和边界      → 单元 / API
服务契约、权限和数据    → API
少量关键用户旅程        → UI
容量、并发和资源        → 性能
未知风险、体验和可用性  → 探索式测试
```

UI 自动化不是“覆盖越多越好”。如果一个数量边界可以用 API 在 100 毫秒内稳定验证，就不应复制十个脆弱 UI 用例。

### 第 5 步：执行与取证

每次测试至少记录：

- 测试对象和版本；
- 环境和启动命令；
- 前置状态和合成数据；
- 操作或请求；
- 期望结果及其依据；
- 实际结果；
- 时间、状态码、关键响应和日志位置；
- 清理或重置方式。

创建订单的公开示例：

```bash
curl -i \
  -X POST http://127.0.0.1:8000/api/orders \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: tutorial-order-0001' \
  -d '{"items":[{"product_id":1,"quantity":2}]}'
```

再次执行同一命令，比较两个响应的订单 ID。然后保持幂等键不变，把数量改为 3：

```bash
curl -i \
  -X POST http://127.0.0.1:8000/api/orders \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: tutorial-order-0001' \
  -d '{"items":[{"product_id":1,"quantity":3}]}'
```

预期得到 `409` 和稳定错误码 `idempotency_key_reused_with_different_payload`。

证据应足以复现，但不要保存 Cookie、Token、真实账号或整份未经检查的日志。本实验没有真实凭据；未来迁移到其他公开练习系统时仍要执行脱敏检查。

### 第 6 步：形成发布结论

测试总结至少回答：

```markdown
# 测试总结

## 范围
- 已验证：
- 未验证：

## 环境
- 版本 / 启动方式：
- 已知限制：

## 结果
- P0 风险证据：
- P1 风险证据：
- 未解决缺陷：

## 残余风险
- 风险：
- 影响：
- 临时控制：
- 所有者：

## 建议
- 可以发布 / 有条件发布 / 不建议发布：
- 决策依据：
```

“所有用例通过”不等于“没有风险”。如果没有测试持久化、并发和鉴权，就必须把这些缺口写入结论。

## 四、探索式测试

脚本化用例验证已知规则；探索式测试用于学习系统、发现未知失败和修正模型。推荐使用时间盒 charter。

模板：

```markdown
探索目标：
关注风险：
使用数据 / 工具：
时间盒：
观察与证据：
新问题：
下一步：
```

示例 charter：

1. 在 30 分钟内探索商品关键词的大小写、空白、空字符串、中文和超长输入，关注过滤一致性和错误处理。
2. 在 45 分钟内改变幂等键、请求体、顺序和重发时机，关注是否产生重复订单或不稳定响应。
3. 在 30 分钟内通过浏览器和 API 交替创建、查询订单，关注页面状态、错误反馈和跨层一致性。

探索不是随便点。结束时必须输出观察、证据、新风险和下一轮假设。

## 五、缺陷报告

高质量缺陷报告让不了解现场的人也能复现并判断影响。

```markdown
# [严重级别] 简短描述可观察的问题

## 环境
- 版本：
- 操作系统 / 浏览器 / API：
- 数据状态：

## 前置条件

## 复现步骤
1.
2.
3.

## 期望结果
写出规则、接口契约或用户目标依据。

## 实际结果
只写观察，不先猜根因。

## 影响与风险

## 最小证据
- 请求 / 状态码 / 已脱敏响应：
- 相关日志时间：

## 补充
- 复现率：
- 临时绕过：
- 尚未验证：
```

标题不要写“下单有问题”。更好的标题是：

```text
[P0] 同一 Idempotency-Key 重试创建两个不同订单
```

## 常见误区

### 误区 1：需求写什么就只测什么

需求描述通常遗漏边界、冲突、失败恢复、权限和依赖。测试需要主动澄清，但不能擅自发明业务规则。

### 误区 2：用例数量等于覆盖

一百条重复正常流程不如一张清晰判定表。覆盖应映射到风险、规则、状态和场景。

### 误区 3：只验证状态码

`201` 不能证明总价、订单 ID、幂等和持久状态正确。还要验证响应结构、业务结果和后续查询。

### 误区 4：把所有检查堆到 UI

UI 用例慢且易受页面变化影响。业务规则和组合优先在 API 或更低层验证。

### 误区 5：实际结果里直接写根因

“数据库并发锁失败”是未经验证的假设。实际结果应写可观察事实，根因由证据逐步确认。

### 误区 6：环境限制不写入结论

本实验使用内存数据和单进程服务。它不能证明持久化、跨实例幂等和生产容量。

### 误区 7：复制真实公司需求练习

即使替换公司名和字段名也不允许。应使用本章虚构规则，从零设计测试。

## 练习

### 练习 1：风险分析

为 `demo-shop` 创建至少 10 条风险，包含：

- 3 条业务正确性风险；
- 2 条数据风险；
- 2 条接口或错误处理风险；
- 1 条用户体验风险；
- 1 条环境风险；
- 1 条当前范围外但需要显式记录的风险。

每条写出影响、可能性、优先级和最小证据。

### 练习 2：测试范围评审

写一页测试范围，必须包含：

- 用户与目标；
- 系统边界；
- 本轮包含和不包含；
- 依赖与环境限制；
- P0/P1 风险；
- 退出条件。

请另一位学习者只根据这页内容复述测试目标。如果理解不同，修改文档。

### 练习 3：执行三个 charter

从本章示例中选择三个 charter，每个时间盒 30～45 分钟。记录：

- 实际探索路径；
- 至少一个新问题或新风险；
- 支持观察的最小证据；
- 下一轮要验证的假设。

### 练习 4：缺陷与结论

主动修改一个请求制造失败，例如缺少幂等键、数量为 0 或未知商品。分别写：

1. 一份缺陷报告；
2. 一份测试总结；
3. 为什么这个结果是产品缺陷、正确拒绝或环境限制。

## 验收标准

- [ ] 能用自己的话说明测试目标、范围和环境限制；
- [ ] 风险清单至少覆盖业务、数据、接口、体验和环境，并有真实排序；
- [ ] 每个 P0 风险都有明确的测试方法、层级、数据和证据；
- [ ] 至少使用三种系统化设计方法，而不是只列正常/异常；
- [ ] 能运行商品查询、创建订单、同键重试和冲突请求；
- [ ] 缺陷报告可由另一人按步骤复现，期望有依据，实际结果不夹带未经验证的根因；
- [ ] 测试总结包含已测、未测、残余风险和发布建议；
- [ ] 探索记录有目标、时间盒、观察、新风险和下一步；
- [ ] 测试数据可重复构造，凭据通过环境配置注入。
