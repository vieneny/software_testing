# 综合实战：建立可展示的质量工程作品

综合项目不是把所有工具各运行一次，而是围绕一组明确风险建立证据链。初学阶段使用本仓库的 [demo-shop](../../labs/demo-shop/README.md)；中高级阶段使用[复杂系统测试实战](../../labs/复杂系统测试实战/README.md)中的 FastAPI + React 社区问答系统、Spring Boot + Vue 企业智能客服系统和统一 Python AI 中间件。

建议顺序：

```text
demo-shop 基础闭环
→ 社区问答系统：内容、互动、并发、搜索与审核
→ 企业智能客服：多租户、工单状态机、SLA 与审计
→ 统一 AI 中间件：契约、降级、评测、安全与可观测
```

## 项目目标

你需要回答六个问题：

1. 用户和系统最重要的目标是什么？
2. 哪些失败影响最大，依据是什么？
3. 每类风险在哪一层测试最经济、最可靠？
4. 自动化结果如何帮助发布决策？
5. 失败如何快速诊断，残余风险如何表达？
6. 当系统包含 AI 能力时，质量、安全、延迟和成本如何一起评估？

## 推荐目录

在自己的练习分支中新建：

```text
portfolio/demo-shop-quality/
├── README.md                 # 背景、目标、运行和结论
├── scope.md                  # 范围、假设、依赖、不在范围
├── risk-register.md          # 风险、优先级、策略、状态
├── models/                   # 状态图、判定表、数据模型
├── exploratory/              # charter 与 session 记录
├── tests/                    # 接口、UI、性能、AI 评测
├── data/                     # 仅合成数据与数据说明
├── reports/                  # 小型 Markdown 总结，不提交巨型原始报告
└── decisions/                # 关键取舍记录
```

浏览器 trace、视频、HAR、性能原始结果可能很大且可能包含敏感信息，本仓库默认忽略。报告只保留经过检查的关键证据和复现方式。

## 任务 1：定义范围和质量目标

### 交付内容

- 用户：浏览者、购买者、支持人员（均为虚构角色）；
- 核心旅程：查看商品、创建订单、读取订单；
- 质量属性：正确性、可用性、性能、安全、可访问性、可测试性；
- 明确不在范围：真实支付、真实物流、真实账号、生产容量；
- 业务目标的教学假设，例如“下单 API 的错误率低于 1%”必须标为**实验阈值**，不能冒充行业标准。

### 验收

范围能让另一位学习者判断哪些问题该报、哪些暂不处理；每个目标都有可观察证据。

## 任务 2：建立风险登记表

推荐字段：

| 字段 | 说明 |
|---|---|
| 风险 | 可能发生的失败，不是测试步骤 |
| 触发条件 | 数据、状态、并发、依赖或用户动作 |
| 影响 | 用户、业务、合规、运维和恢复成本 |
| 可能性依据 | 复杂度、变更、历史公开案例或技术机制 |
| 可发现性 | 发生后多快能被谁看到 |
| 优先级 | 高 / 中 / 低，并说明理由 |
| 测试层 | 静态、单元、API、契约、UI、性能、安全、线上观测 |
| 证据 | 测试、指标、日志或人工评审 |
| 残余风险 | 测完后仍未知或未覆盖的部分 |

至少包含：金额错误、重复下单、库存并发、契约不兼容、权限越界、服务重启数据丢失、UI 关键旅程失败、性能退化、日志泄密和 AI 幻觉/越权。

## 任务 3：功能测试设计

- 对数量、列表长度设计等价类和边界值；
- 对订单规则建立判定表；
- 对订单生命周期建立状态迁移模型，并指出当前教学应用缺少哪些状态；
- 设计三个探索式测试 charter：幂等性、异常恢复、可访问性；
- 记录观察、调整、问题、证据和下一步。

验收重点不是用例数量，而是高风险规则与状态是否可追踪。

## 任务 4：接口与契约自动化

从现有 `tests/api` 开始扩展：

- 正常：多商品、总价和查询一致性；
- 边界：数量 1 / 10 / 11，列表限制 1 / 100 / 101；
- 异常：未知商品、空条目、重复商品、非法 JSON、错误内容类型；
- 幂等：相同键相同请求、相同键不同请求、并发相同键；
- 契约：字段类型、必填字段、错误结构、OpenAPI 兼容；
- 健壮性：超时、连接失败、服务重启；
- 安全：输入编码、错误信息、未授权能力（先写风险，勿连接真实安全目标）。

要求测试可乱序、可重复，并为请求设置显式超时。失败输出中不记录 Cookie、Token 或真实数据。

## 任务 5：Web UI 关键旅程

只保留两至四条高价值端到端路径：

1. 页面加载并展示商品；
2. 用户购买商品并看到订单结果；
3. API 失败时显示可理解且可恢复的反馈；
4. 键盘和可访问名称能完成核心操作。

验收：无固定休眠；稳定定位；用例数据隔离；失败有 trace；说明为什么大量字段组合没有放在 UI 层。

## 任务 6：性能实验

先提出问题，再运行工具：

```text
问题：当商品浏览到达率逐步上升时，p95 何时超过实验阈值？
假设：单进程应用首先受 CPU 或事件循环饱和影响。
自变量：到达率。
因变量：p50/p95/p99、错误率、吞吐和服务端资源。
控制：相同代码、数据、机器、预热和脚本版本。
```

至少完成：基线、阶梯负载和一次短压力实验。报告应标出时间线、阈值、资源数据、瓶颈假设、环境限制和下一轮验证。不对开发电脑结果做生产外推。

## 任务 7：AI 评测扩展

在 `tests/ai/人工智能评测数据集.jsonl` 上扩展：

- 至少 30 条全部为合成的样本；
- 正常、边界、无答案、规则冲突、注入、敏感请求和计算各有切片；
- 每条样本定义期望行为、确定性检查和是否需要人工判断；
- 安全关键项单独门禁，不允许总平均分掩盖；
- 对关键词评分器制造同义表达和否定句，证明它的误报/漏报；
- 设计模型裁判 rubric，但在使用云模型前先确认数据、费用和权限；
- 多次运行非确定性系统，报告失败率和波动。

如未接入真实模型，也可以用固定候选输出完整练习数据集、评分、报告和 CI。先掌握评测工程，再增加提供商依赖。

## 任务 8：CI 质量门禁

设计反馈速度分层：

| 触发 | 内容 | 目标 |
|---|---|---|
| 本地 / 提交前 | 格式、静态检查、小型确定性测试 | 秒级反馈 |
| 合并请求 | API smoke、契约、AI 小型集 | 阻止明显回归 |
| 合并后 / 定时 | 完整 API、关键 UI、较大评测集 | 扩大覆盖 |
| 人工触发 | 性能、红队、破坏性实验 | 受控资源与授权 |

门禁必须使用退出码；不能只上传一个报告但让失败任务显示成功。重跑用于确认 flaky，不能把三次中一次通过算成通过。

## 任务 9：故障演练与失败分诊

主动注入以下变更，每次记录第一个有效信号和定位路径：

- 商品价格字段改名；
- 服务返回 500；
- 页面按钮文本和 DOM 层级变化；
- 响应延迟增加 500 ms；
- AI 固定输出包含禁止词；
- 幂等记录在重启后丢失。

分类为：产品缺陷、测试缺陷、环境问题、数据问题、不稳定或预期变更。对误报也要复盘，因为低可信门禁最终会被团队绕过。

## 作品验收清单

- [ ] 任何人只按 README 能在 15 分钟内开始运行；
- [ ] 所有数据为公开或从零合成，未读取本机其他工作目录；
- [ ] 风险、需求、测试和证据可追踪；
- [ ] 自动化可重复、可乱序、失败可诊断；
- [ ] UI 只覆盖高价值旅程；
- [ ] 性能结论包含负载模型与环境限制；
- [ ] AI 评测分项报告质量、安全、延迟和成本；
- [ ] CI 的门禁确实能在回归时失败；
- [ ] 说明工具取舍、未知项和残余风险；
- [ ] `git diff` 中没有密钥、真实数据、大型运行产物或公司资料。

达到这些标准后，作品展示的是测试思维、工程能力与决策质量，而不是工具截图集合。
