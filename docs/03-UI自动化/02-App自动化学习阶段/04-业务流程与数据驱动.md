# 第四章：业务流程与数据驱动

课程主线是“进入首页 → 登录 → 搜索 → 加入购物车 → 下单”。本章将它拆成可诊断的独立能力测试和一条关键旅程。

## 1. 业务状态模型

```text
STARTED
  → AUTHENTICATED
  → SEARCHED
  → CART_READY
  → ORDERED
```

每次迁移都要定义前置、动作、结果与副作用。配套 `SyntheticCommerceApp` 会拒绝跳过搜索直接加购、跳过购物车直接结算等非法迁移。

## 2. 四组测试

| 领域 | 正常 | 边界/异常 | 关键断言 |
|---|---|---|---|
| 登录 | 合成账号成功 | 空值、格式、错误密码、会话失效 | 用户状态和目标页 |
| 搜索 | 精确/模糊词 | 无结果、特殊字符、重复搜索 | 结果与规则匹配 |
| 购物车 | 首次加入 | 数量 0、库存上界、重复加入 | 商品、数量、金额 |
| 订单 | 正常结算 | 前置缺失、重复点击、提交失败 | 订单号、总额、幂等性 |

UI 测试不需要穷举所有组合。字段规则和大量数据优先在单元/API 层，UI 保留用户可见的高价值组合。

## 3. 数据文件契约

```json
{
  "case_id": "login-invalid-format",
  "username": "invalid.example.test",
  "password": "demo-pass",
  "expected": "账号格式错误"
}
```

加载时按字段名校验，不使用 `tuple(item.values())`。每条数据具有稳定 `case_id`，报告能直接定位输入、预期和来源。

数据分四类管理：

- 固定合成数据：进入 Git，可重复；
- 每次生成数据：带测试前缀和清理策略；
- 本地配置：放 `.env`；
- 设备/应用资产：使用绝对路径，不进入数据文件。

## 4. 一条关键 E2E

`tests/unit/test_course_purchase_flow.py` 运行：

```text
登录成功 → 搜索“毛巾” → 加购 2 件 → 结算
```

它断言订单 ID、商品 ID、数量、金额和完整事件顺序。负向测试分别验证登录失败、无结果、库存边界、幂等与非法状态，失败后能立即知道是哪一层。

## 5. 实际 App 的前置状态

优先级：

1. 测试 API 或 seed 构造受控状态；
2. 明确的固定演示账号；
3. UI 前置步骤；
4. 禁止依赖上一条用例留下的登录、购物车或订单。

订单场景应使用不会产生真实交易的本地或公开练习系统，并在结算前明确测试终点。
