# 性能工具实践：k6、JMeter 与 Locust

> 工具选择主线：代码化 HTTP 性能测试优先 k6；需要兼容大量既有 `.jmx` 与企业生态时使用 JMeter；Python 团队和复杂用户行为可选 Locust。所有命令只压本地虚构 Demo Shop。

## 学习目标

完成本章后，你应当能够：

1. 运行仓库现有 k6 与 Locust 脚本，并解释其工作负载。
2. 用 k6 threshold 让性能失败产生非零退出码。
3. 正确使用 JMeter GUI 设计/调试、CLI 执行负载。
4. 在相同负载语义下比较工具，而不是只比较配置行数。
5. 保存可审计结果，并避免把敏感流量与内部资料提交仓库。

## 1. 工具选型

| 需求 | 建议工具 | 原因 |
|---|---|---|
| 新建代码化 HTTP 测试、CI 门禁 | k6 | JavaScript API、Scenario/Threshold 内建 |
| 已有 JMeter 资产、插件或非研发使用者 | JMeter | 成熟 GUI 与企业存量生态 |
| Python 用户行为、需自定义调度逻辑 | Locust | Python 代码、分布式 Worker |
| 浏览器前端性能 | 浏览器 RUM/Lighthouse/Playwright Trace 等 | 协议压测工具不等于渲染性能工具 |

三种工具都能发 HTTP 请求；决定因素是负载模型、团队技能、可观测性、CI/分布式运行和存量资产。

## 3. k6：本项目主线

按 [k6 官方安装文档](https://grafana.com/docs/k6/latest/set-up/install-k6/) 安装当前稳定版，然后：

```bash
cd labs/demo-shop
k6 version
k6 run tests/performance/轻量性能冒烟脚本.js
```

仓库脚本的核心：

```javascript
export const options = {
  scenarios: {
    browse_products: {
      executor: 'constant-vus',
      vus: Number(__ENV.VUS || 3),
      duration: __ENV.DURATION || '20s',
      gracefulStop: '5s',
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<300'],
    checks: ['rate>0.99'],
  },
};
```

默认语义：

- 3 个封闭虚拟用户。
- 持续 20 秒，每次查询后 `sleep(1)`。
- 只访问 `GET /api/products`。
- 错误率、p95 和业务检查是教学阈值。
- Threshold 失败时 k6 返回非零退出码，可作为 CI 门禁。

小幅覆盖参数：

```bash
DEMO_BASE_URL='http://127.0.0.1:8000' \
VUS=5 \
DURATION='30s' \
k6 run tests/performance/轻量性能冒烟脚本.js
```

先跑默认 Smoke。不要因为环境变量可改就把 VUS 调大或改成未授权 URL。

### 3.1 检查与标签

现有脚本同时检查状态码和非空商品列表，并用 tag 聚合操作：

```javascript
const response = http.get(`${baseUrl}/api/products`, {
  tags: { operation: 'list_products' },
  timeout: '3s',
});

check(response, {
  'list returns 200': (res) => res.status === 200,
  'list is not empty': (res) => {
    try {
      return res.json().length > 0;
    } catch (_) {
      return false;
    }
  },
});
```

`check` 失败默认不会像代码异常一样立即中止；Threshold 才决定整次运行是否通过。两者应配合。

### 3.2 开放模型练习

若需求是“固定每秒 5 次到达”，可另写公开本地练习脚本：

```javascript
import http from 'k6/http';
import { check } from 'k6';

const baseUrl = __ENV.DEMO_BASE_URL || 'http://127.0.0.1:8000';

export const options = {
  scenarios: {
    fixed_arrival_rate: {
      executor: 'constant-arrival-rate',
      rate: 5,
      timeUnit: '1s',
      duration: '30s',
      preAllocatedVUs: 2,
      maxVUs: 10,
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
    'http_req_duration{scenario:fixed_arrival_rate}': ['p(95)<300'],
    dropped_iterations: ['count==0'],
  },
};

export default function () {
  const response = http.get(`${baseUrl}/api/products`, {
    timeout: '3s',
  });
  check(response, {
    'status is 200': (result) => result.status === 200,
  });
}
```

`dropped_iterations` 表示发生器没有按计划启动迭代，可能是 VU 不足或发生器/系统过慢。不要只提高 `maxVUs`，先看资源和停止条件。

### 3.3 保存结果

需要逐时间点分析时，使用实时 JSON 输出：

```bash
mkdir -p reports/k6
k6 run \
  --out json=reports/k6/points.json \
  tests/performance/轻量性能冒烟脚本.js
```

它会保存每个指标样本，文件可能较大。只需要聚合结果时，在脚本末尾实现当前推荐的 `handleSummary`：

```javascript
export function handleSummary(data) {
  return {
    'reports/k6/summary.json': JSON.stringify(data, null, 2),
  };
}
```

运行前先创建 `reports/k6`。旧的 `--summary-export` 当前仍可用，但 k6 官方已建议用 `handleSummary` 获得更灵活、可版本化的格式。控制台摘要适合人读，JSON 适合留存/加工。正式趋势分析应接入受控的时序后端并记录脚本、环境和提交版本。公开仓库报告只含虚构本地数据。

## 4. JMeter：兼容企业存量

按 [JMeter 官方入门](https://jmeter.apache.org/usermanual/get-started.html) 安装兼容的 Java 和 JMeter。

### 4.1 GUI 只用于设计与调试

在 GUI 建立：

```text
Test Plan
└── Thread Group
    ├── HTTP Request Defaults
    ├── HTTP Header Manager
    ├── GET Products
    ├── Response Assertion
    └── Summary Report（只用于小流量调试）
```

配置：

- Thread Group：3 threads，ramp-up 3 秒，duration 20 秒，启用 Scheduler。
- HTTP Request Defaults：
  - Protocol：`http`
  - Server：`${__P(base_url,127.0.0.1)}`
  - Port：`${__P(port,8000)}`
  - Connect/Response timeout：`3000` ms
- GET Products：
  - Method：`GET`
  - Path：`/api/products`
- Response Assertion：Response Code 等于 `200`，Response Text 包含 `"name"`。

用 1 个线程、1 次循环验证脚本。不要在真正负载运行中开启 View Results Tree、保存完整响应或大量 Debug 日志，它们会消耗内存并扭曲结果。

### 4.2 CLI 执行

把公开测试计划保存为 `demo-shop.jmx`，关闭 GUI 后执行：

```bash
mkdir -p reports/jmeter/run-001
jmeter -n \
  -t demo-shop.jmx \
  -Jbase_url=127.0.0.1 \
  -Jport=8000 \
  -l reports/jmeter/run-001/results.jtl \
  -e \
  -o reports/jmeter/run-001/html
```

`-n` 是非 GUI；`-l` 保存样本；`-e -o` 生成 HTML 报告。HTML 输出目录必须不存在或为空，建议每次使用新的运行编号，不要覆盖历史证据。

### 4.3 创建订单请求

为少量虚构订单添加：

- HTTP Header Manager：
  - `Content-Type: application/json`
  - `Idempotency-Key: ${__UUID()}`
- HTTP Request：`POST /api/orders`
- Body Data：

```json
{"items":[{"product_id":1,"quantity":1}]}
```

- Response Assertion：状态 `201`，响应含 `"status":"created"`。

每次迭代使用新 UUID，避免幂等重放把两次请求合并。若目标就是测重放，则显式把同一 UUID 保存为变量并在同一事务中复用。

## 5. Locust：Python 行为建模

仓库已经提供 `tests/performance/用户负载模型.py`：

- `browse_products` 权重 4。
- `create_order` 权重 1。
- 用户请求之间随机等待 0.5～1.5 秒。
- 每个订单使用新的 UUID。

交互运行：

```bash
cd labs/demo-shop
source .venv/bin/activate
locust \
  -f tests/performance/用户负载模型.py \
  --host http://127.0.0.1:8000
```

打开终端显示的本地 Web 地址，先用 1 个用户验证，再使用低负载。

无头执行并保存公开报告：

```bash
mkdir -p reports/locust
locust \
  -f tests/performance/用户负载模型.py \
  --host http://127.0.0.1:8000 \
  --headless \
  --users 5 \
  --spawn-rate 1 \
  --run-time 30s \
  --csv reports/locust/demo \
  --html reports/locust/demo.html
```

Locust 的 `HttpUser` 是封闭用户模型：响应变慢时，每个用户下一次请求也推迟。

### 5.1 给 Locust 增加退出门禁

可在学习副本中增加停止监听器：

```python
from locust import events


@events.quitting.add_listener
def enforce_thresholds(environment, **_kwargs) -> None:
    total = environment.stats.total
    p95 = total.get_response_time_percentile(0.95)
    if total.fail_ratio >= 0.01 or p95 >= 300:
        environment.process_exit_code = 1
```

这只是与 k6 示例相同的本地教学阈值。低样本下百分位不稳定；正式使用还要处理“无请求”、分场景阈值和环境噪声。

## 6. 公平比较工具

若要比较 k6、JMeter、Locust，至少对齐：

- 开放/封闭模型。
- 用户数或到达率，而不是只对齐一个“线程数”字段。
- 思考时间、持续时间和 ramp-up。
- HTTP Keep-Alive、重定向、超时。
- 业务比例、请求体和数据唯一性。
- 正确性检查。
- 发生器硬件、网络和工具版本。

同一“5 用户”在不同默认等待和迭代模型下，RPS 可以完全不同。工具优劣不能由一次不同语义的吞吐数字决定。

结果表：

| 项目 | k6 | JMeter | Locust |
|---|---|---|---|
| 模型 | `constant-vus` | Thread Group | `HttpUser` |
| 用户/到达率 |  |  |  |
| 思考时间 |  |  |  |
| 实际 RPS |  |  |  |
| p50/p95/p99 |  |  |  |
| 错误/检查 |  |  |  |
| 发生器 CPU/内存 |  |  |  |

## 7. CI 与可观测性

推荐流程：

```text
启动隔离 Demo Shop
  → 健康检查
  → 低负载 Smoke
  → Threshold/退出码
  → 上传脱敏摘要
  → 无论成功失败都停止服务
```

PR 只跑短 Smoke；更长负载放到稳定专用环境和定时任务。共享 Runner 的性能数据噪声大，适合发现严重回归，不适合做精确容量认证。

不要上传：

- 公司域名、IP、Header、Token、Cookie。
- 真实请求体、账号和客户标识。
- 内部监控截图、日志、Trace。
- 未经审查的 JMX、HAR、CSV 或 HTML 报告。

## 8. 常见错误

1. 直接把 VUS/线程数当 RPS。
2. 在 JMeter GUI 和大量 Listener 下正式发压。
3. k6 只写 `check`，没有 Threshold，CI 仍返回成功。
4. Locust 行为权重相同，却忽略不同任务耗时导致的实际比例。
5. 比较三个工具时没有对齐等待、连接和负载模型。
6. 发生器先饱和，却把吞吐平台误判为服务容量。
7. 每次覆盖输出目录，无法追溯版本和条件。
8. 把可配置 URL 指向未授权公网/公司系统。

## 9. 练习与验收

### 练习

1. 运行现有 k6 Smoke，解释每个指标和 Threshold。
2. 把 k6 p95 阈值故意改得极低，确认退出码非零，再恢复。
3. 建立最小 JMX，用 1 用户调试、CLI 低负载运行并生成 HTML。
4. 无头运行 Locust，保存 CSV/HTML，并说明实际浏览/下单比例。
5. 用相同封闭模型对齐三种工具，填写比较表。
6. 写一个开放模型 k6 脚本，观察 `dropped_iterations`。

### 验收标准

- [ ] 三种工具都只访问 `127.0.0.1`。
- [ ] k6 Threshold 失败会返回非零。
- [ ] JMeter 正式运行使用 `-n`，没有重型 GUI Listener。
- [ ] Locust 无头运行可限定用户、增速和时长并保存报告。
- [ ] 比较时对齐负载语义、等待、检查和环境。
- [ ] 报告写明版本、模型、结果、限制，且不含公司内容。
