# 性能测试方法：从业务问题到可信结论

> 本章只对本机虚构 Demo Shop 做低强度实验。未经书面授权，不得对公司、第三方或公网系统发压。负载测试可能造成真实故障、成本和数据污染。

## 学习目标

完成本章后，你应当能够：

1. 把“系统要快”转化为可验证的工作负载、指标和通过标准。
2. 区分烟雾、平均负载、压力、突增、耐久和断点测试。
3. 解释吞吐、并发、响应时间百分位、错误率和资源饱和度。
4. 区分开放与封闭负载模型，避免错误外推。
5. 设计可重复实验，并对结论的适用边界负责。

## 1. 性能测试先回答业务问题

一份可执行的性能需求至少回答：

```text
谁在做什么？
以怎样的到达速率、并发和业务占比？
持续多久，是否有预热和突增？
数据规模、缓存状态和依赖条件是什么？
什么指标算通过？
在哪个环境与版本上测得？
达到什么停止条件必须中止？
```

不充分的说法：

```text
支持 1000 并发，响应要快。
```

更可验证的虚构学习目标：

```text
在单机本地 Demo Shop、固定 3 个商品、服务刚启动的条件下，
3 个封闭虚拟用户按每次请求后等待 1 秒的节奏查询商品，
持续 20 秒；http_req_failed < 1%，p95 < 300 ms，检查通过率 > 99%。
```

这个目标只验证测试链路和阈值机制，不能证明生产容量。

## 2. 核心指标

### 2.1 响应时间

报告分位数，而不是只看平均值：

- `p50`：典型体验。
- `p90/p95`：大部分请求的尾部体验，常用于服务目标。
- `p99`：更极端尾部，需要足够样本量。
- `max`：易被单个异常影响，只作为调查线索。

`p95=300 ms` 表示约 95% 的观测不超过 300 ms，不表示“每个用户都在 300 ms 内”，也不表示剩余 5% 可以无限慢。

### 2.2 吞吐

常见单位：

- requests/s（RPS）
- transactions/s
- 每分钟订单数
- 每秒传输字节数

先定义“事务”。一次下单用户旅程可能包含商品查询和订单创建，不能把两个 HTTP 请求直接当成两个业务订单。

### 2.3 并发

并发是某时刻正在系统中处理或等待的工作量，不等同于注册用户、在线用户，也不等同于 RPS。

稳定系统中可用 Little's Law 做合理性检查：

```text
平均系统内请求数 N ≈ 到达率 λ × 平均停留时间 W
```

例如 20 RPS、平均响应 0.1 秒，平均在途请求约 2。这个关系是检查模型的工具，不是脱离思考直接推导容量的公式；非稳态、排队增长或闭环思考时间都会影响解释。

### 2.4 错误率与正确性

至少区分：

- 连接、DNS、TLS、超时等传输错误。
- HTTP 5xx。
- 非预期 4xx。
- HTTP 200 但业务断言失败。

负载下“快速返回错误”不是好性能。每个关键请求应有轻量正确性检查。

### 2.5 饱和度

服务端和发生器都要观察：

- CPU、内存、GC。
- 线程/协程、事件循环、连接池。
- 数据库连接、锁、慢查询。
- 磁盘/网络 I/O。
- 队列长度与排队时间。
- 负载发生器自身 CPU、网络、连接数。

只看客户端响应时间无法定位瓶颈；发生器饱和还会制造假结论。

## 3. 测试类型

| 类型 | 目标 | 典型负载 | 主要产出 |
|---|---|---|---|
| Smoke | 验证脚本、环境、监控 | 极低、数十秒 | 脚本可运行 |
| Average/Load | 验证预期日常负载 | 目标负载、稳定时段 | SLO、资源余量 |
| Stress | 超过目标逐步加压 | 阶梯上升 | 拐点与退化方式 |
| Spike | 验证突然流量变化 | 快速上升/下降 | 弹性、限流、恢复 |
| Soak/Endurance | 发现泄漏和累积问题 | 中等负载、长时间 | 内存/连接/队列趋势 |
| Breakpoint | 探索极限 | 控制地增加到失败 | 容量边界与保护机制 |

先 Smoke，再负载；没有授权、监控和停止条件时不要做 Stress、Spike 或 Breakpoint。

## 4. 开放与封闭负载模型

### 封闭模型

固定虚拟用户完成请求、等待，再发下一次。响应变慢时，用户也被拖慢，实际到达率可能下降。

```text
用户 → 请求 → 等响应 → 思考时间 → 下一请求
```

现有 `轻量性能冒烟脚本.js` 的 `constant-vus` 和 Locust `HttpUser` 都属于封闭模型，适合表达有限用户循环。

### 开放模型

按外部到达率产生请求，不等待上一批完成。系统变慢时，在途请求和排队会增加，更接近 webhook、消息或独立用户到达。

```text
时间轴 → 5 次/秒持续到达，无论前一请求是否完成
```

错误选择封闭模型可能产生“协调遗漏”：系统越慢，发生器发得越少，从而低估排队和尾延迟。开放模型也可能在失控时快速堆积，必须设置最大虚拟用户和停止条件。

## 5. 为 Demo Shop 建工作负载

公开实验的业务比例可设为：

| 场景 | 比例 | 数据 |
|---|---:|---|
| 浏览商品 | 80% | `GET /api/products` |
| 创建订单 | 20% | `POST /api/orders`，每次新 Key |

先说明实现限制：

- 订单只存内存，重启清空。
- 没有数据库、认证、分布式锁或多实例。
- 创建订单不会真实扣减库存。
- 商品只有 3 个，无法代表大数据量查询。

因此它适合学习脚本、负载模型、阈值和报告，不适合得出电商系统容量结论。

### 教学用假设阈值

```text
错误率 < 1%
HTTP p95 < 300 ms
业务检查通过率 > 99%
```

阈值来自仓库现有 k6 Smoke 配置，只是本机练习门禁。真实阈值应来自用户体验、上下游预算、历史基线和业务价值。

## 6. 可重复实验流程

### 6.1 定义

记录：

- 被测提交/镜像版本。
- 服务、运行时、依赖与配置。
- 硬件/容器资源。
- 数据规模和初始化方式。
- 负载模型、脚本版本和随机数据策略。
- 指标、阈值、停止条件。

### 6.2 校验

1. 单用户手工验证请求与断言。
2. 低负载 Smoke，确认客户端和服务端监控。
3. 检查负载发生器没有饱和。
4. 确认测试数据不会碰真实用户或不可逆操作。

### 6.3 执行

- 保留预热期，避免把首次编译/连接与稳态混在一起。
- 稳态持续足够长，获得有意义的样本。
- 每次只改变一个主要变量。
- 同一条件重复多次，报告离散程度。
- 达到错误率、资源或业务保护上限立即停止。

### 6.4 分析

按时间对齐：

```text
负载变化
  → 客户端吞吐/延迟/错误
  → 服务 CPU/内存/连接/队列
  → 依赖与日志/Trace
```

相关不等于因果。CPU 与延迟同时升高是线索，还要通过剖析、慢查询、队列和对照实验验证。

### 6.5 报告

最小报告结构：

```text
结论：在何种条件下是否满足哪个阈值
范围：版本、环境、数据、时间
模型：开放/封闭、负载曲线、业务比例
结果：吞吐、p50/p95/p99、错误、检查、资源
异常：发生时间、证据、可能原因、待验证项
限制：不能外推到哪些场景
行动：优化/复测/监控/容量建议
```

## 7. 基线与回归

性能回归比较必须尽量保持：

- 同类硬件和资源配额。
- 同样数据与缓存策略。
- 同一脚本、工具版本和负载模型。
- 相近的背景流量与依赖。
- 足够重复次数。

不要把一次本机运行与一次 CI 共享 Runner 运行直接比较。可以同时维护：

- 绝对阈值：用户/业务不能接受的上限。
- 相对基线：同条件下版本间的显著变化。

相对变化也需要噪声带与重复实验，不能因 2% 波动立即判定回归。

## 8. 安全与停止条件

执行前清单：

- [ ] 目标域名/IP 和时间窗口获得授权。
- [ ] 只使用隔离测试数据和专用账号。
- [ ] 相关研发、运维和业务方知情。
- [ ] 有服务健康、成本和依赖监控。
- [ ] 有明确停止阈值和负责人。
- [ ] 工具不会跟随重定向误入第三方。
- [ ] 日志与报告已脱敏。

本仓库的所有示例固定为 `127.0.0.1`。即使脚本允许环境变量覆盖，也不得将公开仓库教程直接用于未授权目标。

## 9. 常见错误

1. 用“并发用户数”代替完整工作负载模型。
2. 只报告平均响应时间。
3. 不做业务检查，把大量 4xx/5xx 当成高吞吐。
4. 用封闭模型验证固定到达率，却没发现系统变慢后请求量下降。
5. GUI 监听器、Debug 日志或发生器 CPU 成为瓶颈。
6. 测一次就宣布容量，没有重复和环境记录。
7. 在 Demo Shop 上测得数字后外推到真实电商系统。
8. 对公网、第三方或公司生产环境擅自发压。

## 10. 练习与验收

### 练习

1. 为 Demo Shop 写一个 80% 查询、20% 下单的工作负载说明。
2. 分别用封闭和开放模型表达“5 个用户循环”和“固定 5 RPS”。
3. 为 Smoke、平均负载、Spike 写负载曲线与停止条件。
4. 根据 Little's Law 检查一个虚构结果：10 RPS、平均响应 200 ms 的平均在途请求。
5. 写一份报告，明确为什么本机结果不能外推到生产。

### 验收标准

- [ ] 需求同时写明负载、持续时间、数据、阈值和环境。
- [ ] 报告包含 p50/p95/p99、吞吐、错误、检查和服务端资源。
- [ ] 能解释开放与封闭模型，以及协调遗漏风险。
- [ ] 先完成 Smoke，再执行更高负载。
- [ ] 结论明确适用范围与限制，不把本机数字当生产容量。
- [ ] 目标仅为本地授权实验，无公司或第三方内容。
