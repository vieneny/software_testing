# HTTP 与 API 基础

> 本章只使用仓库内的虚构系统 `labs/demo-shop`。不要把公司域名、Token、Cookie、请求日志、HAR、客户数据或内部接口定义复制进本仓库。

## 学习目标

完成本章后，你应当能够：

1. 把一次 HTTP 交互拆成方法、URL、请求头、请求体、状态码、响应头和响应体。
2. 解释安全方法、幂等、缓存、超时和内容协商，并避免把它们混为一谈。
3. 从 OpenAPI 文档提取接口约束，设计正常、边界、异常和状态相关测试。
4. 用 `curl` 独立复现 Demo Shop 的查询、创建订单和幂等冲突。

## 1. 启动公开实验系统

在仓库根目录执行：

```bash
cd labs/demo-shop
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[test]'
uvicorn app.商城服务:app --host 127.0.0.1 --port 8000
```

保持这个终端运行，再打开另一个终端验证：

```bash
curl --silent --show-error --include http://127.0.0.1:8000/health
```

预期状态为 `200 OK`，响应体为：

```json
{"status":"ok"}
```

可浏览：

- Web 页面：`http://127.0.0.1:8000`
- Swagger UI：`http://127.0.0.1:8000/docs`
- OpenAPI：`http://127.0.0.1:8000/openapi.json`

服务只绑定 `127.0.0.1`。学习时不要把负载发送到公网或未获得书面授权的环境。

## 2. 用一张图理解 HTTP

```text
客户端
  └─ 请求：方法 + URL + 请求头 + 可选请求体
         ↓
      服务端路由、校验、业务处理
         ↓
  ┌─ 响应：状态码 + 响应头 + 可选响应体
客户端
```

下面的命令同时展示状态行、响应头和 JSON：

```bash
curl --silent --show-error --include \
  'http://127.0.0.1:8000/api/products?keyword=马克杯&limit=1'
```

逐项观察：

- 方法：未显式指定时 `curl` 使用 `GET`。
- URL：`/api/products` 是路径；`keyword`、`limit` 是查询参数。
- 状态码：成功查询为 `200`。
- 响应头：`Content-Type: application/json` 描述表示格式；`Cache-Control: no-store` 表示不应缓存。
- 响应体：JSON 数组，包含 `id`、`name`、`price_cents`、`stock`。

## 3. 方法、安全性与幂等

| 方法 | 常见用途 | 安全方法 | 本质上幂等 | Demo Shop |
|---|---|---:|---:|---|
| `GET` | 查询资源 | 是 | 是 | 商品和订单查询 |
| `POST` | 创建或触发动作 | 否 | 否 | 创建订单 |
| `PUT` | 整体替换 | 否 | 是 | 未实现 |
| `PATCH` | 局部修改 | 否 | 不保证 | 未实现 |
| `DELETE` | 删除资源 | 否 | 是 | 未实现 |

“安全”指规范语义上不应改变服务端状态；“幂等”指重复执行一次或多次，预期效果相同。幂等不代表每次响应字节完全一致，也不代表请求一定成功。

Demo Shop 用业务请求头让 `POST /api/orders` 具备重试保护：

```bash
curl --silent --show-error --include \
  --request POST \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: learn-order-0001' \
  --data '{"items":[{"product_id":1,"quantity":2}]}' \
  http://127.0.0.1:8000/api/orders
```

用完全相同的请求体和 Key 再执行一次。两次都应为 `201`，且返回相同订单 `id`。这是 Demo Shop 明确约定的契约，不代表所有系统都必须在重放时返回 `201`。

再用同一个 Key 发送不同请求体：

```bash
curl --silent --show-error --include \
  --request POST \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: learn-order-0001' \
  --data '{"items":[{"product_id":1,"quantity":1}]}' \
  http://127.0.0.1:8000/api/orders
```

预期为 `409 Conflict`，错误标识是：

```json
{"detail":"idempotency_key_reused_with_different_payload"}
```

## 4. 状态码要和业务语义一起判断

| 范围 | 含义 | Demo Shop 示例 |
|---|---|---|
| `2xx` | 请求被成功处理 | `200` 查询、`201` 创建 |
| `4xx` | 客户端输入或当前状态不允许 | `404` 商品不存在、`409` 库存/幂等冲突、`422` 校验失败 |
| `5xx` | 服务端未按契约处理 | 本实验没有故意制造 |

不要只断言“不是 500”。下面这些错误都应验证准确状态和稳定错误标识：

```bash
# 不存在的商品：404 + product_not_found
curl --silent --show-error --include \
  http://127.0.0.1:8000/api/products/999

# limit 越界：422
curl --silent --show-error --include \
  'http://127.0.0.1:8000/api/products?limit=0'

# 数量超过商品 2 的虚构库存 8：409 + insufficient_stock
curl --silent --show-error --include \
  --request POST \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: learn-order-0002' \
  --data '{"items":[{"product_id":2,"quantity":9}]}' \
  http://127.0.0.1:8000/api/orders
```

## 5. 请求头、媒体类型和超时

测试时至少关注：

- `Content-Type`：发送的请求体是什么格式；JSON 通常是 `application/json`。
- `Accept`：客户端希望接收什么格式。
- 认证头：真实项目常见 `Authorization`，但本实验无认证。不要提交真实凭证。
- 缓存头：查询接口是否允许缓存，本实验商品列表返回 `no-store`。
- 关联标识：真实系统可用公开测试环境生成的 trace/request ID 关联日志，不能上传内部日志。
- 超时：网络调用必须有上限；“一直等”会把慢故障变成测试挂死。

调试时推荐 `--show-error`；自动化脚本可加 `--fail-with-body`，让 HTTP 失败返回非零退出码且保留错误体：

```bash
curl --silent --show-error --fail-with-body \
  --max-time 3 \
  http://127.0.0.1:8000/api/products
```

## 6. JSON、Schema 与 OpenAPI

JSON 只是数据格式；JSON Schema 描述结构约束；OpenAPI 描述 HTTP API 的路径、操作、参数、请求/响应模型等。三者不是同一个概念。

保存并检查公开契约：

```bash
curl --silent --show-error \
  http://127.0.0.1:8000/openapi.json \
  --output /tmp/demo-shop-openapi.json

python -m json.tool /tmp/demo-shop-openapi.json
```

从契约和实现可提取下列维度：

| 接口 | 正常 | 边界 | 异常 | 状态/一致性 |
|---|---|---|---|---|
| 商品列表 | 默认查询、关键字命中 | `limit=1/100`、50 字符关键字 | `limit=0/101` | 响应禁止缓存 |
| 商品详情 | 已知 ID | 最小/大整数 | 未知 ID | 错误标识稳定 |
| 创建订单 | 单/多商品 | 1/20 行、数量 1/10 | 缺 Key、未知商品、库存不足 | 幂等重放、Key 冲突 |
| 订单详情 | 创建后查询 | 新生成 ID | 未知 ID | 与创建结果一致 |

OpenAPI 能帮助生成测试，但不能代替业务规则。比如“同 Key 不同请求体返回 409”是业务契约，需要显式测试。

## 7. 常见错误

1. **只测状态码**：`200` 的字段、类型或金额仍可能错误。
2. **把 POST 当成天然幂等**：必须有服务端契约和唯一键策略。
3. **复用固定测试数据却不清理**：会产生顺序依赖。本实验每次重启清空内存。
4. **不设置超时**：失败时测试可能无限等待。
5. **把 `422` 一律当 Bug**：先核对契约；本实验由参数/请求体校验产生 `422`。
6. **把 OpenAPI 当完整需求**：它通常不包含全部跨请求状态和业务风险。
7. **提交真实密钥或流量文件**：环境变量文件、Cookie、HAR、内部 URL 都不应进入公开仓库。

## 8. 练习与验收

### 练习

1. 用 `curl` 验证商品关键字搜索、`limit=1`、`limit=100` 和两个越界值。
2. 创建一个虚构订单，随后用返回的订单 ID 查询它。
3. 验证同 Key 同请求体重放与同 Key 不同请求体冲突。
4. 从 `/openapi.json` 找出订单行数和商品数量的上下界。
5. 写出一个 OpenAPI 没有完全表达、但仍值得测试的业务规则。

### 验收标准

- [ ] 能说清 `Content-Type` 与 `Accept` 的区别。
- [ ] 能用证据区分 `404`、`409`、`422`。
- [ ] 同 Key 同体返回同一订单；同 Key 异体得到 `409`。
- [ ] 所有命令只访问 `127.0.0.1`，无真实公司数据或凭证。
- [ ] 测试记录同时包含请求条件、预期、实际状态码和关键响应字段。
