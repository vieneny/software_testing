# 接口测试实战：从风险到可重复证据

## 学习目标

完成本章后，你应当能够：

1. 从接口契约与业务风险建立测试矩阵，而不是堆请求数量。
2. 使用 `curl` 和 Postman 形成可复现的手工探索链路。
3. 在 2026 年工具现状下正确选择 Postman CLI 与 Newman。
4. 验证契约、边界、错误语义、幂等和跨接口一致性。
5. 输出不含敏感信息、其他人可以复现的缺陷证据。

## 1. 准备环境

先按 [Demo Shop README](../../labs/demo-shop/README.md) 启动服务，然后设置公开本地地址：

```bash
export DEMO_BASE_URL='http://127.0.0.1:8000'
curl --silent --show-error --fail-with-body "$DEMO_BASE_URL/health"
```

如果你使用 Windows PowerShell，可直接在命令和工具环境中填写 `http://127.0.0.1:8000`，不要把公司测试地址写进仓库。

## 2. 先建风险模型，再写步骤

Demo Shop 最重要的风险不是“接口能否返回”，而是：

- 商品查询：筛选、限制条数、字段契约和错误语义是否稳定。
- 订单计算：单价快照、数量和总金额是否正确。
- 库存约束：请求数量超过库存是否拒绝。
- 重试安全：网络重试是否重复创建订单。
- 跨接口一致性：创建结果能否被订单查询原样读取。

将风险变成决策表：

| Key | 请求体 | 前置状态 | 预期 |
|---|---|---|---|
| 合法新 Key | 合法 | 商品存在且库存足 | `201`，创建订单 |
| 同 Key | 与首次相同 | 首次已成功 | `201`，订单 ID 相同 |
| 同 Key | 与首次不同 | 首次已成功 | `409`，幂等冲突 |
| 缺 Key/过短 Key | 合法 | 无 | `422` |
| 合法新 Key | 数量超过库存 | 商品存在 | `409`，库存不足 |
| 合法新 Key | 未知商品 | 商品不存在 | `404` |

> 表中“缺 Key”是输入缺失，不是服务异常。状态码和错误体都要断言。

## 3. 一条完整的探索链路

### 3.1 查询商品

```bash
curl --silent --show-error --fail-with-body \
  "$DEMO_BASE_URL/api/products?keyword=马克杯&limit=1"
```

预期只有“星光马克杯”，字段包括 `id=2`、`price_cents=3900` 和虚构库存。

### 3.2 创建订单

```bash
curl --silent --show-error --include \
  --request POST \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: practice-order-0001' \
  --data '{"items":[{"product_id":2,"quantity":1}]}' \
  "$DEMO_BASE_URL/api/orders"
```

记录返回的订单 ID。预期 `total_cents=3900`、`status=created`。

### 3.3 查询并比对

假设上一步订单 ID 为 `1`：

```bash
curl --silent --show-error --fail-with-body \
  "$DEMO_BASE_URL/api/orders/1"
```

不要只看“查到了”。应比对订单 ID、行项目、数量、单价快照、总金额和状态。

### 3.4 构造状态冲突

再次使用 `practice-order-0001`，但把数量改为 `2`：

```bash
curl --silent --show-error --include \
  --request POST \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: practice-order-0001' \
  --data '{"items":[{"product_id":2,"quantity":2}]}' \
  "$DEMO_BASE_URL/api/orders"
```

预期 `409` 和稳定错误标识 `idempotency_key_reused_with_different_payload`。

## 4. 用 Postman 组织可复用探索

### 4.1 Collection 与环境

建立一个只含公开数据的 Collection：

```text
Demo Shop
├── Health
├── Products
│   ├── List products
│   └── Get unknown product
└── Orders
    ├── Create order
    ├── Replay same request
    └── Reuse key with different body
```

环境变量：

| 名称 | 初始值 | 是否敏感 |
|---|---|---|
| `base_url` | `http://127.0.0.1:8000` | 否 |
| `idempotency_key` | 留空，由脚本生成 | 否 |
| `order_id` | 留空，由响应保存 | 否 |

在创建订单请求的 Pre-request Script 中生成 Key：

```javascript
pm.environment.set("idempotency_key", pm.variables.replaceIn("{{$guid}}"));
```

请求头：

```text
Content-Type: application/json
Idempotency-Key: {{idempotency_key}}
```

测试脚本：

```javascript
pm.test("创建成功", function () {
  pm.response.to.have.status(201);
});

pm.test("订单契约正确", function () {
  const body = pm.response.json();
  pm.expect(body.id).to.be.a("number");
  pm.expect(body.status).to.eql("created");
  pm.expect(body.total_cents).to.eql(3900);
  pm.expect(body.items).to.have.length(1);
  pm.environment.set("order_id", String(body.id));
});
```

要测试重放，第二个请求必须复用第一次生成的 Key 和完全相同的请求体；不要在第二个请求前再次生成 Key。

### 4.2 2026 年 CLI 选择

对新建的 Postman 工作流，优先使用 **Postman CLI**。它支持当前 Postman 平台、Collection v2/v2.1/v3 和云端能力。示例：

```bash
postman collection run ./postman/demo-shop.collection.json \
  -e ./postman/local.environment.json
```

具体认证与 CI 参数应以 Postman CLI 当前官方文档和工具生成的命令为准。不要把 API Key 写进命令、Collection 或仓库；CI 中使用密钥变量。

**Newman 是兼容路径，不是新项目默认主线。** 它仍适合只使用 Collection v2.1 的开源/离线兼容场景：

```bash
newman run ./postman/demo-shop.collection.v2.1.json \
  -e ./postman/local.environment.json \
  --reporters cli,junit \
  --reporter-junit-export ./reports/newman.xml
```

Postman 已明确建议需要 Collection v3 或 Postman v12 新能力的团队迁移到 Postman CLI。迁移前先检查脚本、报告器和 CI 集成，不要假设两个 CLI 完全等价。

## 5. 契约、属性与状态测试

### 5.1 响应结构

结构断言至少包括：

- 必填字段存在。
- 类型正确，且不接受额外字段时应明确检查。
- 金额使用整数分，不用浮点数猜测。
- 数组长度、枚举值和数值上下界正确。

仓库的 `tests/api/测试_商品接口.py` 使用 `jsonschema` 验证商品对象，并设置 `additionalProperties: false`。这能发现“字段突然增加/拼错”，但契约是否允许扩展要由团队版本策略决定。

### 5.2 边界值

订单行数量允许 `1..20`，每行数量允许 `1..10`。每个范围至少覆盖：

```text
min-1, min, min+1, nominal, max-1, max, max+1
```

还要区分两类上限：

- Schema 上限：数量 `11` 应由输入校验拒绝，当前实现返回 `422`。
- 当前库存：商品 2 库存为 `8`，数量 `9` 在 Schema 内，但业务返回 `409`。

两者发生在不同层，不能写成同一个模糊用例。

### 5.3 跨请求状态

一条高价值链路是：

```text
查询商品 → 创建订单 → 重放创建 → 查询订单 → 冲突重用 Key
```

每一步都从上一响应提取动态 ID，但测试之间应保持独立。需要并行执行时，每条用例生成自己的 Key。

### 5.4 可选：规范驱动探索

Schemathesis 可以从 OpenAPI 生成属性测试，作为手写业务用例的补充：

```bash
python -m pip install schemathesis
schemathesis run \
  http://127.0.0.1:8000/openapi.json \
  --url http://127.0.0.1:8000
```

运行前确认只命中本地授权目标。生成式工具擅长发现输入空间问题，但不会自动理解金额、幂等和库存等全部业务规则。

## 6. 缺陷证据模板

```text
标题：同一 Idempotency-Key 与不同请求体未返回冲突
环境：本地 Demo Shop，提交版本 <commit>
前置：服务刚启动
步骤：
1. POST /api/orders，Key=fictional-key-0001，quantity=1
2. 使用相同 Key，quantity=2 再次 POST
预期：第二次 409，detail 为约定错误标识
实际：<只记录虚构实验结果>
证据：脱敏后的请求、状态码、响应关键字段、时间
影响：客户端重试可能产生不一致状态
```

不要附带内部域名、真实用户信息、Authorization、Cookie 或整份未脱敏日志。

## 7. 常见错误

1. Collection 中写死真实 Token 或测试环境地址。
2. 每个请求都生成新 Key，导致“幂等重放”实际没有重放。
3. 只检查 JSON 字段存在，不检查值、类型、边界和跨接口一致性。
4. 让测试依赖固定订单 ID 或执行顺序。
5. 把 Newman 当作 Collection v3 的默认执行器。
6. 看到 OpenAPI 扫描全绿就认为业务规则已覆盖。
7. 对未授权公网系统做模糊测试或并发测试。

## 8. 练习与验收

### 练习

1. 建立 Demo Shop Collection，并覆盖上面的订单决策表。
2. 分别验证 Schema 上限和库存上限，解释为何状态码不同。
3. 导出不含密钥的 Collection 和本地环境模板，用 Postman CLI 执行。
4. 若需要 Newman 兼容，另导出 v2.1 并比较两种 CLI 的结果。
5. 写一份只含虚构数据的缺陷报告。

### 验收标准

- [ ] Collection 可在新环境中仅修改 `base_url` 后执行。
- [ ] 至少覆盖 2xx、404、409、422 和幂等重放。
- [ ] 创建与查询结果的金额、行项目、状态一致。
- [ ] CLI 退出码能反映断言失败，并生成机器可读报告。
- [ ] 导出文件不含 Token、Cookie、公司 URL、真实客户数据。
