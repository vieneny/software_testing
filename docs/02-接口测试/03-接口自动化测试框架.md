# pytest 接口自动化

> 主线组合：Python 3.11+、pytest、Requests、JSON Schema。所有示例只访问本地虚构 Demo Shop。
>
> 想直接在公开 API 和本地 Demo 上跟着代码练习，请进入
> [接口自动化项目全流程](./04-接口自动化项目全流程.md)。

## 学习目标

完成本章后，你应当能够：

1. 设计职责清晰、可独立运行的 pytest 接口测试。
2. 使用 fixture 管理会话和地址，给每个请求设置超时。
3. 用参数化覆盖边界，用状态链验证创建、查询和幂等。
4. 输出 JUnit 报告，并让失败通过退出码阻断 CI。
5. 判断何时继续使用 Requests，何时引入 HTTPX。

## 1. 运行仓库现有测试

终端 A 启动服务：

```bash
cd labs/demo-shop
source .venv/bin/activate
uvicorn app.商城服务:app --host 127.0.0.1 --port 8000
```

若尚未安装实验依赖，先按 [Demo Shop README](../../labs/demo-shop/README.md) 创建虚拟环境并安装 `.[test]`。

终端 B：

```bash
cd labs/demo-shop
source .venv/bin/activate
export DEMO_BASE_URL='http://127.0.0.1:8000'
pytest tests/api -q
```

只运行订单、单个用例或显示测试名称：

```bash
pytest tests/api/测试_订单接口.py -q
pytest tests/api/测试_订单接口.py::test_same_idempotency_key_returns_same_order -q
pytest tests/api -vv
```

`DEMO_BASE_URL` 的默认值也是本地地址。仓库和 CI 配置中不要写入公司环境 URL 或真实凭证。

## 2. 测试分层与目录职责

现有结构：

```text
tests/api/
├── conftest.py       # 地址、Session、marker
├── 测试_商品接口.py  # 查询、契约、边界、错误
└── 测试_订单接口.py    # 创建、查询、幂等、库存、校验
```

建议职责：

- fixture：资源生命周期和通用配置。
- client/helper：协议细节、公共请求头、超时和少量解析。
- test：业务场景、可读断言和失败原因。
- schema：稳定的结构契约；契约较大时放独立文件。

不要建立一个“万能基类”隐藏所有请求和断言。测试失败时应能快速看出输入、动作和预期。

## 3. fixture：集中配置，不共享业务状态

仓库的 `conftest.py` 等价于：

```python
from __future__ import annotations

import os
import pytest
import requests


@pytest.fixture(scope="session")
def base_url() -> str:
    return os.getenv("DEMO_BASE_URL", "http://127.0.0.1:8000").rstrip("/")


@pytest.fixture
def api() -> requests.Session:
    session = requests.Session()
    session.headers.update({
        "Accept": "application/json",
        "User-Agent": "demo-shop-tests/1.0",
    })
    yield session
    session.close()
```

设计要点：

- 地址来自环境变量，默认只指向 `127.0.0.1`。
- 每个测试得到独立 Session，减少共享 Cookie/头造成的串扰。
- fixture 负责关闭资源。
- fixture 不创建“供全套测试共享”的固定订单，避免顺序和并行依赖。

## 4. 一个请求至少断言什么

```python
def test_list_products_contract(api, base_url):
    response = api.get(f"{base_url}/api/products", timeout=3)

    assert response.status_code == 200
    assert response.headers["Content-Type"].startswith("application/json")
    assert response.headers["Cache-Control"] == "no-store"

    products = response.json()
    assert products
    assert all(product["price_cents"] > 0 for product in products)
    assert all(product["stock"] >= 0 for product in products)
```

四层断言：

1. 传输层：在超时内完成。
2. HTTP 层：状态码、媒体类型、关键响应头。
3. 契约层：字段、类型、必填、额外字段策略。
4. 业务层：金额、库存、状态、跨接口关系。

只写 `assert response.ok` 会把多种 2xx/3xx 混在一起，不适合精确契约测试。

## 5. 参数化覆盖边界

```python
import pytest


@pytest.mark.parametrize(
    ("limit", "expected_status"),
    [
        (0, 422),
        (1, 200),
        (100, 200),
        (101, 422),
    ],
)
def test_product_limit_boundary(api, base_url, limit, expected_status):
    response = api.get(
        f"{base_url}/api/products",
        params={"limit": limit},
        timeout=3,
    )
    assert response.status_code == expected_status
```

参数化适合“同一规则、不同输入”。如果每一行代表不同业务原因，应拆成命名清楚的测试，避免失败只显示一堆数字。

## 6. 用动态数据验证状态链

幂等测试必须主动控制 Key：

```python
from uuid import uuid4


def test_idempotent_replay(api, base_url):
    key = str(uuid4())
    payload = {"items": [{"product_id": 2, "quantity": 1}]}
    headers = {"Idempotency-Key": key}

    first = api.post(
        f"{base_url}/api/orders",
        json=payload,
        headers=headers,
        timeout=3,
    )
    second = api.post(
        f"{base_url}/api/orders",
        json=payload,
        headers=headers,
        timeout=3,
    )

    assert first.status_code == second.status_code == 201
    assert first.json()["id"] == second.json()["id"]
    assert first.json()["total_cents"] == 3900
```

同一个测试内完成“创建—重放—比较”，比拆成三个依赖顺序的测试可靠。每个测试使用新的 UUID，避免与其他运行互相污染。

创建后查询：

```python
from uuid import uuid4


def test_create_then_get(api, base_url):
    create = api.post(
        f"{base_url}/api/orders",
        json={"items": [{"product_id": 1, "quantity": 2}]},
        headers={"Idempotency-Key": str(uuid4())},
        timeout=3,
    )
    assert create.status_code == 201

    expected = create.json()
    query = api.get(
        f"{base_url}/api/orders/{expected['id']}",
        timeout=3,
    )
    assert query.status_code == 200
    assert query.json() == expected
```

## 7. 契约校验

商品 Schema 的核心写法：

```python
from jsonschema import validate

PRODUCT_SCHEMA = {
    "type": "object",
    "required": ["id", "name", "price_cents", "stock"],
    "additionalProperties": False,
    "properties": {
        "id": {"type": "integer", "minimum": 1},
        "name": {"type": "string", "minLength": 1},
        "price_cents": {"type": "integer", "minimum": 0},
        "stock": {"type": "integer", "minimum": 0},
    },
}


def test_each_product_matches_schema(api, base_url):
    response = api.get(f"{base_url}/api/products", timeout=3)
    assert response.status_code == 200
    for product in response.json():
        validate(instance=product, schema=PRODUCT_SCHEMA)
```

`additionalProperties: False` 是严格兼容策略。若 API 允许向后兼容地增加字段，应调整策略，而不是机械复制。

## 8. Marker、报告与退出码

项目在 `pyproject.toml` 注册了 `api` marker。可以运行：

```bash
pytest -m api -q
```

输出机器可读报告：

```bash
mkdir -p reports
pytest tests/api -q --junitxml=reports/api-junit.xml
```

pytest 的退出码是质量门禁关键：

- `0`：全部通过。
- `1`：测试失败。
- 其他非零：无测试、用法错误、内部错误或被中断等。

CI 不应使用 `|| true` 吞掉失败。日志和报告中也不应输出认证头、Cookie 或真实个人信息。

## 9. Requests 还是 HTTPX

| 场景 | 建议 |
|---|---|
| 同步 HTTP、团队已有 Requests 经验 | Requests，简单稳定 |
| 需要原生 async、HTTP/2 或统一同步/异步 API | 评估 HTTPX |
| FastAPI 应用进程内测试 | 可评估 FastAPI/Starlette TestClient（基于 HTTPX） |
| 黑盒环境端到端接口测试 | 像本实验一样访问真实监听端口 |

不要为了“新”同时维护两套客户端封装。迁移 HTTPX 时先验证超时、重定向、连接池、代理、异常类型和异步 fixture 的差异。

## 10. 稳定性与可维护性

- 每个请求显式设置超时。
- 测试生成唯一数据；有持久化系统时设计 API/fixture 清理。
- 断言稳定业务字段，不断言随机 ID 的具体值。
- 时间、随机数和外部依赖要可控。
- 失败信息说明业务意图；避免在重试插件中掩盖真实不稳定。
- 先修复可重复的 flaky 根因，再考虑有限重试。
- 测试数据只用公开虚构值。

Demo Shop 是内存实验：重启后订单清空，没有事务、真实库存扣减、认证、分布式锁或多实例一致性。测试通过不能外推为生产级能力。

## 11. 常见错误

1. 用模块级变量保存订单 ID，让测试依赖顺序。
2. Session 作用域过大并在测试中修改公共头。
3. 没有超时，网络故障时整套测试挂住。
4. 只断言状态码，不验证错误标识和业务值。
5. 参数化几十种无差异输入，覆盖数字很多但风险很少。
6. 在失败日志打印 Token、完整 Cookie 或敏感响应。
7. 把单次失败直接标成 flaky 并无限重跑。

## 12. 练习与验收

### 练习

1. 参数化验证 `limit=0/1/100/101`。
2. 增加未知商品订单测试，断言状态码和 `detail`。
3. 增加“同 Key 不同请求体”的状态测试。
4. 为订单响应建立 JSON Schema，并验证创建与查询。
5. 生成 JUnit XML，再故意改错一个断言，确认命令返回非零。

### 验收标准

- [ ] `pytest tests/api -q` 可重复通过。
- [ ] 每个网络请求都有有限超时。
- [ ] 用例之间没有固定 ID、共享订单或执行顺序依赖。
- [ ] 同时覆盖正常、边界、错误、契约和幂等状态。
- [ ] 报告可被 CI 读取，失败不会被吞掉。
- [ ] 代码、报告和日志不含任何公司内容或真实凭证。
