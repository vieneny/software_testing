## 学习目标

读完并完成练习后，你应该能够：

- 区分“某些公开岗位反复出现的要求”和“有方法说明的统计调查”；
- 从岗位任务而不是工具热度出发，规划功能、接口、自动化、性能、质量工程和 AI 测试能力；
- 解释本仓库为什么选择 Python、pytest、Playwright、k6、Docker 等主线，同时保留 Selenium、JMeter、Jenkins 等市场适配能力；
- 按初级、中级、高级三个层次建立可验收的学习目标；

## 一、证据如何分级

技术选型最容易犯的错误，是把三条招聘信息、一个排行榜或一篇厂商文章直接当成“行业结论”。本仓库采用以下证据分级。

| 级别 | 资料类型 | 能回答什么 | 不能回答什么 |
|---|---|---|---|
| A | 标准组织、基金会、官方研究计划、有方法说明的大样本报告 | 行业方向、实践成熟度、跨组织共性 | 某个中国城市具体招聘数量 |
| B | 招聘平台当前可访问的具体岗位 | 企业正在描述哪些职责、工具和能力组合 | 全市场占比、真实录用标准、薪资中位数 |
| C | 官方工具文档、官方仓库、平台遥测 | 工具能力、维护状态、生态变化 | 企业是否一定采用、学习后是否一定就业 |
| D | 个人文章、课程宣传、搜索热度 | 提供待验证假设 | 不能单独支撑路线或市场结论 |

本文把 A 类资料称为“统计与趋势证据”，把 B 类资料称为“岗位样本观察”。两者会交叉验证，但不互相替代。

### AI 测试定向样本结构

本次从多个同义关键词页人工判断相关性并去重，保留 26 个岗位：

- 本科及以上为 **24/26**；
- 明确要求 3 年及以上经验为 **20/26**；
- 北京、上海、深圳、杭州为 **21/26**。

这些比例只描述主动覆盖中高级测试开发和评测岗位的定向样本，不能外推全国。样本内页面展示也存在月薪、日薪及不同“几薪”，所以不计算平均或中位薪资。

样本反映出三种明显不同的职责层：

1. **AI 产品测试**：传统功能/API/性能/安全能力叠加模型效果；
2. **AI 测试开发与质量平台**：自动化框架、评测流水线、数据、CI/CD 和 AI 提效工具；
3. **模型评测与算法测试**：评测体系、Benchmark、数据构造、统计、多模态和算法理解。

### 从当前样本中可以稳妥得出的结论

1. **功能测试仍是基本盘。** 需求、风险、用例、异常、缺陷和报告没有被 AI 替代。
2. **接口、SQL、Linux和一门编程语言是技术测试底座。** 当前样本同时出现 Python 和 Java，教程选择 Python 主线是为了学习闭环，不代表市场只需要 Python。
3. **自动化要可维护、可诊断并接入交付。** 框架、数据、报告、失败定位和 CI/CD 比“脚本能运行一次”更重要。
4. **性能岗位强调模型和诊断。** JMeter 等工具之外，还要能解释业务负载、监控证据和容量边界。
5. **AI 测试已经形成可识别的岗位族，但不是一种工作。** AI 应用测试、模型评测、Agent 测试和评测平台需要不同能力与作品。
6. **AI 提效也进入职责。** 生成用例、自动执行和缺陷定位需要用采纳率、返工、有效缺陷和反馈时间证明价值。
7. **学历和经验门槛在本次 AI 定向样本中偏高。** 小白应先完成普通测试与自动化作品，再用合成数据和可运行评测证明专项能力。
8. **领域知识会放大通用能力。** 金融、汽车、工业、芯片、多模态等岗位仍要求把测试方法迁移到具体系统。

这些结论是“本次 BOSS 样本观察”，不是全国岗位比例。招聘数量、真实薪资分布和地区差异需要平台授权的完整数据集、固定时间窗及公开去重方法。

### 平台遥测，不是问卷

[GitHub Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/) 基于 GitHub 平台活动，显示 TypeScript 在 2025 年成为月活贡献者最多的语言，Python 仍主导 AI 项目，包含 Dockerfile 的项目明显增长。这支持课程增加 TypeScript/Playwright 阅读能力、保留 Python 主线和容器化实践，但它不能证明“某语言在中国测试岗位的需求占比”。

### 全球趋势对个人学习的含义

```text
AI 提高代码产出速度
        ↓
变更数量、依赖和验证压力增加
        ↓
更需要快速自动化反馈、风险测试、质量门禁和可观测性
        ↓
测试角色从“执行案例”扩展为“设计质量控制系统”
```

因此，AI 不是删除测试基础的理由。相反，需求分析、正确断言、数据治理、可重复实验和人工复核变得更重要。

## 四、岗位能力分层

不同企业对年限和职级命名不一致，下面按“可独立承担的责任”分层，不按年限硬切。

### 初级：能可靠完成明确任务

- 从明确需求设计正常、边界、异常和权限测试；
- 写出可复现的缺陷报告和有结论的测试总结；
- 使用 curl/Postman 调用 API，理解状态码、JSON 和常见鉴权；
- 编写基础 SQL，使用 Linux 命令查看进程、端口和日志；
- 使用 Git，能读写简单 Python 和 pytest 用例；
- 知道何时需要请产品、开发或领域专家澄清，而不是自行补需求。

### 中级：能独立负责系统或特性

- 主导测试分析、风险排序、方案和评审；
- 设计接口自动化分层，管理数据、配置、报告和失败证据；
- 选择少量高价值 UI 自动化旅程并治理不稳定性；
- 从业务量设计性能场景，结合日志和监控定位瓶颈；
- 将测试接入 CI/CD，使用 Docker 获得可重复环境；
- 熟悉缓存、消息队列、微服务和一个业务领域。

### 高级 / 测试开发：能建立质量系统

- 设计测试框架、测试平台、质量门禁和环境治理方案；
- 在架构与需求阶段推动可测性、可观测性和故障隔离；
- 用风险、生产缺陷、恢复时间和业务影响衡量质量，而不只看用例数量；
- 处理分布式、一致性、容量、稳定性和安全等跨层问题；
- 评估自动化投入产出，治理 flaky test、测试债务和工具碎片；
- 指导团队、推动跨团队决策并清楚表达残余风险。

### AI 测试专项：两条能力线

**AI 辅助测试**适用于所有层级：

- 用公开或合成需求生成第一版风险和用例；
- 辅助生成脚本骨架、测试数据和日志诊断假设；
- 人工核对协议、业务规则、断言、隐私和运行结果；
- 记录模型、提示词、参数和人工修改，不把生成结果直接当事实。

**测试 AI 系统**通常建立在中级测试能力之上：

- 理解 LLM、Embedding、RAG、Agent/tool calling 的系统边界；
- 建立版本化评测集、基线、评分规则和回归报告；
- 分开评价检索、生成、端到端任务成功率、安全、延迟和成本；
- 测试幻觉、偏见、鲁棒性、提示注入、敏感信息泄露和过度权限；
- 结合确定性评分、人工评价与模型裁判，并校准误差。

可参考 [ISO/IEC TS 42119-2:2025](https://www.iso.org/standard/84127.html)、[NIST AI Risk Management Framework](https://airc.nist.gov/) 和 [OWASP 2025 Top 10 for LLM/GenAI Applications](https://genai.owasp.org/llm-top-10/) 建立风险与评测框架。

## 五、本仓库的技术选型方法

每个候选工具按六个维度评估，单项 1～5 分。分数只帮助讨论，最终必须做小实验。

| 维度 | 问题 |
|---|---|
| 岗位迁移性 | 能力能否迁移到不同公司和同类工具？ |
| 反馈价值 | 是否能更快发现高风险问题并给出诊断证据？ |
| 可维护性 | 测试是否可读、隔离、可重复、可并行和易于调试？ |
| 生态与维护 | 是否有活跃官方维护、清晰文档和稳定社区？ |
| 本地可复现 | 学习者能否在个人电脑和免费 CI 中完成闭环？ |
| 安全与边界 | 是否可以只用公开、虚构和合成数据练习？ |

一个候选工具即使热度很高，只要无法形成可执行实验、维护成本不清或主要价值可被通用原理替代，就先放入选修。

## 六、主线技术选择与取舍

| 领域 | 主线 | 必须理解的市场适配 | 选择理由 |
|---|---|---|---|
| 功能测试 | 风险驱动、探索式测试、等价类/边界值/判定表/状态迁移 | Jira/禅道等工具只作为记录载体 | 方法可迁移，工具不能替代分析 |
| API 探索 | HTTP、OpenAPI、curl、Postman | Apifox、Bruno 等同类工具可快速迁移 | 先理解协议、契约、权限和数据，再谈自动化 |
| API 自动化 | Python + pytest + requests + JSON Schema | Java + TestNG/RestAssured 作为企业栈选修 | BOSS 当前样本同时出现 Python 和 Java；Python 主线便于连接 API、性能和 AI 数据处理，不代表岗位只需要 Python |
| Web UI | Playwright（Python） | Selenium 必须能读、能维护、能判断迁移；移动端学习 Appium | Playwright 适合新项目的自动等待、隔离和 trace；BOSS 当前自动化样本仍出现 Selenium/Appium |
| 性能测试 | k6 用于代码化场景、阈值和 CI；Locust 用于 Python 扩展 | JMeter 是当前 BOSS 性能样本中的常见适配工具；LoadRunner 作为传统企业选修 | 主线强调负载模型和可执行门禁，同时保持岗位适配 |
| CI/CD | GitHub Actions 完成本仓库闭环 | 理解 Jenkins Pipeline 和 GitLab CI 的对应概念 | 公开仓库可免费复现，阶段、制品、缓存、门禁概念可迁移 |
| 环境 | Docker 基础 | Kubernetes 在中高级阶段学习部署、日志、资源和故障定位 | 先解决环境可复现，再学习编排规模问题 |
| 可观测性 | 结构化日志、RED/USE 指标、Trace Context | Prometheus/Grafana、OpenTelemetry | 性能和稳定性结论必须有服务端证据 |
| AI 测试 | 数据集 + 确定性检查 + 人工复核 + 安全测试 | promptfoo、DeepEval、Ragas、OpenCompass、Inspect AI 等按实验选修 | 工具变化快，数据、评分、风险和回归方法更耐久 |

### 为什么 Python 是主线，但不能只会 Python

Python 适合把 API、pytest、Locust、数据处理和 AI 评测串成一套作品。学习者仍需：

- 能读 Shell 和 CI 配置；
- 能理解浏览器侧 JavaScript/TypeScript 错误；
- 面向 Java 企业系统时能阅读基本堆栈、接口和 TestNG/RestAssured 用例；
- 理解语言之外的 HTTP、SQL、进程、网络和分布式系统机制。

### 为什么 Playwright 主线仍保留 Selenium

Playwright 适合从零建立稳定的现代 Web 自动化；2026-07-27 的 BOSS 自动化样本仍明确出现 Selenium。正确策略不是二选一：

1. 用 Playwright 学会面向用户的定位、自动等待、上下文隔离和 trace；
2. 用一个小练习理解 Selenium 的 WebDriver、显式等待和 Page Object；
3. 面试或接手项目时，根据现有资产、浏览器范围、团队语言和迁移成本决策。

### 为什么性能主线不是只讲 JMeter

JMeter 的市场适配价值很高，但“会拖组件”不等于会做性能工程。本仓库先统一学习：

- 业务量与到达率；
- 场景比例、思考时间和测试数据；
- p95/p99、错误率、吞吐和资源饱和度；
- 预热、噪声、客户端瓶颈和结果可重复性；
- 基于证据的瓶颈假设。

然后用 k6、JMeter、Locust 分别实现同一个小场景，比较脚本化、插件生态、分布式执行和 CI 集成。

这是课程设计建议，不是市场统计：

| 模块 | 建议占比 | 核心交付物 |
|---|---:|---|
| 测试基础与业务质量 | 20% | 风险清单、测试模型、探索记录、测试总结 |
| API、SQL、Linux 与接口自动化 | 25% | 可在 CI 运行的接口测试工程 |
| Web/App UI 自动化 | 15% | 少量稳定关键旅程与失败诊断证据 |
| 性能、稳定性与可观测性 | 15% | 负载模型、阈值、监控证据和容量结论 |
| CI/CD、Docker 与云原生 | 10% | 分层流水线、环境说明和质量门禁 |
| AI 辅助测试与 AI 系统评测 | 15% | 评测集、评分器、安全用例和回归报告 |

如果时间不足，优先完成“功能分析 → API → pytest → CI → 诊断”闭环，再扩展 UI、性能和 AI。五个半成品工具项目，不如一个能解释风险、自动执行、保存证据并给出结论的完整项目。

## 常见误区

### 误区 1：搜索到十条岗位，就计算技能占比

搜索引擎有排序、地区、付费推广、重复职位和收录偏差。正确表达是“在本次公开样本中反复出现”，而不是“市场上有 80% 的岗位要求”。

### 误区 2：报告百分比可以直接套到中国个人求职

全球高管调查、测试工具用户调查和 CNCF 社区调查的样本结构不同。百分比只在原报告定义和样本范围内成立。

### 误区 3：AI 会让测试基础过时

AI 可以更快生成代码和用例，也会更快生成错误、重复和不可信断言。没有风险判断、测试预言和人工复核，产出越快，噪声可能越大。

### 误区 4：工具越多，竞争力越强

岗位更关注能否解决问题：为什么选这层测试、如何隔离数据、如何定位失败、如何阻止有风险的发布。工具列表不能替代这些证据。

### 误区 5：高级路线就是写更复杂的框架

高级能力还包括质量策略、可测性、指标、流程、风险沟通和跨团队推动。框架只有在降低反馈时间或维护成本时才有价值。

## 练习

### 练习 1：建立岗位证据表

按[最新招聘调研](04-软件测试与人工智能测试招聘需求调研.md)的方法，从 BOSS 直聘为自己的目标城市和方向选择 20 个当前公开岗位。AI 测试至少同时检索“AI 测试、AI 测试开发、大模型评测、Agent 测试”四组同义词，记录：

```markdown
| URL | 采集时间 | 关键词 | 城市 | 岗位层级 | 业务职责 | 必备技能 | 加分技能 | 可展示证据 |
|---|---|---|---|---|---|---|---|---|
```

要求：

- 先去重并记录排除原因；
- 比例只描述自己的定向样本，不外推市场；
- 区分“职责”“必备”和“加分”；
- 月薪、日薪和不同“几薪”分开保留；
- 每个技能写出一个可执行作品证据，例如“pytest + API”对应“CI 中可重复执行的接口回归”，而不是只写“学过”。

### 练习 2：做一次技术选型

为“给公开课程预约系统增加 Web UI 回归”比较 Playwright 和 Selenium。按六维框架评分，完成一个相同的最小流程，再写 300 字决策记录：

- 目标和约束；
- 实验环境；
- 两个方案的证据；
- 选择与不选择的理由；
- 何种条件变化会推翻当前选择。

### 练习 3：设计个人能力缺口

把自己按初级、中级、高级能力逐项标记：

- `0`：不了解；
- `1`：能解释；
- `2`：能独立完成；
- `3`：能设计、取舍并排查复杂问题。

只选择未来四周能形成证据的三项，不以“看完课程”为验收。

## 验收标准

完成本文学习需要同时满足：

- [ ] 能说明岗位样本与统计报告的区别，并指出至少三种采样偏差；
- [ ] 能按关键词、城市和层级从至少二十个当前 BOSS 岗位提炼技能簇，完成去重和相关性过滤；
- [ ] 所有比例都带本次样本分母，没有编造全国出现率或薪资结论；
- [ ] 能引用至少两份带方法说明的报告，并写出各自适用边界；
- [ ] 能解释 Python、Playwright、Selenium、k6、JMeter、Docker 和 Kubernetes 在本路线中的不同定位；
- [ ] 能把学习目标映射为可运行代码、测试报告、流水线或诊断证据；
- [ ] 技术选型记录包含“何时改选”的条件，而不是只陈述个人喜好；
- [ ] 所有案例和数据均来自公开资料、`demo-shop` 或从零生成的合成场景；
- [ ] 没有把任何公司资料、内部链接、真实日志、账号、密钥或业务数据放入练习。

## 后续更新规则

普通测试每季度、AI 测试每月执行轻量核对：

1. 使用固定关键词矩阵和目标城市重新打开 BOSS 公开页面；
2. 记录时间、关键词、原始条数、去重后条数、相关条数和排除原因；
3. AI 岗分开统计产品测试、模型评测、Agent 测试和评测平台；
4. 查看 DORA、CNCF、质量工程调查和 GitHub/Stack Overflow 的新报告，但不让全球报告替代中国岗位样本；
5. 检查主线工具官方维护状态、Python 版本范围和 CI Action 大版本；
6. 新工具先进入选修并完成对照实验；
7. 只有当岗位任务、公开趋势和本地实验三者都支持时，才调整主线。
