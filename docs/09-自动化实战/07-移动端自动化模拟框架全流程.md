# 移动端自动化模拟框架全流程：无设备也能练习架构、执行链与故障恢复

> 适用对象：当前没有可用 Android/iOS 设备、Appium 环境尚未搭好，或者希望先把移动端自动化框架基本功练扎实的同学。
>
> 配套代码：[`labs/automation-practice`](../../labs/automation-practice/README.md)
>
>
> 架构来源说明：本章经授权参考了一份移动端测试资料中的通用分层思想，但所有业务模型、字段、代码和示例均重新设计；只保留可公开复用的工程原则，不转载任何内部业务内容。

前置阅读：

- [Android 真机自动化全流程](./03-安卓真机自动化全流程.md)
- [iOS 自动化全流程](./04-苹果移动端自动化全流程.md)

## 1. 学完能得到什么

你不需要手机、模拟器、Android SDK、Xcode、Appium Server 或公网，就可以实际运行以下链路：

```text
pytest 收集测试
  → 选择合成 DeviceProvider
  → DriverFactory 创建 Fake Session
  → AppManager 启动合成 App
  → Screen / Task 读取 LocatorRepository
  → MobileActions 执行查找、输入、点击和滑动
  → Test 断言页面与业务状态
  → EvidenceCollector 保存首次失败证据
  → Cleanup 逆序释放资源
```

完成本章后，你应当能：

1. 解释 Mock 移动端测试能证明什么、不能证明什么。
2. 画出 `DeviceProvider → DriverFactory → Session → Screen/Task → Test → Evidence → Cleanup` 完整执行链。
3. 区分 Core、Adapter、Project Pack 三层，以及它们的依赖方向。
4. 理解为什么统一的是 Run、Driver、Locator Contract，而不是强行统一 Android/iOS 实现。
5. 用同一业务流程分别运行 Android 与 iOS 合成平台契约。
6. 稳定复现定位失败、操作超时、设备断连和 App 崩溃。
7. 保留第一次失败，不让重试、证据采集或清理覆盖根因。
8. 将 Fake Adapter 一项项替换成 UiAutomator2 或 XCUITest Adapter。

本章不是“用假对象假装已经做过真机测试”。它是一座训练桥梁：

```text
离线框架练习
  → Android Emulator / iOS Simulator
  → 专用真机 smoke
  → 受控设备矩阵
```

## 2. 为什么先做 Mock

真实 App 自动化的准备成本较高：

- Android 需要 SDK、ADB、Appium Server、UiAutomator2 Driver、合法来源 APK 和明确 UDID。
- iOS 需要 macOS、Xcode、XCUITest Driver、WDA；真机还涉及签名、Developer Mode 和 Provisioning。
- 设备、数据线、系统弹窗、网络、App 安装和版本组合都可能让初学者停在环境层。
- 一些故障是偶发的，很难为了练习稳定复现“第 3 次查找超时”或“点击时设备断连”。

Mock 解决的是“可控性”：

| 真实环境中的困难 | Mock 中的替代练习 |
|---|---|
| 没有设备 | 内存中的平台与设备描述 |
| 没有安装包 | 合成页面状态机 |
| 没有 Appium Server | API 形状相近的 Fake Driver |
| 故障很难复现 | 一次性故障注入计划 |
| 失败证据不稳定 | 明确带 `synthetic=true` 的合成证据 |
| 设备状态会污染用例 | 每个 Session 深拷贝独立应用 |
| 清理遗漏难以观察 | 记录 LIFO 清理顺序并断言 |

Mock 最有价值的场景不是“证明 UI 正常”，而是快速验证：

- 配置与目标选择逻辑；
- Fixture 生命周期；
- Page/Screen/Task 的依赖方向；
- 业务流程编排；
- Locator Contract；
- 等待、重试和故障分类策略；
- 首次失败证据；
- 清理是否一定执行；
- Android/iOS 共享业务与平台差异的边界。

## 3. Mock 能证明什么，不能证明什么

### 3.1 可以证明

| 能力 | 可以得到的可信结论 |
|---|---|
| 配置校验 | 错误平台、空定位器、错误应用标识会在预期位置失败 |
| 业务状态机 | 登录后进入列表、滑动后看到商品、点击后进入详情 |
| 平台契约 | Android 与 iOS 接受不同定位方式和手势命令 |
| 会话生命周期 | 活跃、终止、断连、崩溃、退出之间的状态约束 |
| 故障处理 | 指定操作第一次失败，错误类型和状态迁移符合约定 |
| 证据编排 | 失败时按固定目录保存清单、日志和可用证据 |
| 清理 | 正常、断言失败、断连和崩溃后仍执行已注册清理 |
| 测试隔离 | 每个 Session 有自己的 App 状态，不依赖执行顺序 |
| CI 可运行性 | 普通 Python + pytest 环境即可离线执行 |

### 3.2 绝对不能证明

| Mock 无法证明 | 必须在哪一层验证 |
|---|---|
| ADB 能否发现、授权并稳定连接 Android 设备 | Android Emulator 或专用真机 |
| WDA 能否构建、签名、安装和连接 | iOS Simulator / 专用真机 |
| APK、`.app`、`.ipa` 能否安装和启动 | 对应平台真实运行环境 |
| `resource-id`、accessibility id、Predicate 在真实 UI 树中存在且唯一 | Appium Inspector + 真实 AUT |
| Android/iOS 系统权限弹窗的真实布局和行为 | 对应系统版本的模拟器/真机 |
| 键盘、手势、动画、横竖屏、后台恢复真实表现 | 模拟器和真机 |
| App 崩溃、进程回收、弱网、USB 断连的真实时序 | 受控集成/设备测试 |
| 不同机型、分辨率、系统版本的兼容性 | 设备矩阵 |
| UI 渲染、截图视觉、无障碍真实效果 | 真实页面与视觉/无障碍检查 |
| 性能、耗电、温度、内存和网络指标 | 真机性能工具 |

因此报告必须明确写：

```text
本结果是离线 Mock 框架验证，不代表真实设备兼容性或真实 App 功能通过。
```

严禁把合成截图放进真实项目测试报告，或把 Mock 通过率写成“Android/iOS 回归通过率”。

## 4. 五条执行通道

建议把移动端自动化拆成五条 Lane，而不是在一个命令里混合：

| Lane | 环境 | 主要目标 | 是否 PR 门禁 |
|---|---|---|---|
| 1. Offline Contract | Python + pytest | Contract、状态机、异常、证据、清理 | 是 |
| 2. Local Fake Flow | 内存 Project Pack | Screen/Task/业务流 | 是 |
| 3. Emulator/Simulator Smoke | Android Emulator / iOS Simulator | Driver、安装、真实 UI 树、手势 | 可按团队条件 |
| 4. Real Device Smoke | 专用测试机 | 签名、权限、硬件、真机行为 | 人工/受控 |
| 5. Device Matrix | 设备池 | 系统/机型兼容与发布风险 | 定时/发布 |

Mock 应快、确定、完全离线。真实设备用例应少而关键。二者互补，不互相替代。

## 5. 三层架构：Core、Adapter、Project Pack

### 5.1 总体依赖方向

```text
┌─────────────────────────────────────────────┐
│ Project Pack：公开合成演示商城              │
│ 页面、业务任务、逻辑 Locator 名称、断言     │
└──────────────────────┬──────────────────────┘
                       │ 只依赖 Contract
┌──────────────────────▼──────────────────────┐
│ Core：Run / Driver / Locator Contract       │
│ 生命周期、错误模型、动作与证据接口          │
└──────────────────────▲──────────────────────┘
                       │ 实现 Contract
┌──────────────────────┴──────────────────────┐
│ Adapter                                      │
│ In-memory Fake / Android Appium / iOS Appium│
└─────────────────────────────────────────────┘
```

依赖规则：

```text
Project Pack → Core ← Adapter
```

Core 不导入 Appium，不知道某个业务页面。Project Pack 不直接创建
`webdriver.Remote()`。Fake、UiAutomator2、XCUITest 都是可替换 Adapter。

### 5.2 Core

Core 定义稳定的公共语言：

- `RunContract`：这次运行是谁、何种模式、何种平台、产物放哪里。
- `DriverContract`：建立/退出会话、查找元素、执行动作、读取证据。
- `LocatorContract`：一个逻辑元素如何映射到平台定位器。
- 会话状态、错误类别与恢复边界。
- `DeviceProvider`、`DriverFactory`、`EvidenceCollector` 等抽象职责。

本仓库第一版可运行 Core 位于：

```text
labs/automation-practice/src/qa_learning/mobile/mock/移动端契约.py
```

它已经定义：

- `安卓平台契约`、`苹果平台契约`；
- `定位器`；
- `元素定义`、`页面定义`、`公开演示应用`；
- `会话状态`；
- 定位失败、超时、设备断连、App 崩溃等异常。

### 5.3 Adapter

Adapter 把 Contract 翻译为某种执行技术：

| Adapter | 设备提供 | Driver | 证据 |
|---|---|---|---|
| In-memory Fake | 合成设备描述 | `假移动端驱动` | 合成 PNG/XML/JSON |
| Android Appium | ADB/设备池 | UiAutomator2 WebDriver | 截图、Page Source、Server/logcat |
| iOS Appium | simctl/设备池 | XCUITest WebDriver/WDA | 截图、Page Source、WDA/Xcode 日志 |

本仓库的 In-memory Adapter：

```text
mobile/mock/假移动端驱动.py
mobile/mock/故障注入.py
mobile/mock/证据采集.py
```

### 5.4 Project Pack

Project Pack 是一个可替换的业务练习包，包含：

- 页面和元素；
- 逻辑 Locator；
- Screen；
- Task/Flow；
- 合成测试数据；
- 业务断言；
- App 状态恢复规则。

本仓库的 Project Pack：

```text
mobile/mock/公开演示应用.py
```

它是从零构造的“公开合成演示商城”，只有登录、商品列表和商品详情，不来自任何真实公司应用。

## 6. 统一 Contract，不统一平台实现

### 6.1 Run Contract

一次运行至少要回答：

| 字段 | 示例 | 用途 |
|---|---|---|
| `run_id` | `learning-20260727-a1b2` | 数据、证据和日志关联 |
| `mode` | `fake` / `emulator` / `real` | 防止把 Mock 当真机 |
| `platform` | `android` / `ios` | 选择平台 Adapter |
| `project` | `synthetic_public_shop` | 选择 Project Pack |
| `target_id` | `fake-android-01` | 明确执行目标 |
| `artifact_root` | `test-results/<run-id>` | 证据根目录 |
| `fault_plan` | `none` / 指定故障 | 可复现失败 |

本仓库当前最小 Fake 直接在测试中构造平台、应用和故障计划。进阶时可把这些字段封装成不可变
`RunContext`，由 pytest 命令行或配置工厂创建，但不要在 import 阶段连接设备。

配套代码已经落地一个最小 `移动端运行契约`：

```python
运行 = 移动端运行契约(
    平台="android",
    设备标识="synthetic-android-01",
    应用配置="公开合成商城",
)
```

它先解决最重要的防误操作边界：平台只能是 Android/iOS、Project Pack 必须是公开合成商城、离线设备
标识必须以 `synthetic-` 开头。`run_id`、产物根目录和 Worker 租约可在 L6/L8 练习中继续补充。

### 6.2 Driver Contract

业务层真正需要的 Driver 能力很小：

```python
class DriverContract(Protocol):
    capabilities: dict[str, object]

    def find_element(self, by: str, value: str): ...
    def execute_script(self, script: str, arguments: dict[str, object]): ...
    def back(self) -> None: ...
    def terminate_app(self, app_id: str) -> bool: ...
    def activate_app(self, app_id: str) -> None: ...
    def save_screenshot(self, filename: str) -> bool: ...
    def get_log(self, log_type: str) -> list[dict[str, object]]: ...
    @property
    def page_source(self) -> str: ...
    def quit(self) -> None: ...
```

不要把 Appium 的几百个方法全部包装一遍。只为 Project Pack 实际需要且能清楚定义语义的能力建立
Contract。

### 6.3 Locator Contract

统一的是“逻辑元素”和定位器数据结构，不是定位值：

```text
逻辑键：login.username
Android：("id", "org.example.publicshop:id/username")
iOS：("accessibility id", "login.username")
```

Android 常用：

- `id` / resource-id；
- `accessibility id` / content-desc；
- `-android uiautomator`；
- 最后才是短且稳定的 XPath。

iOS 常用：

- `accessibility id` / accessibilityIdentifier；
- `-ios predicate string`；
- `-ios class chain`；
- 最后才是短且稳定的 XPath。

下面是错误的“统一”：

```python
if platform == "android":
    点击安卓坐标(320, 700)
else:
    点击苹果坐标(330, 720)
```

正确边界是：

```python
定位 = LocatorRepository.获取("product.learning_backpack", platform)
MobileActions.点击(定位)
```

Project Pack 只说“学习背包”，平台仓库决定如何定位。

## 7. 完整执行链

Mock 也必须跑完整流程，不能在测试里直接把 `True` 写死：

```text
DeviceProvider
    ↓ 返回唯一、已租用、可解释的目标
DriverFactory
    ↓ 按 Run Contract 创建 Adapter
Session
    ↓ 保存 capabilities、状态、生命周期
AppManager
    ↓ 激活/终止/重置目标 App
LocatorRepository
    ↓ 将逻辑元素解析为平台 Locator
Screen / Task
    ↓ 用 MobileActions 执行业务动作
Test
    ↓ 断言用户可观察结果
EvidenceCollector
    ↓ 在第一次失败后尽早保存证据
Cleanup
    ↓ 逆序释放业务数据、App、Session、设备租约
```

### 7.1 DeviceProvider

职责：

- 枚举或租用一个明确目标；
- 返回平台、目标 ID、系统版本和能力标签；
- 防止多个 Worker 使用同一设备；
- 在结束时释放租约。

Fake 版本返回固定合成目标，绝不能调用 `adb`、`simctl` 或扫描 USB：

```python
合成目标 = {
    "target_id": "fake-android-01",
    "platform": "android",
    "platform_version": "synthetic",
    "capabilities": {"touch": True, "real_device": False},
}
```

真实 Android Provider 才能调用受控 ADB/设备池；真实 iOS Provider 才能调用 simctl 或设备服务。

### 7.2 DriverFactory

职责：

- 校验 Run Contract；
- 选择 Fake、Android 或 iOS Adapter；
- 创建且只创建一个 Session；
- Session 创建失败时输出明确所属层；
- 不做业务登录、不查找页面元素。

```text
mode=fake, platform=android → 假移动端驱动 + 安卓平台契约
mode=fake, platform=ios     → 假移动端驱动 + 苹果平台契约
mode=real, platform=android → Appium + UiAutomator2Options
mode=real, platform=ios     → Appium + XCUITestOptions
```

### 7.3 Session

Session 持有：

- 当前状态；
- capabilities；
- App 状态；
- Driver 日志；
- 清理栈；
- 当前页面或真实会话 ID。

Fake Session 状态机：

```text
创建
  ↓
活跃 ── terminate_app ──→ 应用已终止
  │                         │
  │                         └─ activate_app ─→ 活跃并回到起始页
  ├─ 注入设备断连 ───────→ 设备已断连
  ├─ 注入应用崩溃 ───────→ 应用已崩溃
  └─ quit ───────────────→ 已退出

任何非“已退出”状态 ── quit ─→ 已退出并执行清理
```

### 7.4 Screen / Task / Test

三者不要混淆：

| 层 | 示例 | 应负责 | 不应负责 |
|---|---|---|---|
| Screen | `登录页` | Locator、页面就绪、单页动作 | pytest 开关、设备选择 |
| Task | `登录并打开学习背包` | 跨页业务编排 | 创建 Driver、吞掉异常 |
| Test | `test_用户可查看商品价格` | 风险、数据、关键断言 | 散落 Locator、无限重试 |

### 7.5 Evidence 与 Cleanup

Evidence 在第一次失败后尽早采集，Cleanup 在任何路径最后执行：

```text
第一次异常
  → 保存原始异常和 traceback
  → 尽力采集 screenshot/page source/driver log/manifest
  → 某项证据失败只记 secondary error
  → 重新抛出原始异常
  → finally / fixture teardown 清理
```

证据采集错误不能把“点击时 App 崩溃”改写成“截图失败”。清理错误也不能覆盖原始断言失败。

## 8. 八个公共组件

### 8.1 AppManager

统一业务需要的 App 生命周期语义：

```python
class AppManager:
    def 启动或激活(self) -> None: ...
    def 终止(self) -> None: ...
    def 重置到已知状态(self) -> None: ...
```

平台实现不同：

- Fake：调用 `activate_app`，重置内存页面和输入值。
- Android：按评审策略使用 `activate_app`、`terminate_app` 或仅清目标包数据。
- iOS：Simulator 可受控重装/重置；真机避免整机破坏性清理。

不要提供“清空全部设备”这种公共 API。

### 8.2 LocatorRepository

职责：

- 用逻辑键管理定位；
- 按平台返回 `定位器`；
- 检查空值、重复、未知平台；
- 支持定位器版本与废弃迁移；
- 不在测试中堆砌 fallback。

示意：

```python
LOCATORS = {
    "login.username": {
        "android": 定位器("id", "org.example.publicshop:id/username"),
        "ios": 定位器("accessibility id", "login.username"),
    },
    "product.learning_backpack": {
        "android": 定位器("accessibility id", "商品-学习背包"),
        "ios": 定位器("accessibility id", "product.learning-backpack"),
    },
}
```

当前配套代码把这组映射集中在 `公开演示应用.py`。进阶练习可抽成独立 Repository，但不应再次复制到测试。

### 8.3 MobileActions

职责：

- 查找可见/可点击元素；
- 输入、点击、返回；
- 有界滑动；
- 记录动作名称和耗时；
- 将底层异常保留为 cause，映射成稳定错误类别。

不要在这里：

- 写业务断言；
- 使用固定 `sleep`；
- 把任何异常返回成 `False`；
- 对非幂等点击无限重试；
- 失败后无条件刷新页面。

### 8.4 SystemHandler

处理系统级事件：

- 权限弹窗；
- 键盘；
- 横竖屏；
- App 前后台；
- Android Activity/iOS SpringBoard 等系统上下文；
- 仅对目标测试 App 执行的恢复动作。

Fake 只能模拟“系统事件处理的控制流”。它无法证明真实系统弹窗的 Locator、语言和权限状态正确。

### 8.5 EvidenceCollector

应当独立尝试每种证据：

| 证据 | Fake | 真实 Android/iOS |
|---|---|---|
| Screenshot | 固定 1×1 PNG，标记 synthetic | 真实屏幕截图 |
| Page Source | 合成 XML | Driver 返回的 UI 树 |
| Driver Log | 内存 JSON 日志 | Appium/Driver 日志 |
| Manifest | mode/platform/run_id/错误 | 设备、App、驱动版本与 hash |
| 系统日志 | 不提供 | 按最小范围截取 logcat/WDA/Xcode |

断连时截图和 Page Source 可能失败，但 Driver 日志和 manifest 仍应保留。每个采集器分别
`try/except`，最后输出 `collection_errors`，不能因为一项失败而放弃全部证据。

### 8.6 DeviceProvider

Provider 不等于 Driver：

```text
Provider：找到/租用/释放执行目标
Driver：在目标上建立会话并执行命令
```

这个分离让 CI 可以先检查设备池，再决定是否创建 Appium Session。

### 8.7 DriverFactory

Factory 只组装技术对象，不执行页面动作。真实实现可复用当前：

```text
mobile/移动端驱动工厂.py
```

Mock 实现组装：

```python
假移动端驱动(
    安卓平台契约(),
    构建安卓公开演示应用(),
    故障计划=故障注入计划(),
)
```

### 8.8 CleanupCoordinator

推荐逆序清理：

```text
5. 释放设备租约
4. 退出 Driver Session
3. 恢复/终止目标 App
2. 删除本次合成业务数据
1. 关闭证据 writer
```

实际注册顺序与执行顺序相反。配套 Fake 使用 `ExitStack`，`quit()` 幂等，允许 fixture、上下文管理器和
紧急清理都安全调用。

## 11. 从代码理解完整成功流程

### 11.0 先看已经装配好的全链代码

下面这段与 `测试_离线移动端运行装配.py` 对应：

```python
import pytest

from qa_learning.mobile.mock import (
    假驱动工厂,
    应用管理器,
    演示商城任务,
    移动端运行契约,
    系统处理器,
)


@pytest.mark.parametrize(
    ("平台", "设备标识"),
    [
        ("android", "synthetic-android-01"),
        ("ios", "synthetic-ios-01"),
    ],
)
def test_统一运行契约可驱动两端相同业务任务(
    平台,
    设备标识,
) -> None:
    # Run Contract：所有目标输入显式化；“synthetic-”也是安全闸门。
    运行 = 移动端运行契约(平台, 设备标识)

    # DeviceProvider → DriverFactory → Session。
    # with 退出时一定调用幂等 quit，并执行 LIFO 清理。
    with 假驱动工厂().创建(运行) as 驱动:
        # Screen/Task：测试描述业务意图，不散落定位器和平台手势。
        任务 = 演示商城任务(驱动, 平台)
        任务.登录("public_learner", "synthetic_password")
        任务.打开学习背包()

        assert 驱动.当前页面 == "商品详情"
        assert 驱动.capabilities["synthetic"] is True

        # SystemHandler：系统返回集中处理。
        系统处理器(驱动).返回上一页()
        assert 驱动.当前页面 == "商品列表"

        # AppManager：App 生命周期集中处理。
        应用管理器(驱动).重启并重置()
        assert 驱动.当前页面 == "登录"
```

代码调用链：

```text
移动端运行契约
  → 假驱动工厂
    → 假设备提供器.获取
    → 假移动端驱动.__init__
      → 演示商城任务
        → 移动端动作
          → 演示商城定位仓库
          → Driver find/click/send_keys/execute_script
      → 业务断言
      → 系统处理器 / 应用管理器
  → __exit__
    → quit
      → ExitStack LIFO Cleanup
```

故意传入看似真实的设备标识：

```python

    移动端运行契约("android", "real-device-serial")
```

错误必须在 Provider/Driver 创建前发生，保证离线测试不可能误连真机。

## 14. 故障注入：稳定练习不稳定世界

### 14.1 故障模型

配套代码支持：

| 故障 | 注入点示例 | 预期异常 | 会话状态 |
|---|---|---|---|
| 定位失败 | `find_element` | `元素未找到错误` | 保持活跃 |
| 操作超时 | `find_element` / `click` | `操作超时错误` | 保持活跃 |
| 设备断连 | `swipe` | `设备断连错误` | 设备已断连 |
| App 崩溃 | `click` | `应用崩溃错误` | 应用已崩溃 |

规则包含：

- 故障类型；
- 操作名；
- 可选 Locator；
- 剩余次数；
- 面向学习者的说明。

### 14.2 第一次定位失败，第二次成功

```python
用户名 = 定位器(
    "id",
    "org.example.publicshop:id/username",
)

计划 = 故障注入计划().添加(
    故障类型.定位失败,
    操作="find_element",
    定位=用户名,
    次数=1,
    说明="合成的首次查找失败",
)

驱动 = 假移动端驱动(
    安卓平台契约(),
    构建安卓公开演示应用(),
    故障计划=计划,
)

with pytest.raises(元素未找到错误, match="首次查找失败"):
    驱动.find_element(*用户名.转为元组())

# 规则已经消费，第二次查找成功。
assert 驱动.find_element(*用户名.转为元组()).is_displayed()
```

这个示例用于学习“有前提、有次数上限的恢复”。它不表示真实元素查找都应该重试一次。

安全重试必须同时满足：

1. 操作幂等或尚未产生业务副作用。
2. 错误属于明确可恢复类别。
3. 有最大次数和总时间。
4. 保留第一次失败证据。
5. 最终报告记录发生过恢复，而不是伪装成一次通过。

点击“提交订单”这类可能已成功但响应丢失的操作，不可盲目重试。

### 14.3 操作超时

Fake 超时不会真的等待，测试可以毫秒级验证策略：

```python
计划 = 故障注入计划().添加(
    故障类型.操作超时,
    操作="find_element",
    定位=用户名,
    说明="合成等待条件超时",
)
```

真实 Adapter 必须保留：

- 等待了什么条件；
- Locator；
- 最大等待；
- 当时页面；
- 原始 `TimeoutException`；
- Appium/Driver 版本。

不要只输出“timeout 了”。

### 14.4 设备断连

```python
计划 = 故障注入计划().添加(
    故障类型.设备断连,
    操作="swipe",
    说明="合成 USB 连接中断",
)

with pytest.raises(设备断连错误, match="USB"):
    驱动.swipe("up")

assert 驱动.状态 is 会话状态.设备已断连
驱动.quit()
```

断连后的原则：

- 不继续执行页面动作；
- 不把后续“元素找不到”当产品缺陷；
- 证据采集采用 best effort；
- Driver 日志和运行 manifest 优先；
- 仍尝试 Session/设备租约清理；
- 报告分类为 environment，等待复核后再下结论。

### 14.5 App 崩溃

```python
登录 = 定位器("accessibility id", "登录")
计划 = 故障注入计划().添加(
    故障类型.应用崩溃,
    操作="click",
    定位=登录,
    说明="合成应用进程退出",
)

按钮 = 驱动.find_element(*登录.转为元组())

with pytest.raises(应用崩溃错误, match="进程退出"):
    按钮.click()

assert 驱动.状态 is 会话状态.应用已崩溃
驱动.quit()
```

真实崩溃应补充：

- App 进程/前台状态；
- 目标包最小时间窗口日志；
- 崩溃堆栈；
- 操作前最后一条业务步骤；
- 设备、系统、App build；
- 是否可稳定复现。

Fake 只能验证框架如何处理“崩溃信号”，不能生成真实崩溃堆栈。

## 15. 首次失败证据

### 15.1 为什么必须保存第一次

错误的重试流程：

```text
第一次查找失败
  → 不留证据
  → 重试成功
  → 报告只显示通过
```

这会隐藏不稳定性。正确流程：

```text
第一次查找失败
  → 立即保存原始异常、页面、日志和运行上下文
  → 标记 first_failure=true
  → 按政策决定是否允许一次恢复
  → 最终结果同时包含首次失败和恢复结果
```

至少记录：

| 字段 | 说明 |
|---|---|
| `run_id` | 关联同一次运行 |
| `test_node_id` | 精确到 pytest 用例和参数 |
| `phase` | setup/call/teardown |
| `failure_type` | 定位、超时、断连、崩溃、断言等 |
| `original_exception` | 原始类型和消息 |
| `first_failure` | 必须为 `true` |
| `session_state` | 失败瞬间状态 |
| `platform/mode` | Android/iOS，Fake/real |
| `available_artifacts` | 实际成功获得的文件 |
| `collection_errors` | 哪些证据因断连等原因无法获得 |
| `synthetic` | Fake 必须为 `true` |

### 15.2 当前合成证据

`采集假证据()` 写入：

```text
<前缀>_合成截图.png
<前缀>_合成页面源码.xml
<前缀>_合成驱动日志.json
<前缀>_证据清单.json
```

四类文件均只来自内存合成状态。驱动日志包含 `FAULT_INJECTED`、`ELEMENT_NOT_FOUND`、
`NAVIGATION` 等事件，可用来回答“哪一步先失败”。

第一次故障后应立即采集，再执行允许的恢复：

```python
try:
    驱动.find_element(*用户名.转为元组())
except 元素未找到错误:
    # 此时 Session 仍活跃，先保存第一次失败现场。
    首次证据 = 采集假证据(
        驱动,
        tmp_path / "first-failure",
        前缀="首次定位失败",
    )
    raise
```

上面代码选择重新抛出，适合正式测试。若当前练习专门验证有限恢复，可保存异常与证据后再执行第二次查找，
并断言日志同时存在：

```text
FAULT_INJECTED
ELEMENT_FOUND
```

最终报告仍应写“首次失败后恢复”，不能只写“通过”。

### 15.3 Best-effort 采集

断连或崩溃后：

- `save_screenshot()` 可能失败；
- `page_source` 可能失败；
- Driver 本地日志通常仍可读；
- Run Contract 和原始异常一定应由 pytest 进程保存。

建议 EvidenceCollector 按通道独立保护：

```python
def 尽力采集(驱动, 目录):
    结果 = {"available": {}, "collection_errors": {}, "synthetic": True}

    try:
        结果["available"]["screenshot"] = 保存截图(驱动, 目录)
    except Exception as exc:
        结果["collection_errors"]["screenshot"] = repr(exc)

    try:
        结果["available"]["page_source"] = 保存页面源码(驱动, 目录)
    except Exception as exc:
        结果["collection_errors"]["page_source"] = repr(exc)

    try:
        结果["available"]["driver_log"] = 保存驱动日志(驱动, 目录)
    except Exception as exc:
        结果["collection_errors"]["driver_log"] = repr(exc)

    # 即使三个通道都失败，也写 manifest；它由 pytest 本地进程生成。
    return 写入清单(目录, 结果)
```

真实项目的日志不能直接 `repr` 所有对象，应先做 Token、Cookie、路径、账号和业务数据脱敏。

## 16. pytest Fixture 与失败 Hook

### 16.1 Fixture 管理所有权

下面是从第一版 Fake 演进到框架 Fixture 的示例：

```python
from pathlib import Path

import pytest

from qa_learning.mobile.mock import (
    假移动端驱动,
    安卓平台契约,
    构建安卓公开演示应用,
)


@pytest.fixture
def 离线安卓会话(
    request: pytest.FixtureRequest,
    tmp_path: Path,
):
    # Arrange：Fixture 创建 Session，因此它拥有并负责退出 Session。
    驱动 = 假移动端驱动(
        安卓平台契约(),
        构建安卓公开演示应用(),
    )

    # 给失败 Hook 暴露当前 Driver 和证据目录。
    request.node._移动驱动 = 驱动
    request.node._证据目录 = tmp_path / "evidence"
    request.node._已采集首次失败 = False

    try:
        yield 驱动
    finally:
        # 测试通过、断言失败、故障异常时都执行。
        # quit 幂等，并会继续关闭内部 LIFO 清理栈。
        驱动.quit()
```

关键点：

- Fixture 创建的资源由 Fixture 清理。
- 不能让测试自行决定是否 `quit()`。
- 不使用 session 级全局 Driver，避免状态污染。
- Fake 不依赖 `mobile_guard`，真实设备 Fixture 必须依赖它。

### 16.2 Hook 在 teardown 前采集

pytest 的 `pytest_runtest_makereport` 可以在测试 `call` 失败后、Fixture teardown 前采集：

```python
@pytest.hookimpl(hookwrapper=True, tryfirst=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()

    if report.when != "call" or not report.failed:
        return
    if getattr(item, "_已采集首次失败", False):
        return

    驱动 = getattr(item, "_移动驱动", None)
    目录 = getattr(item, "_证据目录", None)
    if 驱动 is None or 目录 is None:
        return

    # 先置位，防止证据代码自身异常导致重复采集。
    item._已采集首次失败 = True
    try:
        清单 = 尽力采集(驱动, 目录)
        report.user_properties.append(
            ("first_failure_evidence", str(清单))
        )
    except Exception as 证据异常:
        # 只增加 secondary 信息，不能 raise 覆盖原始测试失败。
        report.sections.append(
            ("evidence-collection-error", repr(证据异常))
        )
```

正式实现还要：

1. 对 setup/call/teardown 分别定义证据等级。
2. 保存 `call.excinfo` 的原始异常摘要。
3. 规范化 node id，防止非法/过长路径。
4. 多 Worker 下以 `run_id/worker_id/node_hash` 隔离目录。
5. 通过用例只留摘要，失败用例才留重证据。
6. 设置产物保留期。

### 16.3 为什么不用 autouse 全局 Session

全局 autouse Driver 容易造成：

- 不相关单元测试也创建设备会话；
- 失败传播到后续用例；
- App 状态互相污染；
- 并行 Worker 争用设备；
- 无法判断谁负责清理；
- 默认 `pytest` 误操作真机。

显式请求移动 Fixture，意图更清楚。

## 17. 清理设计

### 17.1 四种必须覆盖的路径

| 路径 | 应执行的清理 |
|---|---|
| 测试通过 | 全部清理 |
| 业务断言失败 | 先证据，后全部清理 |
| Driver/设备故障 | 尽力证据，仍执行本地清理与租约释放 |
| 清理本身失败 | 记录 secondary error，不覆盖原始失败 |

### 17.2 `quit()` 为什么必须幂等

下列层可能都尝试兜底：

- Context Manager；
- pytest Fixture；
- DriverFactory；
- Job 最终清理；
- 设备池租约回收。

因此：

```python
驱动.quit()
驱动.quit()
```

第二次不应抛出新异常或重复删除业务数据。

### 17.3 清理失败与原始失败

错误示例：

```python
try:
    yield 驱动
finally:
    删除测试账号()  # 若这里失败，报告可能只显示删除错误。
```

工程化做法是分别保留：

```text
primary_failure：商品价格断言失败
cleanup_errors：
  - 删除合成账号超时
  - 设备租约释放返回冲突
```

如果测试本身通过而清理失败，测试仍应失败，因为环境已经被污染；但分类要明确为 cleanup/framework，
不能伪装成产品功能失败。

### 17.4 只清本次资源

真实设备或共享环境中，清理必须基于：

- 明确 UDID；
- 明确 package/bundle id；
- 本次 `run_id`；
- 本次创建的数据 ID；
- 设备租约 token。

禁止使用未解析变量、通配符或“清全部 App/全部 Simulator/全部账号”的命令。

- 真实命令必须显式 `--run-mobile`；
- 只控制唯一目标；
- App 来源、版本和 hash 可复核。

### L9：迁移到专用真机

Android：

- 唯一 ADB UDID；
- 专用无私人数据测试机；
- 合法来源 APK；
- UiAutomator2 doctor；
- 失败日志最小化。

iOS：

- 自己有权使用的签名和测试 Team；
- 唯一真机 UDID；
- WDA 构建/签名；
- 合法来源/自行构建公开 App；
- 不提交证书、Profile 或 Team ID。

验收：

- 能指出每个 Mock 结论在哪个真实步骤被重新验证；
- 报告不把 Simulator 结果当真机；
- 清理只作用于目标测试 App。

## 21. 从 Mock 到真实 Android/iOS 的一一迁移表

迁移原则是“替换 Adapter，保留业务意图，重新验证所有真实边界”。

| 框架位置 | Fake 当前实现 | Android 真实实现 | iOS 真实实现 | 必须重新验证 |
|---|---|---|---|---|
| Run Contract | `移动端运行契约` | 环境、设备租约、APK/profile | 环境、Simulator/真机、build/profile | 输入来源、Secret、模式标记 |
| DeviceProvider | `假设备提供器` | 明确 ADB UDID/设备池 | 明确 Simulator/真机 UDID | 在线、唯一、未被占用 |
| Device Record | `假设备` | 型号、API、serial、能力标签 | 型号、iOS、UDID、能力标签 | 数据脱敏与资产授权 |
| DriverFactory | `假驱动工厂` | `移动端驱动工厂` + UiAutomator2Options | `移动端驱动工厂` + XCUITestOptions | Appium/Driver/OS 兼容 |
| Session | `假移动端驱动` | Appium → UiAutomator2 server → ADB | Appium → XCUITest → WDA/XCTest | 建连、超时、端口、会话回收 |
| App 资产 | 合成状态机 | 合法公开 APK + SHA-256 | Simulator build 或有权签名真机 build | 安装、签名、架构、最低系统 |
| AppManager | `应用管理器` | terminate/activate/受控清包状态 | terminate/activate/受控重装或状态恢复 | reset 副作用与目标边界 |
| LocatorRepository | `演示商城定位仓库` | Inspector 核对 resource-id/accessibility id | Inspector 核对 identifier/Predicate/Class Chain | 存在、唯一、可交互 |
| MobileActions | `移动端动作` | 显式等待、UiAutomator2 手势 | 显式等待、XCUITest 手势 | 动画、stale、键盘、屏幕尺寸 |
| SystemHandler | `系统处理器` 仅返回 | Android 权限/键盘/系统弹窗 | SpringBoard/权限/键盘 | 系统版本、语言、真实权限状态 |
| Screen | 合成页面/可见条件 | Android 原生 Screen Object | iOS 原生 Screen Object | 页面就绪、滚动容器、可访问性 |
| Task | `演示商城任务` | 保留业务接口，注入 Android Screen | 保留业务接口，注入 iOS Screen | 端间业务语义是否一致 |
| Test | 当前页面/合成 XML | 用户可见结果与真实业务状态 | 用户可见结果与真实业务状态 | 真实风险与产品结论 |
| Evidence | 合成 PNG/XML/JSON/manifest | 截图、Page Source、Appium/logcat | 截图、Page Source、WDA/Xcode | 最小化、脱敏、保留期 |
| Fault Injection | 一次性内存规则 | 本地代理、受控 App hook、设备实验 | 本地代理、受控 App hook、设备实验 | 真实故障时序与恢复 |
| Cleanup | `ExitStack` + 幂等 quit | 退出 Session、目标 App、数据、租约 | 退出 Session/WDA、目标 App、数据、租约 | 只清本次资源 |
| CI Marker | `mobile and mock and contract` | `mobile and device and android` | `mobile and device and ios` | 真实 Lane 必须显式授权 |

### 21.1 DeviceProvider 迁移

Fake：

```python
设备 = 假设备提供器().获取(
    移动端运行契约("android", "synthetic-android-01")
)
```

Android 真实 Provider 应：

1. 从任务参数获得预期 UDID。
2. 执行最小范围 `adb devices -l` 或调用设备池 API。
3. 精确匹配一个目标。
4. 状态不是 `device` 时拒绝。
5. 多个设备时绝不猜测。
6. 建立 Worker 独占租约。

iOS 真实 Provider 应：

1. 区分 Simulator 与真机。
2. 使用准确 UDID。
3. Simulator 从 `simctl` 已安装 runtime 中选择。
4. 真机从受控设备资产/`xctrace` 验证。
5. 不使用 `udid=auto` 控制未知设备。
6. 建立独占租约。

Provider 只做选择和租约，不安装 App，不执行登录。

### 21.2 DriverFactory 迁移

Fake Factory：

```python
驱动 = 假驱动工厂().创建(运行)
```

Android：

```python
options = UiAutomator2Options()
options.load_capabilities(
    {
        "platformName": "Android",
        "automationName": "UiAutomator2",
        "udid": target.udid,
        "app": str(verified_apk),
        "appPackage": public_package,
        "appActivity": public_activity,
        "noReset": False,
        "autoGrantPermissions": False,
    }
)
driver = webdriver.Remote(appium_url, options=options)
```

iOS：

```python
options = XCUITestOptions()
options.load_capabilities(
    {
        "platformName": "iOS",
        "automationName": "XCUITest",
        "udid": target.udid,
        "app": str(verified_ios_build),
        "bundleId": public_bundle_id,
        "noReset": False,
        "autoAcceptAlerts": False,
    }
)
driver = webdriver.Remote(appium_url, options=options)
```

以上是字段示意。Simulator/真机 build、签名、WDA、端口和当前 Driver 版本约束必须按
[iOS 全流程](./04-苹果移动端自动化全流程.md)核对，不能照抄示例值。

### 21.3 LocatorRepository 迁移

每个逻辑键按平台逐项替换：

```text
login.username
  Fake Android → 合成 resource-id
  Real Android → Inspector/源码核对后的稳定 resource-id
  Fake iOS     → 合成 accessibility id
  Real iOS     → 开发维护的 accessibilityIdentifier
```

迁移步骤：

1. 固定公开样例 App 版本。
2. 在目标平台打开实际页面。
3. 用 Inspector/源码确认 Locator。
4. 检查唯一性和交互目标。
5. 为页面就绪元素增加 Contract Test。
6. 连续、单独、乱序运行。
7. 升级 App 版本时重新核对。

不能把 Fake 定位值直接当成真实 App 定位值。

### 21.4 EvidenceCollector 迁移

保持目录与 manifest Contract，替换采集实现：

```text
Fake screenshot    → driver.save_screenshot 真实界面
Fake page source   → driver.page_source 真实 UI 树
Fake driver log    → Appium Server/Driver 对应时间窗口
Fake manifest      → 设备、OS、App hash、Client/Server/Driver 版本
```

真实证据新增隐私闸门：

- 截图前确认前台是公开样例；
- 关闭通知预览；
- Page Source 可能包含用户文本；
- logcat/syslog 只截必要包与时间窗；
- URL、Token、Cookie、账号和本机路径脱敏；
- 证据目录不提交 Git；
- CI 设置访问权限与保留期。

### 21.5 Fault Injection 迁移

不要为了制造故障破坏共享公共服务或私人设备。使用：

- 自己控制的本地演示 App；
- 测试构建内明确的 debug hook；
- 本地代理/WireMock 模拟接口异常；
- Emulator/Simulator 的网络与进程控制；
- 专用设备上的人工受控断连；
- 经过评审的设备池故障实验。

禁止：

- 对公共站点主动制造流量/429；
- 对未知设备执行断网、卸载或清数据；
- 为模拟崩溃引入生产后门；
- 上传真实崩溃日志前不做脱敏。

## 22. 框架验收清单

### 22.1 安全

- [ ] 只包含公开、合成或自己有权使用的内容。
- [ ] 没有公司项目名、页面、字段、域名、代码、截图、日志或安装包。
- [ ] 没有真实账号、Token、Cookie、证书、Profile、Team ID 或私人 UDID。
- [ ] Mock 不运行 ADB、simctl、Appium 或公网请求。
- [ ] 真实设备用例仍需显式 `--run-mobile`。
- [ ] 所有 Fake 证据明确标记 `synthetic=true`。

### 22.2 架构

- [ ] 能画出 DeviceProvider 到 Cleanup 的全链。
- [ ] Core 不依赖具体 Project Pack。
- [ ] Project Pack 不直接创建 `webdriver.Remote()`。
- [ ] Fake/Android/iOS Adapter 实现共同 Contract。
- [ ] Run Contract 明确 mode/platform/target。
- [ ] Locator 通过逻辑键集中管理。
- [ ] Android/iOS 实现差异没有被大量 `if platform` 泄露到测试。
- [ ] AppManager、MobileActions、SystemHandler 职责清楚。
- [ ] Task 表达业务，Test 保留关键断言。

### 22.3 成功路径

- [ ] Android/iOS 合成流程都能运行。
- [ ] 登录、滑动、详情跳转都有状态断言。
- [ ] 不使用固定 `sleep`。
- [ ] 滑动有次数上限或明确条件。
- [ ] 每个 Session 深拷贝独立应用。
- [ ] 单独、乱序、重复执行结果一致。

### 22.4 故障与证据

- [ ] 定位失败可稳定复现。
- [ ] 操作超时可稳定复现且不真的等待。
- [ ] 设备断连会改变 Session 状态。
- [ ] App 崩溃后不继续执行页面动作。
- [ ] 第一次失败在恢复前留证据。
- [ ] 一次性规则不会污染后续步骤。
- [ ] 断连/崩溃后仍保存 Driver Log 和 evidence manifest。
- [ ] 截图/Page Source 失败不会覆盖原始异常。
- [ ] 合成输入内容不会进入日志。

### 22.5 清理

- [ ] 正常通过后清理。
- [ ] 断言失败后清理。
- [ ] 设备断连后清理。
- [ ] App 崩溃后清理。
- [ ] 清理顺序为 LIFO。
- [ ] `quit()` 幂等。
- [ ] 清理错误单独记录，不覆盖 primary failure。
- [ ] 真实环境只清本次 run/目标 App/目标设备的数据。

### 22.6 真实迁移

- [ ] Android 用唯一 UDID，不靠 `deviceName` 猜。
- [ ] iOS 区分 Simulator build 和真机签名 build。
- [ ] App 来源、版本、许可证和 SHA-256 可复核。
- [ ] 真实 Locator 在实际版本中确认存在且唯一。
- [ ] Android/iOS 手势分别验证。
- [ ] 权限、键盘、WDA/ADB、签名和兼容性在真实环境重新验证。
- [ ] Mock、Simulator、真机报告严格分开。

## 23. 常见错误

### 23.1 “Mock 通过，所以 App 没问题”

错误。只能说明合成 Contract 和框架控制流符合预期。真实 App 结论必须来自真实 AUT。

### 23.2 Fake Driver 复制 Appium 全部 API

会形成一个难维护的“假 Appium”。只实现 Project Pack 当前需要的最小能力。

### 23.3 用随机故障制造真实感

随机失败会让测试不可复现。故障注入必须在 Arrange 阶段声明操作、Locator、类型和次数。

### 23.4 将平台差异全部塞进测试

测试不应遍布：

```python
if android:
    ...
else:
    ...
```

将 Locator、手势和系统处理留在 Adapter/Screen/Repository。

### 23.5 所有失败都重试

重试会隐藏 Locator、状态、产品和环境缺陷。只允许对已分类、可恢复、幂等的操作设置有限恢复，并保留首次
失败。

### 23.6 证据采集全有或全无

断连后常拿不到截图，但仍可保存本地 manifest 和日志。每个证据通道应独立。

### 23.7 清理代码吞掉原始异常

报告应同时保留 primary failure 与 cleanup errors。清理失败本身也需要治理。

### 23.8 Mock 与真实测试使用同一 Marker

二者都可有 `mobile`，但必须进一步区分：

```text
Mock：mobile + mock + contract
真实：mobile + device + android/ios
```

只有真实 Lane 需要 `--run-mobile`。

### 23.9 把公司业务“改几个名字”放进 Project Pack

这仍可能泄露内部模型。正确做法是从零设计公开合成业务，像本章的三页商城一样，只表达通用测试概念。
