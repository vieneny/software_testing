# 自动化实战学习地图

> 核对日期：2026-07-27
> 配套工程：[`labs/automation-practice`](../../labs/automation-practice/README.md)

这一模块把接口、Web、Android 和 iOS 自动化组织成一条可执行的学习路线。
目标不是“会调用某个库”，而是能够独立完成：

```text
理解需求与风险
  → 选择自动化层
  → 建立可重复环境
  → 设计独立测试
  → 实现框架
  → 运行与收集证据
  → 诊断失败
  → 接入分层 CI
  → 汇报质量结论
```

开始前，请按当前系统完成
[Windows / macOS 测试工具安装与快速使用知识库](../00-学习指南/05-测试工具安装与快速使用/README.md)
中的 Python、Node.js、浏览器和移动端工具准备。只安装当前练习需要的工具。

## 2. 为什么不是一个“万能脚本”

不同测试层能回答的问题不同。

| 层 | 最擅长回答 | 典型速度 | 主要风险 |
|---|---|---:|---|
| 纯逻辑/单元 | 数据生成、Schema、转换、脱敏是否正确 | 毫秒级 | 不能证明真实集成 |
| API | 规则、状态、错误语义、数据一致性 | 快 | 共享数据、依赖不稳定 |
| Web UI | 浏览器中关键用户旅程是否成立 | 中 | DOM、网络、浏览器差异 |
| Android/iOS UI | 真正 App 交互、系统权限、设备行为 | 慢 | 设备、驱动、签名、动画 |
| 跨端 E2E | 多入口是否共享正确业务结果 | 最慢 | 失败原因多、清理困难 |

成熟策略不是把所有测试都升级为 E2E，而是：

1. 用大量确定性的低层测试覆盖规则；
2. 用少量 UI 测试覆盖关键用户行为；
3. 用更少的跨端旅程验证集成；
4. 为每层建立独立失败证据；
5. 让不稳定的公共环境与 PR 质量门禁解耦。

## 3. 练习环境矩阵

| 环境 | 所有权与状态 | 主练习 | 运行策略 |
|---|---|---|---|
| Fake Response / 本地函数 | 完全可控 | Client、Schema、异常信息 | 每次提交 |
| 本仓库 `demo-shop` | 完全可控，重启清空 | API、Web、性能、AI 基线 | 每次提交或本地 CI |
| WireMock / Mockoon / Prism | 完全可控 | 故障注入、状态机、契约 | 每次提交或专题任务 |
| JSONPlaceholder | 第三方公共，写入模拟 | HTTP、查询、基础结构 | 手工低频 |
| Restful Booker | 第三方公共，真 CRUD、周期重置 | 鉴权、数据链、清理 | 手工低频、串行 |
| TodoMVC / SauceDemo | 第三方公共 | Web 定位、业务流 | 手工低频 |
| ApiDemos / My Demo App | 本机安装的公开练习 App | Android/iOS 自动化 | 显式控制设备 |
| Toolshop | 公共或自建开源综合靶场 | API/Web/Android/iOS Capstone | 公共 smoke、本地完整回归 |

公共靶场没有为个人 CI 提供 SLA。不得对其做性能、压力、安全扫描、爬虫、
并发写入或无限重试。性能学习只能指向本地、自建或获得明确授权的目标。

## 4. 五个学习阶段

### 阶段 A：能运行，但先理解边界

交付：

- 一个可重建的虚拟环境；
- 一次安全的默认 `pytest -q`；
- 能解释三个显式开关；
- 一份不包含私密信息的 `.env` 本地配置；
- 一次 `git status --short` 检查。

验收：

- 默认运行不会访问公共 API/Web；
- 默认运行不会创建 Appium Session；
- 知道 APK、`.app`、日志、截图和 Trace 为什么默认不提交；
- 所有身份、地址、订单和文本都是公开演示或虚构数据。

### 阶段 B：让测试可信

交付：

- API 状态、结构和业务三层断言；
- Web 的语义化 Locator 与条件等待；
- Android/iOS 的稳定定位与 Session 配置；
- 每条测试独立的数据与清理；
- 一条能主动失败的负向测试。

验收：

- 失败信息能指向具体违反的规则；
- 不依赖用例执行顺序；
- 不用固定睡眠代替状态等待；
- 不用“失败就重试三次”制造假绿。

### 阶段 C：让失败可诊断

交付：

- API 脱敏请求/响应摘要；
- Playwright Trace 与失败截图；
- Appium 日志、截图和 Page Source；
- 一份环境、测试数据、定位、断言四类失败归因表；
- 一个可复现的缺陷记录。

验收：

- 不重新运行也能从证据判断优先排查方向；
- 证据不包含 Secret 或非公开资料；
- 环境失败不会被误写成产品缺陷；
- 产品断言失败不会被自动 `skip` 隐藏。

### 阶段 D：让工程可持续

交付：

- Config、Client/Driver、Service/Page/Screen、Flow、Test 清晰分层；
- fixture 负责资源生命周期；
- 合成数据工厂和可追踪运行 ID；
- Offline、Local、Public、Mobile 四条 CI/执行通道；
- 一份升级与失效靶场处理策略。

验收：

- PR 只依赖本地确定性测试；
- 公共 smoke 可人工触发、低频、串行；
- 移动任务绑定明确设备；
- 失败产物有保留周期和数据检查；
- 框架没有变成包装库全部方法的“万能基类”。

### 阶段 E：完成跨端作品集

使用
[Practice Software Testing / Toolshop](https://github.com/testsmith-io/practice-software-testing)
完成一个跨端 Capstone：

- API：鉴权、目录、购物车或订单契约；
- Web：登录、搜索、购物车、结算关键路径；
- Android：真机核心旅程与系统交互；
- iOS：Simulator 核心旅程与 XCUITest/WDA 证据；
- Cross-channel：少量跨端数据一致性验证；
- Engineering：配置、隔离、清理、报告与分层 CI；
- Analysis：缺陷、风险、限制和下一步。

官方仓库有明确许可边界。只链接官方源码和下载，不在本仓库重新分发 App、
上游源码或公开部署。公共实例只做低频 smoke，完整回归在自己控制且符合许可的
本地环境进行。

## 5. 运行安全门

配套工程提供三个必须手工加入的 pytest 开关：

```bash
pytest tests/api -q --run-public-api
pytest tests/web -q --run-public-web
pytest tests/mobile -q --run-mobile
```

| 开关 | 它授权的动作 | 它不授权的动作 |
|---|---|---|
| `--run-public-api` | 当前命令低频访问教程中的公共 API | 压测、并发扫描、访问其他地址 |
| `--run-public-web` | 当前命令打开教程中的公共 Web | 批量注册、爬取、绕过站点限制 |
| `--run-mobile` | 控制 `.env` 明确配置的设备/模拟器 | 自动挑选未知设备、安装未知 App |

离线 App Mock 不控制设备，因此不需要 `--run-mobile`，可直接运行：

```bash
pytest tests/unit/测试_离线移动端成功流程.py \
  tests/unit/测试_离线移动端故障与清理.py \
  tests/unit/测试_离线移动端运行装配.py -q
```

只有带 `device` 标记的真实 Appium 用例受 `--run-mobile` 安全门保护；Mock 和
Contract 测试默认运行，且不会扫描 adb/simctl、连接 Appium Server 或访问公网。

开关不会替你判断目标是否正确。执行前仍需检查：

```bash
pytest --collect-only -q
adb devices -l
git status --short
```

公共目标 URL 只能来自教程公开来源；移动 App 只能来自官方 Release；任何看起来
像公司域名、内网 IP、工作账号或真实数据的配置都应立即停止并删除。

## 6. 求职作品集怎么展示

作品集应展示测试思维与工程判断，而不是只写“共 300 条用例”。

建议结构：

```text
README
├── 项目目标和公开来源
├── 风险与测试范围
├── 环境与安全边界
├── 技术选型与分层图
├── 三分钟运行方式
├── 用例与追踪矩阵
├── 失败证据示例
├── CI 分层
├── 已知限制
└── 复盘与下一步
```

面试时至少能解释：

1. 为什么 API Client 不自动 `raise_for_status()`；
2. 为什么 JSONPlaceholder 的 201 不等于真正落库；
3. 为什么 Page/Screen 不应该封装成万能 `click(selector)`；
4. 为什么固定睡眠和盲目重试会掩盖问题；
5. 为什么每条测试需要隔离 Context/App 状态；
6. 为什么公共 smoke 不应成为 PR 硬门禁；
7. Android 的 adb、UiAutomator2、Appium 各负责什么；
8. iOS 的 XCUITest、WDA、Xcode 签名各负责什么；
9. 如何用日志、Trace、截图、Page Source 缩小故障层；
10. 如何证明一个跨端缺陷可复现而不是环境偶发。

## 7. 完成标准

- [ ] 七篇教程全部完成至少一个可运行练习；
- [ ] 无设备时能运行 App Mock 成功流和四类故障流，并解释其证明边界；
- [ ] 默认执行没有外部副作用；
- [ ] 公共 API/Web 与移动控制均显式开启；
- [ ] API、Web、Android、iOS 各有一条关键路径和一条负向路径；
- [ ] 测试数据可识别、可追踪、可清理；
- [ ] 没有真实个人信息、公司内容或 Secret；
- [ ] 有至少一份 API 脱敏日志；
- [ ] 有至少一份 Web Trace；
- [ ] 有至少一份 Android 或 iOS 的截图 + Page Source + Appium 日志；
- [ ] 有一条本地 Demo Shop API/UI 联调；
- [ ] 能区分公共环境故障、测试代码故障与产品故障；
- [ ] 没有用无限重试、固定等待或扩大超时掩盖失败；
- [ ] Toolshop Capstone 有策略、代码、证据、缺陷与复盘。

## 8. 资料维护规则

公开工具、靶场、系统版本和下载链接会变化。更新本模块时必须：

1. 优先查官方文档、官方仓库和官方 Release；
2. 记录核对日期和重要版本；
3. 不从第三方网盘重新分发安装包；
4. 不把搜索摘要当成事实来源；
5. 发现许可、下载或公共服务政策变化时先收紧教程边界；
6. 链接失效时优先寻找官方替代或本地开源部署；
7. 不通过增加重试把已失效的靶场伪装成可用。
