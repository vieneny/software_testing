# Android 真机自动化全流程：Appium 3 + UiAutomator2 + pytest

> 适用对象：第一次接触移动端自动化的同学，以及需要把“能运行的脚本”升级为安全、稳定、可排障测试工程的测试工程师。
>
> 内容核对日期：2026-07-27。版本、下载链接与设备支持范围会变化，执行前必须重新核对官方页面。
>
## 1. 完成后的能力

学完本章，你应当能独立完成这条链路：

```text
确认公开样例与许可证
  → 从官方 Release 下载并校验 SHA-256
  → 配置 Android SDK、USB 调试和唯一真机 UDID
  → 安装 Appium 3 与指定 UiAutomator2 Driver
  → 启动本地 Appium Server
  → 用 Python Options 创建 W3C Session
  → 用稳定定位器和显式等待执行 smoke
  → 采集最小必要失败产物
  → 根据客户端、Server、Driver、ADB、AUT 五层定位故障
```

本仓库对应实现：

- `labs/automation-practice/src/qa_learning/mobile/移动端驱动工厂.py`：Appium 3 driver factory。
- `labs/automation-practice/src/qa_learning/mobile/screens/移动端基础页面.py`：等待、滚动和截图。
- `labs/automation-practice/src/qa_learning/mobile/screens/安卓组件演示页面.py`：ApiDemos Page Object。
- `labs/automation-practice/src/qa_learning/mobile/screens/跨端演示商城页面.py`：My Demo App Page Object。
- `labs/automation-practice/tests/mobile/`：默认禁止运行、显式开启的真机 smoke。

## 2. 架构先理解

Appium 不是直接点击手机的 Python 库。一次操作经过五层：

```text
pytest / Appium Python Client
          │ W3C WebDriver HTTP
          ▼
Appium 3 Server
          │ 选择 automationName
          ▼
UiAutomator2 Driver
          │ ADB + 设备端 instrumentation
          ▼
Android 真机
          │
          ▼
公开练习 APK（AUT）
```

排障时必须先判断错误在哪一层。比如：

- Python 报导入失败：客户端依赖层。
- `Could not find a driver for automationName`：Server/Driver 层。
- `device unauthorized`：ADB/真机授权层。
- 能建 Session 但找不到按钮：AUT 状态、定位或等待层。

## 4. 安装前置环境

### 4.1 Node.js 与 Appium 3

Appium 3 当前要求较新的 Node.js。以对应版本 `package.json` 的 `engines` 为准；2026-07-27
官方包显示 Node 约束为 `^20.19.0 || ^22.12.0 || >=24.0.0`，npm 至少 10。

```bash
node --version
npm --version
npm install --global appium
appium --version
```

安装 Android Driver：

```bash
appium driver install uiautomator2
appium driver list --installed
appium driver doctor uiautomator2
```

若团队要求可复现，不要每个人随手装 latest。先在隔离环境验证，再用明确版本：

```bash
appium driver install uiautomator2@7.6.2
```

版本选择必须以 `appium driver list`、Driver 的兼容声明和目标 Android/Xcode 环境共同决定。

### 4.2 Android SDK 与 platform-tools

推荐从 [Android Studio 官方站点](https://developer.android.com/studio)安装 SDK，通过 SDK Manager
安装目标平台和最新兼容的 platform-tools。至少确认：

```bash
adb version
adb start-server
adb devices -l
```

macOS/Linux 通常还要正确设置 `ANDROID_HOME` 或 `ANDROID_SDK_ROOT` 及 `PATH`。不要复制同事电脑或公司
CI 的私有路径；根据自己电脑的 SDK 安装位置配置。

### 4.3 Python 项目

在 `labs/automation-practice` 中创建独立虚拟环境，然后安装仓库声明的 mobile extra：

```bash
cd labs/automation-practice
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e '.[mobile,dev]'
```

这里使用 `UiAutomator2Options`，不会使用已经被新版 Client 移除的
`desired_capabilities=` 参数。

## 6. 真机安全准备

### 6.1 使用专用测试机

推荐使用恢复出厂、无私人账号、无相册/联系人/短信/公司应用的专用设备。最低要求：

- 不连接公司 VPN。
- 不登录私人 Google 账号。
- 不放私人照片、短信、联系人、支付应用和密钥。
- 不开启与用例无关的辅助权限。
- 用完关闭 USB 调试并撤销电脑授权。
- 截图、录屏和日志只包含公开样例界面。

本仓库不会调用联系人、相册、短信、剪贴板或文件浏览 API，也不会自动扫描设备选择目标。

### 6.2 开启调试与授权

按 [Android 官方“配置开发者选项”](https://developer.android.com/studio/debug/dev-options)
开启开发者选项和 USB 调试。连接后，手机会显示电脑 RSA 指纹确认框；只在自己的可信电脑上允许。

```bash
adb kill-server
adb start-server
adb devices -l
```

典型输出：

```text
List of devices attached
R3XXXXXXXXX device product:... model:... transport_id:1
```

第一列就是 UDID/serial。状态必须是 `device`：

- `unauthorized`：解锁手机，确认 RSA；必要时撤销 USB 调试授权后重连。
- `offline`：更换数据线/USB 口、重启 ADB 和设备。
- 空列表：检查“仅充电”模式、驱动、platform-tools 与线缆。
- 多台设备：每条 ADB 命令都加 `-s <UDID>`。

本项目对 Android 强制 `MOBILE_UDID`，因为官方 Driver 文档明确指出 `deviceName` 并不负责选择真机。
这是避免误操作另一台已连接设备的关键安全闸门。

只查询自动化所需系统属性：

```bash
adb -s R3XXXXXXXXX shell getprop ro.build.version.release
adb -s R3XXXXXXXXX shell getprop ro.build.version.sdk
```

不要执行通讯录、相册、短信或应用数据目录查询。

## 7. 启动 Appium Server

先检查 Driver，再启动：

```bash
appium driver doctor uiautomator2
appium
```

Appium 2/3 默认基址是：

```text
http://127.0.0.1:4723
```

不要沿用 Appium 1 教程中的 `/wd/hub`，除非你明确用 `--base-path` 配置过。Server 只绑定本机环回
地址即可；练习环境不要暴露到局域网/公网。

另开终端验证状态：

```bash
curl --fail http://127.0.0.1:4723/status
```

从 `环境变量示例.env` 复制本地 `.env`，但 `.env` 不应提交：

### 8.1 ApiDemos

```dotenv
APPIUM_SERVER_URL=http://127.0.0.1:4723
MOBILE_PLATFORM=android
MOBILE_APP_PROFILE=api_demos
MOBILE_DEVICE_NAME=Android
MOBILE_UDID=R3XXXXXXXXX
MOBILE_PLATFORM_VERSION=
MOBILE_APP=/绝对路径/qa-public-mobile-apps/ApiDemos-debug-v6.0.14.apk
```

### 8.2 My Demo App

```dotenv
APPIUM_SERVER_URL=http://127.0.0.1:4723
MOBILE_PLATFORM=android
MOBILE_APP_PROFILE=my_demo_app
MOBILE_DEVICE_NAME=Android
MOBILE_UDID=R3XXXXXXXXX
MOBILE_PLATFORM_VERSION=
MOBILE_APP=/绝对路径/qa-public-mobile-apps/mda-2.2.0-25.apk
ANDROID_APP_PACKAGE=com.saucelabs.mydemoapp.android
ANDROID_APP_ACTIVITY=com.saucelabs.mydemoapp.android.view.activities.SplashActivity
```

为什么 `MOBILE_APP` 必须是绝对路径：

- Appium Server 的工作目录可能与 pytest 不同。
- CI、IDE 与命令行的当前目录不同。
- 相对路径可能误指向同名的公司 APK。

factory 会在访问 Server/设备前拒绝相对路径、不存在文件、错误扩展名、未知平台/profile，以及未设置
Android UDID 的请求。

`MOBILE_PLATFORM_VERSION` 可以为空，让 Driver 从指定 UDID 识别；不要复制网上或别人手机的版本号。

## 9. Capabilities 设计

| Capability | 本项目值 | 理由 |
|---|---|---|
| `platformName` | `Android` | W3C 标准平台 |
| `appium:automationName` | `UiAutomator2` | 显式选择官方 Android Driver |
| `appium:udid` | 真机 serial | 真正选择唯一设备 |
| `appium:deviceName` | 描述性值 | 兼容性字段，不承担选择 |
| `appium:app` | 绝对 APK 路径 | 只安装显式公开样例 |
| `appium:appPackage` | profile 固定/配置 | 启动目标包 |
| `appium:appActivity` | profile 固定/配置 | 启动目标 Activity |
| `appium:noReset` | `false` | smoke 从可重复的干净应用状态开始 |
| `appium:autoGrantPermissions` | `false` | 不悄悄扩大应用权限 |
| `appium:newCommandTimeout` | `120` | 避免遗留会话长期占用设备 |

Python Client 的 Options 会为 Appium 扩展 capability 处理 `appium:` 前缀。不要同时维护一份陈旧 JSON。

`noReset=true` 不是“提速开关”：它会保留账号、购物车、权限和本地数据，导致用例相互污染。只有当用例
明确测试持久化且自带前后清理时才使用。

## 10. 运行与选择

查看测试而不触碰设备：

```bash
cd labs/automation-practice
.venv/bin/pytest tests/mobile --collect-only -q
.venv/bin/pytest tests/mobile -q
```

没有 `--run-mobile` 时整个目录在 collection 阶段跳过，不会创建 Session。

显式运行当前 `.env` 指向的 profile：

```bash
.venv/bin/pytest tests/mobile --run-mobile -m 'mobile and android and smoke' -vv
```

即使显式开启，profile 不匹配的模块也会给出明确 skip。例如配置 `api_demos` 时，My Demo App 用例
不会先创建 Driver 再跳过。

只跑一条：

```bash
.venv/bin/pytest \
  tests/mobile/测试_安卓组件演示应用.py \
  --run-mobile -m smoke -vv
```

运行前四项确认：

1. 屏幕已解锁，电量充足，自动锁屏时间足够。
2. `adb devices -l` 中目标 UDID 唯一且状态为 `device`。
3. Appium Server 正在 `127.0.0.1:4723` 监听。
4. `.env` 的 APK 是刚校验的公开样例绝对路径。

## 11. Page Object 与等待策略

测试只表达业务：

```python
app.wait_for_catalog()
app.open_first_product()
app.add_one_to_cart()
app.open_cart()
assert app.cart_has_item()
```

屏幕对象负责定位、等待与页面切换。不要在测试里散落 XPath 和 `time.sleep()`。

### 11.1 定位器优先级

建议顺序不是绝对教条，而是稳定性基线：

1. 唯一、稳定、由开发维护的 `resource-id`。
2. 技术型且稳定的 accessibility id/content-desc。
3. Android UIAutomator selector（尤其精确文本或可滚动容器）。
4. 简短、带稳定锚点的 XPath，仅在上面都无法满足时使用。
5. 坐标点击只适合探索，不能进入主回归。

My Demo App 例子：

```text
com.saucelabs.mydemoapp.android:id/cartRL
com.saucelabs.mydemoapp.android:id/itemsTV
Tap to add product to cart
```

注意：同一 `resource-id` 可能在不同页面复用，等待它可能产生假阳性。进入详情页应等待该页面独有的
“Add to cart”元素，而不是等待两个页面都有的标题 ID。

2.2.0 源码中点击监听器挂在 `cartRL` 容器而不是子元素 `cartIV`，所以 Page Object 点击真正的交互
目标。Inspector 能看到不代表元素自己可点击；要同时核对 `clickable` 和上游监听器。

### 11.2 显式等待

固定睡眠的问题：

- 快机器浪费时间。
- 慢机器依然失败。
- 不能说明“在等什么”。

`BaseScreen` 提供 `wait_visible`、`wait_clickable`、`wait_until_gone`。页面切换后等待“目标页独有元素”，
而不是刚点击元素消失或随便等待两秒。

### 11.3 有界滚动

滚动必须有终止条件：

```python
element = screen.scroll_until_visible(locator, direction="down", max_swipes=5)
```

Android 实现调用官方 Driver 的 `mobile: swipeGesture`，使用屏幕比例计算区域。超过次数抛
`TimeoutException`，避免死循环。不要用录制器生成的固定坐标跨分辨率运行。

## 12. 权限、系统弹窗和手势

### 12.1 权限

最佳实践：

- 用例明确决定“允许”还是“拒绝”，并断言后果。
- 测试相机时使用专用测试图，不读取相册。
- 不用 `autoGrantPermissions=true` 掩盖产品权限流程。
- 每个用例只申请完成目标所必需的权限。
- 结束后清理样例应用；不要对其他包执行权限命令。

公开练习 APK 若不需要敏感权限，就不要扩展测试范围。

### 12.2 常见手势

优先使用 Driver 官方 `mobile:` 扩展：

- `mobile: swipeGesture`
- `mobile: scrollGesture`
- `mobile: dragGesture`
- `mobile: longClickGesture`

参数和支持范围见
[UiAutomator2 手势扩展文档](https://github.com/appium/appium-uiautomator2-driver/blob/master/docs/android-mobile-gestures.md)。
不同 Driver 版本可能改变行为，升级时做一条手势契约测试。

## 13. Hybrid / WebView

Hybrid 自动化不是“直接用 native 定位网页”。流程是：

```python
print(driver.contexts)               # 仅在公开样例专用设备上调试
driver.switch_to.context("WEBVIEW_...")
# 使用 CSS/DOM 定位
driver.switch_to.context("NATIVE_APP")
```

关键条件：

- AUT 的 WebView 必须允许调试。
- Chrome/WebView 与 Chromedriver 必须兼容。
- context 出现是异步的，要显式等待。
- 切换前后都断言当前 context。

生产项目不要把自动下载任意 Chromedriver 当默认方案；在受控环境固定来源、版本和哈希。练习时也不要
浏览公司网页或登录私人账号。

## 14. 并行执行

移动端并行的基本单位是“设备”，不是线程：

```text
worker-1 → UDID-A → 独立 Appium 端口/系统端口 → 独立测试账号
worker-2 → UDID-B → 独立 Appium 端口/系统端口 → 独立测试账号
```

UiAutomator2 并行需要为每个 Session 分配独立 `systemPort`；若涉及 WebView，还要规划 Chromedriver
端口。每台设备只能让一个会改变同一 AUT 状态的 worker 使用。禁止多个 worker 共享购物车或账号。

先做到单设备连续运行 20 次稳定，再做并行。并行会放大端口、数据、安装、网络和设备温度问题。

## 15. 失败产物

一条失败至少需要：

- pytest 用例名、开始/结束时间和断言。
- Appium Server 日志（去除本机用户名、私有路径和 Token）。
- 当前公开样例的截图。
- Appium/Driver/Python Client/ADB 版本。
- 目标设备型号、Android 大版本和样例 APK SHA-256。
- 必要时只截取目标包时间窗口内的 logcat。

`BaseScreen.save_screenshot(Path(...))` 只保存到调用方明确路径。不要无差别抓取整个设备屏幕；系统通知
可能包含隐私。失败钩子投入使用前应：

1. 专用测试机关闭通知预览。
2. 确认当前前台包是公开样例。
3. 产物目录加入忽略规则。
4. 设置短期保留和清理策略。
5. 上传前人工检查。

本项目没有默认采集 page source、全量 logcat、录屏或设备文件，避免为了“证据完整”扩大数据范围。

## 16. 分层排障手册

### 16.1 `ECONNREFUSED` / 无法连接 Server

```bash
curl --fail http://127.0.0.1:4723/status
lsof -nP -iTCP:4723 -sTCP:LISTEN
```

检查 Appium 是否启动、URL 是否误带 `/wd/hub`、端口是否被占用。

### 16.2 找不到 UiAutomator2 Driver

```bash
appium driver list --installed
appium driver doctor uiautomator2
```

确认运行 Appium 的 Node 环境与安装 Driver 的环境相同。版本管理器切换 Node 后，`APPIUM_HOME` 也可能
不是你以为的目录。

### 16.3 `unauthorized` / `offline`

先解决：

```bash
adb devices -l
```

不要先改 capabilities。真机必须解锁并确认 RSA，必要时更换支持数据传输的线缆。

### 16.4 `more than one device/emulator`

为 `.env` 填入准确 `MOBILE_UDID`。本 factory 不允许 Android 真机依赖 `deviceName` 猜测。

### 16.5 APK 安装失败

检查：

```bash
shasum -a 256 /绝对路径/样例.apk
adb -s R3XXXXXXXXX shell getprop ro.build.version.sdk
```

常见原因：APK 损坏、架构/API 不兼容、签名冲突、存储不足、设备策略禁止安装。只处理公开样例包，不要
尝试卸载或覆盖其他应用。

### 16.6 Activity 启动失败

从 APK/当前前台窗口验证包与 Activity，不能照抄旧博客：

```bash
adb -s R3XXXXXXXXX shell dumpsys window | rg mCurrentFocus
```

该命令仅应在专用测试机且公开样例位于前台时使用。ApiDemos 与 MDA 的 profile 已固定各自官方值。

### 16.7 元素找不到

按顺序确认：

1. 截图中是否已经进入预期页面。
2. 是否遇到权限弹窗、首次引导、键盘或系统更新提示。
3. Locator 在当前 app 版本是否仍唯一。
4. 是否等待了目标页独有元素。
5. 元素是否在滚动容器外。
6. context 是否仍为 `NATIVE_APP`。
7. Appium Inspector 和 Driver 版本是否匹配。

不要第一反应增加 sleep 或复制一条绝对 XPath。

### 16.8 Session 建立慢或偶发失败

- 保持设备解锁、USB 稳定、电量充足。
- 先运行 Driver doctor。
- 检查设备上旧的 UiAutomator2 server 是否异常。
- 看 Server 日志中耗时发生在 APK 安装、辅助 server 安装还是 AUT 启动。
- 不要把超时无限调大；记录阶段耗时并治理根因。

## 18. 分级练习任务

### L1：跑通与解释

- 用 ApiDemos 完成 `App → Activity` smoke。
- 画出五层调用链并为每层列一个常见错误。
- 故意把 `MOBILE_APP` 改成相对路径，记录 factory 的失败信息。
- 故意去掉 UDID，解释为什么在连接多设备时危险。

验收：默认 `pytest tests/mobile` 不创建 Session；显式开关才运行。

### L2：稳定 Page Object

- 为 ApiDemos 增加一个表单控件用例。
- 只使用稳定 ID/accessibility id，不使用绝对 XPath。
- 用显式等待替换全部固定 sleep。
- 设计一个最多五次的有界滚动失败场景。

验收：同一真机连续运行 20 次，统计通过率、P50/P95 时长与失败根因。

### L3：权限与恢复

- 在公开样例或自己创建的最小 App 中验证一次允许、一次拒绝。
- 断言权限前后的可见状态。
- 每条用例清理自己的状态，不依赖执行顺序。
- 证明测试不会访问相册、联系人、短信和其他应用。

### L4：Hybrid 与并行

- 在自己创建的公开练习 Hybrid App 中完成 context 显式等待和切换。
- 两台专用设备分别指定 UDID 和 `systemPort`。
- 故意制造端口冲突，再根据日志定位。
- 设计设备池占用/释放协议和失败产物脱敏规则。

### L5：框架拔高

- 编写 capabilities schema 和启动前校验。
- 为 app hash、版本、设备、Driver 版本生成可审计 manifest。
- 把失败分类为环境、产品、脚本、数据四类。
- 为 flaky test 设置隔离、重跑和根因关闭条件；禁止用无限重跑掩盖问题。
