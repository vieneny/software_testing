# 接口自动化全流程：从公共练习 API 到可维护测试框架

> 资料状态：2026-07-27 核对  
> 技术主线：Python 3.11+、pytest、Requests、JSON Schema  
> 实战代码：`labs/automation-practice`  
这不是一篇“发送一个 GET 请求就结束”的速查笔记。完成本章后，你应当能解释并实践：

- 如何从接口文档、业务规则和风险中设计测试，而不是把所有接口逐个调用一遍；
- 如何组织一个能重复运行、能诊断失败、不会泄露 Token 的 pytest 框架；
- 为什么超时、数据隔离、清理、契约和 Mock 是接口自动化的一部分；
- 哪些公共服务适合入门，哪些写入只是模拟，哪些数据会被其他学习者修改；
- 如何从 JSONPlaceholder 过渡到真实 CRUD、契约测试、异常注入和跨端综合项目；
- 为什么公共练习服务可以做少量功能调用，却不能拿来做压力测试。

## 1. 先认识完整测试链路

一个可维护的接口自动化项目至少包含以下链路：

```text
业务目标和风险
  → 接口契约与状态模型
  → 测试分层与用例选择
  → 环境和合成数据
  → HTTP 客户端
  → 业务服务对象
  → pytest 用例与 fixture
  → schema / 业务断言
  → 清理与隔离
  → 报告和 CI 门禁
  → 失败分析与缺陷证据
```

只封装 `requests.get()` 并不等于框架。框架的价值是统一解决重复且容易出错的问题，同时保留测试真正需要观察的 HTTP 细节。

本项目有意保留 `requests.Response`，不会在服务对象里直接返回一个被加工过的字典。测试仍然能检查：

- HTTP 状态码；
- Header 与 Cookie；
- Content-Type；
- 原始 JSON；
- 响应时间；
- 重定向历史；
- 服务端错误语义。

## 2. 练习目标怎么选

没有一个公共假 API 能同时满足 HTTP 入门、真实写入、鉴权、契约、异常注入和性能测试。合理方案是组合使用。

| 服务 | 官方定位 | 适合练习 | CRUD / 鉴权 / 契约 | 写入和状态 | 使用结论 |
|---|---|---|---|---|---|
| [JSONPlaceholder](https://jsonplaceholder.typicode.com/) | 用于 testing 和 prototyping 的免费假 API | GET、查询参数、嵌套资源、基础状态码 | 支持 CRUD 形式；无鉴权；未发布官方版本化 OpenAPI | POST、PUT、PATCH、DELETE 只模拟响应，不会真正修改服务端 | 小白第一站 |
| [DummyJSON](https://dummyjson.com/docs) | 用于 testing 和 prototyping 的结构化假数据 API | 商品、用户、购物车、分页、搜索、排序、JWT、延迟 | CRUD 形式丰富；Access/Refresh Token；未发现正式发布的版本化 OAS | 商品等写入为模拟，不持久化 | JSONPlaceholder 之后的进阶备选 |
| [Restful Booker](https://restful-booker.herokuapp.com/) | 专门学习 API 测试和工具的 playground | 真 CRUD、Token、数据链、清理、缺陷探索 | Booking CRUD 与鉴权；官方页面提供生成式 HTML 文档 | 公共实例可变，每 10 分钟恢复默认 10 条记录 | 真实生命周期主练习 |
| [Postman Echo](https://learning.postman.com/docs/reference/developer-resources/echo-api/) | Postman 官方请求回显服务 | 方法、参数、Header、认证、请求体；另有 GraphQL、gRPC、WebSocket | 无业务 CRUD | 不保存业务数据 | 诊断“客户端到底发了什么” |
| [httpbin](https://httpbin.org/) | HTTP Request & Response Service | Header、Cookie、重定向、状态码、延迟、流式响应 | 无业务 CRUD | 无业务持久化 | 建议运行维护中的本地容器 |
| [Swagger Petstore](https://github.com/swagger-api/swagger-petstore) | Swagger / OpenAPI 官方示例 | OpenAPI、Schema、内容协商、生成测试 | Pet、Order、User；OAS 3.0；规范声明 API Key 与 OAuth2 | 公共实例共享且无持久性承诺；可用官方 Docker 自托管 | 契约测试主线 |
| [WireMock](https://wiremock.org/docs/) | 开源 API Mock 测试工具 | 请求匹配、动态响应、调用验证、延迟、故障、状态机 | 配置式 Stub，不是业务数据库 | 本地完全可控；Scenario 状态可重置 | 自动化工程主线 |
| [Mockoon](https://mockoon.com/docs/latest/about/) | 本地 Mock API GUI / CLI | 可视化建模、CRUD、规则、多响应、代理和录制 | 支持 OpenAPI v2/v3 导入、v3 导出，但兼容性是部分的 | Data Bucket 在运行期间真正变化，重启恢复 | 对小白友好的 WireMock 备选 |
| [Prism](https://github.com/stoplightio/prism) | OpenAPI Mock 与验证代理 | 规范驱动 Mock、请求/响应契约验证 | OpenAPI 2、3.0、3.1 和 Postman Collection | 当前不提供业务状态持久化 | 契约优先的补充工具 |
| [Practice Software Testing](https://github.com/testsmith-io/practice-software-testing) | Web、REST API、Swagger、移动端联合测试教学项目 | 登录、商品、购物车、订单、Web/API/App 跨端验证 | 完整 REST API 和 Swagger，含多个 Sprint、故障版本 | 公共环境不是个人沙箱；官方提供 Docker 本地部署 | 最终综合项目 |

### 2.1 关于 httpbin 的版本提醒

公共 `httpbin.org` 页面目前显示 0.9.2。维护中的 [PSF/httpbin](https://github.com/psf/httpbin) 仓库明确说明：

- 它是原 `postmanlabs/httpbin` 的维护分叉；
- 公共 `httpbin.org` 并不是由 PSF 仓库驱动；
- 公共部署版本已经过时；
- 可以用 `ghcr.io/psf/httpbin` 在本地运行。

因此，HTTP 高级行为和 CI 测试应优先使用本地容器，不应把公共 httpbin 当成稳定的必过依赖。

### 2.2 关于“假写入”的关键认识

[JSONPlaceholder 官方指南](https://jsonplaceholder.typicode.com/guide/)明确说明资源不会真正更新。DummyJSON 的[产品文档](https://dummyjson.com/docs/products)也明确说明新增、修改和删除只是模拟。

这意味着：

- 可以验证请求方法、Body、Content-Type、返回状态和返回结构；
- 不应该写“创建后再查询一定能查到”的用例；
- 不能把模拟成功当成数据库真实落库；
- 真正的状态链要转向 Restful Booker、本地 Demo Shop、Mockoon CRUD 或 Toolshop。

## 3. 框架目录与职责

代码位于：

```text
labs/automation-practice/
├── pyproject.toml
├── src/qa_learning/
│   ├── 运行配置.py
│   └── api/
│       ├── 接口客户端.py
│       ├── 响应数据契约.py
│       ├── 公开占位文章接口.py
│       ├── 公开预订服务接口.py
│       └── 本地演示商城接口.py
└── tests/
    ├── conftest.py
    └── api/
        ├── 测试_接口客户端.py
        ├── 测试_公开占位文章接口.py
        ├── 测试_公开预订服务接口.py
        └── 测试_本地演示商城接口.py
```

各层职责如下。

### 3.1 `运行配置.py`：环境差异

配置层从环境变量读取 Base URL，并提供安全的公开默认值：

```text
JSONPLACEHOLDER_URL
RESTFUL_BOOKER_URL
```

代码中不硬编码公司域名、个人 Token 或本机文件路径。不同环境只修改环境变量，不复制一套测试代码。

### 3.2 `接口客户端.py`：HTTP 横切能力

`ApiClient` 统一实现：

- Base URL 与相对路径拼接；
- 每个请求都显式设置超时；
- Request / Response 日志；
- Authorization、Cookie、Token、Password、Secret 等字段脱敏；
- 状态码断言；
- JSON Schema 断言；
- 失败时输出经过脱敏的诊断信息；
- 禁止把绝对 URL 传进已有 Client，防止一次测试意外切换到另一台服务器。

它刻意不做两件事：

1. 不自动 `raise_for_status()`：接口测试需要主动验证 400、401、404、409、422、500；
2. 不自动重试：隐藏重试可能让真实故障变成假通过，也可能把一个 POST 重复提交多次。

### 3.3 服务对象：表达业务操作

服务对象把：

```python
client.post("/booking", json=payload)
```

表达为：

```python
api.create_booking(payload)
```

它只负责 URL、方法、参数和认证方式，不在内部偷偷断言。测试仍负责说明“这个场景期待什么”。

### 3.4 `响应数据契约.py`：可复用契约

JSON Schema 用于验证：

- 必需字段；
- 字段类型；
- 数值范围；
- 数组元素；
- 嵌套对象；
- 是否允许额外字段。

Schema 断言不等于全部测试。以下规则仍需要业务断言：

- 订单总金额是否等于单价 × 数量；
- 查询结果是否属于指定用户；
- 使用相同幂等键是否返回同一订单；
- 删除后是否查询不到；
- 更新一个字段时其他字段是否保持不变。

```bash
pytest tests/api/测试_接口客户端.py -q
```

## 7. JSONPlaceholder：读操作与模拟写入

### 7.1 读取与过滤

对应代码：

```python
response = api.list_posts(user_id=1)
client.assert_status(response, 200)
posts = client.assert_json_schema(
    response,
    JSONPLACEHOLDER_POST_LIST_SCHEMA,
)
assert posts
assert {post["userId"] for post in posts} == {1}
```

这里有三层断言：

1. HTTP 层：返回 200；
2. 契约层：每条 Post 都符合 Schema；
3. 业务层：查询 `userId=1` 时不能混入其他用户。

只断言 200 会漏掉“过滤条件被忽略”的缺陷。

### 7.2 模拟创建

测试使用随机但完全虚构的标题：

```python
synthetic_title = f"qa-learning-{uuid4().hex[:10]}"
```

创建后会得到 201 和一个新 ID，但再次查询该 ID 返回 404。这个用例不是在批评服务，而是在证明测试理解了目标环境的契约：这里的 POST 是模拟，不是持久化。

运行：

```bash
pytest tests/api/测试_公开占位文章接口.py \
  --run-public-api \
  -q
```

可以通过环境变量切到自己授权的兼容服务：

```bash
JSONPLACEHOLDER_URL=http://127.0.0.1:3000 \
pytest tests/api/测试_公开占位文章接口.py \
  --run-public-api \
  -q
```

如果本地服务会真正持久化，那么“模拟写入”测试应当调整或标记为只适用于官方公共目标，而不是盲目改成通过。

## 8. Restful Booker：真实 CRUD 和 finally 清理

Restful Booker 官方首页说明：

- 它专门供学习 API 测试；
- 支持 Create、Read、Update、Delete；
- 有 Authentication；
- 故意放入了一些缺陷；
- 公共实例每 10 分钟重置。

完整用例执行：

```text
POST /auth
  → POST /booking
  → GET /booking/{id}
  → PATCH /booking/{id}
  → DELETE /booking/{id}
  → GET /booking/{id} 期待 404
```

### 8.1 合成数据

测试数据只包含虚构内容：

```python
{
    "firstname": "Learn<随机运行号>",
    "lastname": "Tester",
    "totalprice": 321,
    "depositpaid": True,
    "bookingdates": {
        "checkin": "2030-04-10",
        "checkout": "2030-04-12"
    },
    "additionalneeds": "Synthetic breakfast"
}
```

不要把自己、同事、客户或公司的姓名、邮箱、订单、日期和备注放进公共练习服务。

### 8.2 动态关联

创建返回的 `bookingid` 必须保存下来，后续查询、更新和删除都使用同一个 ID。不要在测试里写死公共实例中的某个 ID：

```python
created = client.assert_json_schema(
    create_response,
    RESTFUL_BOOKER_CREATE_SCHEMA,
)
booking_id = created["bookingid"]
```

### 8.3 Token 脱敏

Token 通过 Cookie 发送：

```python
{"Cookie": f"token={token}"}
```

`ApiClient` 会在日志里显示 Cookie 已存在，但值会替换为：

```text
***REDACTED***
```

测试报告和失败截图中也不应该输出完整 Token。

### 8.4 `finally` 清理

清理不能只放在用例最后一行。中间某个断言失败后，最后一行不会执行。

正确结构是：

```python
booking_id = None
try:
    # 创建、查询、更新和断言
finally:
    if booking_id is not None:
        # 最佳努力删除，不掩盖原始失败
```

当前实战在正常路径中完成 DELETE；如果正常路径提前失败，`finally` 会再次尝试清理。网络清理错误不会覆盖原始断言失败。

运行：

```bash
pytest tests/api/测试_公开预订服务接口.py \
  --run-public-api \
  -q
```

公共实例可能正被其他学习者使用，也可能在执行过程中重置。因此：

- 不断言全局 Booking 总数；
- 不依赖固定 ID；
- 不依赖执行顺序；
- 每次生成唯一合成数据；
- 尽快完成一个生命周期；
- 失败时先区分代码缺陷、目标服务故意缺陷、公共环境重置和网络故障。

### 9.3 幂等性用例

同一个 Payload 和同一个 `Idempotency-Key` 连续发送两次：

```python
first_response = api.create_order(payload, idempotency_key=key)
second_response = api.create_order(payload, idempotency_key=key)
```

断言：

- 两次都是约定状态；
- 两次订单 ID 相同；
- 金额正确。

继续扩展：

1. 同一个键、不同数量应返回 409；
2. 缺少键应返回 422；
3. 键长度小于 8 应返回 422；
4. 数量为 0、11、超过库存分别验证；
5. 并发使用两个不同幂等键是否可能突破库存。

最后一项可能暴露教学服务的设计限制。测试发现风险不代表必须立即把服务改成生产系统，先写清证据、影响和建议。

## 10. 断言策略

### 10.1 状态码

明确写出期望：

```python
client.assert_status(response, 200)
```

允许多个契约状态时：

```python
client.assert_status(response, {200, 204})
```

不要为了“让测试绿”而允许所有 `2xx`。201、202、204 表达的语义并不相同。

### 10.2 Header

常见断言包括：

- `Content-Type` 是否为预期媒体类型；
- Cache-Control 是否符合缓存策略；
- Location 是否指向创建资源；
- Correlation-ID 是否可用于追踪；
- Retry-After 是否在 429 / 503 时返回；
- ETag 与条件请求是否一致。

### 10.3 Schema

Schema 检查结构，业务断言检查含义。两者需要同时存在。

错误示例：

```python
assert response.json()
```

这只证明 JSON 是非空真值。

更有价值的断言：

```python
product = client.assert_json_schema(response, PRODUCT_SCHEMA)
assert product["stock"] >= requested_quantity
```

### 10.4 列表不变量

分页、过滤和排序应验证不变量：

- `len(items) <= limit`；
- 所有结果都满足过滤条件；
- 排序键单调；
- 页之间没有意外重复；
- `total` 与当前页大小不是同一个概念；
- 空结果仍返回约定结构。

### 10.5 负向测试

至少覆盖：

- 缺失必填字段；
- null、空字符串、空数组；
- 错误类型；
- 数值上下边界；
- 不存在的资源；
- 无 Token、错误 Token、过期 Token；
- 无权限；
- 重复提交；
- 状态不允许的操作；
- 不支持的 Content-Type。

负向测试不是“随便传乱码”，而是从输入模型、权限模型和状态模型推导。

## 11. 数据隔离与可重复性

### 11.1 唯一标识

公开或共享目标使用运行 ID：

```python
run_id = uuid4().hex[:8]
```

把它加入虚构名称、幂等键或测试描述，以降低碰撞。

### 11.2 不断言共享全局状态

以下断言在共享环境通常脆弱：

```python
assert len(all_bookings) == 10
```

其他用户、新一轮重置和后台任务都会改变数量。

应断言自己创建的实体和局部关系。

### 11.3 测试可乱序

每个测试应当：

- 自己准备前置数据；
- 不依赖另一个测试先运行；
- 自己清理；
- 可以单独运行；
- 重复运行不会污染后续测试。

不要用 `test_01_create`、`test_02_query` 强行建立顺序。业务旅程应该在同一个 E2E 测试或显式 fixture 中表达。

### 11.4 随机但可诊断

随机数据只用于避免碰撞，不应用来产生不可重现的复杂业务输入。属性测试或模糊测试需要记录随机种子和最小失败样本。

## 12. WireMock：把不可控依赖变成可控场景

公共服务不能稳定制造每一种错误。本地 WireMock 可以。

官方 Docker 文档当前使用稳定示例 `wiremock/wiremock:3.13.2`；WireMock 4 仍标记为 Beta。学习项目应固定已验证版本，定期升级，不直接使用漂移的 `latest`。

启动：

```bash
docker run --rm \
  --name qa-learning-wiremock \
  -p 8089:8080 \
  -v "$PWD/mocks/wiremock:/home/wiremock" \
  wiremock/wiremock:3.13.2
```

### 12.1 延迟与 503

`mappings/payment-unavailable.json` 示例：

```json
{
  "request": {
    "method": "POST",
    "urlPath": "/payments"
  },
  "response": {
    "status": 503,
    "fixedDelayMilliseconds": 1200,
    "headers": {
      "Content-Type": "application/json",
      "Retry-After": "2"
    },
    "jsonBody": {
      "code": "payment_temporarily_unavailable"
    }
  }
}
```

可以验证：

- 客户端的读取超时；
- 503 是否进入明确的失败分支；
- Retry-After 是否被读取；
- 是否只对允许重试的操作退避；
- 日志是否保留 Trace ID；
- 最终错误是否可诊断。

### 12.2 请求匹配

WireMock 可以按以下条件匹配：

- URL 和方法；
- Query 参数；
- Header；
- Cookie；
- JSONPath；
- Body 正则；
- multipart；
- JWT。

例如只有带正确幂等键和商品 ID 才返回 201，其他请求返回 400。这样可以证明客户端发出的请求契约，而不只是证明客户端能解析响应。

### 12.3 调用验证

Admin API 能验证调用次数：

```text
POST /__admin/requests/count
```

典型场景：

- GET 遇到一次 503 后最多重试两次；
- POST 没有幂等键时不得自动重试；
- 熔断打开后不再调用下游；
- 同一个业务操作只发送一次支付请求。

### 12.4 状态机

[WireMock Stateful Behaviour](https://wiremock.org/docs/stateful-behaviour/)说明 Scenario 是一个状态机。

可模拟：

```text
库存初始为 1
  → 第一次下单返回 201
  → 状态切换为 SOLD_OUT
  → 第二次下单返回 409
```

还可以模拟异步订单：

```text
CREATED → PROCESSING → COMPLETED
```

测试轮询间隔、最大等待时间和终止条件时，不需要等待一个真实系统偶然出现这些状态。

## 13. Mockoon：可视化 Mock 路线

Mockoon 更适合第一次接触服务虚拟化的同学。

根据官方文档：

- [CRUD Route](https://mockoon.com/docs/latest/api-endpoints/crud-routes/)会自动生成 GET、POST、PUT、PATCH、DELETE；
- Data Bucket 的状态会在同一服务进程的请求之间保留；
- 运行时变化不会写回配置文件；
- 重启服务后恢复初始数据；
- 支持过滤、搜索、排序和分页；
- [OpenAPI 导入/导出](https://mockoon.com/docs/latest/openapi/import-export-openapi-format/)的兼容是部分的，不能假设规范每个字段都会完整转换；
- 多响应可以按规则、随机或顺序返回。

建议练习：

1. 创建 `products` Data Bucket；
2. 建立 CRUD Route；
3. POST 新商品；
4. GET 查询并验证写入；
5. PATCH 库存；
6. 按价格过滤和分页；
7. 重启后验证恢复；
8. 增加 Header 规则：缺少 Bearer Token 返回 401；
9. 增加随机/顺序 500，观察测试是否会产生不稳定；
10. 将随机错误改为确定性规则，使回归可重复。

## 14. 契约测试：Swagger Petstore 与 Prism

Swagger Petstore 当前公开规范：

```text
https://petstore3.swagger.io/api/v3/openapi.json
```

核对时规范为 OpenAPI 3.0.4，API 版本为 1.0.27。官方仓库提供 Maven 和 Docker 运行方式。

契约测试可以检查：

- 规范文件本身是否合法；
- 每个 operation 是否有唯一 `operationId`；
- 必填字段和枚举；
- 请求是否符合规范；
- 实际状态码是否在 responses 中；
- 实际响应媒体类型和 Schema；
- 向后兼容性；
- 示例能否执行；
- 规范与真实实现是否漂移。

不要把 Petstore 规范里声明的 OAuth2 当成生产安全实现模板。示例服务器主要用于演示 OpenAPI 工具链。

### 14.1 Prism 的两个模式

Prism 官方仓库提供：

```text
prism mock <openapi-file>
```

从规范生成 Mock Server。

```text
prism proxy <openapi-file> <real-api-url>
```

把请求转发到真实服务，同时检查请求和响应是否符合规范。

Prism 适合回答“实现是否符合契约”，WireMock 更适合回答“客户端在各种确定性异常下是否行为正确”。两者不是简单替代关系。

## 16. 公共服务禁止压测

截至 2026-07-27，没有在上述公共实例的官方资料中找到允许公众进行负载、压力、峰值或长稳测试的明确授权。

“免费用于练习”不等于“允许无限并发压测”。

以下目标只能进行少量串行功能调用：

- JSONPlaceholder；
- DummyJSON；
- Restful Booker 公共实例；
- Postman Echo；
- 公共 httpbin；
- 公共 Swagger Petstore；
- 公共 Toolshop。

不要对它们运行：

- pytest-xdist 并发；
- HTTPX 批量并发；
- k6；
- JMeter；
- Locust；
- 压力、峰值、容量或长稳测试；
- 绕过 429 的脚本。

性能练习只能针对：

- 自己本地运行的 Demo Shop；
- 自己本地运行的 Toolshop；
- 本地 Petstore；
- 本地 httpbin；
- 本地 WireMock / Mockoon；
- 其他明确归自己控制或获得书面授权的环境。

Mock 服务的压测结果只能证明：

- 压测脚本能运行；
- 阈值能触发；
- 指标和报告链路正常；
- 客户端在并发下的连接池行为。

它不能代表真实生产系统容量。

## 17. 20 个递进练习

下面任务按学习难度排列。每个任务都应交付代码、运行命令、结果和一段限制说明。

### L1：HTTP 与基础断言

1. **查询参数和编码**  
   用 Postman Echo 验证单值、重复参数、空值、空格和中文编码。

2. **Header 与关联 ID**  
   发送 `X-Correlation-ID`，确认服务端收到；日志保留关联 ID 但隐藏 Authorization。

3. **请求体格式**  
   对比 JSON、form-urlencoded 和 multipart；错误 Content-Type 应产生明确失败。

4. **状态码参数化**  
   在本地 httpbin 参数化 200、201、204、400、401、403、404、429、500。

5. **Cookie 与重定向**  
   使用 Session 保存 Cookie，验证重定向历史和最终 URL。

6. **超时分类**  
   在本地 delay 端点分别触发连接和读取超时，输出可诊断错误。

### L2：资源、分页和鉴权

7. **父子资源**  
   JSONPlaceholder 查询用户文章和文章评论，验证关联 ID。

8. **模拟写入语义**  
   JSONPlaceholder POST 得到 201 后再次 GET，证明资源没有持久化。

9. **分页不变量**  
   DummyJSON 验证 `limit`、`skip`、`total`、字段选择和页间不重复。

10. **搜索、过滤和排序**  
    DummyJSON 验证所有结果满足关键词，价格排序单调。

11. **JWT 生命周期**  
    DummyJSON 完成登录、`/auth/me`、Refresh、无 Token、错误 Token 和过期 Token。

12. **延迟与重试边界**  
    DummyJSON delay 只用于少量功能测试；验证超时，不并发压测。

### L3：真实状态和清理

13. **Booking 完整 CRUD**  
    完成创建、读取、PATCH、删除和删除后查询。

14. **鉴权负向场景**  
    比较正确 Token、缺失 Cookie、错误 Token 和公开 Basic Auth 行为。

15. **共享环境隔离**  
    为姓名加入运行 ID，通过 firstname/lastname 找到自己创建的数据，不断言全局总数。

16. **缺陷证据**  
    探索 Restful Booker 故意缺陷，用 `xfail(strict=True)` 或缺陷记录表达，不把错误行为写成正常契约。

### L4：契约、Mock 和韧性

17. **OpenAPI 契约**  
    下载 Petstore OAS，验证规范版本、Schema 和实际响应；保存规范来源和核对日期。

18. **WireMock 请求验证**  
    按 Header、Query、JSONPath 匹配，并通过 Admin API 断言调用次数。

19. **状态机和故障注入**  
    模拟库存变化、429、503、延迟和断连；验证重试、退避和最大等待。

20. **跨端综合项目**  
    用 Toolshop 设计 API 准备数据、Web 执行业务、Android/iOS 验证结果的旅程；公共环境低频，本地环境运行完整回归。

## 20. 常见问题

### 公共测试为什么全部 Skip？

这是预期行为。加显式授权：

```bash
pytest tests/api -m external --run-public-api -q
```

### 为什么 Restful Booker 刚创建的数据突然不见了？

公共实例每 10 分钟重置，也可能被其他学习者修改。缩短单个生命周期，使用唯一数据，不依赖全局状态。本地自托管用于稳定回归。

### 为什么 JSONPlaceholder POST 成功后查不到？

它的写入本来就是模拟。详见官方 Guide。这是环境契约，不是测试框架失败。

### 为什么不用固定 `sleep(3)`？

固定休眠既慢又不可靠。接口调用应使用明确 timeout；异步业务应轮询状态并设置最大等待时间。

### Schema 断言为什么没检查日期格式？

JSON Schema 的 `format` 是否强制执行取决于 Validator 和 FormatChecker 配置。不能看到 `"format": "date"` 就假设已经验证。课程进阶任务应显式接入 FormatChecker 并为非法日期编写失败测试。

### 是否应该同时学 Requests 和 HTTPX？

先用 Requests 掌握同步 HTTP、Session、Fixture 和框架分层。进阶再增加 HTTPX Client / AsyncClient，重点学习连接池、异步并发和 timeout 模型。不要为了“技术更多”在同一初级项目中维护两套重复实现。
