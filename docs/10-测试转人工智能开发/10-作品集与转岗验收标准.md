# 人工智能开发作品集与转岗验收标准

> 原则：作品集证明“能独立交付、能验证、能解释”，不是证明看过多少课程或安装过多少框架。

## 一、作品集应该回答的五个问题

面试官或开源协作者应能从仓库直接找到：

1. 你解决了什么具体问题？
2. 为什么这样设计，而不是另一种方案？
3. 系统在正常、异常和攻击场景下如何工作？
4. 你如何证明结果的质量、性能和安全？
5. 别人能否在不购买云服务的情况下复现？

如果只能看到页面截图、聊天示例和技术名词，作品还不具备转岗说服力。

## 二、项目阶梯

### 项目一：普通后端服务

建议题目：**合成缺陷与测试计划管理服务**。

必须有：

- REST/OpenAPI；
- 用户、角色和资源所有权；
- PostgreSQL/MySQL；
- 数据库迁移、事务和索引；
- 输入校验、统一错误、分页和幂等；
- 单元、接口和真实数据库集成测试；
- Docker 与 CI；
- 故障复盘。

它证明你首先是一名能开发普通软件的工程师。

### 项目二：结构化 AI 功能

建议题目：**公开需求测试点生成服务**。

必须有：

- 模型 Provider 抽象；
- Prompt 和模型版本；
- JSON Schema/结构化输出；
- Mock、本地模型和可选云模型；
- 超时、429、断流、坏 JSON；
- Token/成本限制；
- 确定性测试与小型评测集。

它证明你不是只在 Controller 中转发模型文本。

### 项目三：RAG 知识助手

建议题目：**公开软件测试知识助手**。

必须有：

- 公开来源和许可证清单；
- 可重放 ETL；
- Chunk、Embedding、pgvector；
- 元数据过滤、引用、拒答；
- 文档更新/删除；
- 黄金问题；
- 检索与生成分层评测；
- 恶意文档测试。

它证明你能处理数据和质量，而不只是 Prompt。

### 项目四：受控 Agent

建议题目：**合成缺陷分诊 Agent**。

必须有：

- 明确状态图；
- MCP/Tool Schema；
- 只读与写工具分离；
- 服务端授权；
- 人工审批；
- 幂等、最大步数、超时、恢复；
- Trace 和任务指标；
- Prompt Injection、越权和资源滥用回归。

它证明你能控制副作用和失败。

### 项目五：综合毕业作品

把前四个项目合并成[公开软件测试知识助手与缺陷分诊 Agent](08-智能测试助手综合项目.md)，不要为了“架构感”一开始拆成很多微服务。

## 三、每个仓库必须有的证据

### 3.1 README

至少包含：

```text
项目目标
用户与场景
非目标
数据准备方式
架构图
技术选型与版本
本地运行
测试与评测
故障注入
安全控制
演示步骤
已知限制
路线图
来源与许可证
```

### 3.2 可复现运行

- 无云 Key 可跑 Mock 基线；
- 一条命令启动必要服务；
- 固定依赖和镜像版本；
- 空数据库可初始化；
- 示例配置无真实凭据；
- 运行失败有排查说明；
- ARM64/x86 差异有记录。

### 3.3 测试与质量

- 单元测试；
- 集成测试；
- Provider/Tool 契约测试；
- 端到端关键旅程；
- AI 黄金集与报告；
- 安全回归；
- 性能与成本实验；
- 失败样本和残余风险。

### 3.4 工程决策

至少写三份 ADR（架构决策记录）：

1. 为什么选 Spring AI 或 LangGraph；
2. 为什么先选 pgvector；
3. 为什么写工具需要人工批准。

每份记录背景、方案、决定、后果和复审条件。

### 3.5 变更历史

- commit 小而清晰；
- Issue/任务可追踪；
- 版本标签；
- 变更日志；
- 一次依赖升级记录；
- 一次线上式故障演练和修复。

## 四、100 分评分表

| 维度 | 分值 | 满分证据 |
|---|---:|---|
| 问题与范围 | 8 | 用户、目标、非目标、数据边界清楚 |
| 普通后端 | 14 | API、数据、事务、权限、错误、幂等完整 |
| AI 应用 | 10 | Provider、结构化、流式、预算和失败处理 |
| RAG | 12 | 数据流水线、过滤、引用、拒答、更新和分层评测 |
| Agent/MCP | 12 | 状态、工具契约、授权、审批、恢复和终止 |
| 测试与评测 | 14 | 确定性测试、黄金集、人工校准、门禁 |
| 安全与隐私 | 10 | 威胁模型、硬门禁和脱敏策略 |
| 可观测与性能 | 8 | Trace、延迟、Token、错误、成本和负载报告 |
| 可复现与交付 | 7 | Docker、CI、版本、一键运行 |
| 表达与复盘 | 5 | README、ADR、演示、限制、故障复盘 |

判断：

- 85～100：可以作为核心投递作品；
- 70～84：可以展示，但应补最弱的两项；
- 50～69：更像课程作业；
- 低于 50：先完成普通后端和可复现门槛。

任何以下问题都直接判为不合格，不受总分影响：

- 含公司或客户资料；
- 含真实密钥；
- 简历指标不可复现；
- Agent 可未经授权执行真实写操作；
- 对第三方进行未授权扫描、压测或红队；
- 复制开源代码却未遵守许可证或未说明来源。

## 五、指标如何写才诚实

### 不要这样写

- “准确率提升 80%”；
- “效率提高 10 倍”；
- “企业级高并发”；
- “零幻觉”；
- “精通 10 种 Agent 框架”。

这些说法没有数据集、基线、环境和方法就不可验证。

### 推荐写法

```text
在自建的 50 条公开测试知识黄金集上，对固定模型和 Prompt 比较两种
Chunk 策略；记录 Recall@5、引用正确性、p95 和 Token。结果、失败样本、
运行配置及脚本均在仓库中，结论只适用于该数据集和本机环境。
```

```text
使用 WireMock 注入 429、500、读取超时和 SSE 断流，验证仅可重试错误
采用有上限退避；JUnit 回归覆盖重试上限、客户端取消和降级路径。
```

如果尚未取得数字，可以写“建立并运行了……”，不要捏造提升比例。

## 六、简历项目描述模板

### Java AI 应用

```text
公开软件测试知识助手（个人开源项目）
- 使用 Spring Boot、Spring AI、PostgreSQL/pgvector 实现公开资料的
  导入、检索、引用式问答与无证据拒答；
- 用 Testcontainers 验证真实数据库集成，以 WireMock 覆盖模型 429、
  超时、断流和结构化输出损坏；
- 建立版本化黄金集，分开评估检索与生成，并用 OpenTelemetry 关联
  模型、检索、工具和 HTTP Trace；
- 数据仅来自公开资料与合成样本，仓库提供来源、许可证、Docker 和 CI。
```

### Agent 开发

```text
合成缺陷分诊 Agent（个人开源项目）
- 使用明确状态图编排输入校验、分类、检索、证据检查、人工审批和模拟工单；
- 通过 MCP 暴露只读公开资料工具，写工具采用服务端授权、幂等、审计和
  Human in the Loop；
- 测试工具参数、超时、恢复、Prompt Injection、越权与最大步数；
- 提供端到端 Trace、任务成功/失败分类和可复现评测报告。
```

只保留自己真正实现并能讲清的技术点。

## 七、十分钟演示脚本

### 第 0～1 分钟：问题与边界

- 为什么做；
- 谁使用；
- 哪些功能明确不做。

### 第 1～3 分钟：架构

- 前后端、数据库、模型、RAG、MCP、评测；
- 主线和可替换边界；
- 一个关键 ADR。

### 第 3～5 分钟：正常旅程

- 导入公开资料；
- 带引用问答；
- 缺陷分诊；
- 审批模拟写入。

### 第 5～7 分钟：失败旅程

- 触发无证据拒答；
- 注入 429 或断流；
- 展示越权工具被拒绝；
- 服务重启后恢复。

### 第 7～9 分钟：证据

- 自动化测试；
- 黄金集报告；
- Trace；
- p95/Token/成本；
- 安全回归。

### 第 9～10 分钟：限制与下一步

- 当前数据集和模型的限制；
- 尚未解决的问题；
- 什么证据出现后才会引入 Qdrant、多 Agent 或微调。

演示必须可以在本地重复，不用剪辑隐藏错误。

## 八、面试自查问题

### 普通开发

- 为什么选择这个事务边界？
- 幂等如何保证？应用和数据库分别做什么？
- 这个索引如何由查询模式决定？
- 服务升级失败如何回滚？
- 怎样处理并发更新？

### AI 应用

- Temperature 降为 0 是否等于确定性？
- 结构化输出失败如何处理？
- 为什么不是所有错误都重试？
- Provider 切换时哪些语义不兼容？
- Prompt 和模型如何版本化？

### RAG

- Recall@k 低和答案不忠实如何区分？
- Chunk 大小如何实验，不靠经验拍板？
- 如何处理更新、删除、权限过滤和引用？
- 为什么先 pgvector，不直接上 Milvus？
- 无答案时如何评测拒答？

### Agent

- 为什么使用 Agent，而不是普通工作流？
- 最大步数、超时和预算在哪里执行？
- 工具调用如何鉴权？
- 如何避免成功执行后重试造成重复副作用？
- Checkpoint 恢复会不会重复调用工具？

### 评测与安全

- 模型裁判有哪些偏差？
- 黄金集如何抽样、审核和版本化？
- 间接 Prompt Injection 从哪里进入？
- Trace 为什么不能默认记录全部 Prompt？

如果无法回答，就把问题转成下一次 ADR、测试或故障实验。

## 九、开源贡献证据

不要求一开始提交大功能。可以：

- 复现并报告文档问题；
- 补充最小示例测试；
- 修正文档、类型或错误信息；
- 为开源项目增加版本兼容说明；
- 参与 Issue 讨论并提供最小复现；
- 翻译前先确认项目是否接受及许可证要求。

每次贡献记录：

- 问题；
- 复现；
- 官方贡献规则；
- 你的改动；
- 测试；
- 上游反馈；
- 学到的工程实践。

不要为了作品集刷无意义提交。

## 十、投递前最后检查

### 代码

- [ ] 默认分支可构建；
- [ ] CI 通过；
- [ ] 依赖固定；
- [ ] 无高危已知漏洞；
- [ ] 无密钥和个人隐私；
- [ ] 许可证说明完整。

### 运行

- [ ] Mock 模式无需付费账号；
- [ ] 数据库可自动初始化；
- [ ] 示例数据完全合成；
- [ ] 失败提示可理解；
- [ ] 清理方法明确。

### 证据

- [ ] 架构图；
- [ ] API 文档；
- [ ] 测试报告；
- [ ] AI 评测报告；
- [ ] 安全报告；
- [ ] 性能/成本报告；
- [ ] Trace 截图或导出；
- [ ] 故障复盘；
- [ ] 已知限制。

### 表达

- [ ] 10 分钟演示完成；
- [ ] 能脱离文稿讲清主链路；
- [ ] 能解释三项取舍；
- [ ] 能展示失败而不慌乱；
- [ ] 简历每个指标都可复现。

## 十一、转岗就绪判断

满足以下条件再集中投递：

1. 普通后端关卡全部通过；
2. 至少一个 RAG 或 Agent 核心作品达到 85 分；
3. 能现场修改一个小功能并补测试；
4. 能定位一次模型、检索、工具或数据库故障；
5. 能解释开发与测试的责任差异；
6. 有一份可复现的公开演示；
7. 已根据目标岗位调整简历，而不是用同一份简历海投；
8. 对不会的内容能明确边界，不伪装“精通”。

转岗不是丢掉测试经历，而是把它升级为开发系统、证明系统可靠的能力。
