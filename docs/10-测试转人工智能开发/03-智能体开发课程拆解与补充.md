## 3. 课程页面的整体定位

### 3.1 页面给出的主线

课程页面将“Agent 智能体开发”作为核心主线，并展示了以下知识链：

```text
Python
  ↓
MySQL 与数据分析
  ↓
机器学习与深度学习
  ↓
大模型基础与提示词工程
  ↓
LangChain、LangGraph、MCP、FastAPI、RAG
  ↓
微调、推理服务与部署
  ↓
五个综合项目
```

页面宣称课程目标包括：

- 掌握 Python、MySQL 和数据分析；
- 理解机器学习、深度学习并使用 PyTorch；
- 理解大模型架构和提示词工程；
- 使用 LangChain、LangGraph 和 MCP 开发智能体；
- 完成五个项目并具备部署能力。

这些是课程页面的目标描述，不等于学习者仅完成观看后就自动具备相应能力。真正的能力需要通过独立编码、测试、部署和讲解来验收。

### 3.2 页面列出的适合人群

课程页面明确列出：

- 计算机相关专业学生；
- 希望转向 AI 的传统开发工程师；
- 数据分析师和算法工程师；

测试工程师没有被单列，但测试工作中常见的 Python、API、SQL、异常分析和自动化经验可以迁移到 Agent 开发。

更适合测试工程师的并行方式是：


这样可以避免长时间停留在 Notebook 而没有开发交付物。

#### RAG 不能只测“能否回答”

至少分开评估：

1. 文档是否解析完整；
2. 切片是否保留语义；
3. 正确证据是否被召回；
4. 排序是否把正确证据放在前面；
5. 回答是否忠实于证据；
6. 引用能否定位原文；
7. 无答案问题是否拒答；
8. 恶意文档是否能劫持系统指令；
9. 不同租户数据是否隔离；
10. 更新或删除文档后索引是否同步。

### 7.1 转岗优先级建议

对测试转 Agent 应用开发，推荐顺序是：

1. 先会稳定调用模型；
2. 再会做 RAG 和工具调用；
3. 再补可观测性、评测、安全和部署；
4. 最后根据实际项目需要做微调。

不要因为课程有微调章节，就把微调当作所有 Agent 项目的默认方案。很多问题应优先通过数据清洗、检索、提示词、工具和流程设计解决。

### 7.2 微调前的准入条件

只有能回答以下问题，才进入微调：

- 基线模型哪里不满足要求；
- RAG 或工具为什么不能解决；
- 训练数据的来源和许可是什么；
- 如何划分训练、验证和测试集；
- 如何避免测试集泄露；
- 如何度量微调前后差异；
- 失败时如何回滚；
- 推理成本是否可以接受。

#### 独立补充

- 记录审计日志；
- 不把原始敏感数据发送给模型。

#### 独立补充

多 Agent 不是越多越好。拆分前应先证明：

- 单 Agent 已经无法稳定完成任务；
- 子任务拥有清晰的输入输出；
- 每个子 Agent 的工具权限可以隔离；
- 调度失败后可以恢复；
- 总调用次数和成本可控；
- 最终结论可以追溯到来源。

- 一个带数据库和鉴权的 FastAPI 服务；
- 一个有引用和离线评测集的 RAG；
- 一个包含人工审批的 LangGraph Agent；
- 一个只暴露最小权限工具的 MCP 服务；
- 一套模型和工具 Mock 测试；
- 一套 Prompt Injection 和越权测试；
- 一套 Trace、延迟和成本观测；
- 一次 Docker 化部署；
- 一份架构说明；
- 一份测试报告；
- 一次从零演示和讲解。

- 为什么需要 Agent，而不是普通函数；
- 为什么需要 RAG，而不是微调；
- 为什么选择当前向量库；
- 如果模型超时怎么办；
- 如果工具重复执行怎么办；
- 如果知识库里有恶意指令怎么办；
- 如果模型升级导致回归怎么办；
- 如何证明改动让系统变好；
- 如何防止数据被发往不允许的服务。
