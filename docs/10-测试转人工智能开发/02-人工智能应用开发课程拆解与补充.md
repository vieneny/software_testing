## 2. 课程的真实定位

课程页面给出的主线可以概括为：

```text
Java 语言与 JVM
    ↓
数据库、前端与 Spring 企业开发
    ↓
Spring AI 与 LangChain4j
    ↓
RAG、工具调用、知识库与 Agent
    ↓
微服务、中间件、容器与企业级项目
```

它不是单纯的“大模型 API 调用课”，也不是算法研究或模型训练课程。更准确的定位是：

> 使用 Java 和 Spring 生态构建带有大模型能力的企业应用。

课程页面列出的目标岗位方向包括：

- Java 开发工程师；
- Java 全栈工程师；
- 人工智能应用开发工程师；
- 智能体开发工程师。

对测试工程师而言，这条路线最有价值的地方是：保留质量工程优势，同时补齐业务开发与人工智能工程能力。

### 2.1 页面明确列出的适合人群

| 人群 | 页面描述 | 对测试转开发者的解释 |
| --- | --- | --- |
| 零基础小白 | 对编程感兴趣，希望快速入门 Java | 可以学习，但应预留更多环境、计算机基础和编码训练时间 |
| 转行开发者 | 有其他语言基础，希望转向 Java | Python/JavaScript 测试脚本经验可以迁移，但必须补 Java 类型系统和工程规范 |
| 传统 Java 开发者 | 希望系统学习人工智能开发 | 可直接从 Spring AI、LangChain4j 和生产化能力切入 |
| 计算机专业学生 | 希望获得贴近企业的实战技能 | 应以能运行、能解释、能测试的项目作为学习证据 |
| 技术负责人或创业者 | 需要技术选型和团队建设认知 | 更关注成本、安全、边界和系统架构 |

测试工程师并未在页面中单独列出，但从能力结构看，接口测试、自动化、SQL、性能分析、问题定位和质量风险意识都可以直接迁移。

## 3. 八个阶段的课程拆解

以下“课程页面内容”均来自课程唯一事实来源，不添加页面没有写出的课程承诺。

## 3.1 第一阶段：JavaSE 基础与人工智能工具赋能

### 课程页面明确内容

Java 核心基础：

- 开发环境搭建与 IntelliJ IDEA 使用；
- 数据类型、常量、变量和运算符；
- 流程控制、数组和方法；
- 面向对象：封装、继承、多态、接口和抽象类；
- 常用 API：`String`、包装类、日期时间和 `BigDecimal`。

人工智能工具辅助：

- IDEA 人工智能插件、Cursor、TRAE 的安装和配置；
- 代码生成和优化；
- 辅助重构与代码审查；
- 智能调试与排错；
- 自动生成单元测试；
- 辅助编写文档；
- 辅助学习和知识探索。

Java 高级部分：

- 异常处理；
- `List`、`Set`、`Map` 等集合及源码解析；
- Lambda 和 Stream；
- 文件与 IO；
- 多线程和并发；
- 网络编程；
- 枚举、反射、注解和动态代理；
- 近年 Java 新特性；
- JVM。

### 测试工程师可迁移能力

- 已有测试脚本经验可以迁移到变量、流程控制、函数和异常处理。
- 自动化框架中的数据驱动、配置读取、日志和封装经验可以迁移到 Java 类设计。
- 并发与性能测试经验有助于理解线程安全、线程池和资源竞争。
- 定位失败用例的经验有助于学习断点、堆栈和日志排错。

### 必须额外补齐

公开大纲未明确以下工程基础：

- JUnit 测试生命周期、参数化测试和断言；
- Mockito 测试替身；
- Maven 标准目录和依赖范围；
- Java 编码规范、不可变对象和可测试性设计；
- Git 分支、提交和代码评审习惯；
- 数据结构与复杂度的最低必要知识；
- 不依赖人工智能工具独立完成小功能的能力。

### 推荐学习练习

1. 编写命令行“测试结果统计器”。
2. 输入为自己生成的 JSON 或 JUnit XML 示例。
3. 输出用例总数、成功数、失败数和失败原因分类。
4. 对空文件、错误格式、重复用例和中文编码编写测试。
5. 使用人工智能工具进行一次重构，但必须自己解释每处变化。

### 阶段产出

- 一个标准 Maven 项目；
- 不少于三个领域类；
- 单元测试和参数化测试；
- 异常处理说明；
- 一份“人工智能生成代码审查记录”。

### 验收标准

- 可以在不询问人工智能的情况下完成一个新统计规则。
- 能解释类、接口、继承和组合的区别。
- 能从堆栈定位异常来源。
- 能说明线程安全问题，而不是只会调用线程池。
- `mvn test` 可以重复通过。

### 常见误区

- 把会写自动化脚本误认为已经掌握 Java 工程开发。
- 过早阅读集合或 Spring 源码，却写不出清晰的业务类。
- 直接接受人工智能生成的代码和测试，不验证边界条件。
- 追逐所有 Java 新语法，忽略异常、集合、IO 和调试基本功。

## 3.2 第二阶段：数据库与 ORM

### 课程页面明确内容

- MySQL：SQL、索引、事务和锁；
- Maven：项目构建和依赖管理；
- MyBatis：配置、映射和动态 SQL；
- MyBatis-Plus：提升持久层开发效率。

### 测试工程师可迁移能力

- 数据校验和测试数据准备经验；
- 对 `SELECT`、关联查询和数据状态的理解；
- 并发测试中的事务隔离、一致性和锁等待经验；
- 接口测试中请求与数据库结果的关联验证。

### 必须额外补齐

- 业务实体、聚合和表结构之间的建模；
- 主键、唯一约束、外键和审计字段设计；
- 数据库迁移工具，如 Flyway 或 Liquibase；
- 事务边界和回滚策略；
- N+1 查询、慢 SQL 和连接池；
- 测试环境中使用真实数据库，而不只 Mock DAO；
- 敏感字段、软删除和数据生命周期。

### 推荐学习练习

制作一个使用纯合成数据的“学习任务管理服务”：

- 用户可以创建学习计划；
- 一个计划包含多个任务；
- 任务有状态和截止时间；
- 同一计划下任务标题不可重复；
- 状态变更必须记录审计时间；
- 编写并发更新和事务回滚测试。

### 阶段产出

- ER 图；
- 建表和迁移脚本；
- 索引选择说明；
- MyBatis 动态查询；
- 数据库集成测试；
- 一份慢 SQL 分析记录。

### 验收标准

- 能说明每个索引解决什么查询。
- 能解释事务放在 Service 层的原因。
- 集成测试使用可重复创建的数据库。
- 测试执行前后没有脏数据依赖。
- 能复现并解释一次唯一约束冲突或锁冲突。

### 常见误区

- 只会使用 MyBatis-Plus 生成 CRUD，不理解 SQL。
- 测试只用内存数据库，生产使用 MySQL，却忽略方言差异。
- 为每个字段建立索引。
- 把所有业务一致性都交给应用代码，不使用数据库约束。

### 验收标准

- 不把所有逻辑放在一个组件里。
- 刷新页面后登录态和路由行为符合设计。

### 常见误区

- 因为主要方向是后端就完全跳过前端。
- 只实现“成功路径”，没有加载、空状态和异常状态。
- 用固定等待掩盖异步问题。
- 把密钥或后端管理凭证放进前端代码。

## 3.5 第五阶段：Spring AI

### 课程页面明确内容

- Spring AI 基础与环境集成；
- OpenAI GPT 系列；
- 阿里云百炼和通义千问；

### 测试工程师可迁移能力

- API Client、超时、重试和错误码测试；
- 数据驱动与组合场景；
- 非确定性结果的风险意识；
- 性能、并发和成本测量；
- 模型输出的安全校验。

### 必须额外补齐

- Token、上下文窗口和采样参数；
- System/User 消息和 Prompt 模板；
- JSON Schema 与结构化输出校验；
- 模型供应商抽象和版本管理；
- 超时、限流、退避、取消和降级；
- Prompt 与响应脱敏；
- 人工智能输出评测；
- Token、耗时和成本监控；
- 模型响应不可直接作为可信业务事实。

### 推荐学习练习

制作“公开需求测试点草案生成器”：

1. 输入自己编写的虚构需求。
2. 模型返回固定 JSON 结构。
3. Java 对结构执行严格校验。
4. 保存 Prompt 版本、模型标识和生成时间。
5. 不符合 Schema 时返回可理解错误。
6. 使用 Stub/Fake 模型测试主要逻辑。
7. 少量在线测试必须使用显式开关，避免产生意外费用。

### 阶段产出

- Spring AI 聊天接口；
- SSE 流式接口；
- 结构化输出 DTO；
- Fake 模型测试；
- Token 和延迟指标；
- Prompt 版本说明；
- 成本保护配置。

### 验收标准

- 模型不可用时服务能快速失败或降级。
- 输出无效时不会直接写入数据库或执行操作。
- 在线测试与离线测试分离。
- 日志不输出 API Key、完整敏感 Prompt 或隐私数据。
- 能比较两个模型或两个 Prompt 的效果，而不是凭一次演示判断。

### 常见误区

- 把一次成功回答当成系统已经可用。
- 在单元测试中真实调用付费模型。
- 对所有异常无限重试，放大费用。
- 把聊天记忆当作永久、可信数据库。
- 认为模型输出是确定性的。

### 必须额外补齐

### 推荐学习练习

对同一个小型公开知识库做两个最小实现：

- A 版本使用 Spring AI；
- B 版本使用 LangChain4j；
- 相同文档、相同问题集和相同基础模型；
- 对比代码量、扩展性、日志、评测和测试难度；
- 最终只选择一个作为综合项目主框架。

### 阶段产出

- 技术选型记录；
- RAG 双框架最小实现；
- 固定问题集；
- 检索结果对比报告；
- 升级和回滚说明。

### 验收标准

- 能解释选择框架的原因。
- 不以 GitHub Star 数量作为唯一依据。
- 检索失败和生成失败可以分别定位。
- 知识库返回来源和文档标识。
- 会话不会串用户。

### 常见误区

- 同时深学两个框架，造成概念混乱。
- 直接照抄示例，却无法替换模型或向量库。
- 只测试最终答案，不检查召回文档。
- 把“企业知识库”理解为上传文件后能聊天。

### 必须额外补齐

- 何时应该拆微服务；
- 事件驱动和最终一致性；
- 消息幂等与死信；
- 配置、密钥和环境隔离；
- 数据库归属；
- 服务级别指标；
- 基础设施成本；
- 人工智能任务的异步化、取消和预算控制。

### 推荐学习练习

不要一开始拆完整微服务。先做两个受控练习：

1. 把耗时文档解析改为异步任务。
2. 把模型调用记录和业务服务分离为事件。

必须验证：

- 消息重复消费；
- 任务超时；
- 服务重启；
- 下游不可用；
- 限流；
- 死信和人工恢复。

### 阶段产出

- Docker Compose；
- 一个异步任务；
- 一个消息消费服务；
- Prometheus 指标；
- Trace 示例；
- 故障演练报告；
- CI 配置。

### 验收标准

- 可以从一个请求追踪到检索、模型和工具调用。
- 重复消息不会产生重复业务结果。
- 服务不可用时有明确降级。
- 指标包含延迟、错误、Token 和队列积压。
- 能说明拆分带来的成本，而不只说明好处。

### 常见误区

- 为展示“高级”而拆成大量服务。
- 每种中间件都学一点，却没有解决真实问题。
- 只会启动容器，不会观察健康状态。
- 把日志当成可观测性的全部。

## 4. 三类项目应补充的验收框架

## 4.1 单体项目验收

功能：

- 有清晰需求和业务规则；
- 有成功、失败、冲突和越权场景；
- 支持分页、筛选和状态流转。

代码：

- 分层清晰；
- 统一异常与错误码；
- DTO 与持久化对象分离；
- 配置不含密钥。

数据：

- 有迁移脚本；
- 有约束和必要索引；
- 测试数据可重复生成和清理。

测试：

- 单元测试；
- Web 层测试；
- Testcontainers 数据库集成测试；
- 关键 E2E。

交付：

- README；
- 架构图；
- OpenAPI；
- Docker 启动；
- CI。

## 4.2 人工智能项目验收

模型：

- 模型和参数可配置；
- 请求有超时和限流；
- 在线测试有显式开关。

输出：

- 结构化结果经过 Schema 校验；
- 不把输出直接视为事实；
- 高风险操作需要人工审批。

RAG：

- 文档可追踪；
- 回答返回引用；
- 检索和生成可以分别评测；
- 文档更新、删除和重建可操作。

安全：

- 防止 Prompt Injection；
- 工具最小权限；
- 日志和 Trace 脱敏；
- API Key 不入库、不入 Git。

可观测性：

- 模型延迟；
- Token 使用；
- 错误率；
- 检索延迟；
- 工具成功率；
- 单请求成本估计。

测试：

- 确定性代码单元测试；
- Fake 模型测试；
- 少量模型集成测试；
- 固定评测集回归；
- 对抗与越权测试。

## 4.3 微服务项目验收

- 每个服务有明确边界和数据归属；
- 服务数量有业务理由；
- 请求链路可以追踪；
- 重试不会放大重复写入；
- 消息消费幂等；
- 故障有降级和恢复方式；
- 有容量与成本估算；
- 可以本地一键启动最小环境；
- CI 可以离线执行大部分测试；
- 外部模型不可用不影响核心确定性测试。

## 5. 测试能力如何迁移为开发优势

| 测试经验 | 可迁移到开发 | 必须升级的思维 |
| --- | --- | --- |
| 需求评审 | 业务规则和验收条件 | 从发现歧义升级为设计明确领域模型 |
| 测试用例设计 | 分支、异常和边界 | 在编码前写可验证接口和失败策略 |
| 接口测试 | REST、鉴权、数据契约 | 独立设计 API、错误模型和幂等 |
| SQL 校验 | 数据访问与一致性 | 设计表、索引、事务和迁移 |
| 自动化框架 | 分层、配置、日志和 CI | 设计长期可维护的业务代码 |
| Mock | 依赖隔离 | 理解何时用 Fake、Stub、Mock 和真实集成 |
| 性能测试 | 延迟、吞吐和资源 | 参与缓存、并发、限流和容量设计 |
| 安全测试 | 越权和输入攻击 | 在设计阶段落实最小权限和安全边界 |
| 缺陷定位 | 日志、堆栈和复现 | 对代码修改、回归和上线结果负责 |
| AI 测试 | 非确定性和评测集 | 建立可持续的模型与 RAG 质量门禁 |

最关键的身份变化：

```text
以前：验证别人实现的系统是否符合预期
现在：设计并实现系统，同时证明它符合预期
```

## 6. 生产级内容补充

## 6.1 版本与依赖管理

课程页面没有指定 JDK、Spring Boot、Spring AI 和 LangChain4j 版本。

学习项目建议：

- 选择 LTS JDK；
- 使用 Maven Wrapper；

- Spring AI 2.x 对应 Spring Boot 4.x；

实际建项目时仍应再次检查最新稳定版本：

## 6.4 RAG 数据流水线

完整 RAG 不只是“上传文件到向量库”：

```text
公开文档
  → 解析
  → 清洗
  → 切分
  → 元数据
  → Embedding
  → 索引
  → 查询改写
  → 召回
  → 过滤
  → 重排
  → 上下文组装
  → 生成
  → 引用
  → 评测
```

每一步都应记录：

- 输入和输出；
- 版本；
- 耗时；
- 错误；
- 可复现测试数据；
- 与最终回答的关联标识。

官方资料：

- [Spring AI API 与 ETL](https://docs.spring.io/spring-ai/reference/api/)
- [LangChain4j RAG](https://docs.langchain4j.dev/tutorials/rag/)

## 6.5 人工智能评测

传统测试断言仍然适用于：

- HTTP 状态；
- JSON Schema；
- 权限；
- 数据写入；
- 工具参数；
- 超时；
- 幂等；
- 引用格式。

模型内容则需要：

- 固定问题集；
- 期望事实或参考答案；
- 检索相关性；
- 回答忠实度；
- 引用正确性；
- 拒答正确性；
- 工具选择正确性；
- 人工抽检；
- 版本间回归。

Spring AI 提供 `Evaluator` 相关能力，但“使用模型评价模型”不能作为唯一证据，仍需规则校验和人工样本：

- [Spring AI Evaluation Testing](https://docs.spring.io/spring-ai/reference/api/testing.html)

## 6.6 工具调用与 Agent 安全

每个工具至少包含：

- 明确名称和用途；
- 最小参数 Schema；
- 输入校验；
- 权限校验；
- 超时；
- 幂等键；
- 结果大小限制；
- 审计；
- 失败补偿；
- 敏感操作人工确认。

禁止：

- 给 Agent 任意 Shell 权限；
- 把数据库管理员账号交给模型；
- 让模型自行决定是否绕过审批；
- 把外部网页内容当成可信系统指令；
- 将模型输出直接拼接 SQL 或命令。

官方资料：

- [Spring AI Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html)

- [LangChain4j Agents](https://docs.langchain4j.dev/tutorials/agents/)

## 6.8 可观测性

除 CPU、内存和 HTTP 指标，还应关注：

- 模型供应商；
- 模型版本；
- Prompt 版本；

- 首 Token 时间；
- 总响应时间；
- 检索耗时；
- 召回文档数量；
- 工具调用序列；
- 工具失败；
- 重试次数；
- 单请求成本；
- 安全拦截数量；
- 用户反馈。

日志和 Trace 默认不应记录完整 Prompt、完整模型输出或敏感文档。

## 6.9 人工智能安全

必须覆盖：

- Prompt Injection；
- 敏感信息泄露；
- 不安全输出处理；
- 供应链风险；
- 过度授权；
- 向量库越权；
- 工具调用越权；
- 资源消耗和费用攻击；
- 模型或 Prompt 版本未审计；
- 对模型结果的过度依赖。

参考：

- [OWASP 大模型应用安全项目](https://owasp.org/www-project-top-10-for-large-language-model-applications/)

## 6.10 微调的正确位置

大模型微调需要：

- 明确问题是否不能由 Prompt、RAG 或工具解决；
- 合法、高质量、可追踪的训练和验证数据；
- 基准模型；
- 独立测试集；
- 训练成本；
- 部署和推理基础设施；
- 回滚能力；
- 安全与偏差评测。

对测试转应用开发者，建议优先级：

```text
模型 API
  > 结构化输出
  > RAG
  > 工具调用
  > 评测与安全
  > 生产部署
  > 微调
```
