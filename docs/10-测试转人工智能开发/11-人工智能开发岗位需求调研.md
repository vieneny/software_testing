## 一、调研目的

1. 当前公开职位反复描述哪些任务和能力组合？

## 四、样本中反复出现的能力簇

### 4.1 软件开发底座

反复出现：

- Python 或 Java 至少一门扎实语言；
- 数据结构与算法基础；
- FastAPI/Flask 或 Spring Boot；
- REST API；
- MySQL/PostgreSQL；
- Linux、Docker；
- 模块化、单元测试和工程化；
- 有些中高级岗位继续要求缓存、消息队列、微服务和 Kubernetes。

稳妥结论：

> AI 应用岗依然是软件开发岗。Prompt、Dify 或模型 API 不能替代后端基础。

### 4.2 AI 应用

反复出现：

- 大模型 API 与 Prompt/Context Engineering；
- RAG；
- 文档解析、Chunk、Embedding、向量数据库；
- 检索优化、Rerank 和效果评估；
- Function Calling/Tool Use；
- 至少一个完整落地项目。

稳妥结论：

> RAG 和工具调用是应用岗位的重要共同能力，但企业列出的具体框架不同，因此教程应强调流水线、接口和评测，而不是死记某个 API。

### 4.3 Agent

反复出现：

- LangChain、LangGraph、LlamaIndex、Dify 等任一框架；
- 工作流/状态编排；
- MCP；
- Memory、规划、工具；
- 异步、流式、长任务；
- 多 Agent 在部分岗位出现；
- 检查点、安全、评测和部署更多出现在进阶岗位。

稳妥结论：

> 新手先证明单 Agent 和确定性工作流，再做多 Agent；工具权限、恢复与评测比“Agent 数量”更能证明工程能力。

### 4.4 质量、可靠性与安全

职位常见表述包括：

- 单元测试、工程化；
- 响应速度、稳定性；
- 高并发和性能；
- 评测体系；
- 安全部署、沙箱、身份认证；
- 生产级落地经验。

测试人员可形成差异化：

- 模型和工具 Mock；
- 黄金集与分层评测；
- 故障注入；
- Prompt Injection/越权回归；
- Trace 与根因分析；
- CI 质量门禁。

但不能只做“测试 Agent”的人；仍需自己实现后端、数据和核心流程。

### 4.5 可验证项目

多个岗位明确偏好：

- 完整 RAG/Agent 项目；
- 非简单 Demo；
- GitHub/Gitee 项目；
- 开源贡献；
- 技术文章或可验证产出；
- 生产落地经验。

个人无法伪造生产经验，正确替代证据是：

- 可运行的公开项目；
- 清晰的限制；
- 真实测试和评测；
- 故障与修复；
- 小规模但可信的测量；
- 开源协作记录。

## 七、必修与加分项

### 第一优先级：不具备就难以证明转岗

- 一门主语言；
- 普通后端 API；
- 数据库与 SQL；
- Git、Linux、Docker；
- 单元与集成测试；
- 模型 API、结构化输出和故障处理；
- 一条完整 RAG 链路；
- 一个可复现公开项目。

### 第二优先级：形成 AI 应用竞争力

- RAG 评测与优化；
- Tool Calling/MCP；
- Agent 状态、恢复、HITL；
- OpenTelemetry/Phoenix；
- Prompt Injection 与工具授权；
- CI 中的 AI 回归。

### 第三优先级：按岗位选择

- Spring Cloud/消息队列/Redis；
- Qdrant/Milvus/GraphRAG；
- Kubernetes；
- 多 Agent/A2A；
- LiteLLM/vLLM；
- LoRA/微调；
- PyTorch 深入；
- 图数据库。

不要把第三优先级全部塞进第一份作品。

## 八、从测试转岗的现实定位

### 优势

- 更习惯失败路径和边界；
- 更容易建立评测集和门禁；
- 熟悉 API、SQL、日志与自动化；
- 能把“模型看起来可以”转成可测指标；
- 对权限、回归和变更风险更敏感。

### 风险

- 业务实现和领域建模不足；
- 只会测试框架，不会生产框架；
- 习惯从外部验证，不习惯承担系统所有权；
- 简历仍以执行用例为主；
- 作品只有测试脚本，没有核心应用代码。

### 定位建议

第一阶段求职可以同时关注：

- AI 应用测试/质量工程；
- 测试开发（AI 平台/大模型系统）；
- Java/Python AI 应用初级开发；
- RAG/Agent 应用开发；
- AI 工具链或评测开发。

不要把 Agent Infra、模型训练或高级分布式岗位作为零开发经验时的唯一目标。

## 九、如何把岗位要求转成学习任务

看到招聘文案时，不直接复制工具名。按四步拆解：

```text
岗位任务
→ 可迁移原理
→ 最小可运行练习
→ 可核验作品证据
```

示例：

| 招聘词 | 原理 | 练习 | 证据 |
|---|---|---|---|
| LangGraph | 状态、节点、边、持久化 | 缺陷分诊状态机 | 恢复与终止测试 |
| MCP | 工具发现和调用协议 | 只读公开资料工具 | Schema/权限/兼容测试 |
| RAG | 检索增强流水线 | 公开测试知识库 | Recall@k、引用、拒答 |
| 高并发 | 容量、队列、资源和降级 | 受控负载实验 | p95、错误、Token 和瓶颈 |
| 生产级 | 可靠性、安全、发布、观测 | 故障注入与 Compose | Trace、门禁、回滚说明 |
| 开源项目 | 协作和工程实践 | 文档/测试贡献 | Issue、PR、复盘 |

## 十、调研更新方法

求职期每月、非求职期每季度：

1. 在 BOSS 按 AI 应用、Agent、Java AI、Python Agent 和双栈分别检索；
2. 选择不同城市、行业、经验层级的公开岗位；
3. 保存采集时间、关键词、职位 URL、标题和明示要求；
4. 记录原始、去重、相关岗位条数与排除原因；
5. 不保存需要登录的个人信息、招聘者信息或个人应聘记录；
6. 合并同义能力，不机械统计框架名；
7. 与官方项目维护状态交叉核对；
8. 把稳定能力留在主线，新框架先放选修；
9. 删除失效结论或标记页面下线；
10. 不把小样本扩张成全国统计。

需要真正统计职位数量、薪资或地区差异时，必须取得招聘平台允许使用的完整数据集，并公开采样、去重、时间窗和缺失处理方法。

## 十一、最终结论

这组公开岗位支持以下保守判断：

1. AI 应用/Agent 岗仍然首先要求软件开发基础；
2. BOSS 当前样本同时存在 Python Agent、Java 企业 AI 集成和 Java/Python 双栈岗位；小样本不支持计算语言市场份额；
3. RAG、Tool/Function Calling 和完整项目是重复出现的应用能力；
4. Agent 进阶岗位开始要求异步、状态、检查点、评测、安全和部署；
5. 可验证开源项目比课程完成证明更有说服力；
6. 测试背景的优势应通过质量工程证据体现，而不是停留在“我比较细心”；
7. 两门课程可以作为路线参考，但必须补普通后端、测试、评测、安全、可观测和作品复现。

因此，本模块不再给所有人规定同一门默认语言，而按目标岗位分支：

- 目标 JD 以 Java/Spring、企业系统和后端集成为主：走 Java/Spring AI；
- 目标 JD 以 Python、FastAPI、LangGraph 和 Agent 应用为主：走 Python Agent；
- 目标 JD 接受双栈：选自己能最快交付普通后端的一门做主线，另一门做到能读、能调接口和能写测试；
- 目标是 AI 质量开发：语言跟随被测平台和团队栈，重点证明评测、自动化、服务和 CI 能力。

所有分支都用一个公开、合成、可运行、可评测的综合项目完成转岗证据闭环。
