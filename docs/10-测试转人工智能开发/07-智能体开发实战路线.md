# 智能体开发实战路线

> 目标：帮助测试工程师用可运行、可测试、可部署、可讲解的项目，逐步转向人工智能应用开发和 Agent 智能体开发。
>
> 课程参考：[十指波教育《AI 大模型 Agent 智能体开发就业班》](https://www.itszb.com/agent)，页面核对日期为 2026-07-27。
>
> 本文的阶段顺序、项目设计、验收标准和开源项目选择均为本项目的独立学习建议，不是课程方承诺。

## 1. 最终要达到什么水平

完成路线后，学习者应能独立交付一个“公开演示商城测试 Agent”：

```text
公开或虚构需求
  ↓
知识库检索
  ↓
生成测试计划
  ↓
人工确认
  ↓
调用接口、浏览器或移动端测试工具
  ↓
收集结构化结果
  ↓
失败归因
  ↓
生成带证据的报告
```

这个项目不是让模型不受限制地操作设备，而是训练以下能力：

- Python 工程化；
- FastAPI 后端；
- 模型调用；
- RAG；
- LangGraph 状态编排；
- MCP 工具服务；
- Human in the Loop；
- 自动化测试；
- AI 评测；
- Agent 安全；
- 可观测性；
- Docker 化交付。

## 2. 安全边界先于技术

所有练习必须遵守：

- 仅使用开源靶场、本地演示应用和人工生成数据；
- 用户、订单、简历、知识库和日志全部虚构；
- 不在代码中保存真实 API Key；
- 不把 `.env`、模型缓存、向量库数据和 Trace 数据提交到 Git；
- 高风险工具默认关闭，执行前需要人工确认；
- 先在本地隔离环境运行，再考虑公开部署。

### 2.1 合格的演示数据

```json
{
  "用户编号": "演示用户-001",
  "订单编号": "演示订单-20260727-001",
  "商品名称": "自动化测试学习背包",
  "订单状态": "待发货"
}
```

### 2.2 不合格的数据

- 真实客户手机号；
- 公司工单号；
- 内部接口地址；
- 线上数据库表名；
- 真实 Token；
- 内部缺陷标题；
- 未脱敏的运行日志。

## 3. 推荐路线总览

建议以“验收通过再进入下一阶段”为主，不强制按周数赶进度。

下表时间是本项目对每周投入约 8～12 小时的粗略学习安排，不是课程时长或就业承诺。

| 阶段 | 建议时长 | 核心产出 |
|---|---:|---|
| 0. 边界与环境 | 1 周 | 安全清单、开发环境、最小 CI |
| 1. Python 工程化 | 2～3 周 | 可安装、可测试的 Python 小项目 |
| 2. FastAPI 后端 | 3～4 周 | 演示商城 API |
| 3. 大模型应用基础 | 2～3 周 | 可替换模型的结构化输出服务 |
| 4. RAG | 3～4 周 | 带引用、带评测集的公开知识库 |
| 5. 工具调用与 MCP | 2～3 周 | 最小权限测试工具服务 |
| 6. LangGraph Agent | 3～4 周 | 可恢复、可审批的测试工作流 |
| 7. AI 测试与安全 | 3～4 周 | Golden Set、回归门禁、红队用例 |
| 8. 部署与可观测 | 2～3 周 | Docker、Trace、指标、回滚说明 |
| 9. 综合作品 | 4～6 周 | 智能测试 Agent 完整作品 |
| 10. 选修进阶 | 按需 | Dify/Coze、微调、多 Agent |

## 4. 开源项目的正确使用方法

不要把“收藏仓库”和“复制示例”当作学习。

每个仓库按照以下顺序研读：

1. 阅读项目定位和许可证；
2. 查看稳定版本和安装要求；
3. 运行最小官方示例；
4. 阅读目录结构；
5. 找到测试目录；
6. 修改一个行为并补测试；
7. 记录版本和问题；
8. 用自己的虚构业务重新实现；
9. 不复制受限制的数据和素材；
10. 保留来源链接和许可证说明。

建议建立个人开源研读卡：

```markdown
# 项目名称

- 官方仓库：
- 阅读日期：
- 使用版本：
- 许可证：
- 解决的问题：
- 最小示例：
- 关键抽象：
- 测试方式：
- 已知限制：
- 我自己的重写：
- 是否进入最终项目：
```

## 5. 阶段零：边界、环境和工程基线

### 5.1 学习目标

- 建立独立于公司环境的个人学习目录；
- 掌握 Git 基本操作；
- 建立 Python 虚拟环境；
- 知道密钥、配置、数据和代码的边界；
- 让最小测试能在本地和 CI 执行。

### 5.2 需要学习

- Git 仓库、分支、提交和差异；
- `.gitignore`；
- 虚拟环境；
- `pyproject.toml`；
- 依赖锁定；
- 环境变量；
- Ruff；
- pytest；
- 基础 CI；
- README 的运行说明。

官方开源入口：

- [uv](https://github.com/astral-sh/uv)
- [Ruff](https://github.com/astral-sh/ruff)
- [pytest](https://github.com/pytest-dev/pytest)

### 5.3 实战任务

创建一个“字符串规则检查器”：

- 输入一段公开的虚构测试需求；
- 检查标题长度；
- 检查是否存在验收条件；
- 输出结构化结果；
- 为正常、边界和异常输入写测试。

这一阶段不要接模型。

### 5.4 必须产出

- 项目说明；
- 内容安全边界；
- 依赖清单；
- 配置示例；
- 单元测试；
- 静态检查配置；
- CI 工作流；
- 一次成功执行记录。

### 5.5 验收标准

- 新电脑按照说明可以创建环境；
- 不配置密钥也能运行离线测试；
- 测试全部通过；
- 静态检查通过；
- 仓库中没有真实 `.env`；
- 仓库中没有日志、报告、模型缓存和数据库；
- Git 差异中没有个人或公司敏感信息。

### 5.6 常见坑

- 把虚拟环境提交到 Git；
- 把 API Key 写在 Python 文件；
- 只写代码，不写安装步骤；
- 依赖不锁版本；
- 本地能运行，但换目录就失败；
- 使用公司的测试数据做“临时练习”；
- 一个提交混入大量无关文件。

## 6. 阶段一：Python 从自动化脚本升级为开发工程

### 6.1 学习目标

从“能写 pytest 脚本”升级为：

- 会设计模块；
- 会声明类型；
- 会处理错误；
- 会注入依赖；
- 会写可替换、可测试的代码。

### 6.2 知识清单

- 函数、类、协议和组合；
- 类型标注；
- `dataclass`；
- Pydantic；
- 生成器和上下文管理器；
- `async`、`await`；
- 自定义异常；
- 日志；
- 配置管理；
- 分层；
- 单元测试、参数化、Fixture 和 Mock。

官方开源入口：

- [CPython](https://github.com/python/cpython)
- [Pydantic](https://github.com/pydantic/pydantic)
- [pytest](https://github.com/pytest-dev/pytest)

### 6.3 实战任务：可替换的数据检查器

实现三个端口：

```text
需求读取端口
规则执行端口
结果保存端口
```

默认实现：

- 从本地公开 Markdown 读取；
- 使用纯 Python 规则检查；
- 把结果保存在内存。

测试实现：

- 使用内存假对象；
- 不访问网络；
- 不写真实磁盘；
- 能构造超时和异常。

### 6.4 必须产出

- 架构说明；
- 类型模型；
- 端口接口；
- 默认实现；
- 假实现；
- 异常说明；
- 单元测试；
- 覆盖率结果；
- 一篇“为什么不在业务代码里直接调用外部服务”的说明。

### 6.5 验收标准

- 核心逻辑不依赖网络；
- 每个外部依赖都可以替换；
- 错误类型有业务含义；
- 日志不打印密钥和完整敏感输入；
- 测试不依赖执行顺序；
- 测试可以重复运行；
- 能在五分钟内讲清模块关系。

### 6.6 常见坑

- 所有代码放在一个文件；
- 业务函数里直接读取环境变量；
- 为了测试而大量 Monkey Patch；
- 捕获所有异常后返回空字符串；
- 用日志代替错误处理；
- 异步函数里调用阻塞 I/O；
- 把类型标注当作注释，不做边界校验。

## 7. 阶段二：FastAPI 后端开发

### 7.1 学习目标

独立开发一个“公开演示商城 API”，为后续 Agent 提供稳定工具。

官方开源入口：

- [FastAPI](https://github.com/fastapi/fastapi)
- [SQLAlchemy](https://github.com/sqlalchemy/sqlalchemy)
- [Alembic](https://github.com/sqlalchemy/alembic)
- [Pydantic](https://github.com/pydantic/pydantic)

### 7.2 需要学习

- HTTP 方法和状态码；
- REST 资源设计；
- OpenAPI；
- 请求和响应模型；
- 依赖注入；
- 中间件；
- 统一错误模型；
- 数据库事务；
- SQLAlchemy；
- 数据库迁移；
- JWT 基础；
- RBAC；
- 分页、排序和过滤；
- 幂等性；
- 健康检查；
- 单元、集成和契约测试。

### 7.3 实战业务

只实现虚构业务：

- 商品查询；
- 创建订单；
- 查询自己的订单；
- 取消未发货订单；
- 发起退货申请；
- 查看公开帮助文章。

暂不接模型。

### 7.4 接口设计示例

```text
GET    /商品
GET    /商品/{商品编号}
POST   /订单
GET    /订单/{订单编号}
POST   /订单/{订单编号}/取消
POST   /订单/{订单编号}/退货申请
GET    /帮助文章
GET    /健康检查
```

### 7.5 必须产出

- OpenAPI；
- 数据模型图；
- 数据库迁移；
- 虚构种子数据；
- 接口自动化；
- 权限测试；
- 幂等测试；
- 错误码清单；
- 本地启动说明；
- 数据重置说明。

### 7.6 验收标准

- 用户不能读取别人的订单；
- 重复提交相同幂等键不会创建两个订单；
- 不存在的资源返回明确错误；
- 输入越界在 API 边界被拒绝；
- 数据库升级和回退有说明；
- 集成测试使用独立测试数据库；
- OpenAPI 与实际响应一致；
- 服务关闭后不留下脏进程；
- 所有数据均为虚构数据。

### 7.7 常见坑

- 只实现成功路径；
- 在路由函数中写全部业务逻辑；
- 返回 `200` 表示所有错误；
- 直接把数据库模型作为外部响应；
- 不做所有权校验；
- 把 JWT 当作权限系统的全部；
- 测试直接使用开发数据库；
- 用固定等待代替可观测状态；
- 没有事务，失败后留下半成品。

## 8. 阶段三：大模型应用基础

### 8.1 学习目标

开发一个可替换模型、可离线测试的结构化输出服务。

可参考：

- [Ollama](https://github.com/ollama/ollama)：本地模型运行；
- [LangChain](https://github.com/langchain-ai/langchain)：模型和结构化输出抽象。

### 8.2 需要学习

- Token；
- 上下文窗口；
- System、User 和 Tool 消息；
- 温度和采样；
- 结构化输出；
- 超时和取消；
- 限流；
- 重试和退避；
- 模型降级；
- Token 预算；
- 提示词版本；
- 模型接口抽象；
- 假模型。

### 8.3 实战任务：需求结构化

输入一段公开虚构需求，输出：

```json
{
  "功能名称": "取消订单",
  "角色": ["普通用户"],
  "前置条件": ["订单属于当前用户", "订单未发货"],
  "主流程": ["查询订单", "确认状态", "提交取消"],
  "异常规则": ["已发货不可取消"],
  "待确认问题": []
}
```

### 8.4 设计要求

- 模型输出必须经过 Pydantic 校验；
- 不允许直接信任模型 JSON；
- 模型客户端通过接口注入；
- 测试默认使用假模型；
- 真实模型测试必须使用显式开关；
- 每次调用记录模型、提示词版本、延迟和 Token；
- 日志只保存必要元数据；
- 失败时返回可理解的错误。

### 8.5 必须产出

- 模型端口；
- Ollama 或其他公开模型适配器；
- 假模型；
- 提示词模板；
- 输出 Schema；
- 结构化输出测试；
- 超时测试；
- 解析失败测试；
- 模型切换说明；
- 调用成本记录模板。

### 8.6 验收标准

- 不启动模型也能运行绝大多数测试；
- 模型返回非法 JSON 时服务不会崩溃；
- 超时可被取消；
- 输出不符合 Schema 时返回明确失败；
- 提示词有版本；
- 更换模型不修改核心业务；
- 真实模型调用需要显式同意；
- 不向模型发送公司内容。

### 8.7 常见坑

- 把 Prompt 写死在路由函数；
- 用全文字符串相等测试生成结果；
- 自动无限重试；
- 不设置超时；
- 把完整对话写入公开日志；
- 默认把每次测试都发送给收费模型；
- 模型返回 JSON 外文字就解析失败；
- 模型升级后没有回归基线。

## 9. 阶段四：RAG 知识库

### 9.1 学习目标

用公开资料建立一个“软件测试公开知识库”，实现可引用、可拒答、可评测的 RAG。

开源入口：

- [RAGFlow](https://github.com/infiniflow/ragflow)
- [Qdrant](https://github.com/qdrant/qdrant)
- [Milvus](https://github.com/milvus-io/milvus)
- [LangChain](https://github.com/langchain-ai/langchain)

初学只选择一个向量库。不要同时安装全部。

### 9.2 数据来源

只允许：

- 本项目自己编写的公开教程；
- 官方公开文档；
- 明确允许使用的开源资料；
- 自己生成的虚构需求和 FAQ。

每份资料记录：

- 来源 URL；
- 获取日期；
- 许可证或使用说明；
- 文档版本；
- 是否允许再分发；
- 是否包含个人信息。

### 9.3 需要学习

- 文档解析；
- 切片；
- Metadata；
- Embedding；
- 稠密和稀疏检索；
- 混合检索；
- Top K；
- Rerank；
- Query Rewrite；
- HyDE；
- 引用；
- 拒答；
- 索引更新和删除；
- 检索评测；
- 答案忠实度。

### 9.4 实战任务

实现：

1. 导入公开 Markdown；
2. 显示切片；
3. 建立向量索引；
4. 检索证据；
5. 根据证据回答；
6. 返回来源；
7. 无证据时拒答；
8. 删除文档后清理索引；
9. 用固定评测集回归。

### 9.5 Golden Set

至少准备：

- 20 个可回答问题；
- 10 个不可回答问题；
- 10 个容易混淆的问题；
- 5 个多文档组合问题；
- 5 个含恶意指令的文档；
- 每题期望来源；
- 每题期望行为。

### 9.6 必须产出

- 数据清单；
- 导入器；
- 切片说明；
- 索引配置；
- 检索 API；
- 回答 API；
- 引用；
- Golden Set；
- 离线评测脚本；
- 失败样本分析；
- 文档删除测试。

### 9.7 验收标准

- 引用可以定位到具体来源；
- 不可回答问题能拒答；
- 正确证据的召回结果可量化；
- 修改切片策略前后有对比；
- 删除文档后不能再召回；
- 恶意文档不能覆盖系统指令；
- 测试数据和知识库均可公开；
- 向量库不进入 Git；
- 导入失败可重试且不会重复入库。

### 9.8 常见坑

- 一上来使用复杂 GraphRAG；
- 只看最终答案，不看检索；
- 没有 Metadata；
- 切片过大或过小；
- Top K 越大越好；
- 没有不可回答样本；
- 文档更新后旧向量仍存在；
- 把文档中的命令当系统指令；
- 评测集和调参数据完全相同；
- 把公司知识库拿来“效果更真实”。

## 10. 阶段五：工具调用与 MCP

### 10.1 学习目标

把演示商城查询和测试执行封装成最小权限工具，并使用 MCP 客户端进行调用。

官方开源入口：

- [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk)

注意：MCP SDK 正在持续演进，学习时应固定版本并阅读对应版本文档，不要混用不同主版本示例。

### 10.2 工具分级

#### 只读工具

- 查询公开商品；
- 查询当前演示用户的订单；
- 读取公开帮助；
- 读取测试结果摘要。

#### 可逆写工具

- 创建虚构测试数据；
- 启动本地测试任务；
- 取消尚未执行的本地任务。

#### 高风险工具

- 删除数据；
- 执行任意 Shell；
- 上传文件；
- 调用真实外部系统；
- 控制真实设备；
- 修改权限。

学习项目默认不暴露高风险工具。

### 10.3 实战任务

实现 MCP 服务：

- `查询公开商品`
- `查询演示订单`
- `运行指定测试集合`
- `读取测试结果摘要`

每个工具都要有：

- 明确名称；
- 用途；
- 输入 Schema；
- 输出 Schema；
- 权限；
- 超时；
- 错误；
- 审计信息。

### 10.4 必须产出

- MCP 服务；
- MCP 客户端；
- 工具清单；
- 权限矩阵；
- Schema；
- 合约测试；
- 错误和超时测试；
- 恶意参数测试；
- 版本兼容说明；
- 人工审批设计。

### 10.5 验收标准

- 不存在“执行任意命令”工具；
- 工具输入经过严格校验；
- 工具结果是结构化数据；
- 调用者只能访问自己的虚构数据；
- 超时后任务可取消；
- 重复请求不会造成重复副作用；
- 工具日志不含密钥；
- 客户端会把工具结果当不可信数据；
- 高风险操作必须人工批准。

### 10.6 常见坑

- 给模型一个万能 Shell；
- 工具说明含糊；
- 输入使用任意字典；
- 把异常堆栈直接返回模型；
- MCP 服务默认监听公网；
- 没有身份和会话绑定；
- 工具被重复调用产生副作用；
- 把工具返回文本拼进系统指令；
- 依赖最新示例却不锁 SDK 版本。

- 图集成测试；

- 一张流程图。

### 11.6 验收标准

- 每个节点可以独立测试；
- 中断后从 Checkpoint 恢复；
- 审批前不执行写操作；
- 循环有最大次数；
- 每条结束路径可解释；
- 模型不会直接决定高风险权限；
- 测试能稳定验证路由；
- 错误不会被吞掉；
- 任务状态可以查询；
- 取消任务后不会继续调用工具。

### 11.7 常见坑

- 把所有逻辑放在一个节点；
- State 保存巨大原文；
- 无限制自我反思循环；
- 用模型决定所有分支；
- 没有确定性规则校验；
- Checkpoint 存了密钥；
- 恢复后重复执行工具；
- 多 Agent 只增加复杂度，没有隔离职责；
- 图能运行，但没有任何节点测试。

## 17. 每周学习循环

每一周都按照同一个闭环：

### 第一步：定义一个可验证问题

例如：

> 当模型返回缺少必填字段的 JSON 时，服务应该拒绝并记录可诊断错误。

### 第二步：阅读官方资料

- 只读当前问题需要的章节；
- 记录版本；
- 不一次追完整个生态。

### 第三步：写最小失败测试

- 先用假模型或假工具；
- 明确期望状态；
- 不依赖网络。

### 第四步：实现

- 只实现当前验收；
- 不提前引入多 Agent；
- 不复制大型模板。

### 第五步：真实集成

- 使用显式开关；
- 控制调用次数；
- 记录延迟和成本；
- 不传敏感内容。

### 第六步：复盘

每周写：

- 做了什么；
- 为什么这样设计；
- 哪些失败；
- 如何定位；
- 指标变化；
- 下周风险。

## 20. 最后的学习原则

1. 先写确定性程序，再接模型。
2. 先做单 Agent，再考虑多 Agent。
3. 先做 RAG 基线，再考虑微调。
4. 先做最小权限工具，再让模型调用。
5. 先写测试和验收，再堆框架。
6. 先保证数据可以公开，再导入知识库。
7. 先能够解释失败，再宣传“智能”。
8. 作品的价值来自可复现证据，不来自技术名词数量。

测试工程师转 Agent 开发的最佳路径不是抛弃测试，而是把质量能力写进系统架构：

```text
测试思维
  + 后端开发
  + 大模型应用
  + Agent 编排
  + 评测与安全
  = 可落地的智能体开发能力
```
