# 功能测试与用例设计经典面试题

> 适用岗位：功能测试、业务测试、Web/App 测试、自动化测试。
>
> 使用说明：答场景题时先澄清目标与规则，再建立模型、设计数据和测试预言，最后补充相关的非功能风险；不要一上来罗列几十个无优先级的检查点。

## 01. 一条完整的测试用例包含哪些字段？什么是高质量用例？

**岗位考点**

用例可执行性、可维护性、追踪性与风险意识。

**参考答案**

常见字段包括：唯一编号、标题、关联需求/规则/风险、优先级、前置条件、合成测试数据、步骤、每一步或最终预期结果及其依据、环境/配置，以及执行结果和证据。团队还可以记录用例类型、标签、自动化状态和维护人，但字段数量应服务于执行、追踪和维护，而不是越多越好。

高质量用例有明确目标，覆盖有价值的风险，前置条件可建立，数据具体，步骤最小且无歧义，预期结果可观察、可判定，并能追溯到需求、规则或风险。用例之间应尽量独立、可重复；若依赖状态或顺序，必须明确说明。

**原理或实践解释**

“点击提交，系统正常”不是可判定的预期。更好的表达是：“使用有效合成数据提交后，页面展示唯一订单号；查询接口返回 `created`；库存只减少 1；使用同一幂等键重复提交不产生第二笔业务效果。”预期不仅看 UI，还要覆盖关键状态和数据不变量；具体状态名与幂等规则必须来自测试依据。

**常见追问或误区**

- 追问：“所有用例都要写得很细吗？”新手、跨团队和高风险流程需要更明确；成熟团队的稳定低风险场景可用清单或自动化代码表达。
- 误区：把操作步骤写得很长，却没有说明验证什么。
- 误区：一个用例混入多个互不相关目标，失败后难定位。

## 02. 什么是等价类划分？如何设计有效和无效等价类？

**岗位考点**

黑盒测试设计基础，以及能否从规则而非具体值建立输入模型。

**参考答案**

等价类划分把输入或输出域划分为若干集合，并假设系统会以相同方式处理同一分区中的所有成员，再从每个相关分区选择代表值。对同一个划分维度，分区应互斥且覆盖已知域；既要有有效分区，也要为可能经过不同校验逻辑的失败原因建立独立无效分区。

例如虚构会员年龄只允许 18～60 的十进制整数，可以划分：有效整数 `[18,60]`；小于 18 的整数；大于 60 的整数；数值但非整数；空值；不符合格式的文本。若接口和 UI 的约束不同，还要分别验证客户端提示与服务端强制校验，并明确空白字符串、字段缺失和 `null` 是否属于不同规则。

**原理或实践解释**

等价类的价值是用可解释的少量代表覆盖规则，而不是随便挑一个“正常值”和一个“异常值”。不同无效原因可能经过不同代码分支，不能把所有非法输入合并。还应考虑输出分区，例如搜索有结果、无结果和无权限查看。

**常见追问或误区**

- 追问：“每类选一个值一定够吗？”只是起点；高风险、实现边界、历史缺陷或内部子分区可能需要更多代表值。
- 误区：把 18、30、60 都称为三个等价类；它们可能属于同一有效类，但边界测试另有价值。
- 误区：只测前端控件不允许输入，未直接验证后端。

## 03. 边界值分析怎么做？两值边界和三值边界有什么区别？

**岗位考点**

边界建模、精确数据设计和 off-by-one 风险。

**参考答案**

边界值分析关注有序分区的边界，因为比较运算、长度、数组和循环容易在边界出错。按 ISTQB 常用定义，两值边界分析对每个边界覆盖“边界值 + 相邻分区中最接近的值”；三值边界分析覆盖“边界前、边界本身、边界后”。该定义适用于存在可识别相邻值的有序数据，实际项目还应说明采用的口径。

仍以整数年龄 `[18,60]` 为例，两值集合是 `17,18,60,61`，三值集合是 `17,18,19,59,60,61`。若字段长度为 1～20 个 Unicode 字符，应先确认计数单位，再构造 0、1、2、19、20、21；字节、Unicode 码点和用户感知字符（grapheme cluster）的边界可能不同。

**原理或实践解释**

边界必须来自规则、数据类型和接口约束。日期还涉及月末、闰年和时区边界；金额涉及精度与舍入；分页涉及空集合、1 条、每页上限、总数刚好整除和多 1 条。仅在一个输入框填 `-1` 不等于完成边界分析，也不能未经依据断言底层实现极值。

**常见追问或误区**

- 追问：“无穷大怎么测？”使用规格上限、数据类型极值、系统约束和代表性大值，并测试系统能否安全拒绝。
- 误区：忘记边界属于哪个分区，导致预期结果不明确。
- 误区：只测试数值边界，忽略长度、时间、集合数量和资源边界。

## 04. 什么是判定表？什么时候比逐条列用例更合适？

**岗位考点**

多条件业务规则建模、组合覆盖与规则遗漏识别。

**参考答案**

判定表把条件、条件取值组合和对应动作放在表中，每一列代表一条规则。它适合多个条件共同决定结果、规则数量有限且可明确表达的场景，例如优惠资格、审批、权限或运费计算。

设计步骤是：识别独立条件和动作；列出逻辑上可能的组合；根据业务约束合并不可能或“无关”的组合；为每条有效规则定义预期动作；检查是否存在冲突、遗漏和默认规则；再把高价值规则转成测试用例。

**原理或实践解释**

虚构免运费规则有两个条件：是否金卡会员、订单金额是否至少 99。若规则是“满足任一条件即可免运费”，完整表为：

| 条件/动作 | 规则 1 | 规则 2 | 规则 3 | 规则 4 |
|---|---:|---:|---:|---:|
| 金卡会员 | 是 | 是 | 否 | 否 |
| 金额 ≥ 99 | 是 | 否 | 是 | 否 |
| 免运费 | 是 | 是 | 是 | 否 |

表格能直接暴露金额恰好等于 99 的边界，以及两个条件同时满足时是否只免一次运费。若存在“特殊商品不包邮”等约束，应新增条件或明确优先级，不能私自把它并入现有规则。

**常见追问或误区**

- 追问：“条件很多导致组合爆炸怎么办？”先消除不可能组合，找业务约束，用因果关系和风险选取，再考虑 pairwise；不能盲目生成全部组合。
- 误区：把输入数据清单当成判定表，却没有条件到动作的映射。
- 误区：合并规则时误删会触发不同动作的组合。

## 05. 状态迁移测试如何设计？

**岗位考点**

有状态业务、合法/非法转换、历史序列和并发思维。

**参考答案**

先识别对象的有限状态、触发事件、守卫条件、转换动作和目标状态，再画状态图或状态表。测试既要覆盖重要状态和合法转换，也要覆盖高风险非法转换、重复事件、顺序颠倒、超时和恢复；对依赖历史的风险，可设计包含连续两次或更多转换的序列。覆盖准则要说清是“状态覆盖”“有效转换覆盖”还是更强的序列覆盖。

例如虚构订单状态为 `created → paid → shipped → completed`，另有 `created → cancelled`。应验证未支付订单不能发货、已完成订单不能取消、同一支付事件重放不产生第二次扣款，以及取消与支付竞争时只能按已定义规则形成一个有效终态；同时核对状态、事件和用户展示最终一致。

**原理或实践解释**

只按页面逐个功能测试，会漏掉“同一动作在不同状态下结果不同”。状态模型还能帮助接口自动化参数化和数据库不变量检查。状态不是页面名称，而是决定后续合法行为的业务信息。

**常见追问或误区**

- 追问：“如何测试不可达状态？”优先通过公开测试接口、消息模拟或故障注入验证防护；只有在隔离且获授权环境，才能用合成数据构造内部状态，并记录清理步骤。
- 误区：只覆盖正常状态链，不测非法跳转和重复事件。
- 误区：只看最终 UI 文案，不核对服务端状态与副作用。

## 06. Pairwise（成对组合）是什么？能替代完整组合测试吗？

**岗位考点**

组合测试、覆盖与成本权衡，以及工具输出的边界。

**参考答案**

Pairwise 是组合测试的一种覆盖准则，目标是让任意两个不同参数的任意取值组合至少出现一次。它可用较少用例覆盖所有二因素交互，因此常用于浏览器、操作系统、语言、权限和配置矩阵的压缩；这是一种覆盖保证，不是“必然发现某类缺陷”的保证。

它不能保证发现三因素或更高阶交互，也不理解业务逻辑。使用前要先定义参数、取值、约束和高风险必测组合；生成后人工审查，并单独加入历史缺陷、主流环境、边界及法律/安全要求。高风险场景可能需要三元组合或定向全组合。

**原理或实践解释**

虚构 Web 应用有 4 种浏览器、3 种操作系统、2 种语言、3 种角色，在没有约束时全组合是 72 组。Pairwise 通常可减少组合数，但“管理员 + 中文 + 特定浏览器”的三因素高风险组合仍要显式加入；生成后还应验证约束是否让某些二因素组合无法出现。

**常见追问或误区**

- 追问：“正交试验和 Pairwise 一样吗？”二者都可处理组合问题，但数学设计、平衡性和适用目标并不完全相同，面试时不要混为同义词。
- 误区：把随机抽样称为 Pairwise，却没有验证覆盖。
- 误区：参数取值定义错误，再精巧的算法也没有意义。

## 07. 三个整数判断三角形类型，测试用例如何设计？

**岗位考点**

等价类、边界值、条件组合和规格澄清的综合运用。

**参考答案**

先澄清规格：三个输入是否只能是整数、允许范围是否为 1～200、是否允许系统自行排序、输出类型有哪些。假设输入为 `[1,200]` 的整数，三边能构成三角形必须同时满足 `a+b>c`、`a+c>b`、`b+c>a`；若先按非降序排列，则等价为最小两边之和大于最大边。为暴露只检查固定参数位置的错误，仍应覆盖有代表性的边长排列。

核心用例至少包括：

| 类别 | 示例 | 预期 |
|---|---|---|
| 等边 | `5,5,5` | 等边三角形 |
| 等腰 | `5,5,8` 及排列 | 等腰三角形 |
| 一般 | `4,5,6` | 一般三角形 |
| 退化边界 | `2,3,5` | 不能构成三角形 |
| 边界内一侧 | `2,4,5` | 可构成三角形 |
| 明显非法 | `1,2,4` | 不能构成三角形 |
| 域边界 | `1,1,1`、`200,200,200` | 等边三角形 |
| 越界/类型 | `0,2,2`、`201,2,2`、空、`1.5` | 按规格拒绝 |

**原理或实践解释**

这是一个小型判定问题：先验证输入域，再判断三角形不等式，最后分类。若实现先判断等腰再判断合法性，`1,1,3` 可能被误判；若只判断 `a+b>c`，`2,5,2` 可能暴露位置依赖。因此测试不仅挑分类代表，还要覆盖判断顺序与参数排列。

**常见追问或误区**

- 追问：“为什么要测排列？”实现可能只检查 `a+b>c`，不同排列可暴露遗漏。
- 误区：把 `2,3,5` 当作有效三角形；必须严格大于。
- 误区：没先澄清输入域，就随意加入浮点、负数并断言具体提示。

## 08. 文件上传功能如何测试？

**岗位考点**

功能、边界、安全、兼容、存储和失败恢复的全链路分析。

**参考答案**

先确认允许的类型、大小、数量、文件名、内容校验、存储命名、权限、处理流程和失败策略。全部使用从零生成、无敏感内容的文件，按以下维度设计：

- 正常：每种允许类型、单个/多个文件、预览、下载、替换和删除。
- 边界：0 字节、最大值前/等于/超过、文件数量边界、长文件名、Unicode 名称、同名文件。
- 内容与安全：扩展名与 MIME/文件签名不一致、双扩展名、路径字符、主动内容和异常压缩比应被安全处理；存储端应生成安全名称或正确隔离用户文件。公共学习项目只使用无害模拟或官方测试字符串，不保存真实恶意样本或敏感文件。
- 网络与恢复：取消、超时、断网、重试、分片缺失、重复提交，确认不会产生不可见孤儿文件或重复记录。
- 权限与生命周期：上传、查看、下载、删除权限；链接过期；删除后的访问和缓存。

**原理或实践解释**

上传通常跨越浏览器、网关、应用、对象存储、扫描和异步处理。页面显示“成功”不代表文件已完整、可读且可授权访问，应校验元数据、内容哈希或下载结果，以及记录与对象的一致性。对合成图像还可验证方向元数据、尺寸限制、颜色空间和服务端重编码；删除则要检查元数据、对象、缓存和访问链接的生命周期。

**常见追问或误区**

- 追问：“如何测试木马文件？”在隔离且获授权环境使用官方安全测试样本（如 EICAR）或无害模拟，不下载来历不明恶意程序。
- 误区：只改扩展名验证类型，不检查服务端是否检查内容。
- 误区：用公司文档、个人证件或真实用户文件作为测试数据。

## 09. 搜索框如何设计测试？

**岗位考点**

需求建模、文本处理、排序分页、性能与可用性。

**参考答案**

先问清搜索对象、字段、匹配方式、分词/归一化、大小写、语言、排序、权限、索引时效和无结果体验。功能上覆盖精确/模糊匹配、前后空格、大小写、中文与 Unicode、数字、标点、组合条件、同义词（若有规则）、空输入、无结果和特殊字符。边界覆盖关键词长度、结果数、分页首尾和筛选后页码重置。

还要验证排序字段相同时结果是否稳定、总数与去重、用户只能看到有权限的结果、索引更新延迟符合约定、查询字符被正确转义，以及在目标合成数据规模下的响应时间。自动补全、历史记录和高亮若存在，也要单独建模；不能仅用“页面未报错”证明不存在注入风险。

**原理或实践解释**

搜索虚构商品“测试书”时，可以准备固定小数据集作为测试预言：标题匹配、描述匹配、无权限商品、已下架商品，以及相关度相同但更新时间不同的商品。明确每条记录应出现与排序位置，才能验证包含关系、权限过滤和稳定分页，而不是面对不断变化的数据凭肉眼判断。

**常见追问或误区**

- 追问：“搜索结果和数据库不一致就是 Bug 吗？”先确认索引同步策略、读写延迟、权限和缓存约定。
- 误区：只测输入框能输入和按钮能点击。
- 误区：把 SQL 注入字符串是否报错当作完整安全测试；还需服务端参数化和授权安全评估。

## 10. 如何测试一个电商订单提交流程？

**岗位考点**

端到端业务流、数据一致性、异常补偿和测试分层。

**参考答案**

先画业务流和参与方：用户、商品、价格、优惠、库存、订单、支付沙箱/模拟器和通知。正常场景覆盖单商品、多商品、优惠前后金额、地址和配送选择、提交后订单号与状态。规则场景覆盖商品上下架、库存不足、优惠有效期、价格变化、购买上限、权限和重复提交。

异常场景覆盖依赖超时、网络中断、支付结果未知、消息延迟、部分服务失败、重试和取消。每个场景不仅验证页面，还验证金额不变量、库存变化、订单状态、重复记录、事件投递和约定的一致性窗口。支付场景只使用公开沙箱、mock 和合成账户，绝不使用真实支付资料。

**原理或实践解释**

可以分层实施：价格规则由组件测试覆盖大量组合；订单 API 验证业务规则和幂等；契约测试验证依赖接口假设；UI 只保留关键旅程；隔离环境中用少量故障注入验证恢复。每层都要有可判定预言，端到端结果异常时才能逐层定位。

**常见追问或误区**

- 追问：“支付成功但订单仍待支付怎么办？”先确认回调、主动查询、消息、重试和最终一致性窗口，再验证补偿与告警。
- 误区：只验证“下单成功”，不检查金额、库存和重复副作用。
- 误区：在真实生产环境创建未授权订单或调用真实支付。

## 11. 库存扣减和重复下单的并发问题怎么测试？

**岗位考点**

并发、幂等、原子性、超卖和可观察测试预言。

**参考答案**

先定义不变量：可售库存不能为负；最终确认成功订单中的商品数量之和不能超过初始可售库存；同一幂等键最多产生一次业务效果；失败或取消后的库存按规则释放。准备固定的合成商品和库存，使用并发工具通过栅栏尽量同时发起请求，记录每个请求的 HTTP/业务状态、订单号、幂等键和时间，再核对库存、订单、事件与可观测证据。

场景包括：不同用户竞争最后一件；同一用户双击；客户端超时后使用相同键重试；使用不同键重复请求；扣库存成功后下游失败；消息重复投递；释放与扣减并发。重复多轮并报告配置和结果分布，不能用一次成功证明没有竞争问题。

**原理或实践解释**

并发缺陷可能来自非原子的“先查再改”、约束缺失、锁粒度错误或幂等记录竞态。黑盒测试不应在没有证据时指定根因，而要用不变量判断结果。例如初始库存 1、20 个请求各购买 1 件，在结算窗口结束后最多只能有 1 笔确认成功并扣减库存；其余请求应按契约进入失败、排队或待确认状态，不能笼统要求都返回同一种错误。

**常见追问或误区**

- 追问：“200 响应是否代表成功？”不一定，要核对业务状态和副作用；反之超时也不代表服务端未处理。
- 误区：把串行循环称为并发测试。
- 误区：只看库存不为负，忽略产生多个成功订单或消息。

## 12. 权限功能如何系统测试？

**岗位考点**

身份认证与授权区别、最小权限、对象级权限和服务端验证。

**参考答案**

先建立“主体—角色/属性—资源—动作—条件”的权限矩阵。覆盖未登录、每种角色、资源所有者与非所有者、跨虚构租户、已禁用用户、权限变更前后和会话过期。对每个动作验证 UI 是否按设计隐藏或禁用，更重要的是直接调用公开测试接口，确认可信服务端拒绝越权。

还要验证对象级授权，例如虚构普通用户能读取自己的订单，但不能通过修改 ID 读取另一虚构用户的订单；批量接口、导出、搜索、缓存和异步任务不能绕过同一规则。未认证请求通常按契约返回 401，已认证但无权请求可返回 403，或为防止资源枚举返回 404；选择应与安全策略一致。审计日志按要求记录高风险动作且不泄露秘密。

**原理或实践解释**

“菜单看不见”只是展示层控制。请求方仍可构造 URL、请求体或旧链接，因此授权必须在可信服务端执行。权限变更还涉及授权缓存和既有 token 的失效时机，需按规格验证“立即失效”或“到期失效”，不能自行假定。

**常见追问或误区**

- 追问：“认证和授权区别？”认证确认你是谁，授权决定这个身份可对哪些资源做什么。
- 误区：只测试角色级菜单，不测试记录/对象级越权。
- 误区：用真实他人账号或未经授权的数据做越权实验。

## 13. Web 和 App 的兼容性测试如何开展？

**岗位考点**

市场岗位常见的兼容矩阵、设备选择、交互和风险取舍。

**参考答案**

先基于产品公开支持声明、已授权且合规汇总的环境分布及风险确定矩阵，不追求所有设备全组合。Web 关注浏览器及版本、操作系统、视口、缩放、输入方式、网络和辅助技术；App 关注系统版本、设备类别/屏幕、权限模型、安装升级、前后台切换、中断、弱网、横竖屏、深色模式和厂商定制差异。

执行策略可以分层：CI 在支持列表中的主流浏览器运行稳定自动化；发布前在代表性真实设备做关键旅程、交互和视觉检查；对高风险或公开已知问题环境做专项；云真机可扩大覆盖。记录浏览器/系统/设备和应用的准确版本与限制，并区分应用缺陷、平台预期差异和明确不支持范围。

**原理或实践解释**

设备选择可用等价类和风险思路：系统大版本、屏幕类别、性能档位、厂商定制和权限模型。虚构学习 App 至少验证全新安装、从受支持旧版本升级、会话恢复、来电/通知中断、离线后重连，以及字体放大后关键内容与操作仍可访问。

**常见追问或误区**

- 追问：“模拟器能替代真机吗？”模拟器适合早期功能和可重复场景，但摄像头、传感器、真实性能、厂商定制、蜂窝网络和部分安装升级行为仍需代表性真机证据；具体取舍按风险决定。
- 误区：把分辨率截图对比当成全部兼容性。
- 误区：没有支持范围和使用数据，随意挑自己手边设备。

## 14. 没有需求文档，只有一个可运行系统，如何设计功能测试？

**岗位考点**

探索性测试、逆向建模、测试预言和沟通边界。

**参考答案**

我会把当前系统当作信息来源，而不是绝对正确的测试预言。先在明确授权范围内做侦察：识别用户目标、角色、导航、数据实体、状态和外部依赖；通过界面、公开接口说明和允许访问的测试日志建立模型；可用 SFDPOT 等启发式观察结构、功能、数据、平台、操作和时间；分别记录事实、问题、假设与证据。

然后与有权相关方确认关键规则和验收标准，建立最小基线。无法确认的行为标为“待决策”，可以依据内部一致性、适用标准、用户目标和公开历史版本提出候选预期，但不能把个人猜测直接报成 Bug，也不能未经许可逆向或读取隐藏数据。优先探索高影响、变化大和可疑区域。

**原理或实践解释**

使用会话式探索时，可写 Charter：“在 45 分钟内探索虚构书签功能的保存、同步和冲突恢复，重点关注两个模拟客户端先后离线编辑。”会话后输出测试配置、覆盖、发现、问题、证据和下一步，比漫无目的点击更可复盘。

**常见追问或误区**

- 追问：“没有预期结果怎么测试？”可使用明确标准、系统不变量、跨渠道一致性、用户目标和差分/历史对照，但需说明预言来源。
- 误区：现有实现即需求，因此不能发现业务错误。
- 误区：探索性测试不需要准备、记录或复盘。

## 15. 如何进行用例评审与维护？重复度高的用例要不要保留？

**岗位考点**

测试资产治理、评审质量、回归集选择和成本意识。

**参考答案**

评审应邀请理解需求、实现和风险的相关角色，检查：是否覆盖关键风险与验收条件；规则、边界、状态、异常和相关非功能风险是否遗漏；合成数据与环境是否可得；预期及依据是否可观察、可判定；用例是否独立、重复或互相矛盾；测试级别是否合适；是否遵守隐私与授权边界。评审结论、责任人和待确认项应可追踪。

维护时根据需求、架构、缺陷和风险更新基线，标记并移除已失效用例，合并仅数据不同且预期逻辑相同的用例并参数化。相同业务规则若在不同层验证不同责任，可以保留，例如组件层覆盖计算组合、UI 层确认关键旅程；若多个 UI 用例重复验证同一底层规则且没有新增信心，则下沉到组件或 API 层，只保留关键端到端代表。

**原理或实践解释**

用例库不是越大越好。可将用例分成构建烟测、变更相关、高风险回归和完整周期集合，并观察历史失败、缺陷检出、维护成本和执行时间。某个长期未失败的低风险 UI 组合不能仅凭这一点自动删除，应先判断风险是否变化、断言是否有效，以及能否用更低成本的测试层覆盖。

**常见追问或误区**

- 追问：“用例多久评审一次？”新需求在执行前评审；基线可按版本、重大变更或质量信号定期复查，不必机械地按固定日期重写。
- 误区：为追求用例数量保留大量同义步骤。
- 误区：把自动化覆盖等同于无需维护人工探索和风险模型。

## 16. 给定一个任意新功能，你如何快速说出测试思路？

**岗位考点**

结构化表达、现场分析和从简单到深入的全链路思维。

**参考答案**

我会先用五步框架回答，并在每一步明确合成数据与授权边界：

1. **澄清目标**：谁在什么场景下完成什么任务，成功标准是什么。
2. **建立模型**：输入、输出、角色、状态、规则、依赖、数据和生命周期。
3. **设计覆盖**：正常、边界、异常、组合、状态转换、权限、可访问性和兼容；按风险排序。
4. **定义预言与副作用**：明确 UI、API、持久化状态或事件的可判定结果，以及失败恢复、幂等和审计要求。
5. **安排执行**：选择组件、接口、UI、探索、性能或安全活动，准备合成数据与隔离环境，明确结论和残余风险。

**原理或实践解释**

以虚构的“收藏商品”功能为例：目标是登录用户跨设备保存商品；模型包含收藏/未收藏状态、商品上下架、用户、设备和同步时机；覆盖重复点击、并发、离线冲突、权限和数量上限；验证列表、计数、API 与持久化状态；接口自动化覆盖规则，UI 验证关键交互，再在隔离网络条件下探索同步恢复。

**常见追问或误区**

- 追问：“每道场景题都要讲性能安全吗？”只补充与风险相关的方面，先把核心业务说清楚。
- 误区：机械套“功能、性能、安全、兼容”四个词，没有具体测试预言。
- 误区：未澄清规则就断言具体行为，或一次罗列所有点却没有优先级。
