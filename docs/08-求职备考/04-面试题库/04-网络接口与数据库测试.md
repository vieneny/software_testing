# HTTP、接口与数据库测试经典面试题

> 适用岗位：软件测试、接口测试、自动化测试、测试开发、SDET。
> 招聘信号：公开岗位通常把 HTTP、接口用例设计、鉴权、SQL、数据一致性和故障定位作为共同底座；中高级岗位进一步关注契约、幂等、并发、异步链路与可观测性。
## 使用方法

不要只背状态码或 SQL 语法。每道题建议按“结论 → 原理 → 测试方案 → 失败证据 → 取舍”回答，并能画出请求、服务、数据库和异步依赖之间的链路。

## 1. 一个 HTTP 请求和响应分别由哪些部分组成？接口测试要检查什么？

**岗位考点**

- 能否从协议层而不是只从 JSON 业务字段理解接口。
- 是否知道方法、URI、头、正文、状态码和响应头各自表达什么。
- 是否会构造分层断言。

**参考答案**

HTTP 请求通常包括请求方法、目标 URI、协议相关信息、请求头和可选正文；响应包括状态码、响应头和可选正文。接口测试至少应覆盖：

1. 传输层：DNS、TLS、连接和读取是否成功，是否在规定超时内完成。
2. HTTP 语义层：方法是否正确，状态码是否精确，`Content-Type`、缓存、重定向等响应头是否符合约定。
3. 契约层：字段是否必填、类型是否正确、枚举和格式是否合法、是否允许额外字段。
4. 业务层：金额、库存、状态迁移、权限和跨接口关系是否正确。
5. 非功能层：延迟、限流、安全、幂等、并发与可观测性。

例如虚构的创建订单接口，不应只断言 `status_code == 201`，还要验证订单编号、总价、初始状态、库存变化、重复提交和无权限访问。

**原理或实践解释**

HTTP 是无状态的应用层请求/响应协议。服务可能返回合法 JSON，但状态码、媒体类型或缓存策略错误；也可能状态码正确，但数据库终态错误。因此只检查某一层会产生“假通过”。实践中应保留关联 ID、请求摘要、响应状态和耗时，但对令牌、Cookie、手机号等敏感值脱敏。

**常见追问或误区**

- 误区：`response.ok` 为真就代表业务正确。它通常只表达某一范围的 HTTP 结果，不能替代精确状态码和业务断言。
- 追问：GET 能不能有正文？协议并非简单地把它定义为语法错误，但其语义没有通用约定，很多客户端、代理和服务端不支持，不应依赖。
- 追问：为什么 URL 参数和 JSON 正文要分别测试？因为解析链路、编码、缓存、日志和安全策略不同。

## 2. 什么是安全方法和幂等方法？POST 如何实现幂等？

**岗位考点**

- 是否理解 RFC 9110 中“安全”和“幂等”的区别。
- 能否设计支付、下单、消息提交等重复请求测试。

**参考答案**

“安全”表示客户端请求的语义是只读的，不要求产生客户端所请求的状态变化，例如 GET、HEAD、OPTIONS。“幂等”表示同一请求执行一次和执行多次，其预期服务端效果相同；PUT、DELETE 以及安全方法在协议语义上是幂等的。幂等不等于响应每次完全相同，也不等于服务端不能写日志。

POST 默认没有幂等保证。常见做法是客户端生成唯一的幂等键，服务端在业务作用域内原子地记录“键、请求指纹、执行状态和结果”：

1. 首次收到键时执行业务并保存结果。
2. 相同键和相同请求重放时返回同一业务结果。
3. 相同键但请求正文不同时拒绝，例如返回冲突或业务错误。
4. 并发相同键只能有一次产生副作用。
5. 明确键的作用域、有效期、失败重试和存储清理策略。

**原理或实践解释**

网络超时不能证明服务端未处理请求。客户端可能在服务端提交事务后、收到响应前断线，重试就可能创建两个订单。幂等键把“至少一次到达”转化为“一次业务效果”。测试要模拟串行重放、并发重放、相同键不同载荷、处理中断、过期键和多租户隔离，并查询最终订单数或余额变化。

**常见追问或误区**

- 误区：给数据库字段加唯一索引就完成全部幂等。唯一约束是重要防线，但还要定义请求指纹、失败状态和重放响应。
- 误区：DELETE 第二次返回 404，所以它不幂等。状态码可以不同；判断的是预期资源终态。
- 追问：幂等键放哪里？常见为请求头，也可由协议约定；关键是双方明确语义，而不是字段名称本身。

## 3. 200、201、202、204 有什么区别？如何测试异步接口？

**岗位考点**

- 是否能根据资源生命周期判断成功状态，而不是“成功都返回 200”。
- 是否理解受理和完成的区别。

**参考答案**

- `200 OK`：请求成功，并返回结果表示。
- `201 Created`：请求成功并创建了资源，通常应能通过响应正文或 `Location` 找到新资源。
- `202 Accepted`：请求已被接受，但处理尚未完成；不能据此宣称业务完成。
- `204 No Content`：请求成功且没有响应正文。

测试返回 `202` 的导出任务时，我会验证：

1. 首次响应包含任务 ID、查询地址或明确的轮询协议。
2. 任务状态按允许的状态机迁移，例如 `queued → running → succeeded/failed`。
3. 使用有上限的轮询和退避，不用无限循环或固定长等待。
4. 成功时验证产物及权限；失败时验证可诊断错误。
5. 测试重复提交、取消、超时、队列拥塞和回调重放。

**原理或实践解释**

同步 HTTP 响应与后端业务事务可能不是同一个完成边界。异步接口的 oracle 应包含“受理结果、任务状态和最终副作用”三层。若系统采用 webhook，还要验证签名、重放防护、乱序和至少一次投递造成的重复回调。

**常见追问或误区**

- 误区：收到 `202` 就立即去数据库断言最终数据存在。
- 误区：`204` 响应还应该有 JSON 正文。其语义是不包含内容。
- 追问：轮询频率怎么定？遵循接口约定或 `Retry-After`，设置整体截止时间并记录每次状态变化。

## 4. 400、401、403、404、409、422、429 应如何区分？

**岗位考点**

- 错误分类是否清晰。
- 能否从状态码、错误码和安全策略共同判断。

**参考答案**

- `400 Bad Request`：请求整体无效，例如语法或无法解析。
- `401 Unauthorized`：通常表示缺少或无效的认证凭据，并可能伴随 `WWW-Authenticate`；名称容易误导，更接近“未认证”。
- `403 Forbidden`：服务端理解身份，但拒绝执行；有时为防资源枚举会故意返回 404。
- `404 Not Found`：目标资源不存在或服务端不愿披露其存在。
- `409 Conflict`：请求与资源当前状态冲突，例如版本冲突或唯一性冲突。
- `422 Unprocessable Content`：内容语法可理解，但指令或字段语义无法处理。
- `429 Too Many Requests`：触发限流，通常要关注配额窗口和 `Retry-After`。

回答时应补充：具体系统必须在 API 契约中统一错误模型，例如稳定的业务错误码、用户可读消息、字段级详情和关联 ID；测试不能仅凭自然语言消息断言。

**原理或实践解释**

状态码提供机器可理解的粗粒度分类，业务错误码提供域内细分。测试矩阵应覆盖“无凭据、伪造凭据、过期凭据、有效身份无权限、资源不存在、越权访问、并发冲突、频率超限”。错误响应本身也要做契约和敏感信息检查。

**常见追问或误区**

- 误区：401 表示“已登录但权限不足”，403 表示“没登录”，实际通常相反。
- 误区：所有校验错误都必须是 422。标准提供语义，项目仍需明确定义一致策略。
- 追问：500 和 503 区别？500 是未分类的服务端错误；503 表示暂时无法处理，常与过载或维护有关，是否重试仍要看方法幂等性和服务约定。

## 5. REST API 应如何建模？PUT 和 PATCH 有什么区别？

**岗位考点**

- 是否理解资源、表示和方法语义。
- 能否识别把动作都塞进 POST 的弱设计，并设计更新测试。

**参考答案**

REST 风格通常用 URI 标识资源，用 HTTP 方法表达操作。例如：

```text
GET    /products/42
POST   /orders
PUT    /profiles/7
PATCH  /profiles/7
DELETE /carts/9/items/2
```

PUT 通常表示用请求中的表示创建或整体替换目标资源，并具有幂等语义；PATCH 表示按补丁文档对资源做部分修改，是否幂等取决于补丁格式和操作。例如“把昵称设置为 A”可以幂等，“余额增加 10”通常不幂等。

测试更新接口要覆盖：缺失字段的含义、只读字段、空值与删除、并发版本、重复执行、未知字段、部分失败、验证顺序以及更新后的 GET 表示。

**原理或实践解释**

接口设计不是只看 URL 是否“像名词”，核心是稳定资源语义、状态迁移和可预测错误。测试人员应从消费者视角审查：能否安全重试、能否演进、错误是否可诊断、并发更新是否丢失。

**常见追问或误区**

- 误区：PATCH 天生幂等。
- 误区：PUT 只能更新、POST 只能创建。协议语义比这更细，具体资源规则应在契约中明确。
- 追问：删除资源后 GET 应返回什么？一般是 404 或系统约定的不可见结果；若采用软删除，还要验证恢复、查询过滤和权限。

## 6. Cookie/Session、JWT 和 OAuth 2.0 有什么区别？鉴权接口怎么测？

**岗位考点**

- 是否把会话机制、令牌格式和授权框架区分开。
- 能否设计认证、授权和令牌生命周期测试。

**参考答案**

- Cookie 是浏览器保存并按规则发送的数据容器；Session 通常指服务端保存会话状态，Cookie 中只放不可预测的会话标识。
- JWT 是一种紧凑、URL-safe 的 Claims 表示格式，不等于认证协议，也不保证一定有签名或一定无状态；它可以由 JWS 保护、由 JWE 加密，也存在规范定义的 unsecured JWT。用于鉴权时必须按系统策略校验完整性保护与算法白名单，以及签发者、受众、有效期等声明，不能只解码内容。
- OAuth 2.0 是授权框架，描述客户端如何取得并使用访问令牌；OpenID Connect 在其上增加身份层。

鉴权测试至少覆盖：

1. 无令牌、格式错误、签名错误、过期、尚未生效、错误签发者或受众。
2. 不同角色和资源归属的横向、纵向越权。
3. 访问令牌刷新、撤销、轮换和重放。
4. Cookie 的 `Secure`、`HttpOnly`、`SameSite` 及 CSRF 防护。
5. 日志、错误信息和响应中不得泄露凭据。

**原理或实践解释**

认证回答“你是谁”，授权回答“你能做什么”。接口通过了身份验证，不代表有权访问任意资源。最有价值的测试不是只换成空 Token，而是建立“主体 × 角色 × 资源归属 × 操作”的权限矩阵，并从服务端终态验证未授权请求没有副作用。

**常见追问或误区**

- 误区：能解码 JWT 就说明令牌有效。Base64 解码不验证签名。
- 误区：JWT 一定不能撤销。可通过短有效期、轮换、撤销列表或会话状态实现，但有一致性和成本取舍。
- 追问：401/403 如何防用户枚举？可统一外部响应，同时在授权边界和审计日志中保留内部原因。

## 7. 如何系统设计一个接口的测试用例？

**岗位考点**

- 是否有结构化测试分析能力。
- 能否从单接口扩展到状态链、依赖和风险。

**参考答案**

我会先确认资源模型、输入输出契约、角色、状态机、副作用、SLO 和依赖，再按以下维度设计：

1. 正常：最小合法、典型、最大合法、不同角色和不同状态。
2. 输入：必填、类型、长度、边界、枚举、编码、重复字段、未知字段和组合约束。
3. 协议：方法、路径、查询参数、媒体类型、字符集、状态码、缓存和重定向。
4. 业务：状态迁移、金额计算、库存、重复提交、并发冲突和补偿。
5. 安全：认证、授权、注入、资源枚举、敏感信息和限流。
6. 可靠性：超时、重试、依赖失败、网络中断、异步最终一致性。
7. 契约与兼容：字段增删、默认值、枚举扩展和消费者影响。
8. 可观测性：关联 ID、审计事件、指标和失败诊断。

然后按风险分层：提交前跑确定性的核心回归，较慢的并发、容错和性能检查进入后续流水线。

**原理或实践解释**

接口用例不是对字段做笛卡尔积。要先识别最可能、影响最大且最难发现的失败模式，再选等价类、边界值、判定表、状态迁移、成对组合或属性测试等方法。每条自动化检查应有稳定 oracle 和可控数据。

**常见追问或误区**

- 误区：接口文档中的每个字段写一条正例和一条空值，就叫完整覆盖。
- 追问：时间不足怎么裁剪？优先权限、资金/库存等关键副作用、主流程、不可逆状态、变更区域和历史高风险点，并明确残余风险。
- 追问：如何衡量覆盖？结合需求风险、状态/规则、契约操作、代码或变更覆盖；不能只看用例数量。

## 8. OpenAPI、JSON Schema 和契约测试是什么关系？

**岗位考点**

- 是否理解“文档可读”与“机器可验证”的差别。
- 是否会处理提供者和消费者独立演进。

**参考答案**

OpenAPI Description 用机器可读形式描述 HTTP API 的路径、操作、参数、请求体、响应、安全方案和可复用组件。版本差异必须说明：OAS 3.0 的 Schema Object 采用经过调整并带 OAS 扩展的 JSON Schema 子集，并不是完整 JSON Schema 方言；OAS 3.1 的 Schema Object 方言建立在 JSON Schema Draft 2020-12 之上，并定义 OAS dialect。后续 OAS 3.2 已发布，但不能据此假定现有解析器、校验器或代码生成器已经兼容；规范文件应声明并锁定实际版本。JSON Schema 可验证 JSON 实例的类型、必填、范围、模式和组合约束。

契约测试通常有两类：

- 提供者基于 OpenAPI 检查实现是否符合公开契约，例如操作、状态码、请求和响应 Schema。
- 消费者驱动契约记录某个消费者实际依赖的交互，并由提供者验证，适合多服务独立发布。

契约测试不能替代业务测试。Schema 能证明 `total_cents` 是正整数，却不能单独证明它等于商品价格乘数量。

**原理或实践解释**

契约把“双方隐含假设”变成可版本化、可自动检查的资产。应同时校验示例与 Schema、在 CI 做 breaking-change 检测，并明确额外字段、可空、默认值、枚举扩展和错误响应策略。生成式契约测试还可以从 Schema 自动探索边界，但仍需人为定义业务不变量。

**常见追问或误区**

- 误区：Swagger UI 就是 OpenAPI 规范本身。前者是展示/交互工具，后者是规范。
- 误区：新增字段永远向后兼容。若消费者严格拒绝额外字段或字段影响签名，仍可能破坏。
- 追问：如何避免契约和实现漂移？选择设计优先或代码优先均可，但要建立单一来源、自动校验、评审和发布门禁。

## 9. 接口超时后可以直接重试吗？如何制定重试策略？

**岗位考点**

- 能否结合方法语义、错误类型和退避设计可靠调用。
- 是否知道重试可能放大故障。

**参考答案**

不能看到超时就无条件重试。首先区分连接超时、写入中断、读取超时、服务端 5xx、429 和业务拒绝；再判断操作是否安全或幂等。合理策略包括：

- 对明确可重试且幂等的操作设置有限次数。
- 使用指数退避加随机抖动，避免重试风暴。
- 尊重 `Retry-After` 和整体调用截止时间。
- POST 等有副作用的操作依赖幂等键或查询补偿。
- 对持续故障使用熔断、限流和降级，而不是无限重试。
- 记录每次尝试、最终结果和关联 ID。

**原理或实践解释**

读取超时表示客户端一段时间没收到数据，不代表服务端没完成写入。重试是分布式系统中的负载倍增器：下游越慢，上游越多重试，可能把短暂故障变成雪崩。测试应验证最大尝试次数、总时长、退避区间、可重试错误白名单，以及最终只产生一次副作用。

**常见追问或误区**

- 误区：所有 5xx 都应重试，所有 4xx 都不应重试。429、408 等可能允许稍后重试；某些 5xx 下操作结果未知。
- 追问：客户端和网关都重试怎么办？多层重试次数会相乘，应明确唯一主要重试层或共享预算。
- 追问：自动化请求为什么必须设置 timeout？Requests 默认不会自动超时，不设置可能让测试和 CI 长时间挂起。

## 10. 如何测试分页、排序和过滤接口？

**岗位考点**

- 数据集合测试是否只看第一页。
- 是否理解数据变更下 offset 与 cursor 的差异。

**参考答案**

分页测试应覆盖空集合、单页、刚好满页、多页、第一页/中间页/末页、非法页大小、最大页大小、越界游标，以及过滤和排序组合。核心不变量包括：

- 页内无重复，跨页按契约不遗漏或不重复。
- 排序稳定；主排序键相同时有确定的次排序键。
- 过滤后的总数、页数据和权限范围一致。
- `next` 游标不能被其他用户伪造或越权复用。
- 数据增删时明确一致性语义。

Offset 分页简单，但集合在翻页期间插入或删除会造成位移；cursor/keyset 分页基于稳定且能唯一定位位置的复合排序键，更适合持续变化的大集合。若只用可重复的时间戳做游标，同一时间点的数据仍可能重复或遗漏；常见做法是再加入唯一 ID。游标应被视为不透明值，并绑定排序、过滤和权限作用域。

**原理或实践解释**

不要断言生产式数据中的固定第 N 条。使用从零构造的唯一前缀数据，记录插入顺序，并按公开排序规则计算期望。对大数据量还应检查查询计划和索引，防止深页扫描。

**常见追问或误区**

- 误区：只比较返回长度等于 `page_size`。
- 误区：前端不展示总数，所以无需验证过滤结果的完整性。
- 追问：时间排序为何会重复？多个记录时间戳相同，需要额外用唯一 ID 形成稳定复合排序。

## 11. 如何验证接口与数据库的一致性？是否所有接口测试都要查库？

**岗位考点**

- 能否选择黑盒和白盒验证边界。
- 是否会避免把实现细节绑死在自动化中。

**参考答案**

不是所有接口测试都应直接查库。对公开行为和消费者契约，优先通过 API 或事件验证；对关键写入、迁移、复杂计算、异步最终状态和缺陷定位，可以在受控测试环境做数据库侧验证。

典型验证链：

1. 通过 API 创建带唯一测试标识的虚构记录。
2. 验证响应契约和业务结果。
3. 在只读连接中按业务键查询必要字段，而不是 `SELECT *`。
4. 验证主表、明细、审计或 outbox 的原子关系。
5. 通过公开接口清理；必要时使用有保护条件的测试清理工具。

数据库断言聚焦业务不变量，不把自增 ID、内部时间精度或列顺序等易变实现细节写死。还要先说明读的是主节点、同步副本还是异步副本：若契约承诺写后立刻可读，应优先从消费者实际使用的读取接口验证；若专门验证持久化终态，则应查询测试环境中约定的权威数据源。

**原理或实践解释**

查库提高缺陷定位能力，却增加与内部 Schema 的耦合、权限和清理风险。测试金字塔下层可更多使用存储集成测试，端到端层应主要验证外部可观察行为。对副本延迟或异步落库，使用带截止时间和诊断信息的条件轮询，不能用固定 `sleep` 掩盖不确定性。任何数据库凭据都通过测试环境密钥注入，不提交仓库。

**常见追问或误区**

- 误区：接口返回正确就代表数据库一定正确。
- 误区：为了“彻底”直接连接真实生产数据库做写操作。
- 追问：读副本有延迟怎么办？明确读一致性模型，使用有截止时间的状态轮询，或在要求强一致时读取权威节点。

## 12. INNER JOIN 与 LEFT JOIN 有什么区别？如何发现“一对多导致重复”？

**岗位考点**

- SQL 基础和结果集推理能力。
- 能否从数据关系而非语法表面排查重复计数。

**参考答案**

`INNER JOIN` 只返回两侧满足连接条件的组合；`LEFT JOIN` 保留左表所有行，右表无匹配时对应列为 `NULL`。一对多连接会让左表一行匹配右表多行，因此直接 `COUNT(*)` 或汇总金额可能被放大。

虚构示例：统计每个订单的明细数量：

```sql
SELECT o.id, COUNT(i.id) AS item_count
FROM orders AS o
LEFT JOIN order_items AS i ON i.order_id = o.id
GROUP BY o.id;
```

若要找没有明细的订单：

```sql
SELECT o.id
FROM orders AS o
LEFT JOIN order_items AS i ON i.order_id = o.id
WHERE i.id IS NULL;
```

排查重复时先检查键的唯一性和基数，再分别统计连接前后的行数，最后判断应该预聚合、使用 `EXISTS`、`COUNT(DISTINCT ...)` 还是修正连接条件。

**原理或实践解释**

JOIN 的结果是一组满足谓词的行组合，不会自动理解“业务上一张订单只能算一次”。`WHERE` 中对右表列的非空条件还可能把 LEFT JOIN 实际变成 INNER JOIN。测试数据应包含零、一、多匹配和重复键。

**常见追问或误区**

- 误区：看到重复就一律加 `DISTINCT`。它可能掩盖错误连接并增加成本。
- 误区：`COUNT(column)` 与 `COUNT(*)` 完全相同；前者不统计该列为 NULL 的行。
- 追问：NOT IN 和 NOT EXISTS 如何选？若子查询含 NULL，`NOT IN` 的三值逻辑容易产生意外结果，需特别谨慎。

## 13. WHERE 与 HAVING 有什么区别？SQL 中 NULL 应如何判断？

**岗位考点**

- SQL 执行逻辑和三值逻辑。
- 是否会写可靠的数据校验查询。

**参考答案**

`WHERE` 在分组聚合前过滤行；`HAVING` 在 `GROUP BY` 之后过滤分组结果。例如找出有超过 3 条明细的订单：

```sql
SELECT order_id, COUNT(*) AS item_count
FROM order_items
GROUP BY order_id
HAVING COUNT(*) > 3;
```

SQL 中 NULL 表示未知/缺失，不应使用 `= NULL`，而应使用 `IS NULL` 或 `IS NOT NULL`。普通比较、算术和布尔表达式遇到 NULL 可能得到 UNKNOWN；WHERE 只保留条件为 TRUE 的行。

**原理或实践解释**

数据校验时，NULL、空字符串、0 和字段不存在可能代表完全不同的业务状态。应根据列约束和业务规则分别构造数据。聚合函数通常忽略 NULL，但 `COUNT(*)` 统计行，因此需要明确想统计什么。

**常见追问或误区**

- 误区：HAVING 只是 WHERE 的另一种写法。
- 误区：`NULL != 1` 会返回 TRUE；实际结果是 UNKNOWN。
- 追问：如何查重复业务键？按业务键分组后 `HAVING COUNT(*) > 1`，并进一步检查大小写、空格、租户和软删除条件。

## 14. 什么是事务 ACID 和常见隔离异常？接口并发测试怎么做？

**岗位考点**

- 是否能把数据库事务与接口并发故障联系起来。
- 是否理解隔离级别不是“越高越好”的背诵题。

**参考答案**

ACID 通常指：

- Atomicity：事务内操作要么整体提交，要么整体回滚。
- Consistency：事务使数据从一个满足约束的状态进入另一个满足约束的状态。
- Isolation：并发事务之间按指定隔离模型互相影响。
- Durability：提交后的结果在约定故障模型下持久。

常讨论的并发现象包括脏读、不可重复读、幻读、丢失更新和写偏差。不同数据库对隔离级别的实现与默认值不同，面试时应声明以目标数据库官方文档为准。

接口并发测试不只是“开 100 个线程”：

1. 先定义不变量，例如库存不得为负、优惠券最多使用一次。
2. 用屏障让多个客户端尽量同时发起；屏障只能控制客户端起点，不能证明服务端语句真正同时执行。
3. 记录每个响应和关联 ID。
4. 等所有请求结束后查询权威终态。
5. 验证成功数、拒绝类型、版本号、库存和审计事件之间的关系。
6. 多次重复，改变并发度和故障注入；必要时结合服务端 trace、锁等待和事务日志还原实际交错。

**原理或实践解释**

单请求用例无法发现检查与更新之间的竞争窗口。正确性通常依赖唯一约束、条件更新、乐观锁、悲观锁或串行化事务。测试应验证“最终不变量”，而不是假定哪一个请求必定成功；若要验证某个隔离异常，应使用两个独立数据库会话明确编排读、写、提交点，并以目标数据库和版本的官方行为为准。

**常见追问或误区**

- 误区：使用事务就自动没有并发问题。
- 误区：把接口压测吞吐等同于并发正确性测试。
- 追问：乐观锁怎么测？两个客户端读取相同版本，同时更新；预期只有一个成功，另一个收到明确冲突并可重新读取。

## 15. 什么是最终一致性？异步消息和 Outbox 场景如何测试？

**岗位考点**

- 微服务、消息队列和分布式数据验证能力。
- 是否会处理重复、乱序和延迟。

**参考答案**

最终一致性表示更新后允许短暂不一致，但在没有新更新且系统正常的条件下，副本或派生状态最终收敛。对“订单提交后异步生成发货任务”的虚构场景，应测试：

- 事务提交后事件最终产生，事件包含稳定业务键和版本。
- 消费者重复收到同一事件不会重复产生业务效果。
- 旧版本事件晚到不会覆盖新状态。
- 消费失败会重试并进入可观察的死信/告警路径。
- 事务回滚时不应发布代表成功的事件。
- 在约定 SLO 内轮询最终状态，超时要报告最后观测值。

Transactional Outbox 通常把业务变更和待发布事件写入同一数据库事务，再由发布器转发，减少“数据库已提交但消息未记录”的双写窗口。它本身不提供端到端 exactly-once：发布器可能在“消息已发出、outbox 尚未标记”时崩溃并再次发布，因此仍要测试发布器恢复、重复投递、消费者幂等和积压告警。

**原理或实践解释**

消息系统常提供至少一次投递，消费者必须按业务键、事件 ID 或版本实现幂等。测试 oracle 应包括消息记录、消费者终态和副作用计数；不能以 `sleep(5)` 代替有截止时间的条件等待。

**常见追问或误区**

- 误区：最终一致就是“等一会儿肯定好”，不需要 SLO 和失败路径。
- 误区：队列声称 exactly-once，就不需要业务幂等。端到端副作用仍可能跨越其保证边界。
- 追问：如何测试乱序？构造版本 2 后版本 1 的事件序列，验证消费者保留最新合法状态或明确拒绝旧事件。

## 16. 接口自动化失败时，你如何快速判断是用例、环境还是产品缺陷？

**岗位考点**

- 故障分诊与可观测性。
- 是否会给出证据链，而不是“重跑一下就好了”。

**参考答案**

我会按最短证据链分诊：

1. 确认失败类型：断言、连接、超时、解析、数据准备、清理还是环境不可用。
2. 查看测试版本、配置来源、依赖健康、服务版本和关联 ID。
3. 用已脱敏的最小请求复现，比较预期契约与实际响应。
4. 沿关联 ID 检查网关、应用、依赖和数据库/消息终态。
5. 与同一提交的其他测试、历史运行和环境指标对比。
6. 若重跑通过，不直接关闭；记录是否属于竞争、数据污染、超时阈值或服务抖动。
7. 输出事实、影响、复现条件、初步归属和下一步，而不是先猜责任人。

**原理或实践解释**

高质量自动化必须“失败可诊断”。框架应记录测试 ID、随机种子、请求方法和路径、脱敏头、状态码、耗时、响应摘要、服务版本及 trace ID。对非确定性故障还要保留运行次数、并发 worker 和数据标识。

**常见追问或误区**

- 误区：失败重跑通过就把第一次结果当噪声。
- 误区：把完整 Authorization、Cookie 或真实个人数据写进报告。
- 追问：什么时候判定环境问题？需要健康检查、同范围用例和服务指标等证据；“我本地能过”不是充分证据。

## 版本敏感点

- 本章核对日期：**2026-07-29**。
- HTTP 语义以 RFC 9110 为主；缓存细节由 RFC 9111 定义，不再把已被替代的 RFC 7231 当作最新总入口。
- OpenAPI 版本会演进。解析器、校验器和代码生成器对 3.0、3.1、3.2 的支持不同，项目必须固定规范版本并在升级前验证工具链。
- JSON Schema 有不同 draft；不要把 Draft 7、2019-09、2020-12 的关键字行为混用。
- SQL 隔离、NULL 排序、分页语法、JSON 类型和执行计划因数据库及版本不同；以目标数据库官方文档和真实测试环境为准。
- OAuth、JWT 只给出概念框架；具体安全配置应核对当前 RFC、安全最佳实践和身份提供商文档。
