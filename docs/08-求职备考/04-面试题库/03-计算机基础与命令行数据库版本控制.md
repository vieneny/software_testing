# 计算机基础、Linux、SQL 与 Git 经典面试题

> 适用岗位：软件测试、接口自动化、测试开发、性能测试。
>
> 约定：命令和 SQL 使用公开、虚构的 `users`、`orders` 数据示例。实际语法、执行计划和隔离级别行为要以所用操作系统与数据库版本的官方文档为准，禁止把个人或公司真实数据复制到练习环境。

## 01. 进程和线程有什么区别？测试排障时为什么要理解它们？

**岗位考点**

操作系统基础、并发资源和故障定位。

**参考答案**

进程是正在运行程序的一个实例，拥有独立的虚拟地址空间和系统资源；线程是进程内的执行流，同一进程的线程通常共享代码、堆和打开的资源，但各自有栈、寄存器和调度状态。进程隔离通常更强、创建和通信成本更高；线程共享数据方便，但需要同步，否则会出现竞态、死锁和可见性问题。

测试排障时要区分“服务进程没有启动”“进程存在但某线程阻塞”“线程池耗尽”“多进程实例状态不一致”。只看进程还活着不能证明服务健康。

**原理或实践解释**

虚构 API 服务响应变慢时，可以先确认进程和端口，再看 CPU、内存、线程数、连接池、日志和请求指标。如果 CPU 很低但请求排队，可能是锁、下游 I/O 或线程池阻塞；如果只有一个实例异常，则要比较实例配置和资源。

**常见追问或误区**

- 追问：“多线程一定更快吗？”不一定；受任务类型、锁竞争、上下文切换、核心数和语言运行时影响。
- 误区：把进程 ID、端口和线程 ID 混为一谈。
- 误区：看到进程存在就判断服务可用，应继续做健康检查和真实请求。

## 02. 栈和堆有什么区别？内存泄漏与内存溢出有什么不同？

**岗位考点**

内存基础、稳定性测试和错误日志理解。

**参考答案**

调用栈通常保存函数调用帧、局部状态和返回信息，生命周期与调用关系紧密，空间相对有限；堆用于动态分配、生命周期更灵活的对象，由程序或运行时管理。具体实现随语言和运行时不同，不能把所有“局部变量在栈、对象在堆”当成绝对规则。

内存泄漏指已不再需要的内存仍被引用或未释放，长期运行后占用持续增长；内存溢出指申请内存失败、超过进程/容器限制或栈深度耗尽等可见故障。泄漏可能最终导致溢出，但二者不是同义词。

**原理或实践解释**

稳定性测试应在固定负载和可重复数据下观察 RSS、堆、GC、容器限制和请求量关系。一次瞬时增长可能是缓存预热，不足以证明泄漏；若停止流量并触发合理回收后基线仍随周期上升，才形成更强证据。递归无终止更可能触发栈溢出。

**常见追问或误区**

- 追问：“如何定位泄漏？”先排除监控口径与缓存，再用运行时 profiler、heap dump 和对象增长对比；生产采集需授权并评估开销。
- 误区：把操作系统剩余内存下降直接认定为应用泄漏。
- 误区：只跑短时峰值测试来判断长期泄漏。

## 03. TCP 和 UDP 有什么区别？TCP 三次握手解决什么问题？

**岗位考点**

网络传输基础、接口故障和抓包分析。

**参考答案**

TCP 提供面向连接的可靠字节流，通过序列号、确认、重传、流量控制和拥塞控制等机制处理丢包与乱序；UDP 提供无连接的数据报传输，协议本身不保证送达、顺序或去重，应用可以按需要自行实现可靠性。选择取决于业务对时延、可靠性和消息边界的要求，不能简单说 UDP 永远比 TCP 快。

TCP 建立连接时通常通过 SYN、SYN-ACK、ACK 交换初始序列号并确认双向通信能力和连接参数。它建立的是传输连接，不会自动验证 HTTP 业务、用户身份或应用数据正确。

**原理或实践解释**

“连接被拒绝”通常意味着目标主机可达但端口没有监听或被主动拒绝；“连接超时”可能涉及路由、防火墙、地址错误或对端无响应；连接建立后 HTTP 仍可返回 500。分层判断可以避免把所有故障归因于“网络不好”。

**常见追问或误区**

- 追问：“为什么不是两次握手？”双方都需确认收发能力和彼此的初始序列号，避免旧连接报文被错误接受。
- 误区：TCP 保证应用请求“只处理一次”；超时重试仍可能造成重复业务效果。
- 误区：把 HTTP/3 使用 UDP 理解为完全没有可靠机制；QUIC 在 UDP 之上实现相关能力。

## 04. 从浏览器输入 HTTPS URL 到看到页面，大致发生了什么？

**岗位考点**

DNS、TCP/TLS、HTTP、代理与前后端的全链路定位。

**参考答案**

典型过程包括：解析 URL；查找缓存并通过 DNS 获得 IP；选择路由并建立传输连接（HTTP/1.1、HTTP/2 常基于 TCP，HTTP/3 基于 QUIC）；进行 TLS 握手、验证证书和协商密钥；发送 HTTP 请求；请求经过 CDN、负载均衡、网关和应用；服务访问缓存或数据库并返回响应；浏览器解析 HTML，继续请求 CSS、JavaScript、字体和图片，构建并渲染页面。

现代浏览器会使用连接复用、缓存、Service Worker、预连接等优化，实际步骤可能并行或被省略。排障时应按层收集证据，而不是把这段流程当成严格串行。

**原理或实践解释**

DNS 失败时通常没有 HTTP 状态码；证书错误发生在 HTTP 请求前；`502` 往往由代理表示上游响应异常；浏览器白屏也可能是 HTML 已成功返回但 JavaScript 执行失败。可结合 `dig`/`nslookup`、`curl -v`、浏览器 Network/Console 和服务端 Trace 定位。

**常见追问或误区**

- 追问：“HTTPS 比 HTTP 多什么？”核心是 TLS 提供传输加密、完整性和服务器身份验证；并不自动保证应用无漏洞。
- 误区：看到页面打不开就先清空所有缓存，导致现场证据丢失。
- 误区：认为一个域名永远只解析到一个固定 IP。

## 05. Linux 中如何快速查看日志并定位某次请求？

**岗位考点**

市场岗位高频的 Linux 命令、证据链和日志分析。

**参考答案**

先明确文件、服务和时间范围，再逐步缩小：

```bash
# systemd 管理的虚构服务
journalctl -u demo-api --since "2026-07-27 10:00:00" --until "2026-07-27 10:10:00"

# 持续观察文件
tail -F /var/log/demo-api/app.log

# 按虚构 Trace ID 精确检索并带上下文
grep -n -C 3 'trace-demo-123' /var/log/demo-api/app.log

# 统计日志中的 HTTP 状态码（字段位置需按真实格式调整）
awk '{count[$9]++} END {for (code in count) print code, count[code]}' access.log
```

优先使用请求 ID/Trace ID 关联网关、服务和下游；同时记录时区、实例、容器和版本。大日志先按时间、级别和标识缩小，避免无条件打印全部内容。

**原理或实践解释**

`grep` 找文本，`tail -F` 适合日志轮转后的持续跟踪，`less` 适合交互式搜索，`journalctl` 查询 systemd journal。若服务在容器或 Kubernetes 中，应按平台受控方式读取对应实例日志。任何日志导出前都要检查敏感信息与权限。

**常见追问或误区**

- 追问：“`tail -f` 和 `tail -F` 区别？”`-F` 会按名称重试，更适合发生轮转或文件重建的日志。
- 误区：只搜索 `ERROR`；业务错误可能以状态码、告警指标或非 ERROR 级别出现。
- 误区：在未授权渠道传递包含令牌、手机号或业务数据的日志。

## 06. Linux 中如何查看进程、端口、CPU、内存和磁盘？

**岗位考点**

环境检查、服务不可用和性能问题的基础排障。

**参考答案**

常用只读命令包括：

```bash
ps -ef                         # 进程快照
top                            # 动态观察 CPU/内存
ss -lntp                       # TCP 监听端口及进程（部分信息需权限）
lsof -iTCP:8000 -sTCP:LISTEN   # 查看虚构 8000 端口
free -h                        # Linux 内存概览
df -h                          # 文件系统空间
df -i                          # inode 使用情况
du -sh ./artifacts             # 指定目录占用
uptime                         # 运行时长与 load average
```

排障时把现象、进程、端口、资源、日志和依赖串起来。例如端口未监听先检查进程启动日志；磁盘满要查是文件系统、inode 还是配额；高 load 不一定等于 CPU 满，也可能有不可中断 I/O。

**原理或实践解释**

`df -h` 看文件系统容量，`df -i` 看 inode 是否耗尽，`du` 汇总目录中文件占用；三者回答的问题不同。`df` 与 `du` 可能因已删除但仍被进程打开的文件、挂载点或权限而不一致。`free` 中 available 比单看 free 列更有意义，因为 Linux 会利用内存做缓存。容器还要看 cgroup 限额，不能只看宿主机总量。

**常见追问或误区**

- 追问：“端口被占用怎么办？”先识别进程和归属，确认是否可停；不得看到 PID 就直接 `kill -9`。
- 误区：CPU 100% 一定是 Bug；需结合目标负载、核心数、吞吐和响应时间判断。
- 误区：测试命令使用未经解析的通配符或宽泛目录做删除操作。

## 07. Linux 文件权限 `rwx`、数字权限、管道和重定向如何理解？

**岗位考点**

环境搭建、脚本执行和安全基本功。

**参考答案**

权限分为所有者、所属组和其他用户三组。对普通文件，`r` 是读、`w` 是写、`x` 是执行；对目录，`r` 允许列出名称，`w` 允许创建/删除目录项，`x` 允许进入和访问目录项。数字表示中 `r=4,w=2,x=1`，例如 `750` 是所有者 `rwx`、组 `r-x`、其他无权限。

管道 `|` 把前一命令的标准输出交给后一命令；`>` 覆盖标准输出到文件，`>>` 追加，`2>` 重定向标准错误。权限应遵循最小授权，脚本能运行不代表应使用 `777`。

**原理或实践解释**

```bash
find ./reports -type f -name '*.log' -print
grep -R -n 'FAILED' ./reports > failed-lines.txt
```

以上示例先安全列出目标，再检索并把结果写到明确文件。自动化脚本应检查退出码，必要时使用 `set -euo pipefail`，但也要理解它会改变错误处理行为并编写显式恢复逻辑。

**常见追问或误区**

- 追问：“为什么目录有 `x` 才能访问文件？”目录的执行权限代表路径遍历/查找能力。
- 误区：权限问题一律 `chmod -R 777`，扩大安全风险且掩盖属主配置问题。
- 误区：认为管道后任一命令失败都会默认成为整个管道的失败状态；shell 默认行为需结合 `pipefail`。

## 08. `INNER JOIN`、`LEFT JOIN` 有什么区别？如何避免一对多连接造成重复？

**岗位考点**

SQL 关联查询、数据核验和结果基数意识。

**参考答案**

`INNER JOIN` 只返回连接条件匹配的行；`LEFT JOIN` 保留左表全部行，右表无匹配时对应列为 `NULL`。连接不是“把两个表横向拼一次”，结果行数由关系基数决定：一个用户有多个订单，连接后用户会出现多行，这是正确的一对多展开，不一定是重复数据。

```sql
SELECT u.id, u.name, o.id AS order_id
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id;
```

若只需每个用户的订单数，应先聚合或直接聚合连接结果：

```sql
SELECT u.id, u.name, COUNT(o.id) AS order_count
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id
GROUP BY u.id, u.name;
```

**原理或实践解释**

对 `LEFT JOIN`，右表条件放在 `WHERE` 可能过滤掉 `NULL` 行，使结果效果接近内连接；如果要保留无订单用户，限定订单状态通常写在 `ON` 条件中。用 `DISTINCT` 掩盖错误连接可能丢掉有意义的多行，应先理解基数。

**常见追问或误区**

- 追问：“如何找没有订单的用户？”`LEFT JOIN ... WHERE o.id IS NULL`，或使用 `NOT EXISTS`。
- 误区：连接条件漏掉租户、版本等关键键，产生笛卡尔放大。
- 误区：看到行数增加就直接加 `DISTINCT`。

## 09. `WHERE` 和 `HAVING` 有什么区别？`NULL` 为什么不能用 `= NULL`？

**岗位考点**

过滤顺序、聚合与 SQL 三值逻辑。

**参考答案**

`WHERE` 在分组和聚合前过滤输入行；`HAVING` 对分组后的结果过滤，通常使用聚合条件。例如查找订单数至少为 3 的虚构用户：

```sql
SELECT user_id, COUNT(*) AS order_count
FROM orders
WHERE status = 'completed'
GROUP BY user_id
HAVING COUNT(*) >= 3;
```

SQL 中 `NULL` 表示未知或缺失，与任何值做普通比较通常得到 `UNKNOWN`，包括 `NULL = NULL`。应使用 `IS NULL` 或 `IS NOT NULL`。`COUNT(*)` 统计行，`COUNT(column)` 不统计该列为 `NULL` 的行。

**原理或实践解释**

SQL 条件不只有真和假，还有未知；`WHERE` 只保留为真的行。因此 `column <> 'x'` 也不会保留 `NULL`，如需保留要显式表达。测试数据应包含 `NULL`、空字符串和 0，因为三者语义不同。

**常见追问或误区**

- 追问：“能把聚合条件写 WHERE 吗？”一般不能直接在 `WHERE` 使用当前层聚合结果；可用 `HAVING` 或子查询。
- 误区：把 `NULL` 当成空字符串。
- 误区：`LEFT JOIN` 后用 `COUNT(*)` 统计右表对象，导致无匹配时也计为 1；应数右表非空键。

## 10. 数据库事务的 ACID 是什么？`COMMIT` 和 `ROLLBACK` 如何使用？

**岗位考点**

数据一致性、失败恢复和数据库测试。

**参考答案**

ACID 常解释为：原子性（事务内操作全部成功或全部不生效）、一致性（事务把数据库从满足约束的状态带到另一个满足约束的状态）、隔离性（并发事务的中间影响按隔离规则受控）、持久性（提交确认后结果在约定故障模型下不会丢失）。

事务通常以 `BEGIN` 开始，成功后 `COMMIT`，失败或不接受结果时 `ROLLBACK`。事务本身不能自动保证业务规则正确；约束、正确 SQL、应用逻辑和跨系统一致性方案仍然需要测试。

```sql
BEGIN;
UPDATE inventory SET available = available - 1
WHERE product_id = 101 AND available > 0;
-- 检查影响行数并创建虚构订单
COMMIT;
```

**原理或实践解释**

原子条件 `available > 0` 配合检查影响行数，可以避免简单“先查库存再扣减”的部分竞态，但完整方案还涉及订单写入、唯一约束和外部消息。测试需验证中途异常时是整体回滚、保存点回滚，还是通过补偿达到最终一致。

**常见追问或误区**

- 追问：“数据库提交后消息发送失败怎么办？”这是跨资源一致性问题，可讨论 outbox、可靠消息和补偿，并测试重试与去重。
- 误区：把一致性理解成“多个副本每时每刻完全相同”这一种含义。
- 误区：测试脚本忘记回滚，污染共享环境。

## 11. 常见事务隔离问题有哪些？隔离级别越高越好吗？

**岗位考点**

并发数据库行为、脏读、不可重复读、幻读和权衡。

**参考答案**

常见现象及判定边界如下：

| 现象 | 最小判定条件 |
| --- | --- |
| 脏读 | 事务 A 读到了事务 B 尚未提交、且之后可能回滚的值 |
| 不可重复读 | A 在同一事务内重读同一行，读到了 B 已提交的新值 |
| 幻读 | A 在同一事务内重跑同一谓词，命中的行集合因 B 的提交而变化 |
| 丢失更新 | 两个事务基于旧值写回，其中一次更新未被检测地覆盖 |
| 写偏差 | 两个事务读取同一业务不变量，却更新不同记录，提交后的组合状态破坏不变量 |

SQL 标准主要定义隔离级别和若干读现象；丢失更新、写偏差等还需结合产品语义分析。具体数据库通过锁、MVCC 或序列化检测实现隔离，实际允许和阻止什么应以目标产品及版本文档为准。

更高隔离通常提供更接近串行执行的结果，但可能增加锁等待、冲突重试或降低吞吐，不是无条件越高越好。应根据业务不变量选择隔离与并发控制，并在真实目标数据库上用两个独立会话编排测试。

**原理或实践解释**

可以让会话 A 开启事务读取库存，会话 B 修改并提交，再让 A 重读，观察目标隔离级别行为。测试要记录数据库版本、隔离配置、语句顺序和提交点。用单连接顺序执行无法验证隔离。

**常见追问或误区**

- 追问：“MySQL 与 PostgreSQL 的 Repeatable Read 完全一样吗？”不能假定一样；默认级别和 MVCC/锁行为有产品差异。
- 误区：背诵一张现象表后对所有数据库套用。
- 误区：忽略应用重试，序列化冲突返回后直接把业务判为失败。

## 12. 索引为什么能加快查询？为什么索引不是越多越好？如何看执行计划？

**岗位考点**

数据库性能、查询计划和基于证据优化。

**参考答案**

索引维护有序或专门的数据结构，使数据库不必扫描全部行即可定位候选记录，并可支持排序、唯一性或覆盖查询。代价是占用空间，插入/更新/删除时需要维护，统计信息和缓存也增加成本。低选择性条件、小表、返回大量行或表达式不匹配时，优化器可能合理选择全表扫描。

使用 `EXPLAIN` 查看计划中的扫描方式、连接顺序、估算行数和成本；需要实际统计时可用目标数据库支持的 `EXPLAIN ANALYZE`。后者会真正执行语句：对写语句可能改数据、持锁并触发触发器，对昂贵查询也可能造成明显负载。应先查目标数据库文档，只在隔离环境和可控数据上执行；即使计划用事务回滚，也要确认外部副作用是否可回滚。比较估算与实际行数有助于发现统计信息或数据分布问题。

**原理或实践解释**

联合索引是否有效与列顺序、查询谓词和数据库实现有关。`WHERE status='done'` 若大多数行都是 done，索引可能收益低；`WHERE user_id=? AND created_at>=?` 可能更适合相应组合索引。性能结论应基于代表性数据量和重复测量，不只看“是否走索引”。

**常见追问或误区**

- 追问：“函数包裹索引列会怎样？”可能导致普通索引无法直接使用，取决于数据库是否支持表达式/函数索引和优化规则。
- 误区：看到顺序扫描就认定是慢查询。
- 误区：直接在生产大表执行带实际运行的分析命令。

## 13. 测试人员常用哪些 SQL 检查数据质量？

**岗位考点**

重复、孤儿、聚合一致性和测试预言。

**参考答案**

常见检查应来自业务不变量，而不是为了展示复杂 SQL。例如：

```sql
-- 查找不应重复的外部请求键
SELECT request_key, COUNT(*) AS n
FROM orders
GROUP BY request_key
HAVING COUNT(*) > 1;

-- 查找引用了不存在用户的孤儿订单
SELECT o.id
FROM orders AS o
LEFT JOIN users AS u ON u.id = o.user_id
WHERE u.id IS NULL;

-- 检查金额组成是否一致（示例规则要求各组成项非空）
SELECT id, total_amount, item_amount + shipping_amount - discount_amount AS expected
FROM orders
WHERE total_amount IS NULL
   OR item_amount IS NULL
   OR shipping_amount IS NULL
   OR discount_amount IS NULL
   OR total_amount <> item_amount + shipping_amount - discount_amount;
```

执行前明确字段含义、`NULL`、币种、精度、舍入、软删除、状态和一致性窗口。若业务把空折扣定义为 0，可以按已确认规则使用 `COALESCE(discount_amount, 0)`；不能为让查询“有结果”而自行改写业务语义。查询结果为 0 只说明当前样本未违反这个规则。

**原理或实践解释**

最好把关键不变量变成数据库约束、接口断言或持续监控，而不是发布前临时查一次。对最终一致系统，要在约定等待窗口后验证；对快照数据，要记录查询时间和版本。

**常见追问或误区**

- 追问：“测试能直接改数据库造数据吗？”仅在获授权的隔离环境按约定执行，并优先走公开接口或数据工厂；生产写操作风险极高。
- 误区：将真实数据导出到个人环境练 SQL。
- 误区：用浮点直接比较金额，不考虑数据库 decimal 和舍入规则。

## 14. Git 的工作区、暂存区和仓库是什么？`add`、`commit`、`push` 分别做什么？

**岗位考点**

版本控制基本模型和安全提交习惯。

**参考答案**

工作区是当前检出的文件；暂存区（index）保存准备进入下一次提交的快照；本地仓库保存提交对象与引用。`git add` 把选定的工作区内容放入暂存区，`git commit` 用暂存区创建本地提交，`git push` 把本地引用和对象发送到远端。

因此 `commit` 不等于已上传，`add` 也不是“让 Git 永久跟踪一次就结束”。提交前应分别用 `git diff` 看未暂存改动、`git diff --staged` 看将提交内容，并检查敏感文件和无关变更。

**原理或实践解释**

推荐小而完整的提交：只包含一个逻辑目标，测试和说明一起更新，提交信息解释为什么。`.gitignore` 只能阻止未跟踪文件被默认加入；已经提交过的密钥不会因加入 ignore 自动从历史消失。

**常见追问或误区**

- 追问：“`git status` 显示 clean 是否等于远端一致？”不一定，本地可能有未推送提交或与远端分叉。
- 误区：使用 `git add .` 后不审查暂存内容。
- 误区：把公司配置、令牌、日志或真实数据提交后再删除，就认为泄露已消失。

## 15. `git merge` 和 `git rebase` 有什么区别？什么时候使用？

**岗位考点**

提交图理解、协作历史和安全操作。

**参考答案**

`merge` 把两个开发历史合并，通常创建一个有两个父提交的 merge commit（能快进时除外），保留分叉结构。`rebase` 把一组提交复制并重新应用到新的基点，形成新的提交 ID，使历史更线性。

本地尚未共享的功能分支可以在团队约定下 rebase，整理后再合并；已经被其他人基于其开发的公共历史不应随意改写并强推。选择取决于团队审计、发布和历史策略，不存在所有项目唯一最佳方案。

**原理或实践解释**

两者遇到内容冲突都需要人工理解。Rebase 可能在重放多个提交时多次解决冲突；merge 通常在合并点集中解决。无论采用哪种方式，解决后都应运行测试并审查最终 diff，不能只以“命令成功”为标准。

**常见追问或误区**

- 追问：“rebase 会丢代码吗？”正确操作不会有意丢失，但它改写提交；误解冲突或错误强推可能覆盖远端历史。
- 误区：把“线性历史”当成比可追踪和安全协作更高的目标。
- 误区：在不理解影响时对共享主分支执行交互式 rebase。

## 16. Git 冲突如何处理？

**岗位考点**

协作、代码理解、验证与风险控制。

**参考答案**

先用 `git status` 确认正在进行 merge、rebase 还是 cherry-pick，以及冲突文件。理解双方变更的业务意图，编辑冲突标记，不能机械保留某一侧；随后 `git diff` 检查，运行相关测试，`git add` 标记已解决，再按当前操作执行 `git merge --continue`、`git rebase --continue` 等。若判断不应继续，使用对应的 `--abort` 回到操作前状态。

复杂冲突应联系原作者或领域负责人。配置、数据库迁移、生成文件和测试预期尤其需要语义审查，即使 Git 没报文本冲突也可能存在逻辑冲突。

**原理或实践解释**

冲突是 Git 无法自动决定内容，不代表某一方错误。测试代码冲突解决后应确认产品代码和测试是否仍表达同一规则。提交前搜索残留的 `<<<<<<<` 等标记只是最低检查，不能替代编译和测试。

**常见追问或误区**

- 追问：“ours/theirs 永远指谁？”其含义会随 merge/rebase 上下文变化，不能凭记忆盲选，应先看文档和 diff。
- 误区：删除冲突标记后就算解决。
- 误区：使用破坏性命令丢弃整个工作区来逃避一个文件冲突。

## 17. `revert`、`reset` 和 `restore` 有什么区别？

**岗位考点**

撤销操作、共享历史和数据安全。

**参考答案**

`git revert <commit>` 创建一个新提交来反向应用指定提交，保留历史，通常适合撤销已经共享的提交。`git reset` 移动当前分支指针，并根据 `--soft`、默认 mixed 或 `--hard` 决定如何处理暂存区和工作区；它适合在明确理解影响的本地历史中使用。`git restore` 用于恢复工作区或暂存区中的文件内容，不移动分支历史。

撤销前先执行 `git status`、`git log` 和 `git diff`，确认目标、是否已推送以及未提交工作。共享分支优先用可审计的 revert；`reset --hard <target>` 会把分支、暂存区和受影响的已跟踪工作区内容重置到目标提交，未提交改动会丢失。它不是用于清理全部未跟踪文件的 `git clean`，但妨碍写入目标树的未跟踪路径也可能被删除，因此不应在目标或现场不明确时使用。

**原理或实践解释**

如果一个已上线提交需要回退，用 revert 能让团队看到“加入”和“撤销”的两个事件；如果只是把误加入暂存区的文件拿出，可用 `git restore --staged <file>`，工作区内容仍保留。不同问题应选最小影响的工具。

**常见追问或误区**

- 追问：“误删提交还能恢复吗？”本地对象未被清理时可能通过 reflog 找回，但不能把它当成安全备份策略。
- 误区：把 reset、revert 都称为回滚而不说明是否改写历史。
- 误区：在有未保存工作时复制执行网上的 `reset --hard`。

## 18. `git fetch` 和 `git pull` 有什么区别？如何安全同步远端？

**岗位考点**

远端跟踪分支、同步策略和变更审查。

**参考答案**

`git fetch` 下载远端对象并更新远端跟踪引用，不自动修改当前分支工作区；`git pull` 通常等价于先 fetch，再按配置 merge 或 rebase 当前分支。因此希望先审查差异时，fetch 更可控。

一个安全流程是：确认工作区状态；`git fetch origin`；查看 `git log --oneline --graph --decorate --all` 和本地与 `origin/<branch>` 的 diff；确认后再 merge 或 rebase。若本地有未完成工作，先提交到合适分支或使用明确的 stash 策略，不要让 pull 意外混合多类改动。

**原理或实践解释**

远端跟踪分支只是本地记录的上次远端状态，只有 fetch 后才更新。“Your branch is up to date”是相对当前本地记录而言，长时间不 fetch 时可能已过时。CI 失败还应核对触发的具体提交，而非只看分支名称。

**常见追问或误区**

- 追问：“pull 一定生成 merge commit 吗？”不一定；可能快进，也可能按配置 rebase。
- 误区：把 fetch 说成“只看不下载”；它会下载对象，只是不合并当前分支。
- 误区：同步前不看工作区和分叉状态。

## 19. 如何用 Git 帮助定位“从哪个提交开始出错”？

**岗位考点**

版本二分、可复现测试和工程化排障。

**参考答案**

在能给出一个已知好提交和一个已知坏提交、且问题可重复判定时，可以使用 `git bisect` 做二分搜索：

```bash
git bisect start
git bisect bad
git bisect good <known-good-commit>
# 在 Git 选出的提交上执行最小复现，标记 good 或 bad
git bisect reset
```

如果有稳定自动化脚本，可用 `git bisect run <test-command>`。按 Git 官方约定，退出码 `0` 表示 good，`1`～`127`（`125` 除外）表示 bad，`125` 表示当前提交无法测试并跳过；测试脚本本身的“命令不存在”等错误不能被误报成产品 bad。定位出的提交只是第一个表现为坏的候选，还要审查依赖、环境和测试本身。

**原理或实践解释**

二分搜索比逐个提交验证更快，但要求每个被测提交可构建且测试预言稳定。数据库迁移、外部服务变化或 flaky test 会污染结论，可以为无法判断的提交标记 skip，并固定依赖和合成数据。

**常见追问或误区**

- 追问：“找到提交就等于找到责任人吗？”不是；目标是定位引入行为变化的代码和系统条件，提交作者不等于事故唯一责任人。
- 误区：在脏工作区直接 bisect，混入未提交改动。
- 误区：用不稳定 UI 用例自动判定，最终得到随机候选。

## 20. 测试项目的分支和 CI 应如何配合？

**岗位考点**

Git、自动化测试、质量门禁和团队交付实践。

**参考答案**

常见原则是短生命周期分支、小批量变更、通过 Pull/Merge Request 评审，并让 CI 对同一提交运行分层检查。快速的格式、静态检查、单元和核心接口测试先反馈；较慢的 UI、性能或安全检查按风险在合并前、定时或发布阶段执行。测试报告、日志和 trace 作为有保留期的制品，失败应可定位。

门禁应有明确的阻断规则和例外审批，避免把 flaky test 长期设为“重跑直到绿”。测试代码与产品或契约变更应保持可追溯；环境、依赖和测试数据尽量可重复。受保护分支禁止直接随意推送和改写历史。

**原理或实践解释**

虚构项目可规定：PR 必须通过静态检查、API 烟测和少量浏览器测试；合并后跑完整接口回归；夜间运行更广兼容矩阵。失败时保存请求响应、Playwright trace 和版本信息，但不能上传密钥或真实业务数据。

**常见追问或误区**

- 追问：“自动化失败是否必须阻断？”可信且对应高风险的检查应阻断；已确认 flaky 的用例应隔离、修复并记录风险，不能长期随机阻断。
- 误区：CI 绿色等于可以无条件上线。
- 误区：为了流水线速度删除关键断言，而不做风险取舍。
