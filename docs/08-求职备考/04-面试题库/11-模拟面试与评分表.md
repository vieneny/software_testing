## 一、通用评分量表

每个维度 0～4 分，总分 24 分。

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 | 4 分 |
|---|---|---|---|---|---|
| 概念正确性 | 核心错误 | 大量混淆 | 基本正确但有缺口 | 正确且条件清楚 | 能解释例外与取舍 |
| 分析结构 | 无法回答 | 零散关键词 | 有步骤但主次不明 | 结论和步骤清晰 | 能建立模型并动态收敛 |
| 实践落地 | 无行动 | 只报工具名 | 有普通操作步骤 | 有数据、断言和失败处理 | 能设计可维护反馈系统 |
| 证据意识 | 凭感觉 | 只说“看日志” | 知道若干证据 | 能关联请求、数据和指标 | 能设计可观察性与可证伪实验 |
| 风险与边界 | 绝对化承诺 | 很少谈风险 | 能说部分限制 | 能排序并声明残余风险 | 能提出决策、监控与回滚条件 |
| 沟通真实性 | 编造或泄密 | 回避追问 | 基本真实但模糊 | 清楚区分个人/团队、练习/生产 | 诚实且能把不足转成验证计划 |

### 分数解释

- **0～9：需要回到教程。** 概念和表达尚未形成稳定结构；
- **10～15：初步可答。** 能回答基础问题，但经不起连续追问；
- **16～19：岗位可用。** 大多数回答有行动和证据，可进入针对性实操；
- **20～22：较强。** 能处理边界、失败和权衡；
- **23～24：不要追求常态满分。** 只有题目刚好与深入实践匹配时才合理。

总分不能跨题直接比较。例如基础题得 22 分不等于高级系统设计已经合格。

## 二、初级软件测试模拟（45 分钟）

### 结构

1. 自我介绍：2 分钟；
2. 测试基础：10 分钟；
3. 功能场景：12 分钟；
4. HTTP/SQL/Linux：12 分钟；
5. 项目与反问：9 分钟。

### 题单与合格要点

| 题目 | 合格要点 | 推荐追问 |
|---|---|---|
| 软件测试的目标是什么？ | 发现风险并提供质量信息，不承诺穷尽缺陷 | 测试和调试有何区别？ |
| 冒烟和回归如何选择？ | 目的、范围、触发时机和风险选择不同 | 只有一小时怎么回归？ |
| 给登录功能设计用例 | 输入、状态、权限、安全、兼容和可观察结果 | 验证码、锁定和多端登录呢？ |
| 如何写高质量缺陷？ | 环境、步骤、期望/实际、证据、影响、最小复现 | 难以复现怎么办？ |
| GET 与 POST 有什么区别？ | 语义、幂等/安全属性、缓存，不用“长度/安全”绝对化 | 重试哪个更安全？ |
| SQL 怎样查重复记录？ | 能用 `GROUP BY ... HAVING COUNT(*) > 1` 并解释口径 | `NULL` 怎样处理？ |
| Linux 怎样定位某端口服务？ | 知道 `ss`/`lsof`、进程与日志关联 | 容器里又怎样查？ |
| 开发说不是缺陷怎么办？ | 证据、规则、影响、决策人和记录 | 需求没有写呢？ |

### 通过标准

- 没有严重事实错误；
- 至少 6 题能给出具体行动；
- 场景题覆盖正常、边界、异常和权限；
- 不编造工作经历，不泄露任何公司信息。

## 三、自动化测试模拟（60 分钟）

### 结构

1. 项目与框架：10 分钟；
2. Python/pytest：15 分钟；
3. API：15 分钟；
4. UI 自动化：12 分钟；
5. CI 与失败定位：8 分钟。

### 题单与合格要点

| 题目 | 合格要点 | 推荐追问 |
|---|---|---|
| 自动化框架如何分层？ | 用例、业务/API 客户端、数据、配置、断言、报告分离 | 什么时候不要再抽象？ |
| pytest fixture 的作用域怎样选？ | 生命周期与隔离成本平衡，避免跨用例污染 | 并行执行有什么风险？ |
| 参数化与数据驱动有何边界？ | 相同逻辑、多数据适合参数化；复杂分支应拆用例 | 怎样让失败易读？ |
| 如何测试接口幂等？ | 相同键相同请求、相同键不同请求、重试和并发 | 数据库怎样核对？ |
| 契约测试解决什么问题？ | 消费者/提供者变化反馈，不替代端到端业务验证 | 版本兼容怎么办？ |
| 为什么 UI 用例容易 flaky？ | 等待、选择器、共享数据、环境、异步依赖和资源 | 如何量化并治理？ |
| Playwright 与 Selenium 怎么选？ | 新项目能力、语言/浏览器/生态、存量资产与团队成本 | 移动原生应用呢？ |
| CI 中测试怎么分层？ | 快速检查先行，风险与时长分组，制品和失败证据 | flaky 能否自动重跑？ |

### 实操加试

从 Demo Shop 中任选一个接口：

1. 写一个正向和一个异常 pytest 用例；
2. 解释数据如何隔离；
3. 故意制造断言失败并定位；
4. 说明如何接入 CI 以及保存哪些制品。

只展示绿色运行结果不能得高分，必须能解释失败路径。

## 四、中高级质量工程模拟（75 分钟）

### 结构

1. 系统与质量策略：15 分钟；
2. 性能/稳定性：15 分钟；
3. CI/CD 与测试架构：20 分钟；
4. 故障定位：15 分钟；
5. 团队与取舍：10 分钟。

### 题单与合格要点

| 题目 | 合格要点 | 推荐追问 |
|---|---|---|
| 怎样制定一个系统的测试策略？ | 用户价值、架构、风险、层次、环境、数据、门禁和残余风险 | 证据不足如何发布？ |
| P95 变差但平均值不变说明什么？ | 尾部请求退化，要按路由/实例/依赖/时间分解 | 如何避免聚合指标误导？ |
| 如何由业务量推导并发？ | 到达率、服务时间、峰值系数和 Little 定律，注明假设 | 闭环模型有什么不同？ |
| 质量门禁应包含什么？ | 少而可靠的阻断信号、风险阈值、例外流程和反馈时延 | 谁能豁免？ |
| 如何治理 flaky test？ | 分类、测量、修复责任、隔离、根因和退出标准 | 重跑通过算成功吗？ |
| 如何设计测试数据服务？ | 模板、版本、隔离、隐私、幂等创建、清理和可追溯 | 并行冲突怎么办？ |
| 线上偶发错误怎么定位？ | 关联 ID、日志/指标/Trace、成功失败对照和故障注入 | 没有 Trace 怎么办？ |
| 自动化投入如何评估？ | 风险反馈价值、执行频率、维护成本、失败诊断和替代方案 | 覆盖率是否越高越好？ |

### 系统设计评分附加项

- 能画出数据流和控制流：加分；
- 能定义 SLI、阈值和验证证据：加分；
- 能说明降级、回滚与残余风险：加分；
- 只画工具 Logo、没有故障模型：不得因图复杂而加分。

## 五、AI 测试专项模拟（75 分钟）

### 结构

1. AI 系统边界：10 分钟；
2. 评测设计：20 分钟；
3. RAG/Agent：20 分钟；
4. 安全与在线治理：15 分钟；
5. 传统质量基础：10 分钟。

### 题单与合格要点

| 题目 | 合格要点 | 推荐追问 |
|---|---|---|
| AI 测试和传统断言有什么不同？ | 非确定性、多维质量、抽样、重复运行和人工校准 | 哪些仍可确定性断言？ |
| 怎样构建评测集？ | 任务分层、真实分布代理、困难/安全样本、标签规范、版本与泄漏控制 | 如何维护新鲜度？ |
| LLM-as-a-judge 有什么风险？ | 位置/长度/风格偏差、自洽错误、模型污染和成本 | 如何校准？ |
| RAG 评测为什么要拆层？ | 检索、上下文、生成、引用和端到端任务各有不同根因 | 召回高但答案差呢？ |
| 如何测试 Agent？ | 任务成功、工具选择/参数、状态、停止条件、权限、恢复、成本 | 死循环怎样检测？ |
| 什么是提示注入？ | 直接/间接攻击、信任边界、最小权限、输出验证和人工确认 | 仅靠系统提示够吗？ |
| AI 版本如何做回归？ | 固定数据/配置、重复采样、基线比较、显著退化门禁和人工复核 | 模型被供应商更新呢？ |
| AI 测试结果怎样上线监控？ | 质量代理、反馈、漂移、延迟、成本、安全事件和抽样复核 | 标签延迟怎么办？ |

### 通过标准

候选人必须同时展示传统系统测试基础和 AI 特有方法。只会调用模型 API 或只背指标名称，不足以证明 AI 测试能力。

## 六、追问生成器

对任何回答依次追问：

1. **为什么？** 原理或风险依据是什么？
2. **如何证明？** 观察哪些输出、日志、指标或数据？
3. **失败怎么办？** 超时、并发、重试、部分失败时怎样处理？
4. **条件变化呢？** 数据规模、权限、网络和工具版本改变会怎样？
5. **替代方案？** 为什么不用另一种方法？
6. **边界在哪？** 什么结论不能由当前实验推出？

如果一个回答经不起其中两轮追问，就标记为“知道名词，尚未形成能力”。

## 八、四周训练节奏

| 周次 | 重点 | 验收 |
|---|---|---|
| 第 1 周 | 基础、功能、HTTP、SQL、Linux | 初级模拟达到 16 分以上 |
| 第 2 周 | Python、API 与 UI 自动化 | 实操失败可独立定位 |
| 第 3 周 | 性能、CI/CD、项目与场景题 | 中高级题能说清证据和边界 |
| 第 4 周 | 目标 JD 定制、AI 专项或弱项 | 完成 3 次全真模拟并复盘 |

每周只选择 2～3 个高价值弱项做实验。重复阅读答案不等于训练。
