# 性能测试与稳定性经典面试题

> 适用岗位：性能测试工程师、自动化测试工程师、测试开发工程师、质量工程师。
> 核对日期：2026-07-29。文中的商城、订单和报表系统均为虚构示例，不代表任何真实业务。

性能面试不只考工具命令，更看重候选人能否把业务目标转换为负载模型、用可信指标判断结果，并沿调用链定位瓶颈。选题对应公开性能岗位常见的 JMeter/Locust、Linux、监控、容量与瓶颈分析能力信号；回答时应始终说明测试前提、观测证据和结论边界。

## Q01：怎样建立一套完整的性能指标模型？

**岗位考点**

业务指标、服务级目标、技术指标和资源指标的分层设计能力。

**参考答案**

我会从目标向下建立四层指标：

1. **业务层**：每分钟成功下单数、报表生成成功率、关键用户旅程完成率；
2. **服务层**：吞吐量、成功率、P50/P95/P99 延迟、可用性，以及明确统计窗口的 SLI/SLO；
3. **应用层**：线程池/连接池使用率、队列积压、缓存命中率、GC 暂停、依赖调用耗时与错误；
4. **资源层**：CPU、内存、磁盘 I/O、网络、文件描述符及容器限额和节流。

例如虚构订单接口的准入标准可写成：“稳定 600 RPS 持续 30 分钟时，业务成功率不低于 99.9%，成功请求 P95 小于 300 ms、P99 小于 800 ms，无库存负数；应用和数据库无持续积压，压测结束后 10 分钟内资源回到基线。”具体阈值必须来自产品目标、历史基线或容量预算，不能照抄示例。

**原理或实践解释**

只看平均响应时间会漏掉长尾，只看 CPU 会把“资源空闲但锁等待严重”误判为健康。常用的 RED 方法关注请求速率、错误和时延，USE 方法关注资源利用率、饱和度和错误；二者要与业务正确性结合。指标还要写清口径：客户端还是服务端耗时、是否只统计成功请求、百分位的聚合窗口、重试是否重复计数。

**常见追问或误区**

- 追问：TPS 和 QPS 有何区别？答：QPS/RPS 通常按请求计数，TPS 应按完成的业务事务计数；一个事务可能产生多个请求。
- 误区：把“CPU 低于 80%”当成通用通过标准，忽略线程、锁、I/O、配额和业务错误。

## Q02：负载测试、压力测试、峰值测试、容量测试和稳定性测试有什么区别？

**岗位考点**

测试类型选择、实验目标和停止条件。

**参考答案**

| 类型 | 主要回答的问题 | 典型负载与重点证据 |
| --- | --- | --- |
| 基准/基线测试 | 当前版本和环境的可比较起点是什么 | 可控小负载；延迟、吞吐、资源基线 |
| 负载测试 | 预期正常及峰值负载下是否满足 SLO | 目标业务负载；成功率、百分位和业务正确性 |
| 压力测试 | 超过预期能力后怎样失效、能否恢复 | 逐级超过目标；拐点、限流、降级和恢复 |
| 峰值/突发测试 | 流量快速升降时系统能否承受 | 陡增/陡降；队列、扩缩容滞后和丢弃 |
| 容量测试 | 给定资源和 SLO 下的安全上限是多少 | 多级稳态；最大达标吞吐及安全余量 |
| 稳定性/浸泡测试 | 长时间运行是否持续退化 | 代表性长期负载；泄漏、句柄和慢性积压 |
| 伸缩性测试 | 增加资源的收益和边界是什么 | 改变实例/资源；伸缩效率、共享瓶颈和成本 |

一次测试可以组合阶段，但每个阶段应有独立目标和判定。压力测试尤其要预先约定保护措施、最大负载、停止条件和恢复观察窗口。

**原理或实践解释**

测试名称的价值在于明确假设。例如负载测试回答“目标流量能否达标”，压力测试回答“超过能力后如何坏、能否恢复”，二者不是简单地把并发数调大。若没有故障隔离、限流和授权，不应对生产环境做破坏性压力实验。

**常见追问或误区**

- 追问：什么时候做峰值测试？答：流量具有突发性、依赖弹性扩容或消息缓冲时，应单独验证上升速率和扩容滞后。
- 误区：将长时间运行都叫压力测试，导致目标、通过标准和风险控制不清。

## Q03：并发用户数、在线用户数、RPS 和吞吐量之间如何换算？

**岗位考点**

工作负载建模、用户思考时间和开放/封闭模型。

**参考答案**

这些指标不能直接一一等同。在线用户可能很久不发请求；并发用户通常表示正在执行场景或请求的虚拟用户；RPS 是单位时间到达的请求数。粗略估算时可用：

```text
用户循环速率 ≈ 并发用户数 / 平均循环时长
请求 RPS ≈ 用户循环速率 × 每个循环的平均请求数
```

平均循环时长应包含一轮内所有串行请求的等待时间、思考时间和客户端处理时间；若一轮包含并行请求，则不能把单请求平均响应时间简单相加。例如 300 个虚拟用户，每轮包含 3 个串行请求，整轮总计平均 6 秒，理想情况下约为 `300 / 6 × 3 = 150 RPS`。真实值会受分支、失败重试、并行请求、缓存、网络和工具自身能力影响，必须实测。

我还会区分：

- **封闭模型**：固定虚拟用户完成一轮再发下一轮；系统变慢时到达率会自然下降；
- **开放模型**：按外部到达率持续注入请求；更适合模拟不因系统变慢而停止到达的流量。

**原理或实践解释**

如果业务目标是“每秒 500 个请求到达”，仅配置固定线程并不能保证到达率。当系统变慢，线程被占住，实际 RPS 会下降，可能掩盖排队和过载风险。反过来，只追 RPS 而没有真实会话、思考时间和数据分布，也可能生成不可信负载。

**常见追问或误区**

- 追问：1 万在线用户是否等于 1 万并发？答：不等于，应从访问频率、会话行为和峰值到达率推导活跃并发。
- 误区：只报线程数，不验证负载机实际产生的 RPS、网络带宽和 CPU。

## Q04：什么是 Little 定律？如何用于性能测试？

**岗位考点**

排队论基础、容量估算和指标交叉校验。

**参考答案**

在稳定系统中，Little 定律可写为：

```text
L = λ × W
```

`L` 是所定义系统边界内的平均在途数量，`λ` 是通过该边界的长期平均流率，`W` 是平均停留时间。稳定且无持续积压时，到达率与离开率长期趋于一致；若存在丢弃、超时或重试，要把所有离开路径和重复流量计入口径。虚构报表服务稳定完成 200 请求/秒，平均端到端停留时间为 0.4 秒，则平均约有 `200 × 0.4 = 80` 个请求处于系统中。

实践中我用它做三件事：

1. 估算所需并发或连接规模；
2. 检查吞吐、延迟和在途请求数是否大致自洽；
3. 解释延迟上升：吞吐已到平台期而在途数量持续增加，通常意味着排队加剧。

**原理或实践解释**

Little 定律依赖长期平均和相对稳定的边界，不能把一次瞬时 P99 直接代入平均公式，也不能忽略超时、丢弃和重试改变了系统边界。使用前要说明“系统”包含客户端等待、网关排队还是仅服务内部，以及 `λ` 采用到达率还是成功完成率。

**常见追问或误区**

- 追问：吞吐不变而响应时间翻倍会怎样？答：在稳定口径下，平均在途数量约翻倍，常表现为队列或连接占用增加。
- 误区：用 Little 定律精确预测非稳态峰值，或混用平均吞吐与百分位延迟。

## Q05：为什么性能报告要看 P95/P99，而不能只看平均值？

**岗位考点**

延迟分布、长尾、百分位与统计口径。

**参考答案**

平均值会被分布形状掩盖。若 99 个请求耗时 100 ms、1 个请求耗时 10 s，平均值约 199 ms，看似不高，但最慢的用户体验非常差。P95 表示约 95% 的观测值不大于该值，P99 更关注尾部。

报告中我通常同时给出：

- 样本数与时间窗口；
- P50、P90/P95、P99 和最大值；
- 成功与失败请求是否分开；
- 按接口、场景、状态码和版本切分；
- 直方图或时间序列，避免仅有整场聚合值。

**原理或实践解释**

百分位也可能误导：样本过少时 P99 不稳定；把多个实例的 P99 再求平均并不等于全局 P99；直方图桶过粗会降低精度。应尽量在原始分布或可合并直方图上聚合，并保持基线与候选版本相同口径。

**常见追问或误区**

- 追问：P99 为 800 ms 是否表示所有请求都低于 800 ms？答：不是，仍约有 1% 样本更慢。
- 误区：只优化 P99，不观察错误、超时被排除以及 P99 之外的极端故障。

## Q06：怎样设计真实、可重复的负载模型？

**岗位考点**

流量画像、场景权重、数据参数化和实验控制。

**参考答案**

我会先基于允许使用的公开或自造数据建立画像：

1. 确定关键用户旅程及风险，例如浏览 60%、搜索 25%、下单 10%、查询订单 5%；
2. 明确峰值 RPS、到达曲线、会话时长、思考时间和地理/网络条件；
3. 建立数据分布，包括热商品、冷商品、缓存命中与未命中、已登录和匿名；
4. 处理关联和唯一数据，例如从登录响应提取令牌、为每个虚拟用户生成虚构订单号；
5. 固定脚本、数据版本、随机种子、环境和构建版本；
6. 先单用户校验正确性，再小流量校准，最后分阶段升压。

负载模型必须记录假设；缺少生产画像时，应给出高、中、低多个情景，而不是伪造“真实流量”。

**原理或实践解释**

缓存、数据热点和用户路径会显著改变瓶颈。所有用户请求同一个对象可能把测试变成缓存命中实验；所有请求都用唯一对象又可能高估冷缓存成本。可重复不等于数据完全相同，还要避免幂等冲突和测试间污染。

**常见追问或误区**

- 追问：能否直接导入生产日志？答：应先确认授权、用途、保留周期、最小化范围和脱敏有效性；不能把“做过脱敏”当作自动获得使用权限。
- 误区：录制一次脚本后不做参数化、关联和业务断言，就直接放大线程。

## Q07：什么是协调遗漏（Coordinated Omission）？如何避免？

**岗位考点**

负载生成模型、延迟测量偏差和过载场景。

**参考答案**

协调遗漏指负载发生器因为系统变慢而等待，原本应该到达的请求没有被发送，于是测得的延迟分布偏乐观。例如目标是每 100 ms 到达一个请求，但前一个请求卡住 2 秒；若同一线程等响应后才继续，这 2 秒内本应到达的多个请求被“遗漏”。

缓解方法包括：

- 根据业务选择开放到达率模型；
- 记录计划到达时间和实际完成时间；
- 确认工具调度器是否对遗漏做校正；
- 监控实际到达率与目标到达率的偏差；
- 单独观察排队、超时、丢弃和客户端积压。

**原理或实践解释**

封闭模型并非错误，它适合“用户完成后才进行下一步”的行为；问题在于用它回答外部到达率固定的问题。工具官方文档的警告也不能替代实验验证，应在故意注入延迟的虚构服务上确认脚本会如何表现。

**常见追问或误区**

- 追问：增加线程能否解决？答：可能暂时维持到达率，但会改变并发和资源占用，仍需明确模型并监控负载机。
- 误区：压测图很平滑就认为负载准确，没有对比“计划请求数”和“实际发送数”。

## Q08：拿到“接口变慢”的反馈，你如何定位瓶颈？

**岗位考点**

假设驱动排障、分布式追踪和跨层证据关联。

**参考答案**

我会先定义变慢的范围：哪个版本、接口、租户/数据规模、时间窗口、百分位和错误类型。然后按同一 Trace ID 或请求 ID 建立证据链：

1. 客户端：DNS、建连、TLS、发送、等待首字节和下载阶段；
2. 网关/负载均衡：排队、限流、重试、上游实例分布；
3. 应用：路由耗时、线程/协程、锁、GC、序列化和连接池；
4. 依赖：数据库、缓存、消息、对象存储和第三方的 span；
5. 基础设施：CPU 节流、内存回收、I/O、网络丢包、容器重启；
6. 变更：代码、配置、数据量、索引、流量结构和发布事件。

我会比较成功/失败、快/慢、旧/新版本样本，每次改变一个变量验证假设，而不是仅凭相关性下结论。

**原理或实践解释**

CPU 100% 与延迟上升可能相关，但不等于根因；也可能是下游超时引发重试风暴导致 CPU 上升。指标用于发现范围，Trace 用于拆解单次调用，日志提供事件细节，剖析器用于代码热点，它们应互相印证。

**常见追问或误区**

- 追问：所有服务 CPU 都不高为什么还慢？答：检查排队、锁、连接池、外部 I/O、配额和单核热点。
- 误区：一次压测同时改线程池、缓存和 SQL，最后无法判断哪个改动有效。

## Q09：如何判断数据库是性能瓶颈？

**岗位考点**

SQL、索引、连接池、事务锁和数据库观测。

**参考答案**

我会先从应用 Trace 证明时间主要消耗在数据库调用，再检查：

- 慢查询数量、执行时间分布和调用频率；
- 执行计划是否全表扫描、估算行数是否失真、索引是否命中；
- 锁等待、死锁、长事务和热点行；
- 连接池等待、活跃/空闲连接、连接创建和超时；
- 缓冲区命中、磁盘 I/O、CPU、临时表及排序；
- 主从延迟、读写路由和批量/逐条访问模式。

优化前保留查询、参数分布、执行计划和基线；优化后验证业务结果一致、写放大和存储成本没有不可接受地增加。

**原理或实践解释**

“加索引”不是万能答案。低选择性索引可能无效，过多索引会拖慢写入，函数或隐式类型转换可能导致索引失效。连接池过大还可能把应用排队转移成数据库争用。应优先减少不必要查询、解决 N+1、缩小扫描范围和缩短事务。

**常见追问或误区**

- 追问：数据库 CPU 低但接口等待数据库很久？答：可能在锁、I/O、连接池或远端网络等待，需看等待事件而非只看 CPU。
- 误区：只运行一条固定参数 SQL，忽略真实数据分布和参数敏感性。

## Q10：如何测试缓存、消息队列和异步系统的性能？

**岗位考点**

分布式组件、最终一致性、积压和故障恢复。

**参考答案**

缓存测试除命中率外，要覆盖热键、大 key、穿透、击穿、雪崩、过期抖动和缓存重建；比较冷启动、稳定命中和失效瞬间的延迟及后端压力。

消息/异步链路要分别测：

- 生产速率、消费速率和端到端业务完成延迟；
- 队列深度、最老消息年龄、分区倾斜和消费者利用率；
- 重复、乱序、失败重试、死信与消费幂等；
- 消费者扩缩容、依赖变慢和恢复后清空积压所需时间；
- 处理结果的业务正确性，而不只看“发送成功”。

**原理或实践解释**

API 很快返回“已受理”不代表业务处理性能达标。异步系统至少有接收延迟、排队延迟和处理延迟。若到达率长期大于消费率，积压会持续增加；短期吸收峰值则要验证队列容量和峰值后的恢复预算。

**常见追问或误区**

- 追问：消费者翻倍吞吐一定翻倍吗？答：不一定，可能受分区数、下游、锁或热点数据限制。
- 误区：压测结束立即停止监控，没有观察积压清理、重复消费和最终一致状态。

## Q11：用 k6 设计可进入 CI 的性能测试，你会怎样做？

**岗位考点**

k6 场景、指标、检查、阈值和自动化门禁。

**参考答案**

我会把脚本拆成配置、数据、业务场景和自定义指标，使用 `scenarios` 表达负载模型，按接口或旅程添加稳定标签。`check` 验证单次响应和业务条件，`thresholds` 把聚合指标转成自动化通过/失败标准，例如：

```javascript
export const options = {
  scenarios: {
    browse: {
      executor: 'constant-arrival-rate',
      rate: 20,
      timeUnit: '1s',
      duration: '3m',
      preAllocatedVUs: 20,
      maxVUs: 100,
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
    'http_req_duration{scenario:browse}': ['p(95)<300'],
  },
};
```

在 CI 中先运行短小、稳定、低成本的回归门禁；大规模容量和浸泡测试放在隔离环境按计划运行。保存脚本版本、服务构建、参数、原始结果和趋势链接。

**原理或实践解释**

`check` 失败会使对应检查的成功率下降，但不会仅因某次检查为假就自动让整次运行以失败退出；若要作为 CI 门禁，应对 `checks` 或相关指标设置 threshold。阈值应基于 SLO 或基线变化并设最低样本量，避免共享 CI 环境抖动导致假失败。k6 官方将 threshold 定义为指标的通过/失败条件，失败时可产生非零退出码。

**常见追问或误区**

- 追问：为什么选择 arrival-rate executor？答：目标是控制外部到达率；若模拟固定用户循环，则可选 VU 型 executor。
- 误区：只断言 HTTP 200，没有验证响应内容、业务状态或错误被 200 包装的情况。

## Q12：JMeter 压测有哪些关键最佳实践？

**岗位考点**

JMeter Test Plan、参数化、CLI 执行和负载机资源控制。

**参考答案**

JMeter GUI 用于建模和调试，正式负载应使用 CLI，例如：

```bash
jmeter -n -t demo-plan.jmx -l result.jtl -e -o report
```

实践要点包括：

- 用 CSV Data Set 等方式参数化数据，用提取器完成动态关联；
- 用断言验证业务结果，合理设置连接和响应超时；
- 正式运行禁用 View Results Tree/Table 等重型监听器；
- 控制保存字段，避免结果文件和磁盘 I/O 反过来限制负载；
- 监控注入机 JVM、CPU、内存、网络和实际吞吐；
- 使用变量/属性外置环境参数，JMX、数据和插件版本进入版本控制；
- 大负载时评估多实例或分布式执行，并校准时钟和网络。

**原理或实践解释**

线程组产生的“用户数”不代表负载机必然能产生目标流量。JMeter 本身是 Java 程序，监听器、脚本语言、保存完整响应和本地资源不足都会成为瓶颈。官方手册明确要求负载运行使用 CLI 而非 GUI。

**常见追问或误区**

- 追问：Beanshell 和 JSR223 如何选？答：常用场景优先 JSR223 + Groovy，并缓存可编译脚本；仍应尽量使用内置组件。
- 误区：分布式模式启动成功就认为结果可靠，没有检查各注入节点负载是否均衡。

## Q13：Locust 适合什么场景？如何做分布式和自定义负载？

**岗位考点**

Python 场景建模、greenlet、主从执行与负载形状。

**参考答案**

Locust 适合团队以 Python 表达复杂用户行为、条件分支、自定义协议客户端和事件扩展的场景。`HttpUser` 描述用户，`task` 描述行为，`wait_time` 表达思考时间；无界面运行可用于 CI。

大负载时使用 master/worker：

```bash
locust -f locustfile.py --master --headless --expect-workers 1 -u 200 -r 20 --run-time 5m
locust -f locustfile.py --worker --master-host 127.0.0.1
```

master 负责编排和汇总，worker 实际产生用户。上例等待 1 个 worker；若启动 N 个 worker，`--expect-workers` 也应设置为 N。复杂升降曲线可继承 `LoadTestShape`，在 `tick()` 中返回目标用户数和 spawn rate。运行时监控 worker CPU；Python 进程受单进程 CPU 使用限制时，应增加进程或机器。

**原理或实践解释**

Locust 每个用户运行在 greenlet 中，适合大量 I/O 型并发，但脚本里的阻塞库、重 CPU 计算或第三方客户端可能破坏协作式调度。分布式不会自动修复错误模型，仍需验证总请求率、数据唯一性和节点时钟。

**常见追问或误区**

- 追问：用户数达标但 RPS 不达标怎么办？答：查看响应/思考时间、任务权重、客户端连接、worker CPU 和服务限速。
- 误区：因为 Locust 用 Python，就在虚拟用户里执行大量 CPU 计算，导致注入机先饱和。

## Q14：如何做容量评估和扩容效果验证？

**岗位考点**

安全容量、性能拐点、线性伸缩与成本权衡。

**参考答案**

我会在代表性数据和负载模型下逐级增加到达率，每级保持足够时间，记录吞吐、P95/P99、错误、队列和资源。当负载继续增加而吞吐增长明显变慢，延迟/错误/饱和快速上升时，可认为接近拐点。

容量结论不直接取崩溃点，而是：

```text
安全容量 = 已实测且满足全部 SLO 的最大稳定容量 × 安全系数（0 < 系数 < 1）
```

这是便于沟通的工程估算，不是排队论定理，也不能替代故障容量验证。安全系数用于预留故障、流量波动、预测误差和扩容滞后的余量，不是固定行业常数。然后分别用 1、2、4 个实例验证伸缩效率，记录数据库、缓存和依赖资源是否随之变化，分析共享瓶颈与成本。还要测自动扩容触发阈值、冷启动时间、缩容时连接排空和突发流量下的滞后。

**原理或实践解释**

实例翻倍通常不会吞吐严格翻倍，受串行部分、共享数据库、锁、网络和负载均衡影响。一次结果只能说明该构建、配置、数据规模和环境下的能力，因此报告必须带版本和边界。

**常见追问或误区**

- 追问：安全系数取多少？答：没有通用值，应根据预测误差、流量波动、扩容时间、故障冗余和风险容忍度决定。
- 误区：用平均 CPU 外推容量，却没有实测长尾、依赖限额和故障降级。

## Q15：如何发现内存泄漏和稳定性问题？

**岗位考点**

浸泡测试、趋势分析、资源恢复和故障注入。

**参考答案**

我会设计包含正常流量、周期任务、缓存更新和少量异常的长稳测试，先运行空闲基线和预热，再维持代表性负载。持续观察：

- 进程 RSS、堆使用、GC 后存活量和暂停；
- 线程/协程、连接、文件描述符和临时文件；
- 队列深度、缓存条目、会话和对象数量；
- 延迟、错误和吞吐是否随时间退化；
- 停止负载后是否回到可解释的稳定基线。

发现单调增长后，用 heap dump、分配剖析、对象差异和最小复现场景定位；同时排除正常缓存预热、内存池保留、监控采集误差和负载机泄漏。

**原理或实践解释**

内存高不一定泄漏，关键是不可回收对象或资源随相同工作量持续增长，并最终影响稳定性。稳定性还包括连接泄漏、重试风暴、日志撑满磁盘、证书/令牌刷新失败及依赖短暂故障后的恢复。

**常见追问或误区**

- 追问：测试要跑多久？答：覆盖疑似泄漏周期、定时任务和峰谷，并用增长速率推算风险；“固定跑 24 小时”不是通用答案。
- 误区：只看压测期间曲线，不做停止负载后的资源恢复检查。
