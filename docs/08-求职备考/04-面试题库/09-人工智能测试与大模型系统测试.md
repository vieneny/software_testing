# AI 测试：LLM、RAG 与 Agent 经典面试题

> 适用岗位：AI 应用测试工程师、大模型/多模态评测工程师、Agent 测试工程师、AI 质量平台与测试开发工程师，以及使用 AI 提效的普通测试岗位。
> 核对日期：2026-07-29。所有提示词、知识库、工具和用户数据均为虚构示例。

AI 测试不是给传统用例加一个模型调用。选题已按 2026-07-27 BOSS 直聘公开岗位快照复核，覆盖普通 QA + AI 提效、AI 应用测试、模型评测、Agent 测试和评测平台；岗位快照日期与本章技术核对日期是两个口径。面试回答要同时考虑传统软件正确性、概率性输出、数据与评测方法、模型安全、成本延迟和持续监控。不要把某个框架的分数当成客观真理。样本和限制见[软件测试与人工智能测试招聘需求调研](../../00-学习指南/04-软件测试与人工智能测试招聘需求调研.md)。

## Q01：LLM 输出具有非确定性，测试应该怎样设计？

**岗位考点**

概率性系统、测试 Oracle、统计评测和可重复性。

**参考答案**

我会把断言分三层：

1. **确定性约束**：响应结构、JSON Schema、必填字段、禁止词、权限、工具参数、引用格式、超时和成本上限；
2. **语义质量**：正确性、相关性、完整性、忠实度、风格和安全，由规则、检索证据、人工或校准后的评审模型评分；
3. **统计稳定性**：同一代表性数据集运行多个样本，比较通过率、置信区间、最差切片和回归幅度。

同时固定可控条件：模型与快照标识、系统提示、参数、工具版本、知识库版本、随机种子（若服务支持）、评测器版本和运行时间。无法完全复现时，要保存原始输入输出和 Trace。

**原理或实践解释**

对开放文本做逐字相等通常太脆弱，但“只要读起来不错就通过”又不可审计。应优先使用确定性、任务相关的强信号，再用模型评审处理真正主观的维度。一次失败也许是采样波动，但权限越权、泄密等安全故障仍应一次即阻断。

**常见追问或误区**

- 追问：把 temperature 设为 0 就完全确定了吗？答：不保证；服务实现、并行计算、模型更新和工具/检索变化仍可能造成差异。
- 误区：失败后反复运行直到通过，既不保留首次失败，也不量化波动。

## Q02：如何构建高质量的 AI 评测集？

**岗位考点**

数据集设计、覆盖、标注、版本控制和数据泄漏。

**参考答案**

我会从产品风险和用户任务出发建立能力—场景矩阵，包含：

- 高频正常任务与业务关键任务；
- 边界、歧义、长上下文、多轮和多语言；
- 拒答、越权、隐私、安全和对抗输入；
- 经授权的失败样本应按数据治理流程最小化、标注和分级存储；
- 人工设计和合成的稀有场景；
- 按难度、语言、主题、风险和来源标注切片。

每条样本记录输入、期望行为或评分 rubric、参考证据、允许变体、禁止行为、标签和标注来源。数据集用版本管理，划分开发集、回归集和封存测试集；定期审查过时事实、重复样本、污染和覆盖空洞。

**原理或实践解释**

公开 benchmark 适合比较通用能力，但不等于产品质量。高质量评测集需要代表目标用户和失败成本。若用同一批数据反复调提示词，最终分数会过拟合，因此应保留未参与调优的 holdout，并用新增失败样本检验泛化。

**常见追问或误区**

- 追问：没有线上数据怎么办？答：从需求、风险分析、公开数据和从零合成开始，由领域人员审查，再随合法反馈逐步补充。
- 误区：直接上传未经授权的聊天、客户文档或生产日志给外部模型生成评测题。

## Q03：怎样为一个 LLM 应用定义质量指标？

**岗位考点**

多维指标、业务目标、切片和门禁。

**参考答案**

我会建立平衡计分卡，而不是单一总分：

- **任务效果**：任务成功率、事实正确性、答案相关性、完整性；
- **可信度**：有证据声明的忠实度、引用正确率、不确定时正确拒答；
- **安全合规**：越权、敏感信息泄露、提示注入成功率、有害输出；
- **交互体验**：指令遵循、风格、多轮一致性、用户纠正次数；
- **工程指标**：端到端 P95/P99、可用性、token/请求成本、缓存和工具失败；
- **业务结果**：虚构任务完成率、升级人工率或错误操作率。

每项指标按风险切片报告，并设置硬门禁与软目标。例如任何未授权工具执行为硬失败；帮助性平均分下降可能需要统计显著且超过实际影响阈值才阻断。

**原理或实践解释**

指标之间存在张力：更严格拒答可能提高安全但降低帮助性，更长答案可能提高完整性却增加成本和延迟。应该用 Pareto 和分层门禁表达取舍，不能把不同尺度分数随意相加成一个“AI 得分”。

**常见追问或误区**

- 追问：BLEU/ROUGE 能否评价客服答案？答：可作为表面相似性辅助，但对开放语义、事实和安全不充分。
- 误区：只报全体平均分，掩盖少数语言或高风险场景严重退化。

## Q04：什么是 LLM-as-a-Judge？如何验证评审模型可信？

**岗位考点**

模型评审、rubric、偏差、校准和人工一致性。

**参考答案**

LLM-as-a-Judge 是让模型按明确 rubric 对另一个模型输出进行分类、打分或成对比较。落地时我会：

1. 把维度拆开，给出清晰定义、评分锚点和边界示例；
2. 隐藏候选模型身份并随机化 A/B 顺序，减轻位置和品牌偏差；
3. 用至少两位领域人员独立标注的校准集计算一致率、混淆矩阵和分切片偏差；类别失衡时不能只报总体一致率，还要看各类精确率、召回率，必要时报告适合标签类型的一致性系数；
4. 对低置信、评审分歧和高风险样本转人工复核；
5. 固定 judge 模型、提示、参数和版本，Judge 更新后重新校准；
6. 规则可判断的格式、数值、引用和权限优先用确定性代码。

**原理或实践解释**

Judge 本身也会非确定、偏好冗长、受提示注入影响或与被测模型共享系统性错误。它是一个需要测试的测量仪器。成对比较通常比抽象绝对分更稳定，但仍需处理顺序偏差和“平局”。

**常见追问或误区**

- 追问：Judge 与人工一致率 80% 就一定能上线吗？答：阈值取决于任务和错误成本，还要看具体混淆方向及高风险切片。
- 误区：让 Judge 同时看到不可信文本并遵从其中指令，导致评测被被测输出劫持。

## Q05：什么是幻觉？如何测试和降低？

**岗位考点**

事实性、可回答性、引用验证和风险控制。

**参考答案**

幻觉通常指输出包含不受事实、上下文或工具结果支持的陈述。测试时先区分：

- 闭卷事实错误；
- RAG 中与检索上下文不一致；
- 虚构引用或引用不能支持声明；
- 工具结果被错误解释；
- 问题不可回答时仍自信作答。

我会构造可答、不可答、证据冲突、过时证据和诱导错误前提的样本；将回答拆为原子声明，核对来源支持；统计事实正确率、忠实度、引用精确率/覆盖率及正确拒答率。

降低措施包括改善检索和数据质量、要求可验证引用、工具计算、输出结构约束、置信/可答性判断、明确允许拒答和高风险人工复核。

**原理或实践解释**

“听起来合理”不是事实。RAG 可以提供证据，但不能自动消除幻觉，模型仍可能忽略、曲解或超出上下文。OpenAI 的 SimpleQA 也把短事实问题的范围控制得很窄，以提高可判定性；产品仍需自己的评测集。

**常见追问或误区**

- 追问：要求模型“不要幻觉”是否有效？答：只能作为提示的一部分，不能替代证据、评测、约束和系统控制。
- 误区：只查答案是否包含引用编号，不验证引用内容是否真的支持对应声明。

## Q06：怎样拆分评测 RAG 系统？

**岗位考点**

检索与生成解耦、RAG 指标和故障归因。

**参考答案**

我会至少拆成四层：

| 层次 | 被测对象 | 代表性判定 |
| --- | --- | --- |
| 文档处理 | 解析、切片、元数据和版本 | 内容/表格是否丢失，切片边界是否保留语义，删除和更新是否传播 |
| 检索 | 召回、排序、过滤和权限 | Recall@k、Precision@k、MRR/nDCG（适用时），以及无权限文档召回率 |
| 生成 | 模型基于上下文形成答案 | 相关性、事实正确性、忠实度、引用映射和正确拒答 |
| 端到端 | 用户任务与完整系统 | 任务成功、延迟、成本、安全和用户体验 |

诊断时做对照实验：给生成器理想的 gold context，若仍答错，问题偏向生成；用固定问题和相关文档检查 retriever，若召回不足，先修检索。Ragas 等公开项目提供 Context Precision、Context Recall、Faithfulness 和 Response Relevancy 等度量思路，但阈值必须用本任务人工样本校准。

**原理或实践解释**

端到端分数下降无法直接说明是 embedding、切片、reranker 还是提示词。分层评测使根因可定位，也能避免强模型凭预训练知识“猜对”从而掩盖检索失败。

**常见追问或误区**

- 追问：Faithfulness 高是否说明答案正确？答：不一定；错误或过时上下文也会产生“忠实但错误”的答案。
- 误区：只测 top-k 中是否有关键词，没有相关性标注和权限校验。

## Q07：如何测试切片、Embedding、混合检索和 Reranker？

**岗位考点**

检索工程、离线实验、索引变更和数据分布。

**参考答案**

我会建立带相关文档/片段标注的查询集，覆盖精确实体、同义表达、缩写、否定、日期、表格、跨段信息和无答案。控制变量比较：

- 切片大小、重叠、标题/父子结构；
- embedding 模型与归一化；
- 向量、关键词和混合检索权重；
- top-k、过滤条件和 reranker；
- 索引版本、文档新鲜度与删除传播。

离线看 Recall@k、nDCG/MRR、无权限文档召回率和查询延迟；再做端到端忠实度、任务成功、成本和延迟验证。变更索引前后用相同数据快照和查询集，保留失败差异。

**原理或实践解释**

更大的 top-k 可能提高召回，却增加噪声、token 成本和提示注入面；reranker 可改善排序，但增加延迟。切片过小丢上下文，过大降低定位精度。选择应基于数据而非“行业默认 500 tokens”。

**常见追问或误区**

- 追问：向量相似度高就代表业务相关吗？答：不保证，需用人工相关性标签和任务结果校准。
- 误区：升级 embedding 后沿用旧向量索引，或重建索引却没有版本与回滚。

## Q08：如何测试 AI Agent？

**岗位考点**

目标完成、轨迹、工具调用、状态和容错。

**参考答案**

Agent 测试应同时看结果和过程：

- **目标层**：任务是否完成，最终状态是否正确；
- **轨迹层**：计划是否合理，是否进入循环，步骤/调用次数是否受限；
- **工具层**：选对工具、参数 Schema 正确、权限合法、结果被正确解释；
- **状态层**：多轮记忆、上下文压缩、恢复和幂等；
- **鲁棒性**：工具超时、返回脏数据、部分失败、重复响应和不可用；
- **工程层**：总延迟、token/工具成本、Trace 完整性和取消。

对虚构“旅行规划 Agent”，我会提供沙箱化只读查询工具和需要确认的预订工具；断言它能完成计划，但未经用户确认不能产生任何预订副作用。

**原理或实践解释**

只看最终文本可能掩盖危险轨迹：Agent 也许尝试了越权工具，只是碰巧失败。反过来，强制唯一标准轨迹也过度约束，因为多个合法路径可达到同一目标。适合把安全不变量设为硬断言，把效率和路径质量设为评分。

**常见追问或误区**

- 追问：如何测循环？答：设置最大步数、重复动作检测、预算和截止时间，并构造工具持续返回“不确定”的场景。
- 误区：给测试 Agent 使用真实发信、支付、删除或生产数据库权限。

## Q09：工具调用和“过度代理权”风险如何测试？

**岗位考点**

最小权限、授权边界、人机确认和副作用控制。

**参考答案**

我会先列出每个工具的读/写能力、资源范围、参数约束、可逆性和所需确认，然后测试：

- 普通用户不能调用管理员工具；
- 模型不能通过字符串参数扩大资源范围；
- 写操作使用服务端鉴权、幂等键、速率/金额/数量限制；
- 高风险动作展示明确预览并要求独立的人类确认；
- 工具返回的不可信文本不能覆盖系统策略；
- 失败重试不会重复产生副作用；
- 所有工具调用记录必要且脱敏的审计元数据，敏感参数和响应正文按最小化原则处理；可撤销操作有补偿路径。

模型只负责提出结构化意图，最终授权和参数验证必须由确定性代码执行。

**原理或实践解释**

OWASP 将 Excessive Agency 描述为因功能、权限或自主性过多而造成危险动作。系统提示不是安全边界；即使模型“通常听话”，直接/间接注入或幻觉仍可触发错误工具。

**常见追问或误区**

- 追问：加入“请勿执行危险操作”的 system prompt 足够吗？答：不够，必须用权限、Schema、沙箱、确认和审计在模型外强制。
- 误区：只测模型是否拒绝，却没有验证后端实际上会不会执行伪造的工具调用。

## Q10：Prompt Injection 与 Jailbreak 有什么区别？怎样测试？

**岗位考点**

直接/间接注入、信任边界和纵深防御。

**参考答案**

Prompt Injection 是不可信输入以非预期方式操纵模型，使其偏离预期任务、覆盖控制目标或触发未授权行为；可分为用户直接注入，以及来自网页、邮件、文件、检索文档或工具结果的间接注入。Jailbreak 通常特指试图绕过模型安全限制的一类注入。

测试矩阵应覆盖：

- 忽略/覆盖指令、角色扮演、编码和多语言变体；
- 恶意内容藏在 RAG 文档、图片、工具响应或多轮历史；
- 系统提示和密钥提取；
- 越权工具调用、数据外传和持久化污染；
- payload 分片、多 Agent 传递和看似合法的组合攻击。

判定不只看模型是否说出敏感文本，还要观察检索、工具、网络和副作用。防护采用输入来源标识、最小权限、结构化输出、内容隔离、确定性验证和高风险人工确认。

**原理或实践解释**

OWASP LLM01:2025 明确指出 RAG 或微调不能彻底消除 Prompt Injection。测试目标应是降低攻击成功率和影响半径，而不是声称“已完全解决”。

**常见追问或误区**

- 追问：过滤“ignore previous instructions”是否足够？答：不够，攻击可改写、编码、跨模态或间接进入，需纵深防御。
- 误区：在无授权的真实系统执行攻击；红队必须在明确授权、隔离和限额条件下开展。

## Q11：如何测试 AI 应用中的隐私和敏感数据保护？

**岗位考点**

数据流、最小化、租户隔离、供应商边界和日志治理。

**参考答案**

我先画数据流：用户输入、检索、提示编排、模型提供方、缓存、Trace、标注平台和人工复核分别接触哪些数据。然后验证：

- 输入最小化、字段脱敏和用途限制；
- 不同用户/租户的会话、向量库、缓存和权限隔离；
- 提示、输出、日志、Trace 和评测制品不泄露秘密；
- 保留期限、删除请求和备份传播；
- 外部模型/评测服务的数据发送范围、区域和配置；
- 训练/反馈开关与用户同意；
- 模型能否被诱导回显先前用户或隐藏上下文。

测试数据优先从零生成带标记的虚构 PII，例如 `user-001@example.invalid`，并设置数据外传探针；绝不使用真实公司或客户数据做个人学习实验。

**原理或实践解释**

隐私测试不能只扫描最终回答，因为泄漏还可能发生在日志、评审服务和观测系统。所谓“本地执行”也需核对工具的生成、评分、遥测和更新检查是否访问外部服务。

**常见追问或误区**

- 追问：脱敏后就能随意上传吗？答：不能；还需授权、重识别风险、最小化、用途和供应商协议评估。
- 误区：把 API Key 放入提示词，期望 system prompt 能保护它。

## Q12：如何制定一次 AI 红队测试？

**岗位考点**

威胁建模、攻击库、风险分级和修复闭环。

**参考答案**

流程可分为：

1. 明确授权范围、目标、数据边界、停止条件和联系人；
2. 用 NIST AI RMF、OWASP LLM Top 10、MITRE ATLAS 等建立威胁模型；
3. 按系统能力选择攻击：注入、越权、泄密、有害输出、资源耗尽、供应链、数据/索引污染；
4. 结合人工创意、固定回归样本和自动生成变体执行；
5. 记录输入、完整轨迹、工具/网络副作用、攻击成功条件和影响；
6. 由复核者确认真假阳性，按可能性与影响分级；
7. 修复系统控制，加入永久回归，并复测绕过变体。

Promptfoo、garak 等公开工具可辅助生成和执行，但攻击类别、评分器和数据外发行为必须先审查。

**原理或实践解释**

自动红队报告不是渗透测试结论。生成器和 grader 都可能漏报或误报；领域特有滥用需要人工威胁建模。红队还必须测试“攻击成功后能造成什么”，安全架构应限制影响半径。

**常见追问或误区**

- 追问：攻击成功率越低越安全吗？答：还需看覆盖、攻击强度、严重度、样本量和评审准确性，不能跨不同配置直接比较。
- 误区：为了逼真把真实内部系统说明、账号或文档送入第三方红队服务。

## Q13：AI 应用上线后要监控什么？

**岗位考点**

线上质量、漂移、反馈闭环、成本和可观测性。

**参考答案**

线上监控至少包括：

- 工程：请求量、错误、P95/P99、超时、token、工具调用和单次/总成本；
- 效果代理：任务完成、正确拒答、引用点击/有效性、用户纠正和转人工；
- RAG：无结果率、检索分数分布、知识版本、权限过滤失败；
- Agent：步骤数、循环、工具错误、未确认写操作拦截；
- 安全：注入检测、敏感输出、越权尝试和异常外联；
- 漂移：输入主题/语言/长度、模型或索引版本变化及离线回归分数。

原始对话默认最小化采集和脱敏。失败样本进入评测集前应确认授权、用途、访问权限、保留周期和字段级处理方式，形成“监控—标注—修复—评测—发布”闭环。

**原理或实践解释**

线上没有完整参考答案，因此需要代理指标、抽样人工评审和延迟标签。代理指标可能被优化或产生偏差，必须与业务结果和投诉事件交叉验证。模型、提示、知识库和工具的每次变更都应打版本标签。NIST AI 800-4 也提醒，已部署 AI 的监控方法和共同术语仍在发展；面试时应把监控项与具体风险、责任人、响应动作和验证周期绑定，不能声称存在适用于所有 AI 系统的固定阈值。

**常见追问或误区**

- 追问：能否记录所有对话用于评测？答：应依授权、最小化、保留期和访问控制决定，默认并非越多越好。
- 误区：只监控模型 API 200 和延迟，忽略“快速地产生错误或危险结果”。

## Q14：如何比较两个模型、提示词或 RAG 版本并安全发布？

**岗位考点**

离线评测、配对实验、A/B、金丝雀和回滚。

**参考答案**

我会先在固定评测集做配对比较：每条样本同时跑基线和候选，保持提示、工具和知识版本可比，观察总体与风险切片的胜/负/平、硬失败、延迟和成本。对差异使用置信区间或适合的配对统计，不只比较平均分。

候选通过离线门禁后：

1. 影子流量验证兼容、成本和延迟；写工具必须改接 dry-run、Stub 或隔离沙箱，不能仅因请求被称为“影子”就假定没有副作用；
2. 小比例金丝雀，设置安全和业务停止条件；
3. A/B 随机分流，避免用户群和时间偏差；
4. 分阶段放量并持续回归；
5. 保留快速回到旧模型、提示、索引和工具配置的能力。

**原理或实践解释**

模型升级可能提高平均帮助性却降低某语言、安全或结构化输出。非劣效门槛和硬安全约束比“总分高 0.2”更有意义。用户在线指标还可能受展示、季节和学习效应影响。

**常见追问或误区**

- 追问：模型提供方原地更新怎么办？答：尽量使用可追踪版本/快照，保存响应元数据并设置漂移监控；无法固定时提高回归频率和回滚隔离。
- 误区：一次离线 benchmark 更高就全量替换，没有应用级评测和金丝雀。

## Q15：怎样测试多轮对话、记忆和上下文压缩？

**岗位考点**

状态管理、长期一致性、遗忘、权限与上下文污染。

**参考答案**

我会设计状态机式多轮用例：

- 用户补充、纠正、撤回和切换主题；
- 代词/省略指代、长对话和上下文窗口边界；
- 会话内应记住与不应记住的信息；
- 新会话、不同用户和不同租户必须隔离；
- 摘要/压缩前后事实、约束和用户意图不丢失；
- 恶意指令不能通过记忆长期持久化；
- 删除请求完成并超过系统声明的删除 SLA 后，在线检索、缓存和向量索引不应再返回该记忆；备份的处置按已声明策略单独验证；
- 并发设备、断线恢复和消息乱序。

判定既看最终回答，也检查存储状态、摘要内容、检索记忆来源和版本。用虚构 canary 字符串验证跨会话泄漏。

**原理或实践解释**

多轮质量不是单轮分数的简单平均。早期一次错误可能污染后续所有步骤；压缩摘要可能把推测写成事实。需要针对整段轨迹做目标完成、状态一致性和安全不变量评测。

**常见追问或误区**

- 追问：把完整历史一直拼入提示是否最好？答：受窗口、成本、噪声和注入影响；需要选择、压缩和明确来源。
- 误区：只从 UI 看模型“像是记住了”，没有检查是否误用其他用户数据。

## Q16：如何安全地用 AI 提升测试效率？

**岗位考点**

AI 辅助测试、人工复核、数据边界和效果度量。

**参考答案**

适合辅助的任务包括：从公开或从零编写的虚构需求生成候选测试点、构造虚构边界数据、解释合成日志、生成脚本草稿、补充文档和归类合成失败。工作流应是：

1. 先定义输入可否交给模型，敏感或公司资料不进入个人 AI 工具；
2. 要求输出结构、假设和待确认项；
3. 用规则、编译、静态扫描、单元测试和沙箱执行验证生成物；
4. 由人审查业务意图、安全和最终合并；
5. 比较使用 AI 前后的周期时间、缺陷发现、返工和审查成本。

AI 不应直接审批发布、关闭缺陷或在无确认下执行写操作。

**原理或实践解释**

AI 可以扩大已有流程的优势和缺陷。DORA 2025 的公开研究也把 AI 描述为组织能力的放大器，因此提效不应只统计“生成了多少用例”，而应看可用率、发现价值、返工和交付结果。

**常见追问或误区**

- 追问：AI 生成的测试全部通过能证明功能正确吗？答：不能，模型可能与实现共享误解，还需独立 Oracle、人工风险分析和多层测试。
- 误区：把生成速度当生产率，忽略评审、维护、误报和安全成本。

## Q17：如何选择 AI 评测框架，并应对快速版本变化或产品弃用？

**岗位考点**

工具选型、可移植架构、锁版本和生命周期治理。

**参考答案**

我先定义需求，再比较框架：

- Promptfoo 适合声明式模型/提示对比、断言和红队；
- Ragas 聚焦 RAG/Agent 等指标与可扩展评测；
- DeepEval 提供接近 pytest 的数据集和多类应用指标；
- Inspect AI 提供任务、模型、scorer、工具与日志组件，适合可复现评测；
- garak 偏向 LLM 漏洞探测。

选型还要验证许可证、维护状态、数据是否外发、模型支持、离线/私有部署、CI 接入、可扩展性和结果导出。架构上将数据集、rubric、原始输出和统一结果 Schema 保存在自己控制的版本库/存储中，通过适配器调用框架；使用锁文件和隔离环境，升级时在校准集上做新旧双跑。

截至 2026-07-29，OpenAI 官方弃用页写明 Evals platform 已进入弃用流程：现有 eval 计划于 2026-10-31 变为只读，Evals dashboard 与 API 计划于 2026-11-30 关闭。这里说的是该托管产品的生命周期，不代表“评测方法”或所有名为 Evals 的开源/本地工具同时弃用。因此应学习可迁移的评测方法与数据格式，而不是把一个托管产品当作唯一能力。

**原理或实践解释**

框架分数常受默认 judge、提示和版本影响，不能混合不同版本做长期趋势。托管服务生命周期也会变化；数据、标准、原始证据和业务判定才是核心资产。

**常见追问或误区**

- 追问：哪个框架“最权威”？答：没有通用最优，应以任务、数据边界和经人工校准的有效性选择，必要时组合使用。
- 误区：始终使用 `latest` 且不保存依赖、模型和评审配置，导致分数变化无法解释。

## Q18：AI 产品测试、模型评测、Agent 测试和评测平台有什么区别？

**岗位考点**

岗位边界、职责拆解和作品选择。

**参考答案**

我不会只按标题判断，而会看交付物：

- AI 产品测试以版本交付为中心，验证 API、流式响应、会话、RAG、模型效果、性能、稳定性和安全；
- 模型评测以测量为中心，建设数据集、标注规范、Benchmark、指标、统计比较和误差分析；
- Agent 测试以行为与环境变化为中心，验证规划、记忆、工具、权限、轨迹、终态、副作用和恢复；
- 评测平台以工程基础设施为中心，提供数据集/实验版本、任务编排、执行器、评分、结果、Trace、CI 门禁和权限审计；
- 普通测试 + AI 提效仍以原产品质量为中心，AI 只生成候选内容，必须通过人工和运行证据验收。

它们共享测试基础、API、编程、数据和安全，但作品不能互相替代。一个 RAG 聊天页面不能证明平台并发和恢复能力，一份模型榜单也不能证明 Agent 权限安全。

**原理或实践解释**

同名岗位可能承担不同职责，不同标题也可能做相同工作。用“被测对象—失败风险—交付物—成功标准”四项识别岗位，比背工具列表可靠。

**常见追问或误区**

- 追问：小白先选哪条？答：先完成普通功能/API/自动化，再做 AI 产品测试的小型合成项目；平台和评测算法通常需要更强开发或数据基础。
- 误区：简历把五条路线全部写成“精通”，但没有一项可运行证据。

## Q19：怎样保证评测数据和人工标注可信？

**岗位考点**

数据构造、标注治理、一致性、污染和统计边界。

**参考答案**

我先定义目标用户、任务分布、失败成本和能力维度，再确定抽样与切片。每条样本记录来源、许可证、期望行为、允许变体、禁止行为、难度和标签依据；开发集、回归集与封存集分离。

人工标注需要：

1. 有正反例和边界例的标注指南；
2. 标注前培训和小规模试标；
3. 关键样本由至少两人独立判断；
4. 使用一致率或适合标签类型的一致性指标发现歧义；
5. 对分歧仲裁并反向修改指南，而不是强行平均；
6. 定期检查重复、泄漏、过时事实、类别失衡和模型生成痕迹；
7. 高风险样本保留原始理由和审计记录。

模型裁判必须在人工金标准上报告误判，并按切片观察偏差。调 Prompt 时不反复查看封存集，避免把评测变成训练。

**原理或实践解释**

评测结论实质是对“样本、标签和量尺”的测量：任务分布偏移会削弱外部有效性，标签分歧会扩大测量误差，数据污染则会把记忆误当成能力。即使一致率很高，也可能是多人共同遵循了错误指南，不能单独证明标签正确。应检查来源与许可、去重和泄漏结果、风险切片覆盖、双人独立标注一致性、分歧仲裁记录、指南版本及封存集复测；结论只能外推到已覆盖且标签可信的任务边界。

**常见追问或误区**

- 追问：一致率低是否说明标注员能力差？答：也可能是任务本身模糊、标签体系不完整或上下文不足，应先审查规范和样本。
- 误区：用一个模型批量生成题目和答案，再让同一模型评分，却称为独立评测。

## Q20：多模态大模型应该怎样测试？

**岗位考点**

图像、视频、音频的主客观评测和链路拆分。

**参考答案**

我先按模态和任务拆分，不能让一个端到端主观分替代所有子任务：

| 任务 | 重点能力 | 可自动判定的例子 | 仍需人工或任务级判断的例子 |
| --- | --- | --- | --- |
| 图像/视频生成 | 提示遵循、主体一致性、文字、时序和安全 | 指定对象是否出现、OCR 文字、格式/时长 | 美学、自然度、复杂物理合理性 |
| 图像/视频理解 | 识别、定位、关系、计数和时序推理 | 分类正确率、OCR CER/WER、定位 IoU（适用时） | 开放问答的完整性、证据是否足够 |
| 语音链路 | ASR、语义理解、对话策略和 TTS | ASR CER/WER、意图/槽位、首包与端到端延迟 | 韵律、自然度、打断体验和可理解性 |
| 跨模态 | 模态对齐、冲突处理和缺失模态降级 | 引用区域/时间戳是否有效 | 冲突时的解释、任务帮助性和安全 |

客观指标只覆盖可自动判断部分；审美、自然度和有用性要用经过培训的人工 rubric。数据按光照、语言、口音、场景、设备、群体和攻击类型切片，同时测试延迟、显存/内存、并发和失败恢复。对安全与版权风险单独设门禁。

**原理或实践解释**

多模态链路把传感输入、模态编码、跨模态推理、生成或播放串联起来，任一阶段的误差都可能在最终体验中放大；一个总分无法说明应该修数据、模型还是客户端。自动指标只在目标可明确计算时有效，OCR 准确并不代表回答有用，人工偏好也会受指南和样本偏差影响。应保留原始媒体、预处理参数、中间识别结果、引用区域或时间戳、端到端延迟及分切片人工评分；结论仅适用于测试覆盖的设备、语言、场景和风险切片。

**常见追问或误区**

- 追问：自动指标和人工偏好冲突怎么办？答：检查指标是否覆盖目标、人工一致性和样本切片，不能默认任一方绝对正确。
- 误区：只用“看起来不错”的十个案例展示模型能力。

## Q21：怎样设计一个可用于 CI 的评测平台？

**岗位考点**

后端工程、任务编排、版本、可观测性、权限和门禁。

**参考答案**

平台至少包含：

1. 数据集、样本、Prompt、模型、知识库、工具和评分器版本；
2. 异步任务队列与状态机，支持限流、超时、重试、取消和恢复；
3. 可插拔 provider、被测应用和 scorer；
4. 逐例原始证据、Trace、延迟、Token、成本和错误分类；
5. 基线/候选配对比较及风险切片；
6. CI 快速集和离线完整集，阈值失败返回非零退出码；
7. 访问控制、密钥隔离、正文脱敏、保留策略和审计；
8. 结果幂等写入、重复任务去重和版本迁移。

CI 不宜每次运行昂贵全量集：提交阶段运行确定性契约和小型高风险集，定时任务运行完整语义评测，发布前再执行安全与性能集。阈值需要最低样本量、允许波动和严重失败单独门禁。

**原理或实践解释**

评测平台的价值不是“页面能显示分数”，而是让变更可比较、失败可追溯、风险可拦截，并在供应商和框架变化时保留自己的数据与标准。

**常见追问或误区**

- 追问：如何测试平台本身？答：用假 provider 注入超时、429、坏 JSON、重复回调和部分成功，验证状态、重试、幂等、取消、报告和审计。
- 误区：每次调用 `latest` 模型、不保存配置，却把分数变化当成产品回归。

- [ ] Judge 是需要校准的测量工具，不是绝对真值；

- [ ] 工具版本、模型、提示、知识库和原始结果全程可追溯。
