# 技术纠错与答案重写准则

## 一、原则

外部学习资料的价值在于帮助发现主题，不代表每个答案都可以直接使用。本轮采用五条硬规则：

1. 工具行为按当前官方文档核对；
2. HTTP、网络和安全语义按标准核对；
3. 阈值必须来自需求、SLO、基线或实验；
4. 项目结论必须有可复核证据，不能编造工作数据；
5. 绕过鉴权、后门验证码、生产压测等不安全做法禁止进入教程。

## 二、业务测试常见修订

### 1. 退出标准不是“全部执行、全部通过”

测试结论要写清：

- 风险范围和变更影响；
- 已执行与未执行内容；
- 阻断缺陷与残余风险；
- 关键链路、数据一致性和回滚证据；
- 谁接受剩余风险。

“用例执行率 100%”只能说明计划中的条目被执行，不能证明覆盖充分或软件没有风险。

### 2. HTTP 200 不等于业务成功

GraphQL、传统 REST 和网关封装接口都可能在 HTTP 200 中返回业务失败信息，因此必须识别业务结果；但“库存不足”这类预期拒绝是否计入错误率，要由测试场景和验收口径预先定义，不能见到非成功业务码就一律算系统错误。断言至少分为：

- 传输层：连接、状态、Header、Content-Type；
- 协议/Schema 层：字段、类型、约束；
- 业务层：业务码、状态迁移、权限和副作用；
- 数据层：库存、账户、消息、审计和最终一致性。

### 3. App 权限不是一次“允许/拒绝”

权限测试要覆盖首次申请、仅本次、使用期间、永久拒绝、设置页修改、自动重置、使用中撤销、系统升级与多权限组合。Android 与 iOS 的具体能力以目标系统版本为准。

### 4. Web/H5 白屏不能只看资源状态码

资源返回 200 仍可能存在：

- HTML 路由到错误内容；
- JavaScript 解析或运行错误；
- CSP、跨域或证书阻断；
- Chunk 版本不一致；
- WebView 与 JS Bridge 初始化失败；
- 主线程长任务或渲染失败。

需要把导航、网络、脚本、渲染、缓存和 Native 容器证据对齐。

### 5. Web Vitals 使用当前指标

旧资料中的 FID 已不能代表当前完整口径。答案应核对当前 Core Web Vitals，并区分实验室数据与真实用户监控；具体阈值和工具版本以 web.dev/Chrome 文档为准。

## 三、自动化测试常见修订

### 1. JUnit 与 TestNG 没有跨项目绝对优劣

比较维度包括：

- 现有技术栈与团队经验；
- 参数化、扩展、分组、依赖和并行模型；
- Maven/Gradle/IDE/报告平台兼容性；
- 迁移成本与维护活跃度；
- 用例隔离与失败证据需求。

不能用“功能多”直接推出更适合，也不能把旧版本印象当成当前能力。

### 2. Java 与 Python 不能用固定倍数比较

自动化套件耗时通常由网络、被测系统、数据准备、浏览器/设备和并行策略决定。语言运行速度只是其中一部分。选型应通过代表性试验比较：

- 开发与调试效率；
- 执行和资源成本；
- 库生态与现有平台；
- 类型约束与代码规模；
- 团队能力和长期维护。

### 3. 重跑不能提高测试本身的稳定性

重跑只能提供额外观察。正确做法是：

- 首次失败立即保存证据；
- 区分产品缺陷、环境故障、数据冲突和测试代码缺陷；
- 报告首次失败率与重跑结果；
- 对 flaky 用例建立负责人和修复期限；
- 禁止用最终通过掩盖首次失败。

### 4. Thread.sleep 不是可靠等待

固定睡眠既可能不足，也会浪费时间。应等待可观察条件，并设置有业务依据的超时；失败时保存请求、DOM/页面树、截图、Trace、日志和环境状态。

### 5. ThreadLocal 不是自动隔离方案

线程池会复用线程。若没有 `remove()`，ThreadLocal 中的账号、Token、客户端或驱动可能污染下一条用例。更安全的设计是：

- 尽量使用显式上下文传递；
- 生命周期与测试作用域一致；
- 在 `finally` 或扩展回调中可靠清理；
- 对并行执行做数据、文件、端口和外部资源隔离。

### 6. 日志过滤器不等于敏感字段一定已脱敏

REST Assured 等框架的请求/响应日志能力主要用于记录证据，不能默认它会识别 JSON、表单或嵌套对象中的密码、Token、Cookie 和个人信息。可复用框架应：

- 在自定义 Filter 中先复制并清洗证据，再交给日志与报告组件；
- 用字段名、Header 名和内容类型组合规则处理；
- 对嵌套对象、数组、大小写、空值和非 JSON 正文编写脱敏单测；
- 默认不保存完整响应正文，并限制文件权限和保留周期；
- 录制真实流量前必须取得授权并完成数据分类、最小化和访问控制设计。

### 7. `HttpRequest.timeout` 的语义必须按 JDK 版本说明

JDK 25 及以前，`java.net.http.HttpRequest.Builder.timeout` 在收到响应头后即不再覆盖后续响应体读取；不能把它直接表述为“整个请求和响应的总超时”。JDK 26 修正了这一行为，但跨版本框架仍应显式实现总截止时间、取消任务和流式正文关闭，并分别测试连接、响应头、响应体停顿和调用方取消。

### 8. 外部黑盒自动化不会天然得到 JaCoCo 覆盖

JaCoCo 需要在被测 JVM 中进行字节码插桩并采集执行数据。只有向外部服务发送 HTTP 请求而没有部署和采集覆盖 Agent，不能直接产生可信代码覆盖率。即使采集到覆盖，也只能作为风险线索，不能把百分比等同于测试质量。

### 9. Mock 不能变成测试后门

WireMock、MockWebServer 等用于受控替代外部依赖和注入异常。它们不应：

- 在正式环境保留万能验证码；
- 关闭真实鉴权路径；
- 替代所有真实集成和端到端验证；
- 使用与真实契约无关的固定成功响应；
- 隐藏超时、重试、幂等和 Schema 漂移。

## 四、性能测试常见修订

### 1. 线程数不等于并发用户或请求到达率

JMeter 线程通常处于闭环：响应变慢会让下一次请求更晚发出。负载模型必须明确活动用户、思考时间、请求到达率、业务比例、持续时间和阶段，而不是只写线程数。

### 2. 限速不等于弱网

请求节奏控制只影响何时发送，不能模拟往返时延、抖动、丢包、重排和带宽竞争。弱网要在受控网络仿真层或代理注入，并记录方向、参数和基线。

### 3. 分位数不能跨节点简单求平均

每台压力机的样本量和分布不同。P95/P99 应基于合并后的原始样本或可聚合分布计算，不能把各节点 P95 再取平均。

### 4. JMeter 远程模式不等于每个节点自动保存一份 JTL

标准远程模式通常由压力节点把样本返回控制端。结果设计必须先说明采集拓扑：

- 远程模式保存带 hostname 的控制端 JTL，并保存各压力节点 server 日志；
- 节点独立 CLI 执行，或显式配置本地写入器时，才收集并合并节点 JTL；
- 合并前核对 run_id、节点清单、时间窗、样本数、重复与缺失；
- 大响应正文不要回传控制端，避免结果链路反过来成为瓶颈。

### 5. CPU、内存、磁盘没有跨系统统一阈值

资源判断要结合：

- 业务 SLO 和容量预留；
- 容器配额、核数和虚拟化；
- 利用率、饱和度、错误和队列；
- 设备并行能力、IOPS、带宽和时延；
- 历史基线与同负载对照实验。

看到 CPU、内存或磁盘某个百分比，不能单独下瓶颈结论。

### 6. Java 堆稳定不代表 RSS 增长就是堆泄漏

RSS 还包含已提交但未使用的堆页面、直接内存、线程栈、元空间、代码缓存、本地库和内存映射。Java 堆泄漏通常是“不再需要的对象仍被意外引用”，不是“不可达对象没有回收”。排查顺序是：

1. 对齐 GC 后堆基线、RSS 和容器内存口径；
2. 在从零启动的隔离环境开启 NMT 并建立 baseline；
3. 用 `VM.native_memory summary.diff/detail.diff` 比较分类；
4. 结合 BufferPool、JFR、线程转储和操作系统映射工具；
5. NMT 分类稳定而 RSS 上升时，再检查 JNI、第三方本地库、mmap 和分配器页面归还。

### 7. Trace 不是完整执行时间，也不能替代总体分位数

并行 Span 会重叠，应按关键路径解释，不能把所有子 Span 机械相加。Head/Tail sampling、丢 Span、时钟偏差和未埋点时间都会改变可见结果。总体指标用于计算 P95/P99，Trace 用于解释代表性结构，隔离实验用于验证因果假设。

### 8. 线程池和连接池不能只套公式

公式可以作为初始量级检查，正式配置要通过实验确定。需同时观察：

- 到达率、服务时间和持有时间；
- 队列、拒绝、超时和恢复；
- 数据库或下游真实容量；
- 多实例总连接数；
- 内存、上下文切换和尾延迟；
- 正确性与故障时的背压。

### 9. JVM 不采用固定堆比例或万能收集器

调优前先核对 JDK 版本、容器限制、当前收集器、堆、元空间、代码缓存、直接内存、线程栈和页缓存。泄漏先修代码，异常分配先找热点；收集器和参数只能在代表性负载下比较吞吐、尾延迟、暂停、CPU 和内存余量。

### 10. 性能优化必须可证伪

可靠的优化实验包括：

1. 固定版本、环境、数据和负载；
2. 保存优化前基线；
3. 提出可被否定的单一假设；
4. 一次改变一个因素，或明确设计多因素实验；
5. 重复关键档位并记录波动；
6. 同时观察吞吐、尾延迟、错误、正确性、资源和成本；
7. 恢复原配置做回退验证；
8. 修复后回到完整链路复测。

### 11. 诊断命令不是都能在高峰期无成本执行

`jcmd` 会为每条命令标注影响级别。以当前 JDK 文档为准，`GC.heap_info`、`Thread.print` 属于中等影响，`GC.class_histogram` 属于高影响；直方图、堆转储和高开销 JFR 配置尤其不能在未知影响下直接对生产进程执行。教程中的练习统一使用本地或隔离环境；线上排查必须先确认权限、容量、磁盘、暂停风险和回滚方案，并记录独立诊断时间窗，避免把诊断开销误判成被测系统瓶颈。

## 五、答案质量自检

每道答案提交前检查：

- 是否直接回答问题；
- 是否写明适用条件；
- 是否给出可执行步骤；
- 是否说明要收集什么证据；
- 是否包含失败与恢复场景；
- 是否区分 Mock、组件测试、集成测试和端到端测试；
- 是否出现未经证实的固定数字；
- 是否把练习写成真实工作经历；
- 是否引用了当前官方资料；
- 是否含公司、客户、生产或个人敏感信息。
