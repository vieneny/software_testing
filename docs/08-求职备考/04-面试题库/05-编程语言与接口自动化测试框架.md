# Python、pytest 与接口自动化经典面试题

> 适用岗位：自动化测试、接口测试、测试开发、SDET。
> 招聘信号：公开岗位中的 Python/pytest 往往不是“会写脚本”，而是要求候选人能管理资源生命周期、设计可维护分层、控制测试数据、接入 CI 并治理不稳定失败。
## 使用方法

每道题先用一句话给结论，再用小段代码或测试架构说明。面试官通常会追问“为什么这样做、失败时看到什么、并行后是否仍成立”，应提前准备可运行证据。

## 1. Python 中可变对象与不可变对象有什么区别？为什么会影响自动化测试？

**岗位考点**

- Python 对象模型、引用传递和共享状态。
- 是否能解释数据污染，而不只背类型列表。

**参考答案**

Python 变量绑定到对象。整数、字符串、元组等常被称为不可变对象，操作通常产生新对象；列表、字典、集合等是可变对象，可在原对象上修改。函数参数传递的是对象引用的绑定，函数内原地修改可变对象会被调用者观察到，重新绑定局部变量则不会改变调用者绑定。

自动化中最常见的风险是复用可变模板：

```python
BASE_PAYLOAD = {"items": []}

def build_payload(product_id: int) -> dict:
    payload = {
        "items": [{"product_id": product_id, "quantity": 1}]
    }
    return payload
```

每次构造新数据比修改全局字典可靠。对于嵌套模板，浅拷贝仍共享内部对象，应按需要使用 `copy.deepcopy`、不可变数据类或工厂函数。

**原理或实践解释**

pytest 参数值会原样传入，不会为每次参数化自动复制。若一个用例修改了列表或字典，后续参数实例可能看到污染后的值。并行执行时，共享全局对象还会产生竞争。测试数据应默认“每测试独立创建”。

**常见追问或误区**

- 误区：函数参数都是“值传递”或都是传统意义上的“引用传递”；更准确地说是对象引用按赋值语义传入。
- 误区：`dict.copy()` 能复制任意深度。
- 追问：元组一定不可变吗？元组自身结构不可变，但其中可以引用可变对象。

## 2. 为什么不应把列表或字典作为默认参数？

**岗位考点**

- 默认参数求值时机。
- 是否会发现跨调用累积导致的偶发失败。

**参考答案**

默认参数在函数定义时求值一次，不是每次调用都重新创建。因此下面的 `items` 会被多次调用共享：

```python
def add_item(item, items=[]):  # 不推荐
    items.append(item)
    return items
```

应使用 `None` 作为哨兵：

```python
def add_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items
```

自动化框架中，请求头、参数和日志上下文若使用可变默认值，可能让某个测试的认证头泄露到另一个测试。

**原理或实践解释**

函数对象保存默认参数对象。多次调用不传该参数时，拿到的是同一对象。这个行为有时可被有意用于缓存，但可读性和并发风险较大，测试代码通常不应这样设计。

**常见追问或误区**

- 误区：只有列表有问题；字典、集合、自定义可变对象同样有风险。
- 追问：默认参数为什么可以引用常量？不可变值不会被原地修改，通常安全。
- 追问：如何防止调用者修改返回数据？根据契约返回副本、不可变结构或明确所有权。

## 3. `==` 和 `is` 有什么区别？接口断言应如何选择？

**岗位考点**

- 相等性与对象身份。
- 是否会写出稳定断言。

**参考答案**

`==` 调用相等性比较，判断值是否相等；`is` 判断两个引用是否指向同一对象。判断 `None` 应使用 `is None`，比较字符串、数字、列表或响应 JSON 的值应使用 `==`。

```python
data = response.json()
assert data["status"] == "created"
assert data.get("deleted_at") is None
```

不应使用 `data["status"] is "created"`。字符串驻留等实现细节可能让它偶尔看似可用，但没有值相等保证。

**原理或实践解释**

身份比较不会调用对象的 `__eq__`。接口测试关注序列化后的业务值、类型和关系，而不是 Python 进程中的对象地址。涉及浮点数时还要考虑精度，用最小货币单位整数、`Decimal` 或 `pytest.approx`。

**常见追问或误区**

- 误区：小整数用 `is` 也能通过，所以可以替代 `==`。
- 追问：`None` 为什么推荐 `is`？`None` 是单例哨兵，身份表达语义更准确。
- 追问：JSON 中缺字段与字段值为 null 一样吗？不一样，应分别检查键是否存在和值是否为 `None`。

## 4. 什么是上下文管理器？为什么 Session、文件和临时资源要及时关闭？

**岗位考点**

- `with`、`__enter__`/`__exit__` 和资源生命周期。
- 自动化长时间运行时的连接泄漏治理。

**参考答案**

上下文管理器把资源获取和释放绑定到一个明确作用域，即使中间抛异常也会执行退出逻辑：

```python
import requests

with requests.Session() as client:
    response = client.get(
        "http://127.0.0.1:8000/api/products",
        timeout=(2, 5),
    )
    assert response.status_code == 200
```

在 pytest 中也可使用 `yield` fixture：`yield` 前创建资源，`yield` 后关闭或清理。文件、网络连接、数据库事务、临时目录和浏览器上下文都应有确定释放路径。

**原理或实践解释**

依赖垃圾回收时机释放资源并不可靠。连接池未关闭会耗尽文件描述符或服务端连接；测试异常若跳过清理，会污染后续用例。资源管理本身也应失败可见，关键清理不能被一个宽泛的 `except: pass` 静默吞掉。

**常见追问或误区**

- 误区：脚本运行很短，所以永远不需要关闭 Session。
- 追问：清理失败是否覆盖原测试失败？应保留两者信息，框架可把清理错误作为附加诊断，避免丢失最初原因。
- 追问：`try/finally` 和 `with` 的关系？上下文管理器封装了常见的获取/释放协议，底层仍可用 `try/finally` 实现。

## 5. pytest fixture 是什么？`scope` 应如何选择？

**岗位考点**

- fixture 依赖注入和生命周期。
- 是否会为速度盲目扩大 scope，造成共享状态。

**参考答案**

fixture 用声明式依赖提供测试所需资源。测试函数通过同名参数请求 fixture。常见 scope 有 `function`、`class`、`module`、`package` 和 `session`；默认是 `function`。

选择原则是：尽可能小，同时满足资源成本和隔离要求。

```python
import pytest
import requests

@pytest.fixture(scope="session")
def base_url() -> str:
    return "http://127.0.0.1:8000"

@pytest.fixture
def api():
    with requests.Session() as session:
        session.headers["Accept"] = "application/json"
        yield session
```

稳定、不可变的配置可以是 session scope；会携带 Cookie、业务数据或事务状态的对象倾向 function scope。

**原理或实践解释**

fixture 会建立依赖图并缓存到其 scope 生命周期。大 scope 降低初始化成本，却扩大故障和污染半径。若 session fixture 依赖 function fixture，生命周期不匹配会报错，因为长生命周期资源不能安全依赖更短生命周期资源。

**常见追问或误区**

- 误区：fixture 是传统 `setup/teardown` 的换名字版本；它还提供显式依赖、组合、参数化和作用域管理。
- 误区：所有登录都做成 session scope 才快。共享身份状态可能使并行和权限用例互相影响。
- 追问：fixture 执行顺序如何保证？由依赖关系、scope 和自动使用规则决定，不应靠文件中的定义顺序猜测。

## 6. `yield` fixture 如何保证清理？多资源清理怎样写更安全？

**岗位考点**

- teardown 设计和部分初始化失败。
- 是否能保证测试数据可回收。

**参考答案**

`yield` 前是 setup，测试完成后执行 `yield` 后的 teardown。每个 fixture 最好只完成一个可能改变状态的动作，并立即登记对应清理：

```python
@pytest.fixture
def created_order(api, base_url):
    response = api.post(
        f"{base_url}/api/orders",
        json={"items": [{"product_id": 1, "quantity": 1}]},
        timeout=5,
    )
    response.raise_for_status()
    order = response.json()
    yield order
    delete_response = api.delete(
        f"{base_url}/test-support/orders/{order['id']}",
        timeout=5,
    )
    delete_response.raise_for_status()
```

Requests 收到 4xx/5xx 时不会自动抛异常，因此清理响应也必须检查；必要时把清理失败记录为独立诊断证据。如果多个资源依次创建，可拆成多个依赖 fixture，或使用 `contextlib.ExitStack` 按成功创建的逆序清理；使用 `request.addfinalizer` 时，要在资源确认创建成功后立即注册，因为 finalizer 一旦注册，即使后续 setup 失败也会执行。清理接口仅应存在于隔离测试环境，并有权限保护。

**原理或实践解释**

若 setup 在到达 `yield` 前抛异常，该 fixture 的 teardown 段不会执行，但已经成功进入的上游 fixture 仍会按规则收尾。因此将多个有副作用步骤塞进一个 fixture 会增加半初始化泄漏风险。

**常见追问或误区**

- 误区：用例失败时 teardown 不会执行。
- 误区：清理用 `DELETE FROM orders` 最省事。它可能删除其他并行 worker 的数据。
- 追问：若被测接口没有删除能力怎么办？使用唯一命名空间、短生命周期环境、事务回滚或受保护的测试支持工具。

## 7. `conftest.py` 有什么作用？应该放什么、不应该放什么？

**岗位考点**

- pytest 发现机制和项目组织。
- 是否会治理“万能 conftest”。

**参考答案**

pytest 会在目录层级发现 `conftest.py`，其中的 fixture 和 hook 可供该目录及其子目录使用，无需普通 import。它适合放公共 fixture、命令行选项、marker 注册或少量收集配置。

不应把所有客户端、业务逻辑、数据模板、断言和工具函数都堆进一个巨大 `conftest.py`。推荐：

```text
tests/
├── conftest.py       # 组合和通用 fixture
├── clients/          # HTTP 协议封装
├── builders/         # 合成数据工厂
├── assertions/       # 少量领域断言
└── api/              # 可读场景
```

业务客户端是普通 Python 模块，fixture 只管理它的创建与生命周期。

**原理或实践解释**

`conftest.py` 依赖隐式发现，过度使用会让依赖来源难以追踪。目录越深，fixture 还可能被覆盖。保持作用域清晰、命名具体，并用 `pytest --fixtures` 检查来源。

**常见追问或误区**

- 误区：测试模块应 `from conftest import api`。
- 误区：为了复用把任意工具函数都写成 fixture。
- 追问：多个 conftest 同名 fixture 怎么办？更靠近测试目录的定义可覆盖上层；应谨慎使用并在命名和文档中说明。

## 8. pytest 参数化有哪些方式？什么时候不适合参数化？

**岗位考点**

- `@pytest.mark.parametrize`、fixture `params` 和动态生成。
- 是否能保持测试 ID 和失败原因可读。

**参考答案**

常见方式：

1. `@pytest.mark.parametrize`：同一规则的多个输入输出。
2. `@pytest.fixture(params=[...])`：让使用该资源的测试在多个资源变体上运行。
3. `pytest_generate_tests`：根据命令行或收集上下文动态生成。

```python
@pytest.mark.parametrize(
    ("quantity", "status"),
    [
        pytest.param(0, 422, id="below-minimum"),
        pytest.param(1, 201, id="minimum"),
        pytest.param(100, 201, id="maximum"),
        pytest.param(101, 422, id="above-maximum"),
    ],
)
def test_quantity_boundary(api, base_url, quantity, status):
    ...
```

如果每行代表不同业务原因、需要不同准备或不同断言，就应拆成命名清楚的测试，而不是制造巨大参数表。

**原理或实践解释**

参数化值不会被自动深拷贝，测试若修改字典会污染后续实例。多个 `parametrize` 装饰器叠加会生成组合，数量可能爆炸。应用风险和组合方法选择代表值，而不是把所有字段做全排列。

**常见追问或误区**

- 误区：参数越多覆盖越全面。
- 误区：参数 ID 只为好看；可读 ID 对 CI 定位、重跑和趋势分析很重要。
- 追问：如何给某一行 xfail？使用带 marks 的 `pytest.param`，并写明原因和治理期限。

## 9. `skip`、`skipif`、`xfail` 和 marker 有什么区别？

**岗位考点**

- 测试选择和已知问题管理。
- 是否会把失败隐藏成“全绿”。

**参考答案**

- `skip`：无条件不执行。
- `skipif`：条件满足时不执行，例如某平台无此能力。
- `xfail`：默认仍执行测试；断言失败报告为 XFAIL，意外通过报告为 XPASS。`strict=True` 可让 XPASS 导致套件失败；只有明确需要避免执行危险或崩溃路径时才考虑 `run=False`。
- 自定义 marker：给测试分类，如 `smoke`、`contract`、`serial`，通过 `-m` 选择。

所有自定义 marker 应在配置中注册，并可启用 `--strict-markers` 防止拼写错误悄悄绕过选择。

**原理或实践解释**

跳过表示没有执行证据，预期失败表示失败符合已登记预期，两者都不能当作正常通过。调用 `pytest.xfail()` 会立即停止当前测试并报告 XFAIL，而 marker 还可在收集时表达条件。治理时记录关联问题、原因、负责人或到期条件，并监控数量和年龄。环境健康失败不应批量 skip 后宣称产品质量通过。

**常见追问或误区**

- 误区：用 `try/except AssertionError: pass` 代替 xfail。
- 误区：不稳定测试统一标记 xfail 就完成治理。
- 追问：XPASS 是什么？预期失败的用例实际通过；是否让套件失败取决于 strict 设置。

## 10. Requests 的 Session、timeout 和异常处理应如何使用？

**岗位考点**

- HTTP 客户端工程实践。
- 是否知道 Requests 默认不自动超时。

**参考答案**

`requests.Session` 可复用连接池，并持久化公共头、Cookie 和认证配置。每个外部请求都应显式设置 timeout；可用元组分别表达连接和读取阶段：

```python
import requests

with requests.Session() as client:
    client.headers["Accept"] = "application/json"
    try:
        response = client.get(
            "http://127.0.0.1:8000/api/products",
            timeout=(2, 5),
        )
        response.raise_for_status()
    except requests.Timeout:
        raise AssertionError("接口在约定时间内未响应")
    except requests.RequestException as exc:
        raise AssertionError(f"HTTP 调用失败: {type(exc).__name__}") from exc
```

接口测试不一定每次都调用 `raise_for_status()`；若目标就是验证 4xx，应直接断言精确状态码和错误契约。

**原理或实践解释**

Requests 的 timeout 不是整个响应下载的绝对墙钟上限；读取 timeout 更接近连接在一段时间内没有收到新字节，因此持续缓慢返回数据时总耗时仍可能很长。若业务还有端到端截止时间，应在调用编排或 CI 层单独设置总预算并保留超时阶段。连接复用可提高效率，但共享 Session 也共享 Cookie 和默认配置，需与测试隔离策略一致。

**常见追问或误区**

- 误区：不传 timeout 时默认 30 秒；Requests 默认不会自动超时。
- 误区：捕获 `Exception` 后重试所有错误。
- 追问：重试放哪里？可通过适配器或业务调用层实现，但只对白名单错误和可安全重试操作启用，并设置退避和总预算。

## 11. Requests 和 HTTPX 如何选择？什么时候使用异步客户端？

**岗位考点**

- 工具选型而非工具站队。
- sync/async、连接池和 HTTP/2 等能力边界。

**参考答案**

Requests API 成熟、生态广，适合同步 HTTP 自动化主线。HTTPX 同时提供同步 `Client` 和异步 `AsyncClient`，支持细粒度 connect/read/write/pool timeout，并可使用 HTTP/2 等能力。

选择依据：

- 现有项目和团队熟悉 Requests，普通同步 API 回归：优先保持简单。
- 被测代码是异步 Python，或需要在单进程中管理大量并发 I/O：考虑 HTTPX `AsyncClient`。
- 仅为了“看起来先进”不应把确定性的普通接口用例全部改成 async。

使用 HTTPX 时应复用 Client，不要在热循环里反复创建；异步资源用 `async with` 关闭。pytest 核心不会凭空执行普通 `async def` 测试，需要选定并锁定 pytest-asyncio、AnyIO 等插件，同时明确 event loop/backend 的作用域；这些配置名和默认行为以所锁插件版本为准。

**原理或实践解释**

异步提高的是 I/O 等待期间的并发效率，不会让服务端更快，也不自动变成性能测试。大量并发请求还可能破坏数据隔离、触发限流或让断言顺序复杂化。

**常见追问或误区**

- 误区：async 一定比 sync 快。
- 误区：HTTPX 没有默认 timeout；其官方文档当前说明默认对网络不活动设置超时，但项目仍应显式配置。
- 追问：可以在一个 AsyncClient 上并发吗？通常这是其使用场景之一，但要控制连接限制、任务取消、超时和业务数据隔离。

## 12. 一个可维护的接口自动化框架应如何分层？

**岗位考点**

- 架构职责、可读性和失败诊断。
- 是否把“框架”误解为大量继承和封装。

**参考答案**

建议按职责而不是技术名堆叠：

```text
config        环境无关默认值与配置加载
clients       URL、请求头、超时、序列化和协议调用
builders      从零生成唯一的虚构测试数据
schemas       稳定契约
assertions    少量可复用领域不变量
fixtures      资源创建、组合、清理
tests         场景、输入、动作和业务预期
reporting     脱敏日志、JUnit、关联 ID
```

测试应读起来像业务场景，客户端方法表达资源操作，例如 `orders.create(payload)`，但不要隐藏状态码、原始响应和关键诊断。公共层不应替测试做所有断言。

**原理或实践解释**

好的分层降低变化传播：认证头变化改客户端，数据规则变化改 builder，业务期望仍在测试中。过度封装会让失败堆栈跨越多个万能基类，调试反而变慢。先从最小结构演进，由真实重复驱动抽象。

**常见追问或误区**

- 误区：框架必须包含 BaseTest、BasePage、BaseClient 多级继承。
- 误区：所有接口响应都用一个通用 `assert_success`。
- 追问：客户端应返回 JSON 还是 Response？保留足够协议信息通常更利于测试；可用领域结果包装，但应能访问原始响应。

## 13. 配置、环境和密钥如何管理？

**岗位考点**

- 可移植性、安全和环境隔离。
- 是否会把环境差异写成大量 `if`。

**参考答案**

代码仓库只保存无敏感默认值和 `环境变量示例.env`；运行时通过环境变量、CI secret 或专用密钥系统注入地址和凭据。配置加载时应：

1. 明确优先级和必填项。
2. 启动即校验类型、URL 和允许环境。
3. 默认只指向本地/虚构服务。
4. 日志统一脱敏 Authorization、Cookie、Token、密码和个人信息。
5. 对危险环境同时设置目标地址允许清单和显式写入开关，默认拒绝破坏性操作。
6. 测试账号和数据库凭据遵循最小权限，并与个人、公司生产身份隔离。

不同环境的期望原则上应相同；若能力不同，用清晰的 capability 配置和 marker 管理，不在测试中散布域名判断。

**原理或实践解释**

配置与代码分离不是把所有东西都放环境变量。稳定的测试规则属于代码，可变地址和秘密属于运行环境。配置快照可写入报告，但只能记录来源和非敏感值。

**常见追问或误区**

- 误区：把测试账号写进私有仓库就安全。
- 误区：打印请求的全部 headers 才方便排障。
- 追问：密钥泄露怎么办？立即撤销/轮换、调查访问记录、清理历史并添加扫描门禁；只删除最新提交不够。

## 14. 接口断言应该做到多深？如何做 Schema 和业务断言？

**岗位考点**

- oracle 设计和错误信息质量。
- 是否会在“断言太少”和“绑死全部响应”之间取舍。

**参考答案**

断言应分层：

```python
response = api.get(f"{base_url}/api/products/1", timeout=5)
assert response.status_code == 200
assert response.headers["Content-Type"].startswith("application/json")

body = response.json()
assert body["id"] == 1
assert body["price_cents"] > 0
assert body["stock"] >= 0
```

再用 JSON Schema 或 OpenAPI 校验稳定结构：必填、类型、枚举、范围和额外字段策略。要显式约定是否允许额外属性；JSON Schema 在未声明限制时通常允许对象出现额外属性，不能把“校验器没报错”误解成契约禁止了未知字段。业务断言验证 Schema 无法表达或不适合单独表达的关系，例如订单总价等于所有明细小计之和、取消后库存恢复。

避免比较整个 JSON 快照，除非响应非常稳定且变化本身应被评审。时间、随机 ID 和动态顺序要按契约处理，不应粗暴删除所有动态字段。

**原理或实践解释**

一个断言失败应告诉读者“哪个业务规则被破坏”。pytest 的普通 `assert` 有表达式重写，简单可读的断言通常优于自制复杂 matcher。若循环验证集合，应在错误中包含业务键，或先收集所有违规项再一次报告。

**常见追问或误区**

- 误区：只断言状态码。
- 误区：Schema 通过就代表接口正确。
- 追问：字段顺序要断言吗？JSON 对象成员顺序通常不构成语义；数组顺序是否重要取决于契约。

## 15. 并行执行时如何保证测试数据隔离？

**岗位考点**

- pytest-xdist 或 CI 分片后的稳定性。
- 是否会消除顺序依赖和共享资源冲突。

**参考答案**

并行不是加一个 `-n auto` 就结束。应做到：

- 每个测试或 worker 使用唯一命名空间，例如 UUID 前缀，而非固定用户名。
- 不依赖测试执行顺序，不由一个测试为另一个测试准备状态。
- 清理只删除本测试创建的资源。
- 端口、文件、数据库 schema、消息 topic 和账号配额按 worker 隔离。
- 真正不可并行的少量资源显式串行，并说明原因。
- 聚合报告时保留 worker、随机种子和数据 ID。

如果系统支持测试租户或短生命周期环境，可以按 worker 分配；否则用业务键隔离并让 API 返回创建资源 ID。

**原理或实践解释**

并行会放大原有隐藏依赖。session scope fixture 在每个 worker 进程中通常各有一份，不代表全局只创建一次；这类行为取决于并行插件和执行模型，必须通过文档和实验验证。

**常见追问或误区**

- 误区：给共享文件加 sleep 可避免竞争。
- 误区：失败时关闭并行就算修复。
- 追问：随机数据如何复现？记录生成 seed 和最终业务键；安全数据仍须合成且脱敏。

## 16. 如何治理 flaky test？自动重跑应该放在哪一步？

**岗位考点**

- 稳定性工程、诊断和质量门禁。
- 是否把 retry 当修复。

**参考答案**

flaky 是同一代码、数据和环境条件下结果不稳定。治理流程：

1. 保存首次失败证据，不让重跑覆盖。
2. 按时间竞争、共享数据、外部依赖、环境资源、随机顺序、断言阈值和真实产品竞争分类。
3. 统计测试 ID 的首轮失败率、重跑转绿率、持续时间和最近失败。
4. 先修根因：条件等待、隔离数据、稳定契约、受控依赖、资源预算。
5. 临时隔离必须关联问题和期限，关键覆盖要有替代检查。
6. 重跑只作为短期诊断或对已知瞬时基础设施错误的有限恢复，不能把重跑后绿灯当首轮通过。

**原理或实践解释**

盲目重跑会降低反馈可信度，并让真实竞争缺陷消失。一次重跑转绿是“不稳定”的证据，不是第一次失败无效的证明。质量门禁可分别报告“first-attempt pass rate”和最终结果。框架自身也要有单元测试，例如配置、builder、客户端错误映射和脱敏函数。

**常见追问或误区**

- 误区：flaky 都是测试代码问题；产品竞争条件、异步设计和环境资源不足也可能是真实根因。
- 误区：把超时从 5 秒加到 60 秒就是稳定性治理。
- 追问：何时允许重跑？对明确分类、有限次数且保留首次证据的瞬时故障；有副作用操作必须先确认可安全重试。

## 17. pytest 如何接入 CI，哪些结果应该成为质量门禁？

**岗位考点**

- 从本地脚本到持续反馈的工程能力。
- 退出码、报告、分层和失败分诊。

**参考答案**

CI 中应固定 Python 和依赖版本，创建隔离环境，启动可复现的虚构服务，健康检查后运行测试，并上传 JUnit、日志或其他失败制品。pytest 核心退出码不能只分成“0 或测试失败”：

| 退出码 | pytest 核心含义 | CI 应关注的区别 |
| --- | --- | --- |
| `0` | 全部收集到的测试通过 | 仍要审查 skip/xfail 和选择范围 |
| `1` | 有测试失败 | 产品、用例或依赖失败，需证据分诊 |
| `2` | 用户中断 | 运行未完成，不能给质量结论 |
| `3` | pytest 内部错误 | 测试基础设施无效 |
| `4` | 命令行用法错误 | 流水线配置错误 |
| `5` | 未收集到测试 | 可能是选择表达式或路径错误；是否允许应由项目显式决定 |

除项目明确处理的场景外，非零退出码都应让步骤失败，不能在命令后无条件吞掉错误。包装脚本和插件可能改变退出行为，升级时需要验证。

分层示例：

- 提交门禁：静态检查、框架单测、快速 API smoke。
- 合并前：核心接口回归和契约检查。
- 定时/预发布：更广矩阵、容错、并发和较慢外部兼容测试。

门禁依据应包含失败数量、关键场景、契约破坏和环境有效性；覆盖率只能作为辅助信号，不能替代风险判断。

**原理或实践解释**

流水线失败必须可行动：报告提交 SHA、环境版本、测试选择表达式、首轮结果和制品链接。依赖下载或服务未启动不应被误报为产品回归，也不能在环境无效时给出质量通过结论。

**常见追问或误区**

- 误区：`pytest ... || true` 后还能依赖 HTML 报告人工判断。
- 误区：所有测试每次提交全量串行运行。
- 追问：如何减少反馈时间？风险分层、并行隔离、依赖缓存、选择受影响测试，但保留定时全量校验。

## 版本敏感点

- 本章核对日期：**2026-07-29**。
- Python、pytest、Requests、HTTPX 及插件均会演进；作品应提交锁文件或明确兼容范围，并在升级时读取 release notes。
- pytest 当前稳定文档展示 9.x 行为，但真实项目不得假定所有插件已兼容最新大版本；先在升级分支验证收集、fixture、hook、报告和并行插件。
- Requests 当前稳定文档明确：未显式传入 timeout 时不会自动超时；timeout 也不是完整下载的绝对墙钟截止时间。
- HTTPX 当前文档区分 connect、read、write、pool timeout，并提供同步和异步客户端；具体默认值和 HTTP/2 安装选项应以锁定版本文档为准。
- pytest-xdist、pytest-asyncio、报告插件属于独立项目；不要把第三方插件行为误写成 pytest 核心保证。
