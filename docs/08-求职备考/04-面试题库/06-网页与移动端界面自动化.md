# Web 与移动端 UI 自动化经典面试题

> 适用岗位：Web 自动化测试、移动端测试、自动化测试、测试开发、SDET。
> 招聘信号：公开岗位常见要求包括稳定定位、等待机制、Page Object、失败排查、并行和 CI；移动端岗位还会追问 Appium、原生/混合上下文、真机状态与设备矩阵。
> 技术主线：新建 Web 作品优先学习 Playwright；同时掌握 Selenium 存量兼容；移动端使用 Appium 3 的驱动/插件架构。具体选型仍取决于产品、团队和已有基础设施。
## 使用方法

回答 UI 自动化问题时，不要只说“封装、显式等待、失败截图”。应说明被测风险、元素状态、隔离边界、失败制品和量化后的稳定性结果。

## 1. 哪些场景适合做 UI 自动化？哪些不适合？

**岗位考点**

- 能否基于风险和成本选择自动化，而不是追求用例数量。
- 是否理解 UI 层在测试分层中的位置。

**参考答案**

适合 UI 自动化的场景通常是：

- 稳定、高价值、重复执行的关键用户旅程。
- 必须通过浏览器或设备验证的交互、渲染、无障碍或跨浏览器行为。
- 发布前必须快速确认的少量 smoke。
- 历史回归频繁且有稳定 oracle 的流程。

不优先做的场景包括频繁试验中的 UI、一次性检查、验证码/生物识别等难以安全自动化的外部环节、结果高度主观的视觉体验，以及可在 API/组件层更快更稳定验证的规则。

我会让大量业务规则在单元/API 层验证，只在 UI 保留关键贯穿路径，例如“虚构用户搜索商品 → 加入购物车 → 创建订单 → 看到确认信息”。

**原理或实践解释**

UI 测试跨越浏览器、前端、网络、后端和数据，反馈最接近用户，但速度、环境依赖和故障面也最大。自动化价值应按风险降低、反馈速度、维护成本和故障发现能力衡量，而不是“自动化率”单一数字。

**常见追问或误区**

- 误区：所有手工用例都应该 1:1 转成 UI 脚本。
- 误区：UI 自动化只能测正常流程。
- 追问：怎么选 smoke？覆盖最关键且能代表系统可用性的短路径，数量少、数据独立、失败可诊断。

## 2. Playwright 中 Browser、BrowserContext 和 Page 分别是什么？

**岗位考点**

- Playwright 隔离模型。
- 是否会正确设计 fixture 生命周期。

**参考答案**

- `Browser`：浏览器进程或到浏览器的连接。
- `BrowserContext`：独立的浏览器会话，类似轻量、隔离的全新用户配置，拥有自己的 Cookie、localStorage、权限等。
- `Page`：Context 中的一个标签页或页面。

典型策略是一个 worker 复用 Browser，每个测试创建新的非持久化 BrowserContext，再在其中创建 Page。这样既避免每条测试重启浏览器的高成本，又让 Cookie、存储和权限等会话状态隔离。多标签流程可在同一 Context 中创建多个 Page；这些 Page 共享该 Context 的会话，不能拿来模拟两个隔离用户。

**原理或实践解释**

Context 是 Playwright 测试隔离的关键。若全套测试共享同一个 Page 或 Context，登录、缓存、service worker、权限和本地存储都会导致顺序依赖。保存认证状态可加速登录，但应为不同角色生成独立状态文件，并确保不含真实凭据且不提交仓库。

**常见追问或误区**

- 误区：一个 Page 就等于一个独立用户；同 Context 的多个 Page 共享会话状态。
- 误区：为隔离必须每条用例重启整个 Browser。
- 追问：两个用户如何在同一测试交互？创建两个独立 Context，各自代表一个用户，再通过后端状态或 UI 观察交互结果。

## 3. Playwright 定位器如何选择？为什么优先 role、label 和 test id？

**岗位考点**

- 稳定定位、可访问性语义和 locator strictness。
- 是否会避免脆弱 DOM 路径。

**参考答案**

推荐优先级不是绝对规则，但通常：

1. `get_by_role(..., name=...)`：接近用户和辅助技术看到的语义。
2. `get_by_label()`：适合表单控件。
3. `get_by_text()`、`get_by_placeholder()` 等用户可见属性。
4. 与研发约定的稳定 `data-testid`，用于没有合适用户语义的元素。
5. 短而稳定的 CSS；尽量避免依赖 DOM 层级的长 CSS/XPath。

```python
page.get_by_label("用户名").fill("student-001")
page.get_by_role("button", name="登录").click()
expect(page.get_by_role("heading", name="商品列表")).to_be_visible()
```

Playwright locator 对单元素操作默认严格：匹配多个元素会报错。应通过角色、名称、容器过滤等让定位唯一，而不是习惯性加 `.first`。

**原理或实践解释**

Locator 在执行动作时重新解析当前 DOM，并带有自动等待和重试能力。长 XPath 把测试绑在实现结构上，页面稍微加一层容器就破坏。role 定位还会暴露可访问名称缺失等可用性问题。

**常见追问或误区**

- 误区：`data-testid` 永远优于用户语义。
- 误区：匹配多个时用 `nth(0)` 就修好了；它可能点击了错误目标。
- 追问：动态列表怎么定位？先定位有业务唯一文本/属性的列表项，再在该容器内定位按钮。

## 4. 什么是 Playwright 自动等待？为什么不能用固定 sleep？

**岗位考点**

- actionability checks 和条件同步。
- 是否会从竞争条件解释 flaky。

**参考答案**

Playwright 在执行 `locator.click()` 等动作前会等待定位唯一，并根据动作检查元素可见、稳定、可接收事件、可用等条件；Web-first assertion 也会在超时范围内自动重试。通常不需要手工 sleep。

固定 sleep 的问题：

- 等得短会偶发失败。
- 等得长会浪费每次运行时间。
- 只等待时间，不证明目标状态成立。

应等待业务可观察条件：

```python
page.get_by_role("button", name="提交订单").click()
expect(page.get_by_text("订单已创建")).to_be_visible()
expect(page).to_have_url(re.compile(r"/orders/\d+$"))
```

**原理或实践解释**

现代前端在 DOM ready 后仍可能执行异步请求和重渲染。Playwright 的动作等待解决“元素是否可交互”，但不会替你理解业务完成条件。例如按钮可点击不代表后台订单已生成，仍要断言确认信息、响应或后端状态。

**常见追问或误区**

- 误区：Playwright 有自动等待，所以任何异步场景都无需显式断言。
- 误区：`wait_for_timeout` 是正式同步方案；官方文档主要把它视为调试用途。
- 追问：什么时候使用 `locator.wait_for()`？等待明确的可见、隐藏、附着或分离状态，尤其不是由后续动作/断言自然驱动时。

## 5. Playwright 的自动重试断言与普通 Python `assert` 有什么区别？

**岗位考点**

- Web-first assertion 与瞬时读取。
- 是否能写出稳定且语义清晰的 UI oracle。

**参考答案**

Playwright 的 `expect(locator)` 断言会在超时内反复获取元素状态，适合最终会达到的 UI 条件；普通 `assert` 对当前瞬间值判断，不会自动等待。

```python
# 推荐：等待 UI 最终显示正确值
expect(page.get_by_test_id("cart-count")).to_have_text("1")

# 容易竞争：此刻读取一次
assert page.get_by_test_id("cart-count").text_content() == "1"
```

普通 assert 仍适合已经取得的纯 Python 计算结果、同步配置和稳定数据；关键是选择与被测状态变化模型一致的 oracle。

**原理或实践解释**

自动重试断言解决前端最终渲染的短暂时差，但超时必须有上限。失败信息应包含期望、最后实际值、定位器和 trace。不要把所有断言超时无限拉长，否则真实性能退化会被隐藏。

**常见追问或误区**

- 误区：把普通 assert 包进自己的 while/sleep 就与官方断言完全等价。
- 误区：`is_visible()` 会一直等待到可见；即时查询和 Web-first assertion 的行为要按 API 文档区分。
- 追问：如何断言元素永远不出现？在业务观察窗口内断言隐藏只是有限证据，应结合 API/日志/状态验证关键安全副作用。

## 6. Page Object 应如何设计？断言应该放在哪里？

**岗位考点**

- 维护性、职责边界和领域表达。
- 是否会过度使用万能 BasePage。

**参考答案**

Page Object 封装页面或组件提供的“服务”和定位细节，测试保留场景和业务断言：

```python
class LoginPage:
    def __init__(self, page):
        self.page = page
        self.username = page.get_by_label("用户名")
        self.password = page.get_by_label("密码")
        self.submit = page.get_by_role("button", name="登录")

    def login_as(self, username: str, password: str):
        self.username.fill(username)
        self.password.fill(password)
        self.submit.click()
```

页面对象通常不做测试断言；它可以在构造或导航后确认“这是正确页面”的基本契约。商品卡片、导航栏等复用区域可建 Component Object，而不必让一个 Page Object 管理整站。

**原理或实践解释**

Page Object 的价值是让 UI 结构变化集中修改，并让测试表达用户任务。它不等于把每个元素包装一个 getter，也不应隐藏等待、截图和异常到无法诊断。公共方法应代表领域动作，如 `add_product_named()`，而非暴露底层 driver 到处操作。

**常见追问或误区**

- 误区：Page Object 中包含所有断言才叫封装。
- 误区：所有页面必须继承包含点击、输入、等待几十个方法的 BasePage。
- 追问：一个动作可能成功或失败，返回什么？可设计不同领域方法或返回对应 Page/Component，让场景和结果显式。

## 7. 登录状态如何复用，同时保证测试隔离和安全？

**岗位考点**

- 认证状态、fixture 和敏感数据治理。
- 是否能在速度与隔离之间取舍。

**参考答案**

可先在受控测试环境通过 UI 或 API 完成一次登录，将 Playwright `storage_state` 保存为短生命周期制品；每条测试基于该状态创建新的 Context。不同角色使用不同状态，状态文件加入 `.gitignore`，CI 中从 secret 动态生成。

必须验证：

- 状态是否过期、是否绑定环境。
- 不同测试仍使用独立 Context。
- 角色和租户不会混用。
- 修改密码、退出和刷新令牌等测试不能复用普通缓存状态。
- 文件中可能包含 Cookie/localStorage Token，不能提交或打印。

**原理或实践解释**

复用认证状态省去重复 UI 登录，但跳过了登录页面本身的覆盖。因此保留少量独立登录测试，其余业务旅程用预认证状态。测试账号也应采用最小权限和可回收的虚构数据。

**常见追问或误区**

- 误区：把一个 Context 做成 session fixture，全套测试共享。
- 误区：storage state 是测试代码，所以可以提交仓库。
- 追问：并行 worker 如何使用？读取同一个只读状态模板通常可行，但每个测试要创建独立 Context；会发生服务端会话冲突时需按 worker 创建账号。

## 8. Playwright 如何做网络拦截？Mock 之后还算端到端测试吗？

**岗位考点**

- `route`/响应等待、测试边界和服务虚拟化。
- 是否会混淆组件测试与真实端到端。

**参考答案**

Playwright 可拦截请求并继续、修改、阻断或返回虚构响应。适用场景：

- 稳定复现后端异常、超时和稀有边界。
- 隔离不可控第三方服务。
- 验证前端请求载荷或错误展示。

```python
page.route(
    "**/api/recommendations",
    lambda route: route.fulfill(
        status=503,
        content_type="application/json",
        body='{"code":"TEMPORARILY_UNAVAILABLE"}',
    ),
)
```

Mock 后测试的是浏览器 + 前端 + 模拟契约，不是完整后端端到端。报告和目录命名应明确边界，并保留少量连接真实测试环境的契约/端到端检查。

**原理或实践解释**

服务虚拟化提高确定性和错误路径覆盖，却可能因模拟响应与真实提供者漂移产生假信心。Mock 数据应从版本化公开契约生成或校验，不能随意拼一个“前端喜欢的响应”。

**常见追问或误区**

- 误区：只要从浏览器运行就叫 E2E。
- 误区：网络空闲等于业务完成；轮询、WebSocket 和长期连接会让这种条件不可靠。
- 追问：如何等待某个请求？在触发动作前注册 response/request 期待，再断言状态和载荷，避免请求已经完成后才开始等待。

## 9. 如何处理 iframe、新窗口、下载和 Shadow DOM？

**岗位考点**

- 常见复杂页面上下文。
- 是否会在事件发生前建立等待。

**参考答案**

- iframe：用 `frame_locator` 或明确 Frame 定位，在正确文档上下文中操作。
- 新窗口/标签：在点击前用 `expect_popup()` 等待事件，再操作返回的 Page。
- 下载：在触发前用 `expect_download()`，验证建议文件名、大小/内容和保存路径；测试后清理。
- Shadow DOM：Playwright 定位器通常可穿透开放 Shadow DOM，但 XPath 不具备相同能力；关闭的 shadow root 无法像普通 DOM 一样访问。

```python
with page.expect_popup() as popup_info:
    page.get_by_role("link", name="查看帮助").click()
help_page = popup_info.value
expect(help_page).to_have_title(re.compile("帮助"))
```

**原理或实践解释**

这些能力都涉及不同上下文或异步事件。先触发再等待会产生竞态：事件可能在监听前发生。下载测试还要区分“浏览器收到文件”和“后端生成内容正确”，必要时解析虚构文件验证结构。

**常见追问或误区**

- 误区：iframe 内元素可以永远用主页面 locator 直接找。
- 误区：只检查下载按钮可点击就代表下载成功。
- 追问：如何处理第三方支付 iframe？尽量使用提供方沙箱和明确契约；不要绕过真实安全机制或使用真实支付数据。

## 10. Playwright Python 项目如何并行和分片？

**岗位考点**

- 是否理解语言生态差异和并行执行模型。
- 数据、账号、端口和制品隔离。

**参考答案**

Playwright Python 常与 pytest 插件配合；进程级并行通常使用 pytest-xdist，CI 分片可按测试文件、历史时长或平台矩阵拆分。它与 Node.js 的 Playwright Test runner 并行配置并不完全相同，不能直接照搬。

```bash
# 需要安装 pytest-xdist；先从较小进程数开始校准
pytest --numprocesses 2 --browser chromium
```

这里的“并行”是同一任务内由多个进程执行，“分片”是 CI 先把测试集合划成互斥子集，再由多台机器分别执行；Python 生态没有必要照抄 Node.js Playwright Test 的 `--shard` 参数。

并行前必须：

- 每测试/worker 使用唯一虚构用户和数据前缀。
- Context 独立，不能共享 Page。
- 下载目录、trace、截图和报告文件名包含 worker/test ID。
- 不共享不可并发修改的账号或全局库存。
- 控制 worker 数，避免浏览器、CPU、内存或后端容量成为新瓶颈。

**原理或实践解释**

并行只缩短墙钟时间，不会修复慢测试。它会放大顺序依赖、服务限流和环境资源竞争。应比较串行与并行的首轮失败率、p95 用例时长和基础设施饱和度。

**常见追问或误区**

- 误区：`-n auto` 在任何 CI 机器上都是最优。
- 误区：多个 worker 可安全写同一个 trace.zip。
- 追问：如何处理必须串行的场景？先挑战共享资源设计；确实不能隔离的少数测试单独分组，避免拖累全部套件。

## 11. Playwright 失败时应收集哪些证据？Trace 有什么价值？

**岗位考点**

- 失败可诊断性。
- 是否能利用 trace、截图、视频、控制台和网络证据分诊。

**参考答案**

CI 失败至少保留：

- 测试 ID、提交、浏览器/系统版本和环境版本。
- Playwright trace，包含动作时间线、DOM 快照、网络和控制台上下文。
- 失败时截图；必要时视频。
- 浏览器 console error、page error、关键请求/响应和关联 ID。
- 测试数据唯一标识，敏感值脱敏。

建议只在失败时保留重制品，或首次重试时启用 trace，控制存储成本。首次失败证据不能被重跑覆盖。

**原理或实践解释**

单张截图只能展示失败后的一个瞬间，无法回答之前点击了哪个元素、网络返回什么、DOM 如何变化。Trace 提供时间线和可回放上下文，通常比堆积框架日志更有价值，但它仍可能包含页面数据，要按敏感制品治理。

**常见追问或误区**

- 误区：每一步手工截图就是最佳报告。
- 误区：Trace 可以公开上传，因为它只是测试文件。
- 追问：如何区分产品和脚本问题？结合 actionability 失败、DOM 快照、网络状态、console error 和后端 trace ID 建立证据链。

## 12. 如何设计跨浏览器测试矩阵？

**岗位考点**

- 覆盖、成本和浏览器引擎差异。
- 是否会把所有组合都放到提交门禁。

**参考答案**

矩阵应根据真实用户、产品支持声明和风险建立，而不是机械地把每条测试跑所有浏览器。示例：

- 每次提交：主浏览器的核心 smoke。
- 合并前或定时：Chromium、Firefox、WebKit 的关键旅程。
- 发布前：产品声明支持的真实浏览器/系统组合，包括必要的移动视口或真机。

Playwright 自带浏览器构建便于可复现，但不能完全代表所有渠道和企业策略下的真实浏览器；关键兼容性仍应在产品支持环境验证。

**原理或实践解释**

视口模拟不等于真机：触摸、软键盘、GPU、字体、网络和系统 WebView 都可能不同。矩阵应记录版本、失败分布和退役策略，避免无限增长。

**常见追问或误区**

- 误区：Chrome 通过就能证明所有 Chromium 浏览器完全相同。
- 误区：响应式 Web 只改 viewport 就等于移动端验证。
- 追问：预算有限怎么选？优先用户占比、业务关键性、历史缺陷和变化大的引擎差异。

## 13. Playwright 与 Selenium 如何选择？

**岗位考点**

- 新项目和存量项目的选型能力。
- 是否理解生态、协议和迁移成本。

**参考答案**

Playwright 提供强定位器、自动等待、Context 隔离、网络控制和 trace，新建现代 Web 自动化通常能以较少样板获得稳定反馈。Selenium WebDriver 标准化程度高、语言和 Grid 生态成熟，许多企业有大量存量资产和远程浏览器基础设施。

选择要看：

- 支持的浏览器/平台和特殊能力。
- 团队语言、现有框架和基础设施。
- 调试制品、网络控制、并行和 CI 需求。
- 迁移成本、人才和维护预算。

合理策略可能是新关键路径用 Playwright，存量 Selenium 按价值渐进治理，而不是为了工具统一一次性重写。

**原理或实践解释**

工具不能替代测试设计和数据隔离。Playwright 也会 flaky，Selenium 也能构建稳定套件；差异在默认能力、协议、生态和工程成本。应做小规模 spike，用首轮稳定率、运行时长、故障诊断和维护变更衡量。

**常见追问或误区**

- 误区：Playwright 使用 Selenium WebDriver。
- 误区：Selenium 已经过时，无需学习；公开岗位和存量系统仍常见。
- 追问：迁移如何评估？先盘点测试价值和历史失败，迁移高价值代表场景，双跑一段时间后再决定。

## 14. Selenium 隐式等待和显式等待有什么区别？为什么不要混用？

**岗位考点**

- Selenium 同步机制和 flaky 根因。
- 是否知道官方对混用的警告。

**参考答案**

隐式等待是会话级配置，影响元素查找，在找不到元素时轮询到超时；显式等待针对特定条件，如元素可见、可点击、URL 改变或自定义业务条件。通常优先用针对性的显式等待。

```python
wait = WebDriverWait(driver, 10)
button = wait.until(
    expected_conditions.element_to_be_clickable((By.ID, "submit"))
)
button.click()
```

Selenium 官方文档警告不要混用隐式和显式等待，因为两者叠加可能产生不可预测的实际等待时长。

**原理或实践解释**

页面加载完成只说明特定 `readyState`，不代表单页应用的异步组件已可操作。等待应该围绕可观察条件，而不是 `time.sleep`。遇到 stale element，优先重新定位和理解重渲染，不要无脑捕获后无限重试。

**常见追问或误区**

- 误区：隐式等待设 30 秒，所有同步问题就解决。
- 误区：显式等待只等元素出现；还可等待属性、文本、消失、窗口数或自定义条件。
- 追问：为什么“element_to_be_clickable”仍可能点失败？覆盖层、动画、DOM 替换或业务状态可能在条件满足后再次变化，需要最小复现和更准确条件。

## 15. Selenium Manager、Grid 和 WebDriver BiDi 分别解决什么问题？

**岗位考点**

- Selenium 4 生态的当前能力。
- 本地驱动管理、远程矩阵和双向浏览器事件的区别。

**参考答案**

| 能力 | 主要解决的问题 | 不解决的问题 |
| --- | --- | --- |
| Selenium Manager | 当调用方未显式提供可用 Driver 时，帮助发现、下载和缓存匹配的 Driver；当前版本还可管理部分浏览器版本 | 不替代测试数据隔离，也不保证离线、代理或企业镜像环境无需配置 |
| Selenium Grid | 将 WebDriver session 路由到远程节点，承载不同浏览器/系统矩阵和并行执行 | 不会让单条用例自动变快，也不会消除节点间环境差异 |
| WebDriver BiDi | 在标准 WebDriver 会话上提供双向事件与命令能力，例如逐步落地的日志、网络等能力 | 具体命令并非在所有 binding、浏览器和版本中同时可用 |

三者不是替代关系：Manager 解决依赖发现，Grid 解决远程执行，BiDi 扩展浏览器通信能力。

**原理或实践解释**

Grid 扩容前仍要解决数据隔离和制品归集。BiDi 功能按 Selenium binding、浏览器和版本逐步落地，不能假定所有命令已经跨浏览器一致。锁定版本并用 capability smoke 验证。

**常见追问或误区**

- 误区：用了 Selenium Manager 就不需要固定浏览器版本。
- 误区：Grid 自动让单条测试更快。
- 追问：BiDi 与 CDP 什么关系？CDP 主要面向 Chromium 且版本耦合更强；BiDi 目标是标准化跨浏览器能力，迁移状态需看当前文档。

## 16. Appium 3 的 Server、Driver 和 Plugin 是什么关系？

**岗位考点**

- Appium 3 模块化架构。
- 是否知道安装 Server 后还要安装平台 Driver。

**参考答案**

| 组件 | 职责 | 是否必须 |
| --- | --- | --- |
| Appium Server/Core | 接收 WebDriver 请求、管理 session，并提供扩展框架 | 必须 |
| Driver | 实现具体平台自动化，例如 Android 的 UiAutomator2、iOS 的 XCUITest | 至少安装一个与目标平台匹配的 Driver |
| Plugin | 增加、代理或修改 Server 能力 | 按需求可选 |
| Client library | 用 Java、Python 等语言向 Server 发起 WebDriver 请求 | 编写客户端测试时需要，但它不是 Server 扩展 |

Appium 3 安装包不再内置所有平台 Driver，需要单独安装所需 Driver，并管理其兼容版本。

```bash
appium driver install uiautomator2
appium driver list --installed
appium
```

客户端通过 W3C WebDriver 能力创建 session。Appium 专属 capability 使用 `appium:` 前缀，例如 `appium:automationName`、`appium:deviceName`、`appium:app`。

**原理或实践解释**

模块化让 Server 与各平台 Driver 独立演进，也意味着排障必须记录 Server、Driver、客户端、Node.js、平台 SDK、模拟器/真机和应用版本。升级 Server 不代表 Driver 自动兼容。

**常见追问或误区**

- 误区：安装 Appium 3 后天然能自动化所有手机平台。
- 误区：`deviceName` 能唯一选中任意真机；实际还需平台特定标识和连接配置。
- 追问：Plugin 是必须的吗？核心流程通常不必；只有明确需要扩展能力时安装，并固定版本和验证兼容性。

## 17. Appium 中 Native、WebView 和 Hybrid App 如何定位与切换？

**岗位考点**

- 移动应用上下文和定位策略。
- 是否会处理 WebView 调试与驱动兼容。

**参考答案**

Native 页面由平台 UI 树驱动，优先使用 accessibility ID、稳定资源 ID 或平台语义定位；WebView 内容需要切换到相应 Web context 后，按 Web DOM 定位；Hybrid App 同时包含二者。

典型流程：

1. 查询可用 contexts。
2. 等目标 WebView context 出现，而不是固定 sleep。
3. 切换后验证 URL/标题或关键 DOM，确保选对 WebView。
4. 完成 Web 操作后切回 `NATIVE_APP`。

WebView 自动化还依赖调试开关、系统 WebView/浏览器及对应 Driver 兼容，具体能力以平台 Driver 文档为准。

**原理或实践解释**

Native 元素树与 Web DOM 是两套不同自动化上下文。坐标点击对分辨率、布局和动画非常脆弱，只应作为少数无语义控件的最后手段，并封装相对坐标和设备条件。

**常见追问或误区**

- 误区：Hybrid App 里所有元素都可以用 XPath 从同一棵树找到。
- 误区：移动端 XPath 最灵活，所以应作为首选。
- 追问：找不到 WebView 怎么排查？检查应用是否启用调试、context 列表、设备日志、WebView 版本、Driver 配置和页面是否真正加载。

## 18. 移动端自动化如何治理设备状态、权限和系统弹窗？

**岗位考点**

- 真机/模拟器可复现性。
- 权限、语言、网络、键盘、方向和应用生命周期。

**参考答案**

每条测试应明确初始状态：应用是否安装、是否清数据、登录状态、权限、语言/地区、时区、网络、方向、深色模式和后台状态。按套件成本选择：

- 高隔离：每测试重置应用数据或安装干净包，稳定但慢。
- 中等隔离：每测试通过应用/API 恢复业务状态，设备按 worker 固定。
- 专项：权限首次询问、升级安装、后台恢复等场景显式控制系统状态。

系统弹窗优先用平台/Appium 官方能力处理，并验证允许、拒绝、仅本次允许等分支。不能用固定坐标假定所有系统版本布局相同。

**原理或实践解释**

移动 flaky 很多来自“设备不是同一个起点”。设备农场并行时，要记录设备 ID、系统版本、应用 build、Driver 版本和日志。失败后需收集 Appium server log、设备日志、截图/录屏和页面源，但对个人数据脱敏。

**常见追问或误区**

- 误区：每条测试都 `noReset=true` 能显著提速且没有副作用。
- 误区：模拟器通过就足够证明真机兼容。
- 追问：推送、来电、弱网怎么测？使用平台/设备农场支持的受控能力，并把不可控运营商或外部依赖与产品问题区分。

## 19. 如何测试滑动、长按等手势，而不写死坐标？

**岗位考点**

- W3C Actions 和移动布局适配。
- 是否能定义手势后的业务 oracle。

**参考答案**

优先调用 Driver 提供的高层移动命令或 W3C Actions，并基于元素边界或屏幕比例计算起止点。手势脚本应表达意图，例如“在列表容器内向上滑到商品出现”，设置最大次数和结束条件。

验证不能只看手势命令未抛异常，而应断言：

- 目标元素出现或列表位置变化。
- 不应触发的元素未被误点。
- 到达列表末端能停止。
- 不同分辨率、方向和系统导航模式下仍成立。

**原理或实践解释**

绝对坐标绑定某个屏幕尺寸和布局。无限滑动会掩盖找不到元素的问题。更稳定的方法是定位可滚动容器，执行有限手势，并在每次后检查可观察状态。

**常见追问或误区**

- 误区：TouchAction 的旧示例在所有 Appium/客户端版本仍是首选；接口会随 W3C 协议和 Driver 演进，应看当前文档。
- 误区：手势成功返回等于业务完成。
- 追问：原生滚动与 WebView 滚动一样吗？底层上下文不同，应使用对应驱动/DOM 能力。

## 20. UI 自动化 flaky test 应如何量化和治理？

**岗位考点**

- 稳定性工程，而不是“加等待、加重试”。
- 是否能区分脚本、产品、环境和外部依赖问题。

**参考答案**

先定义指标：首轮通过率、重跑转绿率、每个测试的 flaky rate、p95 时长、失败类别和平均修复时间。治理步骤：

1. 保留首次失败的 trace、截图、日志和数据 ID。
2. 分类为定位/等待、共享状态、测试数据、产品竞争、网络依赖、浏览器/设备资源、框架问题。
3. 修复根因：语义定位、条件等待、Context/数据隔离、契约 Mock、资源容量或产品同步。
4. 临时 quarantine 要有问题单、责任人、期限和替代覆盖。
5. 重跑结果与首轮结果分别报告。
6. 用多次重复和随机顺序验证修复，而不是只看一次通过。

**原理或实践解释**

UI 套件的价值依赖信任。若团队习惯忽略红灯，再高覆盖也没有反馈价值。治理目标不是绝对零波动，而是让每次失败有证据、已分类、可行动，并使关键门禁具有足够高的首轮可靠性。

**常见追问或误区**

- 误区：把 timeout 翻倍后通过，就证明是环境慢。
- 误区：自动 retry 三次后绿即可按通过统计。
- 追问：如何证明修复有效？对原失败条件重复运行，比较修复前后首轮失败率，并回归相关浏览器/设备组合。

## 版本敏感点

- 本章核对日期：**2026-07-29**。
- Playwright 发布频繁，并绑定对应浏览器构建；应固定 Python 包版本并执行匹配的浏览器安装。Node.js Playwright Test 与 Python pytest 插件在配置、并行和报告上有差异。
- Selenium 4 持续把能力从 CDP 方向演进到标准 WebDriver BiDi；具体事件和命令的跨浏览器支持要查当前 binding 与浏览器兼容表。
- Selenium Manager、浏览器自动更新和企业代理/离线镜像之间存在版本与网络差异；CI 应固定并记录实际浏览器、Driver 和 Selenium 版本。
- Appium 3 将 Driver 和 Plugin 独立管理。Server、平台 Driver、客户端库、Node.js、Android/iOS 工具链需一起记录并做升级验证。
- Android UiAutomator2、Espresso 与 iOS XCUITest 的 capability、命令和平台要求不同；不要把某个 Driver 的扩展当成 Appium 核心通用保证。
- 旧版 Appium 示例中的 JSON Wire Protocol capability、未加前缀 capability 或旧手势 API 可能不适合 Appium 3/W3C 环境。
