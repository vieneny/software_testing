# 作品集、简历与面试表达

求职材料的目标不是让项目显得“大”，而是让招聘方快速验证你具备目标岗位需要的判断与执行能力。

## 一份好作品的五个信号

1. **可运行**：README 从零开始，依赖、命令、预期和清理清楚；
2. **风险驱动**：先说明重要风险，再展示测试分层；
3. **会失败**：保留一个主动注入的回归及门禁证据；
4. **可诊断**：报告、trace、日志和服务端指标能定位问题；
5. **诚实**：明确虚构背景、环境限制、未覆盖和残余风险。

大量代码、用例数量、工具 Logo 和通过截图都不是独立能力证据。

## 简历项目描述公式

使用“对象 + 风险/目标 + 行动 + 技术取舍 + 可验证结果”：

弱描述：

> 负责接口自动化，使用 pytest、requests、allure、jenkins。

更可信的公开练习描述：

> 为虚构电商 API 建立 pytest 回归，按 client / fixture / case 分层，覆盖契约、边界、错误语义和幂等；将 smoke 接入 CI，并通过主动修改响应字段验证门禁会失败，13 个基线检查可在本地重复运行。

拔高描述：

> 基于业务到达率设计 k6 阶梯负载，联合 p95、错误率和服务资源时间线定位实验环境瓶颈；明确结果只代表单机教学环境，并给出下一轮 CPU/事件循环对照实验。

AI 方向描述：

> 使用 30 条合成样本建立 LLM 客服评测集，分事实性、拒答、规则和提示注入切片；确定性门禁与人工 rubric 分层，安全失败单独阻断，避免总平均分掩盖高风险问题。

AI 岗位要按当前 BOSS 样本中的职责分流，不能用同一段项目覆盖所有岗位：

| 目标岗位 | 作品必须突出 |
|---|---|
| 普通测试 + AI 提效 | 人工基线、AI 草稿、采纳/修改/拒绝、运行验证和返工 |
| AI 应用测试 | 模型 Mock、API/流式、RAG 分层、性能、安全和版本回归 |
| 模型/多模态评测 | 数据构造、标注规范、一致性、裁判校准、切片和统计比较 |
| Agent 测试 | 工具、权限、轨迹、终态、幂等、副作用和恢复 |
| 评测平台/测试开发 | 异步任务、结果库、版本、Trace、CI 门禁、脱敏和审计 |

详细岗位依据见[最新招聘调研](../00-学习指南/04-软件测试与人工智能测试招聘需求调研.md)，项目验收见[AI 测试岗位能力与实战路线](../06-AI测试/04-人工智能测试岗位能力与实战路线.md)。

不要虚构生产指标、团队规模、缺陷收益或公司项目经验。公开练习就明确写“个人项目/公开实验”。

## 技能栏怎么写

按熟练度和证据组织：

- 熟练：可以独立设计、实现、诊断和解释权衡；
- 掌握：能在明确场景下独立完成并维护；
- 了解：能阅读已有项目、解释用途并完成基础修改。

示例：

```text
测试：风险分析、边界值、判定表、状态迁移、探索式测试
接口：HTTP/OpenAPI、Postman、Python/pytest/Requests
UI：Playwright（主线）；Selenium（存量维护）
性能：k6 负载模型与阈值；JMeter CLI 基础
工程：Git、Linux、SQL、Docker、GitHub Actions/Jenkins 概念
AI质量：版本化评测集、确定性评分、RAG/Agent 分层、OWASP GenAI 风险
```

只写面试时可以现场解释和演示的内容。工具列表越长，追问暴露的风险越大。

## 面试项目讲解：六分钟结构

### 0:00～0:45 背景与目标

“这是完全虚构的个人质量工程项目，目标是验证浏览和下单关键路径，并练习从功能到 AI 评测的分层闭环。”

### 0:45～1:45 风险与策略

讲三项最高风险、为什么重要、分别放在哪层验证。不要从目录结构开始讲。

### 1:45～3:00 一个深度案例

例如幂等：规则、状态、并发风险、API 测试、发现的内存多实例限制和可能修复。

### 3:00～4:00 工程质量

数据隔离、显式超时、日志脱敏、CI 分层、失败 trace 和 flaky 治理。

### 4:00～5:00 结果与主动失败

展示一次回归如何被门禁捕获、定位用了什么证据、修复后如何验证。

### 5:00～6:00 限制与下一步

承认教学应用没有持久化、鉴权、真实监控和生产规模，给出最有价值的下一项实验。

## 高频追问的回答框架

### “为什么选 Playwright，不选 Selenium？”

回答应包含：新项目需求、自动等待/trace/隔离带来的价值、个人主线减少重复；同时承认 Selenium 在 W3C WebDriver、企业存量、语言/Grid 生态中的价值，能维护但不重复建设。

### “接口自动化框架怎么设计？”

先讲问题规模和演进：配置、HTTP client、业务动作、fixture/数据、测试和报告如何分离。强调小项目不过度抽象；并行、重试、插件都在出现真实需求后引入。

### “如何处理 flaky test？”

分类：产品竞争条件、等待/定位、数据/环境、第三方依赖、测试顺序、资源。保留失败证据，统计复现条件，修根因；重试只用于诊断和已知短期缓解，不能把一次成功当通过。

### “如何设计性能测试？”

从业务量、场景比例和 SLO 开始，解释开放/封闭模型、预热、数据、监控和停止条件；用时间线证明瓶颈，不从“开多少线程”开始。

### “怎么测试 RAG/Agent？”

RAG 拆检索、黄金上下文下的生成、端到端；Agent 看最终环境状态、工具参数/顺序、权限、恢复和多次运行。确定性规则优先，模型裁判用 rubric 与人工标签校准。

## 现场编码与实操

常见任务不是造完整框架，而是：

- 解析 JSON 并按条件统计；
- 写一个 API 用例、参数化或 fixture；
- 从失败日志提出假设并验证；
- 设计边界、判定表或 SQL；
- 修复固定 sleep、脆弱定位或无意义断言；
- 分析一段 k6/JMeter 结果；
- 给 AI 输出设计评分规则。

练习流程：先澄清输入输出和边界，写最小正确版本，执行例子，再处理异常和解释复杂度。不要沉默堆代码。

## 面试题的学习方法

把每个题整理成四格：

| 格 | 内容 |
|---|---|
| 定义 | 一句话说明是什么 |
| 机制 | 为什么会这样，关键步骤是什么 |
| 场景 | 何时使用，给一个公开/虚构例子 |
| 边界 | 何时不适用，常见误区是什么 |

例如“等价类和边界值的区别”不能只背定义，要在 `quantity=1..10` 上设计有效/无效类、0/1/10/11 边界，并说明数据类型、空值和组合规则仍需另测。

完整训练入口见[独立面试题库](./04-面试题库/README.md)。题库按测试基础、功能、计算机基础、接口、自动化、UI、性能、质量工程、AI 测试和场景行为题拆分；每题包含岗位考点、参考答案、原理解释以及追问或误区。冲刺阶段使用[模拟面试与评分表](./04-面试题库/11-模拟面试与评分表.md)，不要以“刷过多少题”代替脱稿表达与实操。

## 最终自检

- [ ] 一页简历能在 30 秒内看到目标方向和两项强证据；
- [ ] 每个“熟练/掌握”都有现场可演示项目；
- [ ] 项目描述没有编造生产规模和收益；
- [ ] 能在六分钟内从风险讲到证据，不照念 README；
- [ ] 每个技术选择都能说适用条件与替代方案；
- [ ] 能展示一次失败和诊断，而不只有通过截图；
