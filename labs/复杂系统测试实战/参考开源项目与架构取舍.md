# 参考开源项目与架构取舍

核对日期：**2026-07-27**。

本目录只借鉴公开项目的领域拆分、契约和工程做法，代码由本仓库独立编写。不要复制上游大段源码、品牌素材、示例数据或未确认许可的文件。

## 三、AI 中间件

| 项目 | 借鉴内容 | 本项目取舍 |
|---|---|---|
| [FastAPI](https://github.com/fastapi/fastapi) | 类型化接口、OpenAPI、依赖注入和测试客户端 | 作为 AI 服务 HTTP 边界 |
| [Promptfoo](https://github.com/promptfoo/promptfoo) | 数据驱动评测、断言、跨 Provider 与红队 | 后续接入独立 AI 回归，不嵌入业务单元测试 |
| [DeepEval](https://github.com/confident-ai/deepeval) | pytest 风格的 LLM/RAG/Agent 评测 | Python 评测路线选修 |
| [Ragas](https://github.com/vibrantlabsai/ragas) | RAG 检索与生成分层指标 | 知识问答阶段再引入，首版用确定性 Mock |
| [OpenTelemetry](https://github.com/open-telemetry) | 跨语言 Trace/Metric/Log | 用 request id 起步，再逐步接 OTel |

默认 Provider 是本地规则和合成知识库：

- 无需 API Key；
- 输出可预测，适合功能、契约和故障测试；
- 不上传任何数据；
- 能主动注入超时、错误和低置信度。

云模型只作为显式开启的选修，启用前必须确认数据、保留、地区、成本和权限。

## 四、为什么选择 MySQL、Redis 和两个前端框架

### MySQL

- 中国岗位和 Java/Python 企业项目常见；
- 可以练索引、事务、锁、隔离级别、分页和主从延迟思想；
- 两个系统使用独立数据库，便于练习数据隔离与迁移；
- 测试阶段可用 SQLite/H2 快速反馈，集成阶段必须回到真实 MySQL。

### Redis

- 社区系统用于热点列表、会话、限流、计数；
- 客服系统用于队列视图、短期状态、幂等和限流；
- 所有 Redis 能力都要有失效、穿透、击穿、数据不一致和降级测试；
- Redis 不是数据库真值，关键业务状态仍以 MySQL 为准。

### React 与 Vue

- React 系统练 hooks、组合、TanStack Query/路由和前后端契约；
- Vue 系统练 Composition API、Pinia/路由和企业后台交互；
- 两个前端不追求做相同 UI，而是复用测试模型和 API 规范；
- UI 自动化只覆盖关键旅程，大量规则下沉到 API/组件层。

## 五、暂缓引入的技术

| 技术 | 价值 | 为什么不在首版强制 |
|---|---|---|
| RabbitMQ/Kafka | 异步消息、削峰、事件集成 | 首版先保证同步闭环；第二阶段引入 Outbox、重复消费和死信 |
| OpenSearch/Meilisearch | 全文搜索、相关性和高亮 | 首版用数据库查询建立功能基线，搜索专题再替换 |
| MinIO/S3 | 附件、头像、知识文档 | 文件安全和清理规则准备好后再引入 |
| WebSocket | 实时消息、坐席看板 | HTTP 核心契约稳定后再测试重连、乱序和背压 |
| Kubernetes | 扩缩容、滚动发布、混沌 | Docker Compose 与服务可观测性稳定后再做 |
| 多 Agent | 复杂编排与协作 | 单 Agent、工具边界、评测和人工审批未成熟前只会放大风险 |

## 六、选型原则

1. 业务复杂度服务于测试学习，不为“技术全家桶”服务；
2. 每增加一个组件，都必须新增故障、数据、一致性和运维测试；
3. 领域真值由业务服务和数据库维护，AI 只提供建议；
4. 两个系统共享契约和测试思想，不共享业务数据库；
5. 依赖版本固定，主分支和 Snapshot 不直接作为学习基线；
6. 开源项目只作为根基和对照，最终作品必须能解释自己的取舍。
